# 家族二 优先级排序型：先做哪个

> 资源永远不够，问题永远太多。这一家族的框架把"感觉哪个重要"变成"可解释、可辩论、可复核的排序"。它们的共同价值不是给出精确答案，而是让优先级的假设显式化。

---

## 1. 艾森豪威尔矩阵 Eisenhower Matrix

**核心思想**：用"重要"和"紧急"两个维度把任务分四象限。重要且紧急→立即做；重要不紧急→计划做（最该投入的一格）；紧急不重要→委托/授权；不重要不紧急→删除。核心洞察：**紧急的事会本能地压倒重要的事，必须刻意保护"重要不紧急"象限**。

**什么时候使用**：任务多到被"救火"淹没时；感觉一直很忙但没进展（多半困在"紧急不重要"象限）；需要区分"别人的紧急"和"你的重要"时；规划一天/一周的个人时间。

**什么时候不要使用**：任务本身少而清晰时（不需要矩阵）；团队/项目级的复杂优先级（维度不止两个，用 RICE）；"重要性"高度依赖不确定的未来结果、当下无法判断时。

**优点**：极简、瞬间可用；命中最普遍的时间管理病——被紧急绑架；强迫你面对"该删掉什么"。

**缺点**：只有两维，粗糙；"重要"的判断主观且常被情绪扭曲；对相互依赖的任务无能为力；不给量化排序（同象限内还得再排）。

**AI 如何使用**：把你的任务清单丢给 AI，让它按两维初分并解释理由，你来修正——AI 的价值在于逼你对每项说清"为什么重要/紧急"，很多"紧急"经不起追问。

**Agent 如何使用**：作为个人助理 Agent 的任务调度逻辑——扫描你的待办/邮件/日历，自动标注象限，把"紧急不重要"的候选委托项主动提示给你，保护你的"重要不紧急"时间块不被会议侵占。

**Prompt 模板**：
```
这是我的任务清单：[列表]
用艾森豪威尔矩阵分类，对每项：
1. 判断重要性（对我的核心目标[填目标]有多大贡献）和紧急性（deadline 压力）
2. 归入四象限之一，并一句话说明理由
3. 特别指出：哪些"紧急"任务其实不重要（是别人的优先级伪装成我的）？
4. 我的"重要不紧急"象限有哪些被长期拖延的事？它们才是最该排进日程的。
```

**完整案例**：一个人每天忙于回消息、开会、处理临时请求（全是紧急不重要），而"学习新技能、体检、写年度规划"（重要不紧急）年复一年拖着。矩阵一分诊，问题清晰：他的时间被象限三吞噬。行动：把象限三的消息设为每天两个固定时段批处理（而非实时响应），腾出的整块时间强制分配给象限二。矩阵的贡献是让"瞎忙"这个模糊感受变成了"你困在象限三"这个可操作的诊断。

## 2. RICE 评分

**核心思想**：给每个候选项按 **Reach（影响范围）× Impact（影响程度）× Confidence（置信度）÷ Effort（工作量）** 打分排序。产品管理的经典优先级公式。核心价值：把"我觉得这个功能重要"变成四个可辩论的因子。

**什么时候使用**：一堆候选（功能、项目、实验）需要排序而资源有限时；需要向他人解释"为什么先做 A 不做 B"时；对抗 HiPPO（最高薪者的意见）——用结构化评分制衡权力拍板；多人协作、需要共识排序时。

**什么时候不要使用**：候选项极少或差异悬殊（一眼可辨，评分是形式主义）；因子无法合理估计（全靠瞎猜的数字比不评分更危险，因为它伪装成客观）；战略级/不可逆的重大决策（这类决策不该被一个除法主导）；面对创新性、高不确定项目（RICE 系统性低估高风险高回报项，因为 Confidence 低、Effort 高）。

**优点**：把主观直觉分解为可讨论的因子；Confidence 因子显式惩罚"听起来很好但没把握"的项；结果可排序、可沟通、可复盘。

**缺点**：数字给人虚假的精确感（四个估计值相乘除，误差放大）；容易被操纵（想让某项胜出就调高它的 Impact）；系统性偏向"安全的渐进改进"，压制"高风险高回报"和难以量化的基础工作。

**AI 如何使用**：让 AI 为每个候选项估算四因子并**列出估算依据**，你重点审查依据而非数字。AI 能快速给出一致口径的初估（避免人工评分时"先评的严、后评的松"），但最终数字必须由你和领域知识校准。

**Agent 如何使用**：产品/项目管理 Agent 定期扫描 backlog，用 RICE 自动生成候选排序草案 + 每项的因子依据，供人评审。关键设计：Agent 输出的是"带推理的排序建议"而非"最终决定"，且高分项要附"低 Confidence 警告"防止它把不确定项排太前。

**Prompt 模板**：
```
用 RICE 给以下候选项排序：[候选列表 + 已知背景]
对每一项，输出表格：
| 候选 | Reach(受影响人数/次数,给区间) | Impact(0.25/0.5/1/2/3档,并说明) | Confidence(%,及降低置信的原因) | Effort(人周) | RICE分 |
要求：
1. 每个因子附一句估算依据，不要只给数字
2. 显式标注：哪些项的分数对某个假设特别敏感（假设变了排名就翻转）
3. 提醒我：排名靠后的项里，有没有因为"难量化"而被低估的战略性工作？
```

**完整案例**：产品团队排 5 个功能。"一键导出"：Reach=8000用户/月、Impact=1、Confidence=90%、Effort=2周 → RICE=(8000×1×0.9)/2=3600。"AI 推荐引擎"：Reach=10000、Impact=2、Confidence=30%（没做过没把握）、Effort=12周 → (10000×2×0.3)/12=500。表面上推荐引擎"影响更大"，但低置信+高投入让它排到导出功能之后。团队据此先做导出。复盘价值：三个月后回看 Confidence 估得准不准，校准下次评分。但团队也记下一条警示——推荐引擎被 RICE 压低，需单独用战略视角评估它是否属于"高回报值得赌"的例外。

## 3. ICE 评分

**核心思想**：RICE 的轻量版，只用 **Impact × Confidence × Ease（易做程度）** 三因子（Ease 相当于 Effort 的倒数，越易分越高）。增长黑客常用。牺牲一点严谨换取速度。

**什么时候使用**：需要快速排序大量点子（如增长实验清单）；早期探索阶段，精确度不如速度重要；Reach 难以估计或候选项 Reach 相近时（省掉这一维）；个人项目的轻量优先级。

**什么时候不要使用**：候选项的影响范围差异巨大时（丢掉 Reach 会误判——此时用 RICE）；需要向严谨的利益相关者论证时（三因子更容易被质疑主观）；高风险决策。

**优点**：比 RICE 更快、更少估计负担；适合海量点子的初筛；三个数一分钟出结果。

**缺点**：三个因子都主观，"三个感觉相乘"的客观性存疑；无 Reach 维度，易被"影响深但只影响极少数人"的项误导；同样有被操纵和虚假精确的通病，且更甚。

**AI 如何使用**：批量点子的第一轮粗筛——让 AI 给几十个点子快速打 ICE 分，筛出 top 10 再用更重的方法细评。把 AI 当成"降噪器"而非"决策者"：它帮你从 50 个里挑出值得认真想的 10 个。

**Agent 如何使用**：创意/实验生成 Agent 的自评环节——Agent 头脑风暴出大量点子后，用 ICE 自筛，只把高分的呈现给人，避免用几十个未经排序的点子淹没用户。

**Prompt 模板**：
```
快速用 ICE 给这些点子打分排序（1-10 分制）：[点子列表]
| 点子 | Impact | Confidence | Ease | ICE分 | 一句话理由 |
规则：
- 这是粗筛，求快不求精，但每项理由要能站住
- 标出得分最高的 3 个和最低的 3 个
- 对 top 3，指出它们的分数最依赖哪个假设（后续验证的重点）
```

**完整案例**：一个独立开发者有 20 个改进 App 的想法。逐个 RICE 太重，用 ICE 快筛："加深色模式"Impact=6 Confidence=9 Ease=8 → 432;"重构支付系统"Impact=8 Confidence=7 Ease=2 → 112。深色模式因为易做且有把握排到前面，支付重构虽重要但难做被推后。他先做了几个高 ICE 项快速上线积累动力，把低 Ease 的大工程留到有整块时间时。ICE 在这里的作用是让单人开发者不至于一上来啃最难的骨头而丧失节奏。

## 4. 80/20 帕累托原则 Pareto

**核心思想**：约 80% 的结果来自约 20% 的原因。少数关键因素贡献多数价值，多数因素只贡献零头。数字是隐喻不是定律，真实比例可能是 90/10 或 70/30，核心是"分布极不均匀"。

**什么时候使用**：资源有限需要聚焦时（几乎永远适用）；感觉在很多事上平均用力却收效甚微时；识别"关键少数"——最重要的客户、最高频的 bug、最有用的功能；给 AI 的分析任务定"抓重点"的基调。

**什么时候不要使用**：那 80% 的"次要部分"实际不可或缺时（飞机 20% 的关键零件不能因"贡献小"而省——安全/合规/长尾体验场景，长尾本身就是价值）；分布本就均匀的领域（强行找 20% 是自欺）；用它给忽视重要但不紧急的基础工作找借口时。

**优点**：极强的聚焦力，对抗"什么都想做"；普适性高，几乎每个领域都能找到不均匀分布；快速识别高杠杆点。

**缺点**：容易被滥用为"忽略细节"的借口；识别错"关键 20%"则全盘错（识别本身需要数据，不能拍脑袋）；忽视了有时那 80% 的长尾累积起来也是核心竞争力；动态系统里"关键 20%"会随时间变化。

**AI 如何使用**：让 AI 分析数据/清单，识别贡献最大的少数项及其依据。AI 擅长在大量数据里找出集中度（哪些 bug 占了多数报错、哪些客户占了多数收入）。但"这 20% 是否真的是可聚焦的杠杆点"要人判断——有时高频 ≠ 高价值。

**Agent 如何使用**：分析型 Agent 的默认聚焦策略——处理大数据集时先做帕累托切分，把深度分析算力集中在关键少数上，对长尾做低成本粗处理，优化"分析投入/洞察产出"比。

**Prompt 模板**：
```
分析[数据/清单/问题]，用 80/20 视角找出关键少数：
1. 哪 ~20% 的[因素/项目/客户/原因]贡献了 ~80% 的[结果/价值/问题]？给出数据支撑
2. 这个"关键少数"具体是什么，如何聚焦它们？
3. 反向检查：被归入"次要 80%"的部分里，有没有虽然单项贡献小、但不可省略的（安全/合规/长尾体验）?
4. 这个分布会随时间变化吗？多久该重新评估一次？
```

**完整案例**：客服团队被工单淹没。帕累托分析工单数据：发现 22% 的问题类型（密码重置、退款状态查询、发货时间）占了 78% 的工单量。聚焦动作：为这三类做自助工具和 AI 自动答复，一举消化近八成工单量，人力集中到复杂长尾。反向检查很关键：剩下 78% 的问题类型里，"投诉升级""安全事件"虽然量小但绝不能自动化打发，必须保留优质人工。80/20 帮团队找到了自动化的高杠杆点，同时反向检查守住了不该省的长尾。

## 5. MoSCoW 法

**核心思想**：把需求分为 **Must have（必须）、Should have（应该）、Could have（可以）、Won't have（这次不做）** 四类。区别于评分法，它给的是"承诺等级"而非"排序数字"，特别适合范围管理和期望对齐。

**什么时候使用**：项目/版本的范围界定（哪些进这一版，哪些砍）；和利益相关者对齐期望、管理"什么都想要"的诉求；deadline 固定、必须决定砍什么时；MVP 定义。

**什么时候不要使用**：需要精细排序而非分档时（同为 Must 的项之间还得排——配合 RICE）；因子可量化、更适合打分时；类别会被滥用（所有人都把自己的需求标 Must，失去意义）。

**优点**：直观、非技术人也秒懂；"Won't have"显式化了"这次不做"的决定（很多方法回避这个）；擅长期望管理和范围控制。

**缺点**：Must 类容易膨胀（人人都说必须）；档内无排序；主观，缺乏量化依据；对"Must 到底是不是真 Must"缺乏检验机制。

**AI 如何使用**：让 AI 对需求清单做初步 MoSCoW 分类，并对每个"Must"追问"如果没有它，产品还能发布吗"——用这个反问戳破膨胀的 Must 类。

**Agent 如何使用**：项目管理 Agent 在范围规划时，把需求自动分档并标注 Must 类的膨胀风险（如"当前 Must 占 70%，超出健康范围"），提示人重新审视。

**Prompt 模板**：
```
对以下需求做 MoSCoW 分类：[需求列表 + 项目约束/deadline]
1. 分为 Must/Should/Could/Won't-this-time 四档
2. 对每个 Must，用"没有它就无法发布/上线吗"这个硬标准检验——不通过的降级
3. 明确列出 Won't-have-this-time（这次明确不做的），并说明理由
4. 报告 Must 类的占比，若超过 50% 警告我范围可能失控
```

**完整案例**：团队做一个 MVP，初始需求 30 项，所有人都觉得自己的是"必须"。用 MoSCoW + "没它能否上线"硬检验：真正的 Must 缩到 8 项（注册登录、核心功能、支付、基本安全）；一批"重要但可延后"降为 Should；锦上添花的进 Could；两个争议大的功能明确列入 Won't-this-time 并说明"下版评估"。范围从 30 项收敛到 8 项 Must，MVP 得以按期发布。MoSCoW 的核心贡献是那句"没它能否上线"的检验——它把情绪化的"必须"还原成了可发布性的客观判断。
