# 家族一 问题定义型：把问题看清楚

> 好决策的一半是把问题定义对。定义错的问题，后面所有分析都是精确的错误。本家族的框架不产出答案，产出"正确的问题"。

---

## 1. 第一性原理 First Principles

**核心思想**：把问题拆解到不可再拆的基本事实，抛开一切"大家都这么做"的类比与惯例，从基本事实重新推导结论。区别于类比推理（"别人怎么做我怎么做"），它问"物理/逻辑上到底允许什么"。

**什么时候使用**：现状被"行业惯例"锁死而你怀疑惯例不合理时；成本/性能出现数量级改进空间的探索；进入一个被"专家共识"垄断但共识可能过时的领域；AI 给你一个"通常的做法"而你想突破它时。

**什么时候不要使用**：日常小决策（重新推导午饭吃什么是荒谬的）；惯例其实凝结了你不知道的血泪教训时（见切斯特顿栅栏——拆之前先懂它为何存在）；时间紧迫、需要"足够好"而非"最优"时；你缺乏该领域的基本事实储备（没有事实，"第一性"推导就是空想）。

**优点**：能突破路径依赖，发现被类比遮蔽的可能性；推理链完全显式，可逐环检验；抗权威、抗惯性。

**缺点**：极耗认知资源；容易高估自己对"基本事实"的掌握，从错误的公理出发推得更远；忽视惯例中的隐性智慧；在社会系统里，"逻辑上可行"常撞上"人性/制度不允许"。

**AI 如何使用**：让 AI 帮你列举某个做法背后被默认的假设，然后逐条追问"这条是物理定律还是行业习惯"。AI 见过海量领域的"惯例 vs 本质"，擅长把隐藏假设翻出来——但它给的"基本事实"你必须独立核实，因为它也可能把惯例当事实。

**Agent 如何使用**：作为复杂任务规划前的"假设审计"步骤——Agent 在制定方案前，先跑一个"这个方案继承了哪些未经检验的假设"的子任务，暴露约束后再规划，避免把人类的惰性假设固化进自动化流程。

**Prompt 模板**：
```
我想解决[问题/目标]。当前通行的做法是[现状做法]。
请用第一性原理帮我拆解：
1. 这个问题不可再拆的基本事实/约束是什么？（区分：物理或逻辑的硬约束 vs 仅仅是行业习惯）
2. 逐条标注：哪些"约束"其实只是惯例，理论上可以打破？
3. 若从基本事实重新推导，有哪些现状之外的可能方案？
4. 每个新方案，指出它真正的硬约束在哪、以及现状惯例可能在防范什么风险。
```

**完整案例**：某团队默认"客服必须 7×24 配人"。第一性拆解：基本事实是"用户在非工作时间也会产生问题且期望响应"；被当成约束的惯例是"响应必须由人即时完成"。打破后者 → 分层方案：80% 常见问题用知识库自助 + AI 即时答，20% 复杂问题异步转人工次日处理。硬约束校验：紧急安全类问题不能异步（保留小规模值班）。结果：覆盖同样需求，人力成本大幅下降。关键是第一性帮团队看见"即时"和"人工"是两个可拆开的假设。

## 2. 逆向思考 Inversion

**核心思想**：不问"如何成功"，而问"如何必然失败"，然后避免那些失败因素。源自雅可比"反过来想，总是反过来想"。因为失败模式往往比成功路径更少、更清晰、更稳定。

**什么时候使用**：目标模糊但"搞砸的方式"很具体时；规避灾难比追求卓越更重要的场景（安全、健康、财务、声誉）；正向头脑风暴卡壳时；给 AI 方案做压力测试时。

**什么时候不要使用**：需要正向创造性突破（避免所有失败 ≠ 达成伟大）；已陷入焦虑/悲观情绪时（放大负面无益）；失败模式本身高度不可知的全新领域。

**优点**：暴露正向思考的盲区；心理上更容易——人对"什么会出错"的直觉常强于"什么会成功"；产出可直接转为 checklist 和护栏。

**缺点**：只做逆向会导致过度保守、只求不败不求大胜；避开了已知失败不等于走向成功；可能陷入防御性思维。

**AI 如何使用**：让 AI 扮演"事前验尸官"，为你的计划生成失败清单。这是 AI 极擅长的——它见过无数失败案例的模式。比正向让它"夸夸你的方案"有价值得多。

**Agent 如何使用**：在 Agent 执行高风险操作前内置"逆向自检"：先生成"这一步可能怎样出错、错了什么后果"，据此决定是否需要人工确认或加护栏（与 Pre-mortem、红队思想同源）。

**Prompt 模板**：
```
我的目标是[目标]，计划是[计划]。请做逆向分析：
1. 假设一年后这件事彻底失败了，列出最可能的 8 个失败原因（按概率排序）
2. 每个原因，指出现在有什么早期信号能预警
3. 哪些失败是我的计划已经防住的，哪些是完全裸奔的
4. 给出防住 top 3 风险的最小成本动作
不要安慰我，你的任务是找出所有可能搞砸的地方。
```

**完整案例**：见家族五 Pre-mortem，二者是同一思想的不同应用尺度。一个个人应用：想养成晨间写作习惯，逆向问"如何保证养不成"→ 答案：晚睡、早上刷手机、没定选题、追求完美不敢写烂。据此设计防御：前一晚定好选题放在桌上、手机放另一房间、明确允许写垃圾初稿。逆向把模糊的"我要自律"变成了四个具体的障碍移除动作。

## 3. MECE 与议题树 Issue Tree

**核心思想**：把一个大问题拆成"相互独立、完全穷尽"（Mutually Exclusive, Collectively Exhaustive）的子问题，形成树状结构。相互独立避免重复和交叉，完全穷尽避免遗漏。麦肯锡的看家结构化方法。

**什么时候使用**：面对庞大模糊的问题需要系统拆解时；要确保"没漏掉重要方面"的分析（尽调、诊断、战略）；多人协作分工时（每人一个不重叠的分支）；给 AI 布置复杂分析任务、需要它覆盖全面时。

**什么时候不要使用**：问题小到一眼看穿；创造性/探索性任务（严格穷尽会扼杀发散）；现实问题的维度本就高度交叉、强行 MECE 反而扭曲（很多真实系统不是干净可分的）；时间不允许做完整拆解。

**优点**：系统性防遗漏、防重复；天然支持分工和并行；拆解树本身就是可沟通、可审查的思考地图。

**缺点**：追求完美 MECE 会陷入拆解洁癖；真实世界很多因素相互纠缠，"独立"是理想化假设；容易拆得整齐但抓不住重点（穷尽了但没优先级——需配合 80/20）。

**AI 如何使用**：让 AI 生成初始议题树，人来审查"是否真的穷尽、是否有交叉"。AI 拆解速度快、覆盖广，但容易拆出"看起来 MECE 实际重叠"的分支，需要人把关。这也是 [[03_树状分解Tree|Multi-Agent 树状分解]] 的思维基础。

**Agent 如何使用**：直接映射为 [[05_Planner-Executor|Planner-Executor]] 或树状分解的拆解逻辑——Planner 用 MECE 原则把任务拆成不重叠的子任务分发给 Executor，独立性保证子任务可并行、结果可无缝合并。

**Prompt 模板**：
```
把问题[大问题]拆解成 MECE 的议题树：
1. 第一层拆成 3-5 个相互独立、合起来完全覆盖的子问题
2. 检查：这些子问题有重叠吗？有遗漏吗？（明确自我审查）
3. 对最关键的分支继续下拆一层
4. 拆完后，标注哪 2-3 个分支最可能影响最终答案（为后续聚焦）
输出树状结构，并说明你的拆分维度是什么（按流程？按对象？按原因？）。
```

**完整案例**：问题"我们的利润为什么下降？"。MECE 拆分维度选"利润 = 收入 − 成本"：收入分支（销量↓？单价↓？）× 成本分支（原料↑？人力↑？固定摊销↑？）。逐支查数据后定位到"单价被迫下调"是主因（收入分支），成本分支基本稳定。若不用 MECE，容易一头扎进"是不是成本涨了"的直觉而漏查收入侧。拆解树让"没漏掉"变成可验证的。

## 4. 5 Whys 五问法

**核心思想**：对一个问题连续追问"为什么"（通常约五次），穿透表面症状抵达根本原因。源自丰田生产系统。核心信念：第一个原因几乎总是症状，根因藏在下面几层。

**什么时候使用**：排查故障/错误的根本原因；表面解决方案反复失效（说明没找到根因）时；简单到中等复杂度的因果链；快速根因分析、不需要重型工具时。

**什么时候不要使用**：复杂问题有多条并行因果链时（5 Whys 是单线的，会误导你以为只有一个根因——此时用议题树/鱼骨图）；根因涉及概率而非确定因果时；追问会滑向"甩锅到人"而非"改进系统"时。

**优点**：极简、零成本、人人可用；快速穿透症状；培养"不满足于第一个解释"的习惯。

**缺点**：假设单一线性根因，过度简化多因问题；追问方向依赖提问者的既有认知，容易问着问着拐到预设结论；"五次"是约数不是规律，机械套用会用力过猛或不足。

**AI 如何使用**：让 AI 做 5 Whys 的追问者或被追问者。作为追问者它能保持"再往下一层"的耐心（人容易早停）；但要警惕它顺着你的暗示往你想要的根因走（RLHF 顺从性），最好让它每层给出 2-3 个可能原因而非单线。

**Agent 如何使用**：Agent 在任务失败时的自动归因步骤——不停在"工具报错了"，而是追问"为什么报错→因为参数错→为什么参数错→因为上一步输出格式变了→……"，定位到可修复的根因层再决定重试策略，而非盲目重试。

**Prompt 模板**：
```
问题现象：[描述症状]
请做 5 Whys 根因分析，但改进版：
- 每一层"为什么"，给出 2-3 个可能原因（不要假设单一因果）
- 标注每个原因的证据强度（有数据/合理推测/纯猜测）
- 追到"可采取行动的根因层"就停（能修的那一层），不必凑满五次
- 最后区分：哪些是真根因，哪些只是中间症状
警告我：如果证据不足以支撑某层追问，就明说"这里需要更多信息"。
```

**完整案例**：现象"网站周一上午变慢"。Why1 为何慢→数据库响应慢。Why2 为何 DB 慢→连接池耗尽。Why3 为何耗尽→周一有批量报表任务。Why4 为何影响线上→报表和线上共用连接池。Why5 为何共用→初期图省事没隔离。根因层=资源未隔离（可修：给报表独立连接池），而非表面的"周一慢"。注意此案例恰好单线清晰;若现象是"转化率下降"这类多因问题，5 Whys 就会误导，该换议题树。

## 5. Cynefin 库尼芬框架

**核心思想**：决策前先判断问题所处的"域"，不同域用不同的应对方式。五个域：**简单/清晰**（因果显然→感知-分类-响应，套最佳实践）、**繁杂**（因果需专家分析→感知-分析-响应，找好实践）、**复杂**（因果只能事后看清→探测-感知-响应，做安全试验让方案涌现）、**混乱**（无因果可循→行动-感知-响应，先止血）、**失序**（不知道在哪个域——最危险）。这是"元框架"：帮你选框架的框架。

**什么时候使用**：面对陌生问题、不确定该用什么方法时；团队对"这个问题该怎么搞"有分歧时（常是因为对所处域判断不同）；防止把复杂问题当简单问题处理（最常见、最致命的错配）。

**什么时候不要使用**：问题类型一目了然时（简单域问题不需要先跑 Cynefin）；作为事后叙事而非事前指导（很多人用它讲故事而非做决策）；团队没有耐心理解五个域的区别时（会退化成贴标签）。

**优点**：防止方法错配（用最佳实践套复杂问题=灾难）；解释了为什么"照搬成功经验"经常失败（域变了）；承认了"有些问题不能被规划，只能被探索"。

**缺点**：域的边界模糊，判断本身需要经验；容易变成事后合理化的标签游戏；"复杂"和"繁杂"的区分对新手不直观；框架本身有学习成本。

**AI 如何使用**：让 AI 先帮你判断问题所处的域，再据此推荐方法。关键价值：防止你（和 AI）对复杂问题给出"清晰域"式的自信答案。AI 天然倾向给出确定的最佳实践，主动问它"这真的是个有确定答案的问题，还是个需要试验的复杂问题"能校准过度自信。

**Agent 如何使用**：作为 Agent 的策略选择器——简单/繁杂域任务用确定性工作流（[[01_流水线Pipeline|Pipeline]]/规则），复杂域任务用探索性自主 Agent + 安全试验（小步可回滚），混乱域立即升级人工。把 Cynefin 判断作为路由的第一层，决定"这个任务该用多大的自主性"。

**Prompt 模板**：
```
我面临的问题：[描述]
请用 Cynefin 框架判断它所处的域：
1. 因果关系是：显而易见 / 需专家分析 / 只能事后看清 / 无规律可循？
2. 据此判断域：简单 / 繁杂 / 复杂 / 混乱
3. 对应的应对策略是什么（套最佳实践 / 请专家分析 / 做小规模安全试验 / 先止血）？
4. 最关键：我有没有把它误判成更简单的域？如果我用"标准最佳实践"处理它，会有什么风险？
5. 如果处在"复杂域"，给我 2-3 个低成本、可回滚的探测性试验。
```

**完整案例**：某公司想"提升员工敬业度"，HR 打算照搬另一家的"最佳实践"（发奖金+团建）。Cynefin 判断：员工敬业度是**复杂域**问题（因果是社会性的、情境依赖的、只能事后看清），不是可套最佳实践的简单域。错配的代价：照搬方案很可能无效甚至反效果。正确应对：做几个小规模、可回滚的探测试验（一个团队试弹性工作、一个试导师制、一个试自主项目），观察哪个方向涌现出正反馈，再放大。Cynefin 在这里的核心贡献是拦住了"照搬 = 最佳实践"的直觉错误，把一个被当成简单域的问题正确识别为需要试验的复杂域。
