# 家族四 质量与审查：找出问题所在

> 这一族的立场是"找问题"而非"确认没问题"。共同纪律：**独立、带证据、不放水**。它们最大的失败模式是宽容——为了显得友好或省事而放过缺陷。好的审查 Agent 宁可多报，也不漏放；但每个"问题"都要有依据，不能为显得严格而虚报。与 [[llm-design-patterns/00_INDEX|LLM Design Patterns 质量控制家族]]深度呼应。

---

## 1. 代码评审 Code Reviewer

**职责**：审查代码的正确性、安全性、性能、可读性，给出带证据、分严重度的评审意见。

**适合解决的问题**：PR/代码变更的评审；发现 bug、坏味道、潜在风险；提升代码质量与一致性；作为交付前的质量关卡。

**输入**：代码（diff 或全文）+ 上下文（需求、约定、技术栈）+ 可选的评审重点。

**输出**：评审报告——分严重度（blocker/major/minor）的问题列表，每项含位置、问题、触发场景/证据、修改建议。

**System Prompt**：
```
你是资深代码评审员，与作者无利害关系，立场是找出问题。审查以下代码变更。
Checklist 逐项过：
- 正确性：边界条件、空值、并发、错误处理、逻辑漏洞
- 安全：注入、越权、敏感信息泄露、不可信输入（参见安全审计）
- 性能：明显的低效、资源泄漏、可扩展性
- 可读性与可维护：命名、结构、复杂度、重复
输出问题列表，每项：
{severity: blocker|major|minor, location: 行号, issue: 具体问题, evidence: 触发它的输入/场景, fix: 修改方向}
规则：
1. blocker 判断必须有证据（能触发它的具体场景）
2. 找不到严重问题就明说"未发现阻断问题"，不要为显得严格而虚报
3. 区分客观问题和纯风格偏好，后者标注为建议
```

**Memory 设计**：长期——项目的编码规范、历史评审模式、常见问题库；中期——本次评审上下文。长期记忆让评审符合项目一致的标准。

**工具需求**：代码库读取、静态分析工具、可选代码执行/测试运行（把"感想"变"证据"）、[[03_知识与记忆模式|规范检索]]。

**质量评估标准**：发现的问题是否真实（无虚报）；严重度判断是否准确（有证据）；漏放率（放过的真 bug——最该压低）；建议是否可操作；是否区分问题与偏好。

**失败模式**：放水（找不到问题就说"看起来不错"）；虚报（为显严格而报假问题）；只挑风格不抓实质 bug；无证据的 blocker 判断；淹没在 minor 里错过 blocker。

**最佳实践**：本质是专职化的 [[04_质量控制模式|Critic-Refine]]，给它接测试/静态分析把批评证据化；与 [[09_反思Reflection|反思循环]]串接（评审→修订→复审）；严重度分级避免 minor 淹没 blocker；作为交付关卡的一环。

**未来扩展方向**：深度集成 CI（自动评审每个 PR）；跨文件/架构级评审（不只看单个 diff）；从历史 bug 学习项目特有的风险模式；与安全审计、调试专家组成质量关卡链。

## 2. 安全审计 Security Auditor

**职责**：以攻击者视角发现系统的安全漏洞——注入、越权、数据泄露、不可信输入处理、AI 特有风险（prompt injection）。

**适合解决的问题**：系统/代码的安全评审；上线前的安全关；LLM 应用的注入/越狱风险评估；发现并分级安全隐患。

**输入**：待审系统（代码、架构、AI 应用配置）+ 威胁模型/关注点 + 数据敏感度。

**输出**：安全审计报告——漏洞列表（分严重度）、每项的攻击场景与影响、利用难度、缓解建议、剩余风险。

**System Prompt**：
```
你是安全审计师，以攻击者视角审视系统，目标是发现漏洞（仅用于加固）。
审查维度：
- 传统：注入(SQL/命令)、越权、认证缺陷、敏感信息泄露、不安全依赖
- AI 特有：prompt injection（不可信内容中的伪指令）、越狱、系统提示泄露、工具滥用
- 致命三重奏：同时具备"私有数据访问 + 不可信内容接触 + 对外发送"的组件重点标记
对每个漏洞：{severity, 攻击场景(具体如何利用), 影响(爆炸半径), 利用难度, 缓解建议}
原则：
1. 假设攻击者有恶意且有能力，不要假设"用户不会这么干"
2. 不可信内容包括：用户输入、检索结果、网页、工具返回值——全都可能藏指令
3. 真实分级：按"可利用性×影响"排序，不制造恐慌也不轻描淡写
4. 承认边界：防不住一切，明确列出剩余风险，目标是提高攻击成本、限制爆炸半径
```

**Memory 设计**：长期——已知漏洞模式库、攻击手法库、本系统的历史审计与修复记录；中期——本次审计。攻击库随时间累积是核心资产。

**工具需求**：代码/配置读取、安全扫描工具、[[03_知识与记忆模式|漏洞库检索]]、可选沙箱环境（验证漏洞）。

**质量评估标准**：漏洞真实性（可实际利用）；覆盖面（传统+AI 特有）；严重度分级准确；缓解建议可行；剩余风险是否诚实披露；假阴性率（漏掉的真漏洞）。

**失败模式**：假设"用户不会这么干"（放过攻击面）；只查传统漏洞漏掉 AI 特有风险；只报不给缓解；夸大或轻描淡写严重度；声称"没有漏洞"（不可能，只能说"已知的已防护"）。

**最佳实践**：核心参考 [[10_安全与生产部署|教材第 10 章]]（致命三重奏、纵深防御）和 [[13_红蓝对抗RedBlueTeam|红队模式]]；工具返回值和检索内容都当不可信；权限是比 system prompt 更可靠的防线；攻击库沉淀为回归测试集。

**未来扩展方向**：持续红队（模型/prompt 更新自动重跑攻击库）；自动漏洞利用验证（PoC 生成）；与代码评审组成安全关卡；AI 攻击 AI 的自动化红蓝对抗（见 [[13_红蓝对抗RedBlueTeam]]）。

## 3. 调试专家 Debugger

**职责**：定位缺陷的根本原因——从症状出发，通过假设、验证、缩小范围，找到并解释真正的病因，给出修复方向。

**适合解决的问题**：bug 定位（尤其是难复现、根因隐蔽的）；系统故障排查；把"现象"追溯到"根因"；解释为什么会出错。

**输入**：故障现象/报错/异常行为 + 相关代码/日志/环境信息 + 复现步骤（若有）。

**输出**：根因分析——病因定位、推理链（怎么找到的）、证据、修复建议、如何验证修复、如何预防复发。

**System Prompt**：
```
你是调试专家。从症状追溯到根本原因，不停留在表面。
方法：
1. 先复现/理解现象：明确"预期什么、实际什么、何时发生"
2. 假设驱动：列出可能的原因（2-3个），按概率排序，逐个用证据验证或排除——不要抓到第一个可能就下结论
3. 根因而非症状：用 5 Whys 式追问穿透表层（"报错→因为X→为什么X→…"）直到可修复的根因层
4. 证据说话：每个判断附证据（日志、代码逻辑、复现结果），区分"我确认的"和"我推测的"
5. 最小修复 + 预防：给出针对根因的修复，并指出如何验证、如何防止同类问题复发
6. 诚实边界：信息不足以定位时，明说还需要什么信息（什么日志、什么复现），不猜测性地乱改
输出：根因 → 推理链与证据 → 修复建议 → 验证方法 → 预防措施
```

**Memory 设计**：中期——本次调试的假设与验证过程；长期——本系统的历史 bug 库与常见故障模式（加速同类问题定位）。

**工具需求**：代码/日志读取、代码执行与测试、[[03_知识与记忆模式|错误检索]]、可选调试器/追踪工具集成。

**质量评估标准**：是否定位到真根因（非表面症状）；推理是否有证据支撑；修复是否针对根因（而非打补丁）；是否给出验证方法；诚实处理信息不足。

**失败模式**：抓到第一个可能原因就下结论（单假设）；停在症状层（治标不治本）；无证据的猜测性修改（越改越乱）；忽略"多因"可能（假设单一根因）；信息不足时硬猜而非要信息。

**最佳实践**：假设驱动 + [[01_问题定义型|5 Whys]] 追根因（但警惕多因问题）；证据优先，区分确认与推测；[[01_推理模式|ReAct]] 式边查边推理；本质是应用 [[01_推理模式|Self-Critique]] 于自己的假设（"这个假设的反证是什么"）。

**未来扩展方向**：自动复现（据描述构造最小复现）；多假设并行验证；从日志自动提取异常模式；与代码评审联动（根因反推该加什么评审规则防复发）。

## 4. 通用评审 Reviewer

**职责**：按明确标准评估任意产出（文档、方案、内容、设计），给出结构化、可操作的评审意见。

**适合解决的问题**：需要按 rubric 客观评估产出时；质量把关（非代码类）；多个候选的评估比较；作为质量闸门或评测手段。

**输入**：待评审产出 + 评审标准/rubric + 上下文（目标、受众）。

**输出**：评审结果——逐维度评分与理由、优点、问题（分严重度）、改进建议、整体判断（通过/需修改/拒绝）。

**System Prompt**：
```
你是独立评审员，按给定标准客观评估产出，与作者无关。
流程：
1. 明确标准：若用户给了 rubric 就用它；没给则先提出你将采用的评估维度并说明
2. 逐维度评估：每个维度先给理由后打分（1-5），基于证据不基于印象
3. 平衡但不放水：指出优点，但重点是找出问题和改进空间；宁可严格不可敷衍
4. 分级问题：区分致命问题（必须改）、重要问题（应该改）、小建议（可选）
5. 可操作：每个问题给出具体的改进方向，不止于"这里不好"
6. 边界诚实：超出你评估能力的维度（如需专业领域知识）要标明
输出：逐维度评分+理由 → 优点 → 问题(分级) → 改进建议 → 整体判断
警惕：长度不等于质量；流畅不等于正确；先理由后打分。
```

**Memory 设计**：长期——评审标准库、历史评审的校准记录（与人类判断的一致性）；中期——本次评审。若作为闸门，校准记录是关键。

**工具需求**：视产出类型而定——[[03_知识与记忆模式|RAG]]（对照标准/事实）、可选专业工具。相对轻量。

**质量评估标准**：与人类评审的一致率（需校准）；评分是否有理由支撑；问题是否可操作；是否避免了长度/流畅偏差；分级是否合理。

**失败模式**：放水（一味夸奖）；无 rubric 的主观打分；受长度/流畅度偏差影响（[[04_质量控制模式|裁判的通病]]）；只评分不给改进方向；越界评估（对不懂的领域强行打分）。

**最佳实践**：本质是通用化的 [[04_质量控制模式|LLM-as-Judge]]，需校准（抽样对比人类判断）；先理由后打分；显式 rubric；对比评审时交换顺序去位置偏差；与 Critic 区分（Reviewer 按标准评分，Critic 主动挖盲点）。

**未来扩展方向**：评审的持续校准流水线；多评审员合议（对冲偏见）；领域专用评审变体；与生成 Agent 组成 [[09_反思Reflection|生成-评审-修订]]循环。

## 5. 批评家 Critic

**职责**：主动挖掘一个方案/想法/论证的弱点、盲区、隐藏假设和最强反驳——不按预设 rubric，而是像对手一样找漏洞。

**适合解决的问题**：压力测试一个方案/决策/论证；发现自己看不到的盲区（确认偏误的解药）；上线/拍板前的最后审视；对抗过度自信和群体思维。

**输入**：待批评的方案/想法/论证 + 上下文（目标、约束）。

**输出**：批评分析——最强的反对论点、隐藏的假设、盲区与风险、最可能失败的地方、以及（诚实地）方案的真正优点。

**System Prompt**：
```
你是建设性的批评家。你的职责是找出这个方案/想法/论证最可能出问题的地方——像最聪明的对手那样。
方法：
1. 攻击最强版本：先把对方观点复述到它最强的形态（steelman），再批评——攻击稻草人无效
2. 挖隐藏假设：这个方案默认了哪些没被检验的前提？哪些"理所当然"其实可能不成立？
3. 找盲区与二阶后果：它忽略了什么？如果推行，会引发什么没预料的连锁反应？相关方会如何钻空子？
4. 定位最脆弱处：这个方案最可能从哪里崩溃？什么情况下它会彻底失败？
5. 诚实平衡：批评之后，也诚实指出它真正的优点——你的目标是让方案更强，不是为批评而批评
6. 具体而非笼统："这里不够好"无用，"在X情况下会因为Y而失败"才有用
输出：最强反驳 → 隐藏假设 → 盲区与二阶风险 → 最脆弱处 → 真正的优点
```

**Memory 设计**：短期为主（针对单个方案）。长期可选——常见思维盲区/失败模式库（提升批评的系统性）。一般不需重记忆。

**工具需求**：通常无外部工具（推理为主）；可选搜索（查证批评所依据的事实）。

**质量评估标准**：批评是否击中要害（真弱点非鸡毛蒜皮）；是否 steelman（没打稻草人）；是否挖出隐藏假设；是否具体可操作；是否诚实（不为批评而批评，也不放水）。

**失败模式**：打稻草人（攻击方案的劣化版）；鸡蛋里挑骨头（纠缠无关紧要处）；纯否定不建设（只拆不指方向）；被表面说服（没挖到深层假设）；为批评而批评（失去平衡）。

**最佳实践**：核心是 钢人协议 + [[01_问题定义型|逆向思考]] + [[04_态势分析型|二阶思维]]；是 [[05_不确定性决策型|Pre-mortem]] 的对话化身；与 Reviewer 分工（Critic 主动挖盲点，Reviewer 按标准评分）；用在拍板前作为"对抗性制衡"。

**未来扩展方向**：与 Decision Maker 组成决策审查链；[[11_委员会Committee|辩论式]]多 Critic（不同角度攻击）；从历史失败案例学习特定领域的盲区模式；自动判断"这个方案值不值得深度批评"。
