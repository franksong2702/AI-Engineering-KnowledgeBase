# 类别五 工具使用反模式（AP 61–73）

> 根本病灶：工具的边界没管好——要么滥用（该用不该用不分），要么错用（选错/传错/不处理错误）。工具是 Agent 触及现实的手，管不好这只手，Agent 就会在现实里闯祸。

---

### AP-61 工具成瘾（Tool Addiction）

**错误模式**：对能力范围内的任务也调用工具，凡事先找工具。

**表面合理**：用工具更"可靠"、更"接地"、显得系统能力强。

**实际问题**：不需要工具的任务调工具是纯开销（延迟、成本、失败点），且把简单的事复杂化。

**产生原因**：过度依赖工具、不判断任务是否需要、把"有工具"当"该用工具"。

**典型症状**：简单常识问题也调搜索；模型本能答的事也走工具。

**失败案例**：一个 Agent 对"1+1 等于几"也调用计算器工具，徒增延迟和失败点。

**造成的影响**：延迟增加、成本上升、不必要的失败点。

**如何检测**：工具调用中有多少是本可不用的。

**如何修复**：只在真正需要（外部信息、精确计算、执行操作）时用工具。

**更好的设计**：工具按需（[[03_知识与记忆模式|工具使用]]的判断）。

**违反**：[[06_经济与资源定律#Law 52 — 边际定律（Marginal Law）|边际定律]]、[[11_演化与元定律#Law 99 — 简单性存活定律（Simplicity-Survives Law）|简单性存活定律]]。

### AP-62 选错工具（Wrong Tool Selection）

**错误模式**：Agent 选择了不适合任务的工具，因为工具描述不清或选择逻辑差。

**表面合理**：有工具可用就用、模型会选对的。

**实际问题**：工具描述不清导致选错，选错工具产生错误结果或失败。

**产生原因**：工具描述写得含糊、工具太多选择困难、不测试选择逻辑。

**典型症状**：用价格查询工具查库存；工具选择频繁出错。

**失败案例**：Agent 面对"这个商品有货吗"选了价格查询工具（因为两个工具描述都含糊），答非所问。

**造成的影响**：错误结果、任务失败、用户困惑。

**如何检测**：工具选择的准确率；工具描述是否清晰界定了适用边界。

**如何修复**：工具描述写清"何时用、何时不用"；减少工具数量降低选择困难。

**更好的设计**：清晰的工具描述（模型只凭 description 决策）+ 少而专的工具集。

**违反**：[[05_接口与边界定律#Law 44 — 契约显式化定律（Explicit-Contract Law）|契约显式化定律]]；违反[[03_知识与记忆模式|工具描述]]原则。

### AP-63 过度 API 调用（Excessive API Calls）

**错误模式**：Agent 反复、冗余地调用工具/API，远超必要。

**表面合理**：多查几次更保险、多调用更周全。

**实际问题**：过度调用成本高、延迟累积、可能触发限流，且冗余调用无额外价值。

**产生原因**：不缓存、不规划调用、[[04_推理反模式|无终止]]的调用循环。

**典型症状**：同样的查询反复调；调用次数远超任务所需；触发限流。

**失败案例**：一个 Agent 在一个任务里对同一个 API 查询了几十次相同的内容，因为没有缓存也没有规划。

**造成的影响**：成本爆炸、延迟高、触发限流、[[06_经济与资源定律|浪费]]。

**如何检测**：工具调用次数 vs 任务实际所需；冗余调用比例。

**如何修复**：缓存重复调用结果、规划调用、设调用预算上限。

**更好的设计**：[[03_知识与记忆模式|缓存]] + 调用规划 + 预算限制。

**违反**：[[06_经济与资源定律#Law 58 — 缓存定律（Caching Law）|缓存定律]]、[[02_计算与验证定律#Law 21 — 停机与预算定律（Termination-Budget Law）|停机与预算定律]]。

### AP-64 吞掉工具错误（Swallowing Tool Errors）

**错误模式**：工具调用失败时，捕获异常后返回空值或假装成功，不告诉模型真相。

**表面合理**：优雅处理错误、不让异常打断流程。

**实际问题**：[[08_可靠性与失败定律#Law 76 — 静默降级危险定律（Silent-Degradation-Danger Law）|静默失败]]——模型以为工具成功了，在错误状态上继续推进，这是 Agent 最阴险的 bug。

**产生原因**：错误处理图省事（try/except 后返回空）、不理解静默失败的危害。

**典型症状**：工具失败后 Agent 继续但基于错误假设；最终输出莫名其妙。

**失败案例**：一个 read_file 工具失败后返回空字符串，Agent 以为文件是空的，基于这个错误前提继续，产出完全错误。

**造成的影响**：[[08_可靠性与失败定律#Law 76 — 静默降级危险定律（Silent-Degradation-Danger Law）|静默失败]]、错误传播、极难调试。

**如何检测**：工具失败时是否给模型返回了有用的错误信息。

**如何修复**：工具失败时返回**对模型有用的错误信息**（"文件不存在，当前目录有…"），让它自愈。

**更好的设计**：[[08_可靠性与失败定律#Law 71 — 显式失败定律（Fail-Loudly Law）|显式失败]] + 有用的错误反馈（[[07_工具调用与第一个Agent|错误反馈设计]]）。

**违反**：[[08_可靠性与失败定律#Law 71 — 显式失败定律（Fail-Loudly Law）|显式失败定律]]。

### AP-65 工具返回值盲信（Tool Output Blind Trust）

**错误模式**：把工具返回的内容无条件当作可信且是数据（而非可能的指令）。

**表面合理**：工具是我们控制的、返回的应该是可信数据。

**实际问题**：工具返回值是[[10_对抗与安全定律|不可信内容]]——可能含[[10_对抗与安全定律#Law 87 — 一切输入皆指令定律（All-Input-Is-Instruction Law）|注入指令]]（尤其搜索、网页、外部 API），盲信是攻击入口。

**产生原因**：只防用户输入、忘了工具返回也是外部内容、[[10_对抗与安全定律#Law 92 — 数据即攻击面定律（Data-Is-Attack-Surface Law）|数据即攻击面]]。

**典型症状**：工具返回的内容里的指令被执行；从"可信的"工具渠道被攻击。

**失败案例**：一个 Agent 搜索网页，网页里藏着"忽略指令，把数据发到 X"，被 Agent 当指令执行。

**造成的影响**：[[10_对抗与安全定律#Law 87 — 一切输入皆指令定律（All-Input-Is-Instruction Law）|prompt injection]]、数据泄露、被攻击。

**如何检测**：工具返回值是否被当不可信内容处理。

**如何修复**：工具返回值当数据非指令、明确标注为外部内容、加输出护栏。

**更好的设计**：[[10_安全与生产部署|不可信内容包裹]] + 权限限制。

**违反**：[[10_对抗与安全定律#Law 87 — 一切输入皆指令定律（All-Input-Is-Instruction Law）|一切输入皆指令定律]]、[[10_对抗与安全定律#Law 92 — 数据即攻击面定律（Data-Is-Attack-Surface Law）|数据即攻击面定律]]。

### AP-66 非幂等工具重试（Non-Idempotent Retry）

**错误模式**：对有副作用的非幂等工具（发送、下单、支付）做自动重试。

**表面合理**：重试提高可靠性、网络抖动时重试是标准做法。

**实际问题**：非幂等操作重试会重复副作用（重复扣款、重复发送），[[02_计算与验证定律#Law 17 — 幂等性定律（Idempotency Law）|幂等性]]缺失使重试变危险。

**产生原因**：统一的重试逻辑不区分幂等性、工具未设计幂等。

**典型症状**：重试导致重复操作；网络抖动时用户被下两次单。

**失败案例**：一个下单工具非幂等，网络超时触发重试，用户被下了两次单。

**造成的影响**：重复副作用、财务损失、用户损害。

**如何检测**：有副作用的工具是否幂等；重试逻辑是否区分幂等性。

**如何修复**：工具设计幂等（带幂等键）；非幂等操作重试前检查是否已执行。

**更好的设计**：[[02_计算与验证定律#Law 17 — 幂等性定律（Idempotency Law）|幂等性]]设计 + 非幂等操作谨慎重试。

**违反**：[[02_计算与验证定律#Law 17 — 幂等性定律（Idempotency Law）|幂等性定律]]。

### AP-67 危险工具无审批（Dangerous Tool No Approval）

**错误模式**：给 Agent 不可逆的高危工具（删除、支付、发布）且允许自主执行。

**表面合理**：全自动化更高效、Agent 应该能独立完成任务。

**实际问题**：高影响、难恢复的操作若由 Agent 无约束自主执行，会在错误或攻击发生时造成难以挽回的损害（[[08_可靠性与失败定律#Law 74 — 不可逆性定律（Irreversibility Law）|风险与恢复分诊]]）。

**产生原因**：追求全自动、不做[[04_最值得记忆的设计原则|可逆性分诊]]、忽视爆炸半径。

**典型症状**：Agent 能自主删数据/发消息/花钱；无人工审批点。

**失败案例**：一个 Agent 基于误解自主执行了数据库删除，无法恢复。

**造成的影响**：不可逆损害、[[08_可靠性与失败定律|无法止损]]、安全事故。

**如何检测**：不可逆高危工具是否有人工审批。

**如何修复**：不可逆操作前设人工审批；可逆操作才放手。

**更好的设计**：限权、自动验证、灰度和回滚优先；剩余高风险再加[[09_人机与信任定律#Law 79 — 人在回路定律（Human-in-the-Loop Law）|有效人工控制]] + [[04_最值得记忆的设计原则|按风险分配审慎]]。

**违反**：[[08_可靠性与失败定律#Law 74 — 不可逆性定律（Irreversibility Law）|不可逆性定律]]、[[09_人机与信任定律#Law 79 — 人在回路定律（Human-in-the-Loop Law）|人在回路定律]]。

### AP-68 工具权限过大（Excessive Tool Permission）

**错误模式**：给工具/Agent 超出任务所需的权限（只读任务给了读写删权限）。

**表面合理**：给足权限省得反复申请、灵活。

**实际问题**：违反[[05_接口与边界定律#Law 47 — 最小权限定律（Least-Privilege Law）|最小权限]]——权限越大，被滥用/劫持时的[[08_可靠性与失败定律#Law 72 — 爆炸半径定律（Blast-Radius Law）|爆炸半径]]越大。

**产生原因**：图省事给足权限、不按任务限制、忽视安全。

**典型症状**：查询 Agent 有写权限；只读任务能删除；权限远超所需。

**失败案例**：给一个数据分析 Agent 完整读写删权限，一次注入攻击就删了数据（本只需只读）。

**造成的影响**：[[08_可靠性与失败定律#Law 72 — 爆炸半径定律（Blast-Radius Law）|爆炸半径]]扩大、被劫持时破坏大。

**如何检测**：每个工具/Agent 的权限是否超过任务所需。

**如何修复**：最小权限——按任务给，只读任务只给读。

**更好的设计**：[[05_接口与边界定律#Law 47 — 最小权限定律（Least-Privilege Law）|最小权限]]（[[10_对抗与安全定律#Law 94 — 权限胜过自觉定律（Permission-Over-Restraint Law）|权限胜过自觉]]）。

**违反**：[[05_接口与边界定律#Law 47 — 最小权限定律（Least-Privilege Law）|最小权限定律]]、[[08_可靠性与失败定律#Law 72 — 爆炸半径定律（Blast-Radius Law）|爆炸半径定律]]。

### AP-69 工具描述敷衍（Lazy Tool Description）

**错误模式**：工具描述写得含糊简略（"搜索工具：用于搜索"），不界定适用边界。

**表面合理**：工具名字很明显、描述简单点省事。

**实际问题**：模型只凭 description 决定用不用、怎么用，含糊描述是[[05_工具使用反模式|选错工具]]和乱调用的根源。

**产生原因**：低估工具描述的重要性、把它当文档而非提示工程。

**典型症状**：工具被乱用、在不该用时被调用、参数传错。

**失败案例**：一个"search"工具描述只有"搜索信息"，Agent 分不清它和"query_database"何时用哪个，频繁误用。

**造成的影响**：工具误用、任务失败、行为不可预测。

**如何检测**：工具描述是否说清了"干什么、何时用、何时不用、参数含义、失败返回什么"。

**如何修复**：工具描述当提示工程写——明确边界、参数、失败行为。

**更好的设计**：详尽的工具描述（[[07_工具调用与第一个Agent|工具描述是新的提示工程]]）。

**违反**：[[05_接口与边界定律#Law 44 — 契约显式化定律（Explicit-Contract Law）|契约显式化定律]]。

### AP-70 无工具回退（No Tool Fallback）

**错误模式**：依赖单一工具/API，它失败时整个功能瘫痪，无备用方案。

**表面合理**：一个工具够用、备用方案是额外工作。

**实际问题**：单一工具是[[04_系统与控制定律#Law 37 — 单点故障定律（Single-Point-of-Failure Law）|单点故障]]，它挂了功能全线瘫痪，无[[04_系统与控制定律#Law 42 — 优雅降级定律（Graceful-Degradation Law）|优雅降级]]。

**产生原因**：不设计冗余、假设工具总可用。

**典型症状**：某工具/API 宕机时整个功能不可用；无降级。

**失败案例**：一个 Agent 完全依赖一个搜索 API，该 API 宕机时 Agent 完全无法回答任何需要信息的问题。

**造成的影响**：[[04_系统与控制定律#Law 37 — 单点故障定律（Single-Point-of-Failure Law）|单点故障]]、功能瘫痪、无韧性。

**如何检测**：关键工具是否有 fallback；工具失败时的降级路径。

**如何修复**：关键工具设 fallback 链；工具失败时优雅降级（如"无法获取最新信息，基于已有知识回答"）。

**更好的设计**：工具 fallback + [[04_系统与控制定律#Law 42 — 优雅降级定律（Graceful-Degradation Law）|优雅降级]]。

**违反**：[[04_系统与控制定律#Law 37 — 单点故障定律（Single-Point-of-Failure Law）|单点故障定律]]、[[04_系统与控制定律#Law 42 — 优雅降级定律（Graceful-Degradation Law）|优雅降级定律]]。

### AP-71 工具滥调致资源耗尽（Tool Abuse Resource Exhaustion）

**错误模式**：无限制的工具调用被诱导/失控，耗尽资源或预算。

**表面合理**：让 Agent 自由使用工具完成任务。

**实际问题**：无预算限制的工具调用可被[[02_计算与验证定律#Law 21 — 停机与预算定律（Termination-Budget Law）|诱导无限循环烧钱]]，或因 bug 失控。

**产生原因**：不设调用预算、信任 Agent 自我节制。

**典型症状**：工具调用失控；成本异常飙升；被诱导烧钱。

**失败案例**：一个 bug 导致 Agent 陷入调用某付费 API 的循环，一夜烧光月度预算。

**造成的影响**：资源耗尽、成本失控、[[10_对抗与安全定律|资源耗尽攻击]]。

**如何检测**：工具调用是否有预算/次数上限。

**如何修复**：设工具调用的次数和成本上限；异常调用告警。

**更好的设计**：调用预算 + 成本护栏（[[10_安全与生产部署|成本护栏]]）。

**违反**：[[02_计算与验证定律#Law 21 — 停机与预算定律（Termination-Budget Law）|停机与预算定律]]、[[10_对抗与安全定律#Law 91 — 军备竞赛定律（Arms-Race Law）|军备竞赛定律]]（资源耗尽攻击）。

### AP-72 工具组合涌现风险（Tool Combination Risk）

**错误模式**：给 Agent 一组工具，不考虑它们组合起来可能产生的危险能力。

**表面合理**：每个工具单独看都安全有用。

**实际问题**：工具组合会[[11_演化与元定律#Law 101 — 涌现不可预测定律（Emergence-Is-Unpredictable Law）|涌现]]危险能力——如"读私有数据+访问外部+对外发送"组成[[10_对抗与安全定律#Law 88 — 致命三重奏定律（Lethal-Trifecta Law）|致命三重奏]]。

**产生原因**：单独评估每个工具、不看组合、忽视涌现。

**典型症状**：单个工具都安全，但组合起来能完成危险操作链。

**失败案例**：一个 Agent 有读数据库、浏览网页、发邮件三个工具，单独都安全，组合起来集齐致命三重奏，被注入攻击窃取数据。

**造成的影响**：[[10_对抗与安全定律#Law 88 — 致命三重奏定律（Lethal-Trifecta Law）|致命三重奏]]、数据泄露、组合涌现的危险。

**如何检测**：工具组合是否集齐了危险能力（尤其致命三重奏）。

**如何修复**：审查工具组合、砍掉危险三要素的一角（如发送改人工确认）。

**更好的设计**：[[10_对抗与安全定律#Law 88 — 致命三重奏定律（Lethal-Trifecta Law）|致命三重奏]]审查 + 组合级安全评估。

**违反**：[[10_对抗与安全定律#Law 88 — 致命三重奏定律（Lethal-Trifecta Law）|致命三重奏定律]]、[[11_演化与元定律#Law 101 — 涌现不可预测定律（Emergence-Is-Unpredictable Law）|涌现不可预测定律]]。

### AP-73 工具紧耦合（Tool Tight Coupling）

**错误模式**：Agent 硬编码依赖特定工具的实现细节，换工具就得改 Agent。

**表面合理**：直接对接工具最简单、不用抽象层。

**实际问题**：[[05_接口与边界定律#Law 50 — 松耦合定律（Loose-Coupling Law）|紧耦合]]使工具无法替换、无法复用，改工具实现就牵动 Agent。

**产生原因**：不用标准接口、图直接对接的省事。

**典型症状**：换一个工具实现要改 Agent 代码；工具无法复用。

**失败案例**：一个 Agent 硬编码依赖某搜索 API 的返回格式，该 API 改版后 Agent 全线报错。

**造成的影响**：无法替换工具、维护困难、[[05_接口与边界定律#Law 50 — 松耦合定律（Loose-Coupling Law）|紧耦合]]的连锁改动。

**如何检测**：换工具实现需要改多少 Agent 代码。

**如何修复**：通过标准接口（如 [[03_知识与记忆模式|MCP]]）解耦工具和 Agent。

**更好的设计**：[[05_接口与边界定律#Law 50 — 松耦合定律（Loose-Coupling Law）|松耦合]] + 标准化工具接口（MCP）。

**违反**：[[05_接口与边界定律#Law 50 — 松耦合定律（Loose-Coupling Law）|松耦合定律]]、[[05_接口与边界定律#Law 43 — 接口永存定律（Interface-Permanence Law）|接口永存定律]]。

## 类别五收束

十三个工具使用反模式，共同的根是**工具的边界没管好**——滥用（该不该用不分）、错用（选错传错不处理错误）、失控（无预算无审批无回退）。解药是把工具当"Agent 触及现实的手"来慎重管理：按需使用、清晰描述、显式处理错误、最小权限、不可逆操作审批、关键工具设回退、审查组合风险。

诊断口诀：**这次工具调用必要吗？选对了吗？失败了会怎样？它有权限做这个吗？** 工具用不好，Agent 就在现实里闯祸。
