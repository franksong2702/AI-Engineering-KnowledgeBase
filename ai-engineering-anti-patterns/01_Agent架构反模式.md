# 类别一 Agent 架构反模式（AP 1–16）

> 根本病灶：把 Agent 当成"更高级"的默认选择，而非"在特定条件下才划算"的重型工具。这一类的几乎所有反模式，都源于违背 [[04_最值得记忆的设计原则|简单优先]]——用 Agent 的自主性（和它带来的方差、成本、不可控）去解决本不需要它的问题。

---

### AP-1 过度 Agent 化（Over-Agentization）

**错误模式**：把本可用一次 LLM 调用或确定性工作流解决的任务，做成一个自主 Agent。

**表面合理**：Agent 更"智能"、更灵活、更未来、更能应对变化。

**实际问题**：Agent 的自主性引入了方差、成本、延迟、不可控——这些对本可确定性解决的任务是纯负债。你用一个不可预测的东西替代了一个可预测的东西。

**产生原因**：对"Agent"的兴奋压倒了工程判断；把"能做"当成"该做"；追求技术上的高级感。

**典型症状**：一个固定三步的流程被做成 Agent 让它"自己决定"；简单分类任务用 ReAct 循环；输出方差大、成本高、还不如原来的脚本稳。

**失败案例**：一个"根据规则给邮件分类"的任务被做成自主 Agent，结果分类不稳定、每次成本是规则方案的百倍、还偶尔跑偏。

**造成的影响**：成本和延迟暴涨、可靠性下降、调试困难、维护成本高。

**如何检测**：问"这个任务的步骤可预知吗"——可预知却用了 Agent，就是过度 Agent 化。

**如何修复**：降级——能用一次调用就不用 Agent，能用工作流就不用自主 Agent。

**更好的设计**：[[foundation-of-ai-engineering/00_INDEX|工作流优先于 Agent]]——步骤可预知用确定性流程，只有步骤依输入而变才用 Agent。

**违反**：[[02_计算与验证定律#Law 18 — 确定性优先定律（Determinism-First Law）|确定性优先定律]]、[[11_演化与元定律#Law 99 — 简单性存活定律（Simplicity-Survives Law）|简单性存活定律]]；违反 [[llm-design-patterns/00_INDEX|LLM Design Patterns]] 的"Agent vs 工作流"判据。

### AP-2 God Agent（上帝 Agent）

**错误模式**：一个 Agent 承担所有职责——规划、执行、记忆、工具、评价，无所不做。

**表面合理**：一个 Agent 搞定一切，简单、不用协调、没有接口问题。

**实际问题**：职责混杂导致上下文污染、无法单独测试/优化任何一部分、复杂度集中于一点、任何改动都牵一发动全身（违反[[05_接口与边界定律#Law 48 — 关注点分离定律（Separation-of-Concerns Law）|关注点分离]]）。

**产生原因**：不想设计边界、图省事、低估了单一职责的价值。

**典型症状**：一个巨型 system prompt 塞满所有规则；上下文里混杂各种无关信息；改一个功能影响所有功能。

**失败案例**：一个客服 Agent 同时处理查询、退款、投诉、技术支持、账单，prompt 长到自相矛盾，任何一类都做不好。

**造成的影响**：质量全面平庸、不可维护、不可测试、上下文信噪比崩溃。

**如何检测**：一个 Agent 的职责能用"且"列出五个以上——它是 God Agent。

**如何修复**：按职责/上下文边界拆分，或用[[07_动态路由DynamicRouting|路由]]分发给专门的 handler。

**更好的设计**：单一职责的 Agent + 路由/编排；每个 Agent 上下文干净、可独立优化。

**违反**：[[05_接口与边界定律#Law 48 — 关注点分离定律（Separation-of-Concerns Law）|关注点分离定律]]、[[01_信息与压缩定律#Law 3 — 信噪比定律（Signal-to-Noise Law）|信噪比定律]]；违反[[04_质量与审查|单一职责]]原则。

### AP-3 无清晰职责（No Clear Responsibility）

**错误模式**：系统里的 Agent 边界模糊，没人明确"负责什么"，职责重叠或悬空。

**表面合理**：让 Agent 们"灵活协作"、不设死边界显得更有机、更智能。

**实际问题**：职责不清导致重复劳动、遗漏（都以为别人做了）、以及无法定位问题（出错了不知道是谁的责任）。

**产生原因**：跳过了架构设计、误以为"灵活"比"清晰"好、不愿做边界的硬决定。

**典型症状**：两个 Agent 做同样的事；某个必要工作没人做；出问题时无法归因到具体 Agent。

**失败案例**：一个多 Agent 研究系统，三个 Agent 都在搜索同样的信息，而"核查"这一步没有任何 Agent 负责，导致大量重复和一个未被填补的空洞。

**造成的影响**：资源浪费、质量漏洞、不可调试、[[04_系统与控制定律#Law 39 — 康威定律（Conway's Law）|康威定律]]式的混乱结构。

**如何检测**：问"这个职责由谁负责"——答不出唯一的负责者，就是职责不清。

**如何修复**：用 [[01_问题定义型|MECE]] 重新划分职责，确保不重叠、不遗漏、每个职责有唯一负责者。

**更好的设计**：清晰的职责矩阵，每个 Agent 的边界显式化（[[04_最值得记忆的设计原则|显式胜过隐式]]）。

**违反**：[[05_接口与边界定律#Law 44 — 契约显式化定律（Explicit-Contract Law）|契约显式化定律]]、[[04_系统与控制定律#Law 39 — 康威定律（Conway's Law）|康威定律]]。

### AP-4 无限委托（Infinite Delegation）

**错误模式**：Agent 遇到任务就委托给子 Agent，子 Agent 再委托，层层下推却没人真正做事。

**表面合理**：分解和委托是好的（[[laws-of-ai-engineering/02_计算与验证定律#Law 15 — 分解降难定律（Decomposition Law）|分解降难]]），多一层委托显得更有条理。

**实际问题**：委托本身有成本，无限委托是"击鼓传花"——协调开销累积，却迟迟不产生实际价值，甚至陷入委托循环。

**产生原因**：把"委托"当成万能解、没有委托的终止条件、混淆了"分解"和"逃避执行"。

**典型症状**：调用链很深但产出很少；每层都在"规划如何委托"而非做事；委托的 token 远超干活的 token。

**失败案例**：一个 orchestrator 把任务委托给 sub-orchestrator，后者又委托给 sub-sub-orchestrator，五层之后才有一个 Agent 真正执行，而它本可以一步完成。

**造成的影响**：成本爆炸、延迟累积、[[06_层级Hierarchical|层级官僚化]]、价值稀释。

**如何检测**：测量"协调 token"与"干活 token"的比例——委托远超执行就是无限委托。

**如何修复**：设委托深度上限；每层委托前问"我能不能自己做"；扁平化。

**更好的设计**：浅层委托 + 明确的"何时自己做"判据；委托只在真正需要上下文隔离/并行时。

**违反**：[[02_计算与验证定律#Law 21 — 停机与预算定律（Termination-Budget Law）|停机与预算定律]]、[[06_经济与资源定律#Law 57 — 规模效应定律（Scale-Effects Law）|规模效应定律]]、[[11_演化与元定律#Law 99 — 简单性存活定律（Simplicity-Survives Law）|简单性存活定律]]。

### AP-5 Agent 蔓延（Agent Sprawl）

**错误模式**：随着需求增加，不断添加新 Agent，从不合并或删除，系统里的 Agent 越来越多。

**表面合理**：新需求加个新 Agent 最直接、不动存量、看起来模块化。

**实际问题**：[[04_系统与控制定律#Law 41 — 复杂度累积定律（Complexity-Accumulation Law）|复杂度会在缺少主动偿还时累积]]——Agent 数量膨胀、交互和异常路径快速增加，最终无人理解整个系统。

**产生原因**：缺乏定期精简、加 Agent 比重构容易、每个单独看都"有用"。

**典型症状**：系统里有几十个 Agent；没人能画出完整的交互图；加一个新 Agent 要考虑对一堆现有 Agent 的影响。

**失败案例**：一个系统两年间累积到 40 个 Agent，其中一半的职责重叠或已废弃，但没人敢删，因为不确定依赖关系。

**造成的影响**：不可维护、协调成本爆炸、涌现的意外行为、[[04_系统与控制定律#Law 41 — 复杂度累积定律（Complexity-Accumulation Law）|复杂度压垮系统]]。

**如何检测**：Agent 数量持续增长而从未减少；砍掉某个 Agent 时无人能确定后果。

**如何修复**：定期审计——每个 Agent 问"砍掉它系统会变差吗"，答不出就砍；合并职责相近的。

**更好的设计**：主动偿还复杂度，保持 Agent 数量最小；加之前先问能不能复用/扩展现有的。

**违反**：[[04_系统与控制定律#Law 41 — 复杂度累积定律（Complexity-Accumulation Law）|复杂度累积定律]]、[[06_经济与资源定律#Law 57 — 规模效应定律（Scale-Effects Law）|规模效应定律]]、[[11_演化与元定律#Law 99 — 简单性存活定律（Simplicity-Survives Law）|简单性存活定律]]。

### AP-6 拟人化分工（Anthropomorphic Decomposition）

**错误模式**：按人类职位设计 Agent（CEO Agent、经理 Agent、员工 Agent），而非按上下文/工具/能力边界。

**表面合理**：模仿人类组织直观、好理解、符合"团队协作"的类比。

**实际问题**：同一个模型换个头衔不会变得更强（[[multi-agent-patterns-handbook/00_INDEX#五条跨模式定律|Multi-Agent 定律 1：上下文隔离]]）——拟人分工制造了伪多样性和不必要的层级，收益是幻觉。

**产生原因**：把人类组织类比过度套用；误以为"角色"能提升能力；被"AI 团队"的叙事吸引。

**典型症状**：有 CEO/CTO/员工 Agent 的层级；"经理"Agent 只是转发消息；分工基于职位而非真实的上下文隔离。

**失败案例**：一个"AI 公司"系统，CEO Agent 让经理 Agent 让员工 Agent 做事，实际就是同一个模型自己跟自己传话三次，成本三倍、质量不变。

**造成的影响**：伪多样性、无谓的协调开销、层级传话失真、成本翻倍无收益。

**如何检测**：Agent 是按职位命名的；分工无法用"上下文/工具/权限的真实差异"解释。

**如何修复**：按上下文隔离、工具集、权限边界重新分工，而非按拟人职位。

**更好的设计**：分工的正当理由只有三个——上下文隔离、真并行、权限隔离（[[multi-agent-patterns-handbook/00_INDEX|Multi-Agent 手册]]）。

**违反**：[[04_系统与控制定律#Law 39 — 康威定律（Conway's Law）|康威定律]]、[[multi-agent-patterns-handbook/00_INDEX#五条跨模式定律|Multi-Agent 定律 1：上下文隔离]]；违反[[03_多Agent评价|角色分配]]原则。

### AP-7 自主性错配（Autonomy Mismatch）

**错误模式**：给 Agent 的自主性与它的可靠性、任务的可逆性不匹配——在高风险不可逆的任务上给了完全自主权。

**表面合理**：更自主=更省人力=更强大，全自动化是目标。

**实际问题**：自主性应被可靠性和可逆性证明（[[01_评价的基础理论|自主是成本不是美德]]）；在不可逆高风险任务上的高自主是纯风险。

**产生原因**：把自主性当美德最大化、忽视可逆性分诊、追求"全自动"的理想。

**典型症状**：Agent 能自主执行删除/发送/支付；没有不可逆操作的人工审批；出事无法挽回。

**失败案例**：一个 Agent 被授予自主发送对外邮件的权限，基于一个幻觉信息自主发出了错误的客户通知，无法撤回。

**造成的影响**：不可逆的损害、[[08_可靠性与失败定律|无法止损]]、责任事故。

**如何检测**：检查是否有不可逆操作缺少人工审批点。

**如何修复**：按后果与恢复能力分诊——低影响易恢复的操作走轻流程；高影响、难恢复或证据不足的发送/删除/支付/发布，提高限权、验证、灰度、回滚或人工控制强度。

**更好的设计**：自主性匹配实测可靠性、后果与恢复能力（[[09_人机与信任定律#Law 79 — 人在回路定律（Human-in-the-Loop Law）|人在回路]]）；[[04_最值得记忆的设计原则|按风险分配审慎]]。

**违反**：[[08_可靠性与失败定律#Law 74 — 不可逆性定律（Irreversibility Law）|不可逆性定律]]、[[09_人机与信任定律#Law 79 — 人在回路定律（Human-in-the-Loop Law）|人在回路定律]]、[[09_人机与信任定律#Law 86 — 责任不可委托定律（Accountability-Cannot-Be-Delegated Law）|责任不可委托定律]]。

### AP-8 提示即架构（Prompt-as-Architecture）

**错误模式**：把所有的系统逻辑、约束、流程都塞进一个巨型 system prompt，用提示替代架构设计。

**表面合理**：改 prompt 比改代码快，一个 prompt 搞定所有逻辑显得优雅。

**实际问题**：巨型 prompt 不可测试、不可维护、内部规则互相冲突、且[[10_对抗与安全定律#Law 94 — 权限胜过自觉定律（Permission-Over-Restraint Law）|提示层的约束可被绕过]]（不是可靠的架构）。

**产生原因**：低估架构的必要性、贪图改 prompt 的即时性、把提示工程误当系统工程。

**典型症状**：system prompt 长达数千字；里面有大量"如果…则…"的流程逻辑；规则多到自相矛盾。

**失败案例**：一个 Agent 的所有安全约束、业务逻辑、流程控制都写在 prompt 里，一次 prompt injection 就绕过了全部"约束"。

**造成的影响**：不可靠、不可维护、[[10_对抗与安全定律|安全形同虚设]]、规则冲突导致行为不可预测。

**如何检测**：关键的安全/流程逻辑是否只存在于 prompt 里而无代码层保障。

**如何修复**：把确定性逻辑移到代码、把安全约束移到权限层，prompt 只负责它真正擅长的（语言理解、灵活判断）。

**更好的设计**：架构在代码和权限层，提示负责语言层；[[10_对抗与安全定律#Law 94 — 权限胜过自觉定律（Permission-Over-Restraint Law）|权限胜过自觉]]。

**违反**：[[10_对抗与安全定律#Law 94 — 权限胜过自觉定律（Permission-Over-Restraint Law）|权限胜过自觉定律]]、[[02_计算与验证定律#Law 18 — 确定性优先定律（Determinism-First Law）|确定性优先定律]]、[[08_可靠性与失败定律#Law 78 — 测试即真理定律（Untested-Is-Broken Law）|测试即真理定律]]。

### AP-9 无状态假设（Stateless Assumption）陷阱

**错误模式**：假设 Agent"记得"之前发生的事，不显式管理状态，依赖模型自己保持连续性。

**表面合理**：对话界面让 Agent 看起来有记忆，显式管理状态显得多余。

**实际问题**：模型是无状态的（[[01_信息与压缩定律#Law 2 — 上下文即状态定律（Context-is-State Law）|上下文即状态]]），"记忆"必须靠显式重注入上下文；依赖幻觉般的"它会记得"必然导致状态丢失。

**产生原因**：被对话界面的连续性错觉误导、不理解模型的无状态本质。

**典型症状**：多轮任务中 Agent"忘记"了之前的决定；跨会话状态丢失；假设它记得却没实际存储。

**失败案例**：一个多步 Agent 假设它记得第一步的结果，不显式传递，到第五步时早已"忘记"，基于错误的假设继续。

**造成的影响**：状态丢失、行为不连贯、长任务失败。

**如何检测**：检查是否有"依赖模型记得"但无显式状态存储的地方。

**如何修复**：显式管理状态——把关键状态存进文件/DB，需要时重注入上下文。

**更好的设计**：显式状态管理 + [[03_知识与记忆模式|分层记忆]]；不依赖模型自己"记得"。

**违反**：[[01_信息与压缩定律#Law 2 — 上下文即状态定律（Context-is-State Law）|上下文即状态定律]]；违反[[03_知识与记忆模式|记忆机制]]设计。

### AP-10 峰值驱动设计（Peak-Driven Design）

**错误模式**：基于 Agent"最好的一次"表现来设计和承诺，而非它的可靠分布。

**表面合理**：既然它"能"做到，就按它能做到来设计——展示了能力上限。

**实际问题**：能力是[[01_评价的基础理论|欺骗性的上限]]，前沿即洼地；按峰值设计的系统在平均和最坏情况会频繁失败。

**产生原因**：被一次惊艳的 demo 误导、混淆"能"和"可靠地能"、[[03_统计与泛化定律#Law 23 — 偏差-方差定律（Bias-Variance Law）|忽略方差]]。

**典型症状**：demo 惊艳但生产不稳；承诺基于最好情况；用户体验方差大。

**失败案例**：一个 Agent 在演示中完美完成复杂任务，团队据此上线，实际成功率只有 40%，因为演示是精选的最好一次。

**造成的影响**：生产可靠性远低于预期、用户信任崩塌、频繁失败。

**如何检测**：设计/承诺是否基于单次最好表现而非成功率分布。

**如何修复**：用能力的分布（成功率、方差、最坏情况）而非峰值来设计和承诺。

**更好的设计**：为可靠性而非峰值设计（[[01_评价的基础理论|可靠性定义]]）；用[[06_评价设计模式|大量重复测量]]评估真实能力。

**违反**：[[03_统计与泛化定律#Law 31 — 长尾定律（Long-Tail Law）|长尾定律]]、[[laws-of-ai-engineering/11_演化与元定律#Law 95 — 能力-可靠性剪刀定律（Capability-Reliability-Scissors Law）|能力-可靠性剪刀定律]]。

### AP-11 循环无出口（Loop Without Exit）

**错误模式**：Agent 的自主循环没有可靠的终止条件，依赖它"自己知道何时停"。

**表面合理**：智能的 Agent 应该能自己判断任务完成、设死的上限显得不灵活。

**实际问题**：Agent 会陷入死循环、无效重复、或永不满足的追求（[[02_计算与验证定律#Law 21 — 停机与预算定律（Termination-Budget Law）|停机问题]]），没有硬性终止就是烧钱黑洞。

**产生原因**：过度信任 Agent 的自我判断、忘记设保险丝、乐观地假设"它会停的"。

**典型症状**：Agent 反复执行相似操作；成本失控；任务"永远差一点就完成"。

**失败案例**：一个研究 Agent 陷入"再搜一个来源就更完整"的循环，无限搜索下去，烧掉大量额度仍未产出报告。

**造成的影响**：成本失控、资源耗尽、任务永不完成。

**如何检测**：检查每个循环是否有显式的最大轮数/预算/收敛判据。

**如何修复**：设三重保险——最大轮数 + 预算上限 + "连续无进展即停"。

**更好的设计**：显式终止条件 + 进度检测（[[02_计算与验证定律#Law 21 — 停机与预算定律（Termination-Budget Law）|停机与预算定律]]）。

**违反**：[[02_计算与验证定律#Law 21 — 停机与预算定律（Termination-Budget Law）|停机与预算定律]]、[[06_经济与资源定律#Law 51 — 机会成本定律（Opportunity-Cost Law）|机会成本定律]]。

### AP-12 无失败路径设计（No Failure Path）

**错误模式**：只设计 Agent 的顺利路径，不设计它失败/卡住/无法完成时怎么办。

**表面合理**：先让主流程跑通，失败处理"以后再加"。

**实际问题**：Agent 一定会遇到失败（[[08_可靠性与失败定律#Law 70 — 墨菲定律（Murphy's Law）|墨菲定律]]），没有失败路径时它会硬撑、编造、或崩溃，而非优雅处理。

**产生原因**：乐观偏差、只关注 happy path、把失败处理当次要。

**典型症状**：Agent 遇到障碍时表现诡异（编造、死循环、崩溃）；没有"我做不到"的优雅退出。

**失败案例**：一个 Agent 无法完成任务时，不是报告"我做不到"，而是编造一个看似完成的假结果，误导下游。

**造成的影响**：[[08_可靠性与失败定律#Law 76 — 静默降级危险定律（Silent-Degradation-Danger Law）|静默失败]]、错误传播、不可信。

**如何检测**：问"这个 Agent 失败时会怎样"——答不出，就没有失败路径设计。

**如何修复**：显式设计失败路径——无法完成时[[04_系统与控制定律#Law 42 — 优雅降级定律（Graceful-Degradation Law）|优雅降级]]、报告、上报人工。

**更好的设计**：为失败而设计——[[08_可靠性与失败定律#Law 71 — 显式失败定律（Fail-Loudly Law）|显式失败]]、[[04_系统与控制定律#Law 42 — 优雅降级定律（Graceful-Degradation Law）|优雅降级]]、可上报。

**违反**：[[08_可靠性与失败定律#Law 70 — 墨菲定律（Murphy's Law）|墨菲定律]]、[[08_可靠性与失败定律#Law 71 — 显式失败定律（Fail-Loudly Law）|显式失败定律]]、[[04_系统与控制定律#Law 42 — 优雅降级定律（Graceful-Degradation Law）|优雅降级定律]]。

### AP-13 黑箱 Agent（Black-Box Agent）

**错误模式**：Agent 的决策过程不可见——没有 trace，只有最终输出。

**表面合理**：只关心结果，中间过程不重要，记录 trace 是额外负担。

**实际问题**：不可观测的系统无法调试、无法验证、无法信任（[[04_系统与控制定律#Law 36 — 可观测性定律（Observability Law）|可观测性定律]]）；出问题只能盲猜。

**产生原因**：把可观测性当"以后再加"、低估调试的需要、图省事。

**典型症状**：Agent 出错时无法定位原因；无法审查它为什么这么做；调试靠猜。

**失败案例**：一个多步 Agent 偶尔给出错误结果，但因为没有 trace，团队花了数周也无法定位是哪一步、为什么出错。

**造成的影响**：不可调试、不可信、问题无法定位、[[02_Agent评价框架|无法做轨迹评价]]。

**如何检测**：Agent 出错时你能否重建它的决策过程——不能，就是黑箱。

**如何修复**：加全程 trace——每步的思考、工具调用、观察都记录。

**更好的设计**：可观测性第一天就有（[[04_最值得记忆的设计原则|让一切可观测]]）；trace 是 Agent 的 print 调试。

**违反**：[[04_系统与控制定律#Law 36 — 可观测性定律（Observability Law）|可观测性定律]]；违反[[02_Agent评价框架|轨迹层评价]]要求。

### AP-14 能力堆砌（Capability Hoarding）

**错误模式**：不断给 Agent 加能力/工具/功能，因为"多一个能力总是好的"。

**表面合理**：能力越多越强大、越通用，加个能力不吃亏。

**实际问题**：更多工具导致[[04_系统与控制定律|选择困难]]、决策质量下降、[[04_系统与控制定律#Law 41 — 复杂度累积定律（Complexity-Accumulation Law）|复杂度累积]]；能力多≠有用（[[01_评价的基础理论|能力vs有用]]）。

**产生原因**：把能力等同于价值、忽略选择成本、不做减法。

**典型症状**：Agent 有几十个工具但只用几个；工具越多决策越差；[[04_系统与控制定律|3-5 个工具]]的界限被远远突破。

**失败案例**：一个 Agent 配了 20 个工具，面对任务时经常选错工具或纠结，反而不如只有 5 个核心工具时可靠。

**造成的影响**：决策质量下降、复杂度膨胀、维护负担、[[01_评价的基础理论|强但不用]]。

**如何检测**：统计工具/能力的实际使用率——大量从不用或误用，就是堆砌。

**如何修复**：做减法——砍掉低频/易误用的能力，从核心的 3-5 个开始。

**更好的设计**：少而精的能力集（[[foundation-of-ai-engineering/00_INDEX|Foundation 的"负空间"]]）；加之前先问"值不值它的选择成本"。

**违反**：[[04_系统与控制定律#Law 41 — 复杂度累积定律（Complexity-Accumulation Law）|复杂度累积定律]]、[[06_经济与资源定律#Law 52 — 边际定律（Marginal Law）|边际定律]]、[[11_演化与元定律#Law 99 — 简单性存活定律（Simplicity-Survives Law）|简单性存活定律]]。

### AP-15 意图字面主义（Intent Literalism）

**错误模式**：Agent 严格执行用户指令的字面意思，不理解背后的真实意图。

**表面合理**：照字面执行"更忠实"、责任更清晰、不擅自揣测。

**实际问题**：指令是对意图的有限表达，压缩与省略会丢失任务相关信息（[[01_信息与压缩定律#Law 6 — 压缩必然丢失定律（Compression-Loses Law）|压缩操作边界]]）；字面执行常错过真实目标，歧义时不问就猜同样危险。

**产生原因**：回避理解意图的难度、把"照做"当安全、不愿反问澄清。

**典型症状**：Agent 完成了字面任务但用户不满意；歧义指令被随意解读；从不反问澄清。

**失败案例**：用户说"把这些文件清理一下"，Agent 理解为"删除"并执行，而用户其实想要"整理归类"——字面执行造成了不可逆损失。

**造成的影响**：目标错失、用户不满、有时造成不可逆错误。

**如何检测**：Agent 是否在歧义时直接猜而非澄清；完成字面任务但错过意图的频率。

**如何修复**：从意图而非字面出发；歧义时反问澄清而非猜（[[laws-of-ai-engineering/09_人机与信任定律#Law 83 — 意图-指令鸿沟定律（Intent-Instruction-Gap Law）|意图非指令]]）。

**更好的设计**：服务真实目标（[[09_人机与信任定律#Law 83 — 意图-指令鸿沟定律（Intent-Instruction-Gap Law）|意图-指令鸿沟定律]]）；不确定就问。

**违反**：[[09_人机与信任定律#Law 83 — 意图-指令鸿沟定律（Intent-Instruction-Gap Law）|意图-指令鸿沟定律]]；违反[[02_Agent评价框架|沟通]]维度。

### AP-16 框架依赖症（Framework Dependence）

**错误模式**：完全依赖某个 Agent 框架的抽象，不理解底层循环，出问题时无法调试。

**表面合理**：框架封装了复杂性、加速开发、不用重复造轮子。

**实际问题**：框架的抽象会[[05_接口与边界定律#Law 45 — 抽象泄漏定律（Leaky-Abstraction Law）|泄漏]]，异常时暴露底层；不理解底层就无法调试框架的失败，也无法判断框架是否适合。

**产生原因**：急于上手、把框架当黑箱、跳过了理解基础循环。

**典型症状**：框架顺利时能用，一出框架没覆盖的情况就束手无策；无法判断问题在框架还是自己的代码。

**失败案例**：团队用一个 Agent 框架搭系统，遇到一个框架抽象泄漏的边界问题，因为没人理解底层 ReAct 循环，卡了很久无法解决。

**造成的影响**：调试能力受限、被框架绑架、[[05_接口与边界定律#Law 45 — 抽象泄漏定律（Leaky-Abstraction Law）|抽象泄漏]]时无解。

**如何检测**：团队能否不用框架裸写一个基础 Agent 循环——不能，就是过度依赖。

**如何修复**：先理解底层（裸写一遍 ReAct 循环），再用框架作为加速器而非黑箱。

**更好的设计**：理解底层 + 用框架加速（[[07_工具调用与第一个Agent|先裸写再用框架]]）；[[05_接口与边界定律#Law 50 — 松耦合定律（Loose-Coupling Law）|松耦合]]于具体框架。

**违反**：[[05_接口与边界定律#Law 45 — 抽象泄漏定律（Leaky-Abstraction Law）|抽象泄漏定律]]、[[11_演化与元定律#Law 98 — 认识论永恒定律（Epistemology-Endures Law）|认识论永恒定律]]（理解底层比记框架 API 保值）。

## 类别一收束

十六个 Agent 架构反模式，几乎全部指向同一个根：**把 Agent 当默认选择而非重型工具，用它的自主性去解决本不需要的问题。** 解药也是同一条——[[04_最值得记忆的设计原则|简单优先]]：能用一次调用不用 Agent，能用工作流不用自主 Agent，能用单 Agent 不用多 Agent（见[[02_多Agent反模式|类别二]]）。

诊断口诀：**这个 Agent 的复杂度/自主性，被它的收益证明了吗？** 答不上来，你大概率正在某个 AP 里。
