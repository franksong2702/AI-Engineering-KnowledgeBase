# 类别二 多 Agent 反模式（AP 17–32）

> 根本病灶：把"多"当成"好"。多 Agent 应被"有罪推定"——它必须证明自己的存在合理（[[03_多Agent评价|何时多Agent优于单Agent]]），否则默认是过度设计。这一类反模式几乎都是"多"带来的开销吞噬了"多"的收益却无人察觉。

---

### AP-17 Agent 过多（Too Many Agents）

**错误模式**：用远超必要数量的 Agent 解决一个问题。

**表面合理**：更多 Agent = 更细分工 = 更专业 = 更强。

**实际问题**：Agent 数量的[[06_经济与资源定律|规模不经济]]——协调开销超线性增长，多数 Agent 不产生边际价值。

**产生原因**：把分工当美德、缺乏"够了"的判断、被"AI 团队"叙事吸引。

**典型症状**：十几个 Agent 但砍掉一半系统不变差；协调 token 远超干活 token。

**失败案例**：一个本可单 Agent 完成的任务用了 8 个 Agent，成本 8 倍、延迟更高、质量没提升。

**造成的影响**：成本爆炸、协调地狱、[[03_多Agent评价|协调成本吞噬收益]]。

**如何检测**：逐个问"砍掉它系统会变差吗"——答不出就是多余。

**如何修复**：砍到最少——只保留有明确增值（上下文隔离/并行/权限）的 Agent。

**更好的设计**：最小 Agent 数 + 单 Agent 基线对照证明"多"的价值。

**违反**：[[06_经济与资源定律#Law 57 — 规模效应定律（Scale-Effects Law）|规模效应定律]]、[[11_演化与元定律#Law 99 — 简单性存活定律（Simplicity-Survives Law）|简单性存活定律]]。

### AP-18 通信爆炸（Communication Explosion）

**错误模式**：Agent 间传递完整的对话历史/过程，而非结构化结论。

**表面合理**：传全部信息"更完整"、不丢细节、对方能看到全貌。

**实际问题**：token 指数增长、噪声跨 Agent 传染、信噪比崩溃（[[multi-agent-patterns-handbook/00_INDEX|Multi-Agent 原则 3]]）。

**产生原因**：怕丢信息、不做压缩、图省事直接转发。

**典型症状**：随 Agent 增多 token 爆炸；每个 Agent 收到大量无关的其他 Agent 的过程。

**失败案例**：五个 Agent 互相传递完整对话历史，到第三轮上下文就爆了，且每个 Agent 被无关信息淹没。

**造成的影响**：成本爆炸、[[01_信息与压缩定律#Law 3 — 信噪比定律（Signal-to-Noise Law）|信噪比崩溃]]、质量下降。

**如何检测**：Agent 间传的是结论还是过程；token 是否随协作超线性增长。

**如何修复**：传结构化结论 + 证据 + 置信度，不传原始对话。

**更好的设计**：自包含的结构化工件传递（[[multi-agent-patterns-handbook/00_INDEX|Multi-Agent 原则 3]]）。

**违反**：[[01_信息与压缩定律#Law 3 — 信噪比定律（Signal-to-Noise Law）|信噪比定律]]、[[01_信息与压缩定律#Law 2 — 上下文即状态定律（Context-is-State Law）|上下文即状态定律]]。

### AP-19 重复角色（Duplicate Roles）

**错误模式**：多个 Agent 做实质相同的工作，只是名字或措辞不同。

**表面合理**：多个视角、冗余更可靠、分工更细。

**实际问题**：同源 Agent 是[[multi-agent-patterns-handbook/00_INDEX|伪多样性]]——同一模型换头衔不产生真正不同的视角，只是重复劳动和成本。

**产生原因**：误以为"多个角色"=多视角、不理解伪多样性、拟人分工的副产品。

**典型症状**：几个 Agent 的输出高度相似；"多视角"其实是同一观点的几种措辞。

**失败案例**：一个"委员会"由五个同模型同 prompt 的 Agent 组成，它们的意见几乎一致，"审议"毫无价值。

**造成的影响**：成本翻倍无收益、伪多样性、虚假的可靠感。

**如何检测**：多个 Agent 的输出相关性——高度相关就是重复。

**如何修复**：合并重复角色；若需多样性，用真差异化（不同模型/知识/工具）。

**更好的设计**：真差异化的 Agent 或干脆合并（[[multi-agent-patterns-handbook/00_INDEX|Multi-Agent 原则 2]]、[[03_统计与泛化定律#Law 28 — 集成去相关定律（Ensemble-Decorrelation Law）|集成去相关]]）。

**违反**：[[03_统计与泛化定律#Law 28 — 集成去相关定律（Ensemble-Decorrelation Law）|集成去相关定律]]、[[multi-agent-patterns-handbook/00_INDEX|Multi-Agent 原则 2]]。

### AP-20 共识成瘾（Consensus Addiction）

**错误模式**：系统执着于让所有 Agent 达成一致，把"共识"当成质量目标。

**表面合理**：一致=可靠、达成共识显得系统成熟、分歧让人不安。

**实际问题**：[[03_多Agent评价|高质量的分歧胜过低质量的共识]]；为一致而一致会碾压正确的少数派、抹杀有价值的分歧。

**产生原因**：把共识当质量代理、对分歧的不适、忽略少数派可能正确。

**典型症状**：系统总是趋同；正确的少数意见被多数压倒；快速一致被当成好信号。

**失败案例**：一个多 Agent 决策系统，一个 Agent 正确地反对，但系统为"达成共识"而采纳了错误的多数意见。

**造成的影响**：正确意见被抹杀、[[04_质量控制模式|从众级联]]、决策质量下降。

**如何检测**：系统是否为一致牺牲正确性；少数派正确意见的存活率。

**如何修复**：重视论据质量而非趋同；保留而非抹杀少数派；允许"保留分歧"作为合法结果。

**更好的设计**：独立意见先行 + 基于论据的裁决（[[11_委员会Committee|委员会]]），而非追求趋同。

**违反**：[[07_认识论与真理定律#Law 61 — 贝叶斯更新定律（Bayesian-Updating Law）|贝叶斯更新定律]]、[[03_统计与泛化定律#Law 28 — 集成去相关定律（Ensemble-Decorrelation Law）|集成去相关定律]]。

### AP-21 协调开销失控（Coordination Overhead）

**错误模式**：协调多个 Agent 消耗的资源超过了它们分工带来的收益。

**表面合理**：协调是多 Agent 必要的成本、值得为了协作付出。

**实际问题**：协调成本[[06_经济与资源定律|超线性增长]]，超过某点后"多"是净亏损。

**产生原因**：不核算协调成本、假设分工收益永远大于协调开销。

**典型症状**：管理 token 超过干活 token；加 Agent 反而更慢更贵。

**失败案例**：一个层级多 Agent 系统，35% 的 token 花在拆解、汇报、验收上，实际干活的不到三分之二。

**造成的影响**：净负收益、成本爆炸、[[06_层级Hierarchical|官僚化]]。

**如何检测**：测量协调成本占比；对比单 Agent 基线的总成本。

**如何修复**：减少协调层级、用代码做确定性协调、扁平化。

**更好的设计**：协调最小化 + 只在收益明确超过协调成本时用多 Agent。

**违反**：[[06_经济与资源定律#Law 57 — 规模效应定律（Scale-Effects Law）|规模效应定律]]、[[06_经济与资源定律#Law 51 — 机会成本定律（Opportunity-Cost Law）|机会成本定律]]。

### AP-22 去中心化浪漫主义（Decentralization Romanticism）

**错误模式**：让 Agent 们"自由讨论、自组织、涌现出解决方案"，无中心协调。

**表面合理**：去中心化更有机、更鲁棒、更像[[14_群体Swarm|群体智能]]、更酷。

**实际问题**：无中心的自由讨论在生产中几乎总是灾难——[[14_群体Swarm|不可控、不收敛]]、互相恭维的循环、成本失控。

**产生原因**：被涌现/群体智能的浪漫叙事吸引、低估中心化的价值、高估自组织。

**典型症状**：Agent 们无止境地讨论；收敛不到结论；成本失控；行为不可预测。

**失败案例**：一个"自组织"多 Agent 系统，Agent 们陷入互相赞同和补充的循环，跑了很久也没产出可用结论，成本高企。

**造成的影响**：不收敛、不可控、成本黑洞、[[14_群体Swarm|涌现失控]]。

**如何检测**：系统是否有明确的中心协调和终止；是否依赖"自由讨论涌现"。

**如何修复**：改用中心化编排（orchestrator）+ 明确终止；去中心化留给特定探索场景。

**更好的设计**：默认从[[multi-agent-patterns-handbook/00_INDEX|中心化]]开始（可控），去中心化仅用于真正的探索型任务。

**违反**：[[02_计算与验证定律#Law 21 — 停机与预算定律（Termination-Budget Law）|停机与预算定律]]、[[11_演化与元定律#Law 101 — 涌现不可预测定律（Emergence-Is-Unpredictable Law）|涌现不可预测定律]]、[[11_演化与元定律#Law 99 — 简单性存活定律（Simplicity-Survives Law）|简单性存活定律]]。

### AP-23 无基线对照（No Baseline Comparison）

**错误模式**：构建多 Agent 系统却从不与单 Agent 基线对照，无法证明"多"的价值。

**表面合理**：多 Agent 明显更强，不用对照也知道。

**实际问题**：不做基线对照就无法证明协作有净增值（[[03_多Agent评价|协作质量]]）——很可能"多"是纯开销甚至负增值。

**产生原因**：假设多 Agent 当然更好、跳过验证、怕基线打脸。

**典型症状**：从没跑过单 Agent 版本；无法量化多 Agent 带来了什么。

**失败案例**：一个复杂多 Agent 系统上线后，有人跑了单 Agent 基线，发现质量相当而成本低得多——多 Agent 一直是纯浪费。

**造成的影响**：无法证明价值、可能长期维护一个负收益的系统。

**如何检测**：有没有单 Agent 基线的对照数据。

**如何修复**：跑单 Agent 基线，用质量/成本/延迟三维对照证明"多"的净增值。

**更好的设计**：基线对照先行（[[03_多Agent评价|评价的第一动作]]）；证明不了增值就降级为单 Agent。

**违反**：[[08_可靠性与失败定律#Law 78 — 测试即真理定律（Untested-Is-Broken Law）|测试即真理定律]]；违反[[03_多Agent评价|协作质量评价]]。

### AP-24 状态竞争（State Race）

**错误模式**：多个 Agent 并行读写同一共享状态，无一致性控制。

**表面合理**：共享状态让 Agent 协作、并行提高效率。

**实际问题**：并发写入产生竞态条件——结果取决于谁最后写，不可复现、难调试。

**产生原因**：忽略并发一致性、假设 Agent 不会冲突、没设计写入协议。

**典型症状**：结果不可复现；偶发的状态错乱；难以定位的间歇性 bug。

**失败案例**：两个 Agent 并行更新同一个状态文件，互相覆盖，导致部分更新丢失，结果随机。

**造成的影响**：数据不一致、不可复现的 bug、难调试。

**如何检测**：是否有多个 Agent 并发写同一状态而无协议。

**如何修复**：单一写入者（orchestrator 唯一写，workers 只读+返回）或用事务/锁。

**更好的设计**：状态写入串行化或[[multi-agent-patterns-handbook/00_INDEX|orchestrator 唯一写入]]（[[03_树状分解Tree|Multi-Agent 手册]]）。

**违反**：[[02_计算与验证定律#Law 17 — 幂等性定律（Idempotency Law）|幂等性定律]]（相关）、[[04_系统与控制定律#Law 36 — 可观测性定律（Observability Law）|可观测性定律]]。

### AP-25 失败静默传染（Silent Failure Contagion）

**错误模式**：一个 Agent 编造/错误的结果被下游 Agent 当真，错误沿协作链传播。

**表面合理**：信任协作伙伴的输出、不重复核查提高效率。

**实际问题**：[[08_可靠性与失败定律#Law 76 — 静默降级危险定律（Silent-Degradation-Danger Law）|静默失败向上传染]]是多 Agent 最阴险的失败——一个幻觉被全系统当真并放大。

**产生原因**：Agent 间过度信任、无置信度传递、上游不[[08_可靠性与失败定律#Law 71 — 显式失败定律（Fail-Loudly Law）|显式失败]]。

**典型症状**：一个错误结论被多个 Agent 引用放大；最终输出的错误可追溯到某个 Agent 的幻觉。

**失败案例**：一个研究 Agent 编造了一个数据，核查 Agent 没核出来，撰写 Agent 当真引用，最终报告基于假数据。

**造成的影响**：错误放大、整个系统输出不可信、[[03_多Agent评价|失败传播]]。

**如何检测**：注入一个 Agent 的错误，看是否被下游照单全收。

**如何修复**：Agent 回传结论附置信度和依据；下游抽查；关键结论独立核验。

**更好的设计**：置信度传递 + 抽查 + [[08_可靠性与失败定律#Law 71 — 显式失败定律（Fail-Loudly Law）|显式失败]]（[[03_多Agent评价|失败传播评价]]）。

**违反**：[[08_可靠性与失败定律#Law 71 — 显式失败定律（Fail-Loudly Law）|显式失败定律]]、[[08_可靠性与失败定律#Law 72 — 爆炸半径定律（Blast-Radius Law）|爆炸半径定律]]。

### AP-26 编排者过载（Orchestrator Overload）

**错误模式**：中心协调者承担太多——既协调又执行又记忆又决策，成为瓶颈和单点故障。

**表面合理**：一个强大的协调者掌控全局、方便管理。

**实际问题**：协调者过载使它成为[[04_系统与控制定律#Law 33 — 瓶颈定律（Bottleneck Law）|瓶颈]]和[[04_系统与控制定律#Law 37 — 单点故障定律（Single-Point-of-Failure Law）|单点故障]]，且上下文被撑爆。

**产生原因**：把太多职责给协调者、不区分协调和执行、[[01_Agent架构反模式|God Agent]] 的多 Agent 版。

**典型症状**：协调者上下文爆炸；它一慢全系统慢；它错全系统错。

**失败案例**：一个 orchestrator 不仅分派任务还自己执行一部分、维护所有状态、做所有决策，上下文很快超限，成为系统瓶颈。

**造成的影响**：瓶颈、单点故障、上下文过载、不可扩展。

**如何检测**：协调者是否只做协调，还是也承担了执行/记忆/决策。

**如何修复**：协调者只做协调（拆解、分派、汇总），执行交给 workers，状态外置。

**更好的设计**：清晰的协调-执行分离（[[05_Planner-Executor|Planner-Executor]]）；协调者轻量化。

**违反**：[[04_系统与控制定律#Law 33 — 瓶颈定律（Bottleneck Law）|瓶颈定律]]、[[04_系统与控制定律#Law 37 — 单点故障定律（Single-Point-of-Failure Law）|单点故障定律]]、[[05_接口与边界定律#Law 48 — 关注点分离定律（Separation-of-Concerns Law）|关注点分离定律]]。

### AP-27 层级过深（Excessive Hierarchy）

**错误模式**：用远超必要的层级（协调者的协调者的协调者…）组织 Agent。

**表面合理**：层级化能扩展、模仿大组织、分而治之。

**实际问题**：每层都交[[06_层级Hierarchical|信息损耗税]]，深层级导致传话失真、延迟累积、官僚化。

**产生原因**：过早引入层级、把层级当扩展的唯一手段、组织类比过度。

**典型症状**：一条指令要穿过多层才到执行者；根节点看到的是"摘要的摘要"；延迟高。

**失败案例**：一个三层 Agent 系统，根协调者基于严重失真的层层摘要做决策，与实际情况脱节。

**造成的影响**：[[06_层级Hierarchical|传话失真]]、延迟累积、官僚开销、决策脱离现实。

**如何检测**：层级深度；信息从叶到根的失真度。

**如何修复**：扁平化——先试单层协调，只在单层上下文确实爆了才加层；设越级直达通道。

**更好的设计**：最小层级 + 关键信息越级直达（[[06_层级Hierarchical|层级定律]]）。

**违反**：[[06_层级Hierarchical|信息损耗]]、[[11_演化与元定律#Law 99 — 简单性存活定律（Simplicity-Survives Law）|简单性存活定律]]、[[06_经济与资源定律#Law 57 — 规模效应定律（Scale-Effects Law）|规模效应定律]]。

### AP-28 涌现盲区（Emergence Blindness）

**错误模式**：假设多 Agent 系统的行为完全由各 Agent 的设计决定，不监控涌现行为。

**表面合理**：我设计了每个 Agent，所以我知道系统会怎么行为。

**实际问题**：复杂系统会[[11_演化与元定律#Law 101 — 涌现不可预测定律（Emergence-Is-Unpredictable Law）|涌现]]出无法从部件预测的行为，不监控就会被意外的集体行为反噬。

**产生原因**：还原论思维、低估涌现、只测设计的行为。

**典型症状**：系统出现没人设计的集体行为（成本失控、循环、集体盲区）却无人预见。

**失败案例**：一个多 Agent 系统涌现出"互相验证对方的幻觉"的集体行为，几个 Agent 一致地强化一个错误，无人监控到。

**造成的影响**：意外行为反噬、[[14_群体Swarm|涌现失控]]、难以预防。

**如何检测**：是否监控了没预期的整体行为，而非只测设计的行为。

**如何修复**：把涌现监控纳入评价；分布式 trace 观察整体动态；为负面涌现设护栏。

**更好的设计**：监控涌现 + 从中心化开始（更可控）（[[03_多Agent评价|涌现行为评价]]）。

**违反**：[[11_演化与元定律#Law 101 — 涌现不可预测定律（Emergence-Is-Unpredictable Law）|涌现不可预测定律]]；违反[[03_多Agent评价|涌现评价]]。

### AP-29 子任务不自包含（Non-Self-Contained Subtasks）

**错误模式**：协调者派给子 Agent 的任务描述依赖协调者的上下文，子 Agent 看不到。

**表面合理**：子 Agent 是系统的一部分，应该"知道"背景。

**实际问题**：子 Agent 有独立上下文，看不到协调者的背景，不自包含的任务导致它跑偏而协调者无感知。

**产生原因**：忘记子 Agent 的上下文隔离、假设它有全局视野。

**典型症状**：子 Agent 的输出偏离预期；它"误解"了任务；因为它缺少任务描述里省略的背景。

**失败案例**：协调者派任务"继续之前的分析"，但子 Agent 没有"之前"的上下文，只能瞎猜，产出跑偏。

**造成的影响**：子任务跑偏、协作失败、协调者无感知的错误。

**如何检测**：子任务描述能否被一个无上下文的 Agent 独立理解执行。

**如何修复**：任务描述自包含——包含子 Agent 需要的全部背景。

**更好的设计**：自包含任务描述（[[03_多Agent评价|角色分配]]、[[03_树状分解Tree|树状分解]]的核心纪律）。

**违反**：[[01_信息与压缩定律#Law 2 — 上下文即状态定律（Context-is-State Law）|上下文即状态定律]]；违反[[03_多Agent评价|通信]]原则。

### AP-30 主席篡改（Chair Tampering）

**错误模式**：多 Agent 系统的综合者/主席在汇总时悄悄改变了子结论，无人审查。

**表面合理**：主席负责综合，有权整合和调整。

**实际问题**：综合环节权力过大，可以（有意或无意地）篡改审议结果，而无人核查综合是否忠实。

**产生原因**：过度信任综合者、无综合审计、[[11_委员会Committee|主席权力过大]]。

**典型症状**：最终结论与子 Agent 的实际意见不符；综合"发明"了没人说过的东西。

**失败案例**：一个委员会系统的主席 Agent 在综合时忽略了关键的少数派意见，最终决议不忠实反映审议。

**造成的影响**：审议失真、少数派被抹杀、结论不可信。

**如何检测**：抽查综合结论是否忠实反映子 Agent 的意见。

**如何修复**：独立审计综合的忠实性；或主席轮换；保留原始意见可追溯。

**更好的设计**：综合审计 + 原始意见留痕（[[11_委员会Committee|委员会的改进方向]]）。

**违反**：[[04_系统与控制定律#Law 36 — 可观测性定律（Observability Law）|可观测性定律]]、[[07_认识论与真理定律#Law 68 — 后合理化定律（Post-Hoc-Rationalization Law）|后合理化定律]]。

### AP-31 全同步（Total Synchronization）

**错误模式**：所有 Agent 每一步都互相同步，等待彼此，无异步/并行。

**表面合理**：同步保证一致、大家步调一致更协调。

**实际问题**：全同步扼杀了并行收益（多 Agent 的核心价值之一），把并行退化成串行 + 同步开销。

**产生原因**：怕不一致、不会设计异步、过度协调。

**典型症状**：Agent 们大量时间在等待彼此；墙钟时间没有因并行而缩短；同步开销高。

**失败案例**：一个本可并行的多 Agent 调研系统，每个 Agent 每步都等其他 Agent，退化成串行，失去了多 Agent 的速度优势。

**造成的影响**：并行收益丧失、延迟高、同步开销。

**如何检测**：Agent 是否大量等待彼此；并行是否真的缩短了墙钟时间。

**如何修复**：只在真正需要的点同步，其余异步并行。

**更好的设计**：最小同步点 + 异步并行（多 Agent 的[[03_多Agent评价|真并行]]价值）。

**违反**：[[06_经济与资源定律#Law 57 — 规模效应定律（Scale-Effects Law）|规模效应定律]]（浪费并行红利）。

### AP-32 多 Agent 掩盖单体缺陷（Multi-Agent Masking）

**错误模式**：单 Agent 调不好，就拆成多 Agent，以为能解决问题。

**表面合理**：分工能让每个 Agent 更专注、把难题拆小。

**实际问题**：单 Agent 的根本缺陷（prompt 差、评测缺、逻辑错）不会因拆成多个而消失——现在你有多个有同样缺陷的 Agent 加通信问题。

**产生原因**：把多 Agent 当银弹、逃避解决根本问题、误以为拆分能提升能力。

**典型症状**：单 Agent 版本就有的问题在多 Agent 版本依然存在，还多了协调问题。

**失败案例**：一个 Agent 因为缺乏评测而不可靠，团队拆成五个 Agent，结果五个都不可靠，还多了协调地狱。

**造成的影响**：问题未解决 + 新增协调复杂度、双倍麻烦。

**如何检测**：拆多 Agent 前，单 Agent 版本的根本问题解决了吗。

**如何修复**：先把单 Agent 调好（prompt、评测、逻辑），再考虑是否真需要多 Agent。

**更好的设计**：先单体达标再编排（[[agent-bible/00_INDEX|Agent 圣经]]："先单体，后编排"）。

**违反**：[[11_演化与元定律#Law 99 — 简单性存活定律（Simplicity-Survives Law）|简单性存活定律]]；违反[[03_多Agent评价|何时多Agent]]判据。

## 类别二收束

十六个多 Agent 反模式，共同的根是**把"多"当成"好"，不做"多"的成本核算和价值证明**。解药是[[03_多Agent评价|对多 Agent 的有罪推定]]：它必须用单 Agent 基线对照证明净增值，否则默认降级。

诊断口诀：**这个系统的"多"，被它的收益证明了吗？砍掉一个 Agent 它会变差吗？** 答不上来，你大概率在维护一个本该是单 Agent 的系统。
