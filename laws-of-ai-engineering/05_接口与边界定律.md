# 家族五 接口与边界定律（Law 43–50）

> 根源：软件工程、复杂系统设计。这一族管的是"部件之间的边界"。在 AI 时代它们格外重要：人与 AI 之间的接口（提示规范、输出契约、审批点）比任何一次具体输出都更值得精心设计。

> 研究型 citation、来源强度与工程转译边界见 [[00_EXTERNAL-REFERENCES#05 接口与边界定律|本章外部依据说明]]。日常阅读可以忽略本块。

## Law 43 — 接口永存定律（Interface-Permanence Law）
> [!metadata] 定律元信息
> - `定律性质`: 工程强规律（稳定接口 / 实现替换）
> - `引用层级`: 家族级（接口设计锚点）
> - `引用范围`: 工具协议、数据格式、知识库入口、跨模块链接、外部服务边界、版本兼容。
> - `关系说明`: 与第 44 条、第 50 条成组：接口一旦被依赖就很难改，所以契约要显式，耦合要尽量松。


**定义**：实现可以随时重写，但接口一旦被依赖就近乎永久——设计时应把大部分精力花在边界长什么样上。

**为什么成立**：实现是私有的、可替换的；接口是公开契约，被众多依赖方绑定，改它要协调所有依赖方，成本随依赖数增长。

**理论依据**：软件工程（模块化/信息隐藏，工程强规律级）。

**为何被忽略**：实现是"看得见的工作"，接口设计是"看不见的深思"，容易草率。

**适用范围**：任何被复用/被依赖的组件。**不适用范围**：一次性、无外部依赖的内部实现。

**常见反例**：接口改了也没大事——依赖方少或还没被广泛依赖；依赖越多改动越痛。

**影响** — Prompt：prompt 的输入输出格式是接口，一旦下游依赖就难改。Multi-Agent：**Agent 间的通信协议是接口**，比单个 Agent 的实现更值得精心设计。Workflow：环节间的数据契约是接口。Memory：记忆的 schema 是接口，改它要迁移历史数据。Tool Use：工具的签名（参数/返回）是接口，[[03_知识与记忆模式|MCP]]标准化的正是接口。Eval：评测的输入输出格式是接口。

**100× 后**：仍成立且更关键。**人与 AI 之间的接口（提示规范、审批点、输出格式）比任何一次 AI 输出都更持久、更值得设计。**

**典型案例**：一个工具的返回 schema 被 10 个 Agent 依赖，改它要同时改 10 处；早期把 schema 设计好就避免了这个痛。**错误案例**：随意定义 Agent 间的消息格式，后来发现要改，牵一发动全身，被迫全系统重构。

**如何验证**：统计每个接口的依赖方数量；观察改实现 vs 改接口的成本差异。

## Law 44 — 契约显式化定律（Explicit-Contract Law）
> [!metadata] 定律元信息
> - `定律性质`: 工程强规律（契约式设计 / 可组合边界）
> - `引用层级`: 家族级（边界契约锚点）
> - `引用范围`: 输入输出规范、失败语义、工具调用、智能体交接、验收条件、跨文件引用规则。
> - `关系说明`: 与第 13 条、第 78 条成组：明确契约之后，任务才可委托，行为才可测试。


**定义**：组件间的契约（输入要求、输出保证、失败行为）越显式，系统越可靠、越可组合、越可测试。

**为什么成立**：隐式契约靠"心照不宣"，在边界处产生歧义和误解；显式契约可被检查、被测试、被机器强制。

**理论依据**：契约式设计（Design by Contract，工程强规律级）。

**为何被忽略**：显式化需要前期投入，隐式"能跑就行"更省事，直到边界处出 bug。

**适用范围**：所有组件边界。**不适用范围**：无边界的单体原子操作。

**常见反例**：隐式契约也没出错——双方恰好理解一致，或还没触发边界情况。

**影响** — Prompt：显式的输出格式契约（[[02_提示结构模式|schema]]）让输出可解析。Multi-Agent：Agent 的输入输出契约显式化，避免"它以为传了 X 实际传了 Y"。Workflow：每步的前置条件和后置保证要显式。Memory：记忆的读写契约（存什么格式、返回什么）。Tool Use：工具的 description + schema 就是显式契约。Eval：评测标准是显式契约。

**100× 后**：仍成立。显式契约是可靠组合的基础，与能力无关。

**典型案例**：给工具写清"失败时返回带目录列表的错误信息"的契约，Agent 能据此自愈。**错误案例**：工具的错误行为不显式（有时返回空、有时抛异常），Agent 无法可靠处理，静默失败。

**如何验证**：检查每个边界是否有显式的输入/输出/失败契约；隐式契约处是否更易出 bug。

## Law 45 — 抽象泄漏定律（Leaky-Abstraction Law）
> [!metadata] 定律元信息
> - `定律性质`: 工程强规律（抽象边界 / 底层泄漏）
> - `引用层级`: 场景级（抽象失效引用）
> - `引用范围`: 框架封装、模型接口、工具抽象、提示词模板、平台适配、异常排查。
> - `关系说明`: 与第 65 条互补：抽象是地图，不是疆域；常态下有用，异常时必须回到底层机制。


**定义**：所有非平凡的抽象都会在某些情况下泄漏底层细节——抽象简化了常态，但边界/异常时底层会渗透上来。

**为什么成立**：抽象通过隐藏细节简化使用，但无法完美隐藏所有情况；性能、错误、边界行为等底层现实会在极端情况下暴露。

**理论依据**：软件工程（Spolsky 的泄漏抽象定律，工程强规律级）。

**为何被忽略**：抽象平时工作良好，让人忘记它下面还有一层会漏的现实。

**适用范围**：所有抽象层（框架、工具、模型 API）。**不适用范围**：平凡的、无隐藏的直接操作。

**常见反例**：抽象从没漏过——只是还没遇到触发泄漏的边界情况。

**影响** — Prompt：把模型当"理解语言的抽象"，但它会在 token 化等底层泄漏（[[01_信息与压缩定律#Law 9 — 表征决定能力定律（Representation-Determines-Capability Law）|表征]]）。Multi-Agent：Agent 框架的抽象会在异常时泄漏底层。Workflow：编排框架的抽象在故障时暴露底层复杂性。Memory：记忆抽象在规模/一致性问题上泄漏。Tool Use：工具抽象在错误/超时时泄漏底层。Eval：评测抽象（分数）泄漏被测系统的具体行为。

**100× 后**：仍成立。抽象的泄漏性是根本的；更好的抽象泄漏更少，但不会不漏。

**典型案例**：把 LLM 当"智能助手"抽象使用，直到问它数字母时 token 化的底层泄漏出来。**错误案例**：完全信任 Agent 框架的抽象，从不理解底层循环，出问题时因为"抽象漏了"而完全无法调试。

**如何验证**：在边界/异常情况下使用抽象，观察底层细节是否泄漏、以什么形式。

## Law 46 — 边界即安全定律（Boundary-is-Security Law）
> [!metadata] 定律元信息
> - `定律性质`: 安全强规律（信任边界 / 攻击面）
> - `引用层级`: 家族级（安全边界锚点）
> - `引用范围`: 权限隔离、不可信输入、敏感数据、工具调用边界、检索内容边界、外发能力。
> - `关系说明`: 与第 87 条、第 92 条成组：输入会变成指令，数据也是攻击面，所以边界必须先被画清楚。


**定义**：安全性由边界定义——信任边界画在哪里、什么能跨越它，决定了系统的安全性；边界模糊则安全无从谈起。

**为什么成立**：安全的本质是控制"什么能影响什么"；清晰的信任边界让你能在跨越点施加检查，模糊的边界让攻击无阻穿透。

**理论依据**：安全工程（信任边界/攻击面，强规律级）。

**为何被忽略**：功能开发关注"让数据流动"，安全需要"限制数据流动"，二者张力下边界常被忽视。

**适用范围**：所有处理不可信输入/敏感操作的系统。**不适用范围**：完全封闭、无外部输入的系统。

**常见反例**：边界不清也没被攻破——只是还没被针对，不代表安全。

**影响** — Prompt：区分可信指令（system）和不可信内容（用户/检索）的边界。Multi-Agent：Agent 的权限边界决定爆炸半径。Workflow：不可信数据进入系统的边界要设检查点。Memory：什么能写入记忆是信任边界。Tool Use：工具能访问什么由权限边界定义（[[10_安全与生产部署|致命三重奏]]）。Eval：评测安全性就是测试边界能否被跨越。

**100× 后**：仍成立且更关键。模型越强、越自主，清晰的信任边界越是安全的唯一保障（[[10_对抗与安全定律#Law 94 — 权限胜过自觉定律（Permission-Over-Restraint Law）|权限胜过自觉]]）。

**典型案例**：把"能读邮件的 Agent"和"能发送的权限"用边界隔开，发送需人工确认，切断攻击链。**错误案例**：Agent 的信任边界模糊，检索到的网页内容被当作可信指令执行，遭 prompt injection。

**如何验证**：画出系统的信任边界，测试不可信内容能否跨越边界影响敏感操作。

## Law 47 — 最小权限定律（Least-Privilege Law）
> [!metadata] 定律元信息
> - `定律性质`: 安全强规律（最小权限 / 强制约束）
> - `引用层级`: 核心级（全库安全核心定律）
> - `引用范围`: 智能体权限、工具授权、文件读写、外部发送、生产操作、敏感数据访问。
> - `关系说明`: 与第 94 条成组：第 47 条规定权限最小化，第 94 条说明权限比提示约束更可靠。


**定义**：每个组件只应拥有完成其任务所需的最小权限——按任务给权限，不按能力给。

**为什么成立**：权限越大，被滥用/被劫持时的爆炸半径越大；最小权限限制了任何单点失效或攻击的破坏范围。

**理论依据**：安全工程（最小权限原则，强规律级）。

**为何被忽略**：给足权限"省事"（不用反复申请），限制权限需要精细设计。

**适用范围**：所有有权限的组件。**不适用范围**：无敏感操作的纯计算组件。

**常见反例**：给了过多权限也没出事——只是还没被滥用/劫持。

**影响** — Prompt：无直接影响。Multi-Agent：每个 Agent 按其子任务给最小工具集和数据访问。Workflow：每个环节只能访问它需要的资源。Memory：读写权限分离，按需授予。Tool Use：**工具权限按任务给**——查询 Agent 不给写权限，只读操作不给删除权。Eval：评测权限滥用场景。

**100× 后**：仍成立且更重要。Agent 越自主、能力越强，最小权限越是限制其失控破坏的关键。

**典型案例**：给数据分析 Agent 只读数据库权限，即使它被注入攻击也无法篡改数据。**错误案例**：图省事给 Agent 完整的读写删权限，一次 prompt injection 就删了生产数据。

**如何验证**：审查每个组件的权限是否超过其任务所需；模拟组件被劫持，测量爆炸半径。

## Law 48 — 关注点分离定律（Separation-of-Concerns Law）
> [!metadata] 定律元信息
> - `定律性质`: 工程原则（职责分离 / 可维护性）
> - `引用层级`: 场景级（模块拆分引用）
> - `引用范围`: 工作流分层、代码模块、知识库书目边界、智能体角色拆分、评测与执行分离。
> - `关系说明`: 与第 49 条、第 50 条互补：先分清职责，再让组件可组合，并通过松耦合减少连锁修改。


**定义**：把不同的关注点（职责）分离到不同的组件，每个组件只做一件事，能提升可理解性、可测试性、可维护性。

**为什么成立**：混合职责的组件耦合了多个变化原因，改一个会影响另一个；分离后每个组件可独立理解、测试、演化。

**理论依据**：软件工程（单一职责原则，工程强规律级）。

**为何被忽略**：把功能堆在一起"看起来"更快，分离需要设计克制。

**适用范围**：所有可分解的系统。**不适用范围**：本质不可分的原子功能。

**常见反例**：混合职责也能工作——短期能，长期维护困难。

**影响** — Prompt：一个 prompt 做一件事（[[02_提示结构模式|Prompt Chaining]]），别混合提取+分析+写作。Multi-Agent：每个 Agent 单一职责，靠上下文/工具区分而非头衔。Workflow：每个环节单一职责，可独立测试优化。Memory：不同类型记忆分离（事实/偏好/状态）。Tool Use：每个工具做一件明确的事。Eval：分离的组件可分别评测。

**100× 后**：仍成立。这是复杂度管理的永恒原则；更强的模型能处理更混合的职责，但分离仍利于维护。

**典型案例**：把生成和评审分成两个角色（[[04_质量控制模式|Critic-Refine]]），各自可独立优化。**错误案例**：一个巨型 prompt 同时做分类、抽取、总结、翻译，任何一项想改都牵动全部，且无法定位错误。

**如何验证**：检查每个组件是否只有一个变化原因；混合职责处是否更难维护。

## Law 49 — 组合性定律（Composability Law）
> [!metadata] 定律元信息
> - `定律性质`: 工程强规律（可组合性 / 复杂系统构造）
> - `引用层级`: 家族级（组件组合锚点）
> - `引用范围`: 工具链、工作流积木、智能体能力模块、知识库导航、可复用模板、评测组件。
> - `关系说明`: 与第 44 条、第 48 条成组：可组合依赖清晰契约和职责分离，否则组合会变成隐性耦合。


**定义**：设计良好的组件应能像积木一样组合成更大的系统——组合的能力决定系统能达到的复杂度上限。

**为什么成立**：可组合的组件通过清晰接口连接，组合的复杂度可控；不可组合的组件强行拼接会产生难以管理的耦合。

**理论依据**：软件工程/函数式编程（组合性，工程强规律级）。

**为何被忽略**：单独设计每个组件时不考虑组合，导致接口不兼容、难以拼装。

**适用范围**：需要构建复杂系统的场景。**不适用范围**：简单的单组件系统。

**常见反例**：不可组合的组件也拼出了系统——靠大量胶水代码，脆弱且难维护。

**影响** — Prompt：可组合的 prompt 片段（角色+任务+格式）能灵活拼装。Multi-Agent：**这本《[[multi-agent-patterns-handbook/00_INDEX|Multi-Agent 手册]]》的核心**——模式是可组合的积木（Planner+Reflection+Judge）。Workflow：可组合的环节能重排复用。Memory：可组合的记忆模块。Tool Use：可组合的工具（小而专）优于大而全。Eval：可组合的评测组件。

**100× 后**：仍成立。组合是构建复杂系统的根本手段，永恒。

**典型案例**：把 Planner-Executor、Reflection、Judge 三个模式组合成一个生产系统，每个可独立替换。**错误案例**：几个 Agent 各自设计得无法干净组合，靠一堆特判胶水勉强连接，加一个新 Agent 就崩。

**如何验证**：尝试把组件重新组合成不同系统，观察是否需要大量适配胶水。

## Law 50 — 松耦合定律（Loose-Coupling Law）
> [!metadata] 定律元信息
> - `定律性质`: 工程强规律（依赖管理 / 独立演化）
> - `引用层级`: 家族级（耦合治理锚点）
> - `引用范围`: 多组件系统、知识库跨链接、服务依赖、智能体协作、版本演化、局部替换。
> - `关系说明`: 与第 43 条成组：稳定接口让松耦合成为可能，松耦合让接口背后的实现可以独立演化。


**定义**：组件间的依赖越松（通过稳定接口而非内部细节），系统越能独立演化、局部修改、抵抗连锁故障。

**为什么成立**：紧耦合使一个组件的变化传导到依赖它的所有组件；松耦合通过接口隔离变化，把影响限制在局部。

**理论依据**：软件工程（耦合度，工程强规律级）。

**为何被忽略**：直接依赖内部细节"更方便"，松耦合需要通过抽象层，前期更费事。

**适用范围**：所有多组件系统。**不适用范围**：单组件系统。

**常见反例**：紧耦合系统也能改——只是改动成本高、风险大、连锁反应多。

**影响** — Prompt：prompt 不应硬依赖特定模型的怪癖（松耦合于模型）。Multi-Agent：Agent 通过稳定接口通信而非依赖彼此内部状态。Workflow：环节间松耦合，可独立替换。Memory：记忆访问通过抽象层，不依赖具体存储实现。Tool Use：Agent 依赖工具接口而非实现（[[03_知识与记忆模式|MCP]]）。Eval：评测松耦合于被测系统的实现。

**100× 后**：仍成立。松耦合是可演化系统的基础，与能力无关。

**典型案例**：Agent 通过 MCP 标准接口调用工具，换工具实现不影响 Agent。**错误案例**：一个 Agent 硬编码依赖另一个 Agent 的内部提示格式，后者一改前者就崩。

**如何验证**：修改一个组件的内部实现，观察有多少其他组件被迫跟着改（耦合度）。
