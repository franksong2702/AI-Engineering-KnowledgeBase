# 定律元信息字段说明

> 这页只回答一个问题：每条定律下面那块蓝色的 `定律元信息` 到底是什么意思，读者和 Agent 应该怎么读、怎么写、怎么检查。

相关入口：[[laws-of-ai-engineering/00_INDEX|Laws 总索引]] · [[00_CORE-LAWS|核心定律清单]] · [[00_REFERENCE-POLICY|引用策略]] · [[01_信息与压缩定律|试点文件：信息与压缩定律]]

## 一句话说明

`定律元信息` 不是用来重新解释正文的。正文已经有“定义”“为什么成立”“适用范围”“如何验证”等内容。

它的作用更简单：

> 告诉读者和 Agent：这条定律有多硬、应该在哪里引用、和其他定律是什么关系。

也就是说，它不是“这条定律是什么”，而是“这条定律在整套知识库里怎么用”。

## 标准写法

每条定律标题下面放一块 Obsidian 信息块：

```markdown
> [!metadata] 定律元信息
> - `定律性质`: 硬规律（信息论 / 有损压缩）
> - `引用层级`: 核心级（全库核心定律）
> - `引用范围`: 全库事实性输出、幻觉治理、知识外置与外部验证的根约束。
> - `关系说明`: 与第 6 条构成压缩边界组；第 1 条偏“模型参数中的事实重建与幻觉”，第 6 条偏“摘要、记忆、上下文状态压缩”。
```

读者看到的是一个蓝色信息块；Agent 看到的是一个稳定结构。

## 它和“定义”是什么关系？

正文里的 **定义** 回答：

> 这条定律说的是什么？

`定律元信息` 回答：

> 这条定律应该怎么被放进整套知识库？

举个例子：

- **定义**：说明“模型是有损压缩，所以事实输出不保证正确”。
- **定律元信息**：说明“这是一条核心级硬规律，全库讨论幻觉、事实核查、知识外置时都可以引用它”。

所以不要把定义搬进元信息里，也不要让元信息替代正文解释。

## 四个字段怎么理解？

### 1. `定律性质`

这个字段回答：

> 它凭什么算一条定律？它更像硬规律、工程原则，还是场景经验？

说人话就是：不要让 102 条看起来都一样硬。

常见写法：

- `硬规律（信息论 / 有损压缩）`
- `硬规律（统计学习 / 同分布泛化）`
- `工程强规律（有效注意力 / 位置鲁棒性）`
- `架构原则（知识存储与推理解耦）`
- `场景原则（检索相关性 / 记忆检索）`

不要这样写：

- `很重要` —— 太空。
- `必须遵守` —— 没说为什么。
- `核心定律` —— 这是引用层级，不是性质。

### 2. `引用层级`

这个字段回答：

> 这条定律应该被引用到多大的范围？

目前只用三档：

- **核心级（全库核心定律）**：可以出现在 README、总图、Constitution、Foundation、Evaluation、Agent Decision System 的来源说明里。
- **家族级（某个主题的锚点）**：主要在相关主题里引用，比如检索增强生成、上下文、记忆、长流程。
- **场景级（场景引用）**：只有遇到具体问题时才引用，不要放进全库入口。

判断方法很简单：

- 如果它能解释整套 AI 工程的底层约束，就是核心级。
- 如果它主要支撑某一类设计，就是家族级。
- 如果它只在某个具体坑里有用，就是场景级。

不要把“我觉得它写得好”当成核心级。核心级的标准是：全库多个模块都会反复需要它。

### 3. `引用范围`

这个字段回答：

> 哪些地方适合引用这条定律？读者看到它时，应该知道它管哪类问题。

这就是我之前写成“正典范围”的地方。那个词太学术，改成“引用范围”更直白。

好的写法应该像这样：

- `全库事实性输出、幻觉治理、知识外置与外部验证的根约束。`
- `摘要、状态压缩、中期记忆、智能体交接、上下文裁剪、长流程恢复。`
- `长上下文设计、文档排序、检索增强生成的重排、映射-归约分片、工具输出摘要与关键信息放置。`

它不是要写“所有适用范围”。正文里已经有“适用范围”。

它要写的是：

> 维护知识库时，哪些主题应该想到这条定律？

不要这样写：

- `所有 AI 场景` —— 太泛。
- `很多地方` —— 没用。
- `见上文` —— Agent 不好解析，读者也要多跳一步。

### 4. `关系说明`

这个字段回答：

> 这条定律和其他定律是什么关系？

常见关系有四种：

1. **边界重叠**：两条很像，但不要合并。  
   例：第 1 条和第 6 条都讲压缩，但第 1 条偏模型事实输出，第 6 条偏摘要和状态压缩。

2. **派生关系**：一条更底层，另一条更工程化。  
   例：信息守恒支撑“需要外部事实时必须真的去检索”。

3. **成组互补**：几条一起看才完整。  
   例：信噪比、有效注意力、语义相似不等于相关，可以构成长上下文 / 检索质量的一组约束。

4. **跨家族关联**：这条定律和另一个定律家族里的定律强相关。  
   例：熵反映不确定性，需要和校准一起看。

不要这样写：

- `相关` —— 太模糊。
- `很重要` —— 没有关系信息。
- `同上` —— Agent 不好处理。

## Agent 应该怎么识别？

Agent 不应该靠猜。识别规则如下：

1. 找到每个 `## Law N — ...` 标题。
2. 在这个标题下方寻找下面这个信息块：

```markdown
> [!metadata] 定律元信息
```

3. 在这个信息块里读取四个字段：

```markdown
> - `定律性质`:
> - `引用层级`:
> - `引用范围`:
> - `关系说明`:
```

4. 如果某个定律家族已经启用这套字段，那么每条定律都应该有这四个字段。
5. 如果字段缺失，Agent 应该报告“字段不完整”，不要自己悄悄猜。

## 写作规则

为了让人和 Agent 都能读懂，后续维护时遵守这些规则：

- 字段名必须保持中文，不要改成英文字段名。
- 每个字段尽量一行写完；如果必须换行，也要保持在同一个信息块里。
- `引用层级` 只用核心级、家族级、场景级三档。
- `引用范围` 写具体主题，不写空话。
- `关系说明` 要说清楚是重叠、派生、成组，还是跨家族关联。
- 不要把“试点”“第几批”“施工中”写进读者可见标题；这些信息放在计划或日志里。
