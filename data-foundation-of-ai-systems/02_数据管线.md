# Part 2 数据管线：可靠地持续产出好数据

> 数据质量（Part 1）不是一次清洗的结果，是一个持续过程的产出。这个过程就是数据管线。而数据管线本质上是一个系统——所以整个知识库关于系统的定律，在这里全部适用。

## 2.1 数据管线是一个系统，因此受系统定律约束

一个关键的视角转换：**数据管线不是"脚本的集合"，是一个由部件构成、随时间演化、被维护的系统。** 这意味着 [[laws-of-ai-engineering/00_INDEX|Laws]] 的系统与可靠性定律直接适用：

- **瓶颈定律**——管线的吞吐由最慢环节决定，优化非瓶颈是浪费。
- **显式失败**——某环节数据出错时要显式报警，不能[[laws-of-ai-engineering/00_INDEX|静默]]让脏数据流过（数据管线的静默失败最阴险——错误数据看起来和正确数据一样，直到污染了下游模型才被发现）。
- **可观测性**——管线的每一步都要可监控（数据量、质量指标、异常率），看不见就无法保证质量。
- **幂等性**——数据处理步骤应幂等，重跑不产生重复或不一致。
- **恢复优于预防**——管线会失败，需要检查点和可重跑，而非从头再来。

**把数据管线当系统工程对待，而非一次性脚本，是这一部分最重要的心法。**

### 反例与边界：什么时候不值得建"重"管线

管线工程自己也要过[[foundation-of-ai-engineering/00_INDEX|简单优先]]检验——这是本书对自己主张的有罪推定：

- **一次性实验**（探索性分析、原型验证、只跑一遍的数据准备）：一个带注释的脚本 + 一份输入输出快照就够了。为它建调度、监控、版本系统是过度工程（[[ai-engineering-anti-patterns/00_INDEX|Anti-Patterns]] 的镜像也适用于数据侧）。
- **数据量小且低频**（几百条、每月更新一次的配置类数据）：人工审核每一批可能比自动质检更可靠、更便宜。
- **升级的触发信号**：同一处理被第三次重复执行、数据开始被多个下游消费、出过一次"脏数据流入下游"事故——任何一条出现，就该从脚本升级为管线。**规则和代码一样：第三次重复时抽象**。
- 但有一条不随"轻重"豁免：**训练/评测数据的隔离纪律（Part 1 防泄漏）在一次性实验里同样成立**——泄漏不需要管线也能发生。

## 2.2 数据管线的典型阶段

```
采集 → 校验 → 清洗 → 转换 → 标注 → 质检 → 存储/版本 → 供给下游
 每一步都应: 可观测(记录质量指标) + 显式失败(脏数据报警) + 幂等(可重跑)
```

**采集（Ingestion）**——从源头获取数据。关键是记录来源和采集条件（[[laws-of-ai-engineering/07_认识论与真理定律#Law 60 — 证据分级定律（Evidence-Hierarchy Law）|证据分级]]——一手数据优于二手转述）。

**校验（Validation）**——入口质量关卡。schema 校验、范围检查、格式检查。**这是防止脏数据入库的第一道闸**，应该显式拒绝不合格数据而非静默接受。

**清洗（Cleaning）**——去重、修正、处理缺失和异常。这是提纯的主战场（质量>数量）。

**转换（Transformation）**——格式统一、特征工程、标准化。

**质检（Quality Check）**——出口质量关卡，度量本批数据的质量指标，不达标则拦截。

**存储与版本（Storage & Versioning）**——见 2.4。

### 每个阶段的验收标准（工程手册）

| 阶段 | 做对了的判据 |
|------|------------|
| 采集 | 每条数据能回答"从哪来、什么时候、什么条件下采的"；断源时报警而非产出空批次 |
| 校验 | 存在一份**显式的数据契约**（字段、类型、取值范围、允许缺失率），违约数据被拒收并计数——拒收率本身是被监控的指标（突然升高 = 上游变了） |
| 清洗 | 每条清洗规则有注释说明"为什么"；被清洗掉的数据进**隔离区（quarantine）**而非直接删除——隔离区是排查误杀和统计洗损的依据 |
| 转换 | 同一输入重跑输出逐字节一致（幂等验证是回归测试的一部分） |
| 质检 | 出口指标与 Part 1 六维对应；不达标批次被拦截的同时保留样本供人工裁决 |
| 存储/版本 | 任一版本可在有限时间内完整重建或回滚；版本号进入下游模型的元数据（模型能反查"我是用哪版数据训的"） |

三个值得点名的工程模式：**隔离区**（校验/清洗失败的数据单独存放并每周人工抽检——它是"上游在发生什么变化"的最灵敏传感器）；**金丝雀批次**（管线代码变更后，先跑一小批新旧对比 diff，确认变更影响符合预期再全量）；**增量处理的补数（backfill）设计**（增量管线必须预先设计"如何安全重算历史区间"，等出了事再想，就会在生产库上手搓出不幂等的一次性脚本——事故的经典温床）。

## 2.3 可复现性：数据管线的核心要求

一个常被忽略但致命的要求：**数据管线必须可复现**——同样的输入，同样的处理，得到同样的输出。

为什么关键：不可复现的数据管线意味着你无法调试问题（"上次那批数据怎么来的？"）、无法回溯错误、无法在数据出问题时定位是哪一步。这直接对应 [[laws-of-ai-engineering/04_系统与控制定律#Law 36 — 可观测性定律（Observability Law）|可观测性定律]]——看不见、追溯不了的系统无法被信任。

可复现的要件：确定性的处理步骤、记录所有转换、固定随机种子、版本化的代码和配置。**一个不可复现的数据管线，是一个你无法真正信任其产出的管线。**

**可复现性的新边界——管线里的 LLM 环节**：当清洗/标注/抽取环节使用 LLM 时，严格的逐字节复现不再可得（模型版本会下线、采样有随机性）。此时可复现性退而求其次但不可放弃：固定模型版本与参数并记录在版本元数据里、缓存全部模型输出（同输入不重调）、对无法复现的环节保留输入和输出的完整快照。**用了 LLM 不是放弃可复现的理由，只是把"重算可复现"降级为"快照可追溯"。**

## 2.4 数据版本化：被低估的基础设施

代码有版本管理，数据也必须有。**数据版本化**记录：这批数据是什么时候、用什么代码、从什么源、经过什么处理得到的。

为什么必需：当模型表现变化时，你需要知道是数据变了还是代码变了（数据管线的调试）；当发现数据问题时，你需要能回滚到干净版本；当复现实验时，你需要精确的数据快照。没有数据版本，模型的表现变化就是无法归因的黑箱（[[laws-of-ai-engineering/04_系统与控制定律#Law 36 — 可观测性定律（Observability Law）|可观测性]]）。

数据版本化也是[[laws-of-ai-engineering/08_可靠性与失败定律#Law 77 — 恢复优于预防定律（Recovery-Over-Prevention Law）|恢复优于预防]]在数据领域的体现——出问题时能回滚，比祈祷不出问题可靠。

**版本化的最小可行实现**（不需要专用平台就能做到）：每批产出附一个清单文件（manifest），内容至少包含——源数据的标识与哈希、处理代码的版本号、配置快照、产出的行数与质量指标、生成时间。清单本身入代码库。有了它，"哪个数据、哪次处理、什么表现"三问就能回答；专用的数据版本平台只是把这件事做得更顺手，而非做不做的分界。

## 2.5 数据管线的反模式（对照 Anti-Patterns）

- **静默通过脏数据**——校验失败却不拦截，脏数据静默流入下游（对应[[laws-of-ai-engineering/08_可靠性与失败定律#Law 76 — 静默降级危险定律（Silent-Degradation-Danger Law）|静默降级]]反模式）。
- **不可复现管线**——手工的、一次性的、无记录的处理，出问题无法追溯。
- **无质量监控**——管线跑着但没人知道产出的数据质量如何（[[laws-of-ai-engineering/04_系统与控制定律#Law 36 — 可观测性定律（Observability Law）|无可观测性]]）。
- **优化非瓶颈**——花力气优化不是瓶颈的环节（[[laws-of-ai-engineering/04_系统与控制定律#Law 33 — 瓶颈定律（Bottleneck Law）|瓶颈误优化]]）。
- **无数据版本**——数据说变就变，无法回滚无法归因。
- **在生产数据上手搓补数脚本**——增量管线没有预设的 backfill 机制，出事后临时写不幂等的脚本直接改历史数据（见 2.2）。

## 2.6 验收清单：怎么判断你的管线做对了

- ☐ 存在显式数据契约吗？违约数据被拒收且拒收率被监控吗？
- ☐ 注入一条坏数据，它会在哪一关被拦下？拦下后有人能看到吗？（对应 [[The-Constitution-of-AI-Engineering|宪法]]"注入一个错误你能快速定位"的数据版）
- ☐ 被清洗掉的数据在隔离区里吗？最近一次抽检隔离区是什么时候？
- ☐ 任选一批历史产出，能在有限时间内说出它的源、代码版本、配置吗（manifest 三问）？
- ☐ 管线代码变更走金丝雀批次对比了吗？
- ☐ 含 LLM 的环节固定了模型版本并缓存了输出吗？
- ☐ 增量管线的 backfill 程序预先存在并测试过吗？
- ☐ 这条管线的复杂度被它的使用频率和下游数量证明了吗（简单优先的反向检验）？

## Part 2 收束

数据管线是一个系统，受所有系统定律约束——可观测、显式失败、幂等、可恢复、可复现、可版本化。把它当系统工程而非一次性脚本，是持续产出好数据的关键；但管线工程自身也要过简单优先检验——一次性实验配脚本，被复用的处理才配管线。

**一个记忆点**：数据管线最危险的失败是"静默通过脏数据"——因为脏数据看起来和好数据一样，它会一路流到污染模型才暴露。所以数据管线的质量关卡必须显式拦截，而非静默放行。
