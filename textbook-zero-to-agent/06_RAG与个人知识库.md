# 第 6 章 RAG 与个人知识库

> RAG（检索增强生成）解决 LLM 的两大硬伤：知识过时、私有数据不可知。核心思想一句话：**与其让模型"记住"一切，不如在回答前把相关材料找出来塞给它。** 检索质量决定一切——RAG 系统的上限在检索，不在生成。

## 学习目标

- 独立构建端到端 RAG 系统：切分 → 向量化 → 检索 → 生成
- 能诊断 RAG 质量问题出在哪一环（检索没找到 vs 找到了没用好）
- 理解各环节的关键权衡（chunk 大小、top-k、混合检索）并能实验验证

## 知识点

1. **RAG 流水线**：文档加载 → 切分（chunking）→ embedding → 存入向量库 → 查询时检索 top-k → 拼入 prompt → 生成带引用的回答。
2. **Chunking 是最被低估的环节**：块太小丢上下文，太大稀释相关性。经验起点：300-800 token、10-20% 重叠、优先按语义边界（标题/段落）切而不是按字数硬切。
3. **Embedding 检索的本质与局限**：语义相似 ≠ 相关。"苹果发布会"和"苹果的营养价值"向量很近。所以需要——
4. **混合检索**：向量（语义）+ BM25 关键词（精确匹配）互补，专有名词、代码、型号靠关键词救。再加 **rerank**（用更强的模型对 top-50 重排出 top-5）通常是性价比最高的质量提升。
5. **上下文增强**：给每个 chunk 附上它所在文档的标题/摘要（contextual retrieval），大幅降低"孤儿块"问题。
6. **引用与拒答**：要求答案标注来源块；检索结果相关性低时应该说"资料里没有"而不是编。**RAG 不消除幻觉,只是把幻觉从"编造事实"降级为"错误综合"**，引用让错误可审计。
7. **评测三问**：检索命中率（该找到的找到没）、忠实度（答案是否忠于材料）、答案质量。分开测,才知道修哪里。
8. **什么时候不用 RAG**：文档总量小于上下文窗口的一半 → 直接全塞（长上下文吃掉了一批简单 RAG 场景）；需要全局统计/汇总的问题 → RAG 结构性不擅长（它只见树木）。边界的另一面：长上下文吃掉的只是"因为装不下而做的 RAG"；因为**该外置**而做的（知识海量、需实时更新、需引用溯源）不受影响，不会随窗口变大而过时。

## 练习

1. 手工体验向量相似度：用 embedding API 计算 10 对句子的余弦相似度，找出 2 个"语义近但不相关"的反例。
2. 同一份文档用 200/500/1500 token 三种 chunk 大小建库，用同 5 个问题测试，观察差异。
3. 构造关键词检索必胜的案例（问一个具体型号/人名），对比纯向量检索的失败。
4. 忠实度测试：故意问一个资料里没有的问题，调整 prompt 直到系统稳定拒答而不是编造。

## 项目

**个人知识库问答系统**：以你自己的笔记/收藏文章（50+ 篇）为语料，构建可以问答的 RAG 系统，回答必须带来源引用。技术栈自选（LlamaIndex/LangChain/或裸写——推荐至少裸写一次检索部分）。验收：自建 20 个问题的测试集（含 5 个"资料里没有答案"的问题），检索命中率 ≥ 80%，无答案问题的拒答率 100%。附一页报告：你调整过什么，各带来多少提升。

## 阅读资料

- Anthropic《Contextual Retrieval》博客（2024）——工业界最清晰的 RAG 优化实录
- LlamaIndex 文档的概念部分（不急着用框架，先读概念）
- Pinecone Learning Center 的向量检索系列——embedding/索引原理的友好讲解
- 《Lost in the Middle》（Liu et al., 2023）——长上下文位置偏差的实证，解释为什么检索后的排序也重要

## 容易犯的错误

- **上来就堆高级技术**：还没测过基线就上 rerank、query 改写、图谱。正确顺序：最朴素版本 → 建测试集 → 测出瓶颈 → 针对性优化。
- **只调生成不查检索**：答案不好就改 prompt,而 80% 的问题是检索没找对材料。先看检索日志！
- **用演示代替评测**：跑了 3 个顺手的问题就宣布能用。没有测试集的 RAG 是薛定谔系统。
- **忽略文档预处理**：PDF 解析出的乱码表格直接入库。垃圾进垃圾出在 RAG 里被检索放大。
- **该全塞的做检索**：30 页的手册做 RAG 是自找麻烦，直接放进上下文。

## 推荐 Prompt

（RAG 生成端的骨架 prompt）

```
基于且仅基于以下资料回答问题。
规则：
- 每个论断后标注来源编号，如 [2]
- 资料不足以回答时，明确说"提供的资料中没有相关信息"，并说明缺什么
- 资料之间矛盾时，指出矛盾而不是选边
资料：{检索结果}
问题：{用户问题}
```

## 推荐 Agent

- **Claude Code / Cursor**：搭建项目主力。让它写流水线，你负责设计测试集——测试集是无法外包的部分，因为只有你知道你的语料该答出什么
- **NotebookLM / Claude Projects**：作为"商业 RAG 基准"——把同一批文档传上去，用你的 20 个测试题打分，和你自建系统对比。打不过商业产品不丢人，知道差距在哪一环才是本章的目标
## 自测题

1. **Chunking 的两难是什么？经验起点参数是什么？**
   要点：块太小丢上下文、太大稀释相关性；300-800 token、10-20% 重叠、按语义边界切而非字数硬切。
2. **"语义相似 ≠ 相关"——举一个例子，并说出对应的工程解法。**
   要点：如"苹果发布会"与"苹果的营养价值"向量很近；解法是混合检索（向量+BM25 关键词）+ rerank。
3. **"RAG 不消除幻觉，只是把幻觉降级"——降到什么级别？引用的作用是什么？**
   要点：从"编造事实"降为"错误综合"；引用让错误可审计可追查，配合"检索不足时拒答"。
4. **评测三问是什么？为什么必须分开测？**
   要点：检索命中率/忠实度/答案质量；混在一起测不知道该修检索还是修生成——分开才能定位瓶颈。
5. **长上下文会让 RAG 过时吗？说出边界的两面。**
   要点：吃掉的是"因为装不下而做的 RAG"（小文档集直接全塞）；吃不掉"该外置"的（海量/实时/需溯源）——那部分不随窗口变大而过时。
