# 第六章 权限系统设计：AI 能做什么由权限定，不由自觉定

> 权限系统是人机协作的硬骨架——它决定 AI 被授予了什么能力、边界在哪、谁能扩权。因为模型可以被说服、越狱、注入，权限是比提示更可靠的行为约束（[[laws-of-ai-engineering/10_对抗与安全定律#Law 94 — 权限胜过自觉定律（Permission-Over-Restraint Law）|权限胜过自觉]]）。设计好权限，是让"被骗的 AI 也干不了坏事"的关键。

## 底层原则

**原则一：约束行为靠权限，不靠自觉。** 提示层的"禁止"（"不要删数据"）可被绕过，权限层的约束（没有删除权限）是硬的——无论 AI 被如何诱导都无法逾越（[[laws-of-ai-engineering/00_INDEX|Laws]]）。这是权限系统存在的第一理由：它把"AI 可能被骗"降级为"被骗也无法造成实际破坏"。

**原则二：最小权限——按任务给，不按能力给。** 每个 AI/Agent 只应拥有完成其当前任务所需的最小权限。权限越大，被滥用/劫持/出错时的爆炸半径越大（[[laws-of-ai-engineering/05_接口与边界定律#Law 47 — 最小权限定律（Least-Privilege Law）|最小权限]]）。查询任务不给写权限，只读操作不给删除权。

**原则三：权限分级对应后果与恢复能力。** 读、生成草稿等低影响且易恢复的操作可低门槛授予；发送、删除、支付、发布等动作要继续按受众、金额、范围、恢复路径和证据条件分级，使用参数限额、灰度、自动验证、回滚或人工审批（[[laws-of-ai-engineering/08_可靠性与失败定律#Law 74 — 不可逆性定律（Irreversibility Law）|风险与恢复分诊]]）。

**原则四：权限要随可靠性动态调整,且可快速收回。** 新 AI/新任务从窄权限开始,随可靠性数据积累逐步放开(渐进授权);一旦出现问题,权限应能被快速收回。权限不是一次性授予的静态配置,是随信任动态调整的。

**原则五:审查致命三重奏。** 特别警惕同时具备"访问私有数据 + 接触不可信内容 + 对外发送"三者的权限组合——它是数据泄露的定时炸弹,权限设计必须砍掉一角([[laws-of-ai-engineering/10_对抗与安全定律#Law 88 — 致命三重奏定律（Lethal-Trifecta Law）|致命三重奏]])。

## 设计模式

**模式 1 · 能力分级权限（Capability Tiers）**：把操作按风险/可逆性分级（只读 / 可逆写 / 不可逆 / 高危），不同级别对应不同的授予门槛和审批要求。

**模式 2 · 即时最小授权（Just-in-Time Least Privilege）**：不预先授予全部权限，而是任务需要时临时授予、用完收回，缩小任何时刻的权限暴露面。

**模式 3 · 渐进授权（Progressive Authorization）**：新 AI 从最小权限开始，随可靠性证明逐步放开——权限跟随信任增长（呼应第三章）。

**模式 4 · 三重奏隔离**：审查每个 Agent 的权限组合，对集齐致命三重奏的强制砍一角（如能读私有数据+接触不可信内容的 Agent，发送权改人工确认）。

**模式 5 · 权限审计日志**：AI 的每次权限使用可追溯（谁、何时、用了什么权限、做了什么），支持事后审查和责任归属（衔接第七章）。

## 工程手册：LLM Agent 的权限落在哪一层

对 LLM Agent，"权限"不是抽象概念，它有三个具体的实现层，缺一不可：

1. **工具集即权限面**。Agent 能做什么 = 它被注册了哪些工具。最小权限的第一实现就是**按任务裁剪工具集**——查询型任务的 Agent 根本不注册写入工具，而不是注册了再靠 prompt 说"别用"。不存在的工具无法被注入调用，这是最硬的一层。
2. **工具内参数约束**。同一个工具，用参数约束收窄能力：文件工具限定可访问目录、查询工具限定库表和行数上限、发送工具限定收件人白名单。约束在工具的**实现代码**里强制执行，不依赖模型传参的自觉。
3. **数据范围（凭证层）**。Agent 持有的凭证决定它以谁的身份、能看到哪些数据。**Agent 应持有专用的降权凭证，而非复用人类操作员的完整凭证**——复用人类凭证是"权限过大"最常见的形态，因为它最省事。

**分级表的一个可抄起点**（按需增改）：

| 级别 | 操作类型 | 授予方式 | 审批 |
|------|---------|---------|------|
| T0 只读 | 查询、检索、读文件 | 默认授予（仍限数据范围） | 无 |
| T1 可逆写 | 写草稿、暂存、开分支、标记 | 按任务授予 | 无（事后可审计） |
| T2 不可逆 | 发送、删除、支付、发布、改生产 | 显式申请 | **逐次人工确认** |
| T3 高危 | 改权限本身、动凭证、批量不可逆 | 原则上不授予 AI | 不适用（人做） |

**审批点的密度设计**：T2 审批要少而实——把审批集中在真正不可逆的动作上。如果一天弹五十次审批，人必然退化成盖章者（[[05_避免盖章者陷阱|第五章]]），此时权限系统形同虚设。**审批频率本身是一个要监控的指标：太高说明分级错了（把可逆的划进了 T2），该修表而不是催人快点批。**

**收回要演练**。"权限可快速收回"是一个要验证的能力而非声明：做一次演练——发现 Agent 异常，多久能把它降到 T0？路径是什么、谁有权执行、会不会误伤同凭证的其他服务？没演练过的收回机制，事故时大概率不可用（[[laws-of-ai-engineering/08_可靠性与失败定律#Law 77 — 恢复优于预防定律（Recovery-Over-Prevention Law）|恢复优于预防]]的权限版）。

## 反例与边界

- **最小权限不是越细越好**。权限粒度细到任务每一步都要重新授权，摩擦会逼出两种坏结果：人为省事直接给大权限（回到原点），或审批高频化沦为盖章（第五章）。**粒度的正确刻度是"风险边界"而非"操作边界"**——同一风险级别内的操作可以打包授予。
- **低风险内部工具可以粗粒度起步**。一个只读内部文档、不对外发送的辅助 Agent，T0 打包授予即可，不必上完整的分级机器。权限系统自身的复杂度也要被风险证明（[[foundation-of-ai-engineering/00_INDEX|简单优先]]）——但"以后再加权限"的债要显式记录，因为工具集会悄悄长大，长到某天集齐三重奏。
- **权限不能替代评价**。权限兜住的是"坏行为的爆炸半径"，不是"输出的质量"——一个 T0 只读 Agent 照样可以一本正经地答错。权限与评价（[[evaluation-of-ai-systems/00_INDEX|Evaluation]]）是两道互不替代的防线。

## 失败模式

- **权限过大**：图省事给 AI 超出任务所需的权限，扩大爆炸半径（[[ai-engineering-case-library/07_成本与性能|Case 68]]）。
- **靠提示不靠权限**：只在 system prompt 写"别做危险操作"却给了完整权限，越狱即破（[[ai-engineering-case-library/06_安全与对抗|Case 18/53]]）。
- **致命三重奏**：AI 集齐读私有数据+接触不可信内容+对外发送，被注入窃取数据（[[ai-engineering-case-library/06_安全与对抗|Case 51/55]]）。
- **静态权限**：权限一次授予不随可靠性/风险调整，也无法快速收回。
- **权限无审计**:AI 用了什么权限做了什么无法追溯,责任无法归属。
- **复用人类凭证**：Agent 直接拿操作员的完整凭证跑，数据范围完全失控（工程手册第 3 层的缺失形态）。

## 评价方法

- 审计每个 AI/Agent 的权限是否超过其任务所需（最小权限检查）。
- 模拟劫持/越狱/注入，测量爆炸半径：被攻破后 AI 能造成多大破坏？权限层是否兜住？
- 审查权限组合是否集齐致命三重奏。
- 检查不可逆/高危操作是否都有权限门槛+人工审批。
- 检查权限是否可快速收回、每次使用是否可追溯。

## 验收清单

- ☐ 每个 Agent 的工具集是按任务裁剪的，还是"全家桶"？
- ☐ 工具内参数约束（目录/表/白名单）是在工具代码里强制的，还是靠 prompt？
- ☐ Agent 用的是专用降权凭证还是人类凭证？
- ☐ 有分级表吗？T2 的审批频率被监控吗（防盖章化）？
- ☐ 三重奏审查跑过每一个 Agent 吗？砍角的记录在哪？
- ☐ 权限收回演练做过吗？降到 T0 需要多久？
- ☐ 审计日志能回答"这个 Agent 上周用什么权限做了什么"吗？

## 收束

权限系统是人机协作的硬骨架。核心：**靠权限不靠自觉；最小权限按任务给（落在工具集/参数约束/凭证三层）；权限分级对应可逆性；随可靠性动态调整、可快速收回（且演练过）；砍掉致命三重奏。** 粒度以风险边界为刻度，审批少而实，防止权限系统自己制造盖章者。

最该记住的一句：**AI 可以被说服、越狱、注入，但被说服后也干不了它没权限的事——权限是让"被骗的 AI 也造不成实际破坏"的关键防线。** 提示的"禁止"是缓解，权限才是防御。这也是责任边界（第七章）能够成立的技术基础。
