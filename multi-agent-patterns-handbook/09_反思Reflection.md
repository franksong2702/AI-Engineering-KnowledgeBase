# 模式 09 反思 Reflection（生成-批评-修订）

## 为什么存在

一次生成的输出是"初稿质量"——模型逐 token 输出，没有全局回看。而**评价比生成容易**（识别文章的逻辑漏洞比写出无漏洞的文章容易），Reflection 利用这个不对称性：让一个批评者角色审视产出，把批评意见反馈给生成者修订，循环直到达标。这是人类"写完再改三遍"的架构化。

## 适合解决什么问题

有明确质量标准、且质量值得多倍成本的产出：代码（最佳场景——测试提供客观反馈）、重要文书（合同、报告、对外文案）、数学推导、翻译精修。**关键判据：批评者能获得真实信号**——能跑的测试、能核的事实、明确的 rubric。没有客观锚点的反思会退化成文字打磨。

## Agent 如何协作

两个角色（可以是同一模型的两个 prompt，更强的做法是批评者接工具）：**Generator** 产出 → **Critic** 按 checklist 批评（最好附带证据：测试结果、检索核对）→ Generator 收到批评修订 → 再审 → 循环。角色分离的意义：生成时的思维定势会遮蔽自己的错误，换一个"人格"（新上下文 + 批评者立场）能看见。

## 信息如何传递

产出物 + 结构化批评单（问题列表：位置、严重度、修改建议——不是一段散文感想）。修订时 Generator 收到：原稿 + 批评单 + "逐条回应"要求。**批评必须可执行**："第 3 段论据不支持论点，因为引用数据是 2019 年的"可执行；"整体不够有说服力"不可执行。

## 什么时候结束

四选一，必须显式：Critic 通过（所有 blocker 级问题清零）；达到最大轮数（通常 2-3 轮，收益递减极快）；两轮批评意见重复（震荡信号，强行终止）；预算耗尽。**第 1 轮修订收益最大，第 3 轮之后基本是布朗运动**——这是实践中最稳定的经验规律。

## 优点

- 单 Agent 系统提升质量最简单有效的手段，实现成本低
- 有客观反馈（测试/执行）时，提升真实且可观（代码场景 pass 率显著上升）
- 批评单留痕，质量过程可审计
- 天然适合作为其他模式的嵌入组件（Executor 内嵌、Pipeline 段内嵌）

## 缺点

- **自我表扬问题**：同一模型自评时系统性偏宽容，"我觉得我写得挺好"
- 无锚点反思 = 越改越花哨不改本质，甚至改坏（把对的改错）
- 成本 2-4 倍，且是串行循环，延迟同倍数增长
- 批评者的 rubric 就是天花板：rubric 没写的维度永远不会被检查

## Prompt 示例

（Critic——注意"必须找出问题"的校准设计）

```
你是严格的代码评审员，与作者无利害关系。审查以下代码：
按 checklist 逐项检查：正确性(边界/空值/并发) → 安全(注入/越权) → 性能 → 可读性
输出问题列表，每项：
{"severity": "blocker|major|minor", "location": "行号", 
 "issue": "具体问题", "evidence": "触发它的输入示例或测试结果", "fix_hint": "方向"}
规则：
- 附上运行测试的结果，你的 blocker 判断必须有 evidence
- 找不到 blocker 时明确说"未发现阻断问题"，不要为了显得严格而虚报
- 不评论纯风格偏好
```

## Workflow 示例

```
任务：实现一个日期解析函数
[Generator] v1 → [跑测试] 3/10 失败
[Critic] 批评单：blocker×2（时区未处理、闰年边界）major×1
[Generator] v2（逐条回应修订）→ [跑测试] 10/10 通过
[Critic] blocker 清零，minor×2（变量命名）
终止判断：blocker=0 且轮数=2 → 交付（minor 附注不再循环）
成本核算：3.2× 单次生成；测试通过率 30%→100%
```

## 未来还能如何改进

- **批评者工具化**：给 Critic 接执行器、检索、静态分析——把"感想式批评"升级为"证据式批评"，这是当前最大的质量杠杆
- **跨模型批评**：用不同基座模型做 Critic，打破同源盲区（自我表扬问题的最有效缓解）
- **批评记忆**：把历史批评单沉淀为该任务域的 checklist，Generator 的 v1 质量逐步上移，循环次数自然下降
- **收敛检测自动化**：框架层 diff 相邻两版，变化率低于阈值自动终止，省掉无效轮次
