# 模式 02 MapReduce

> **定义归属说明**：本章是 Map-Reduce（多体协调视角）的权威定义；推断视角的精要版见 [[llm-design-patterns/05_编排模式|Design Patterns 家族五]]。

## 为什么存在

三个理由：**并行**缩短墙钟时间；**上下文隔离**——注意力随上下文变长而稀释，塞得下也未必答得好；**单片可复现**，便于抽查和重跑。"上下文窗口装不下全部数据"曾是首要理由，但随着窗口变大正在减弱，前三条不受影响。MapReduce 借用大数据的经典范式：**把数据切片，同一个任务并行作用于每片（Map），再把分片结果聚合（Reduce）**。用多个干净的小上下文替代一个臃肿的大上下文。

## 适合解决什么问题

数据量大且**分片间弱耦合**的同构任务：千条评论的情感与主题分析、百份简历初筛、长书逐章摘要、代码库逐文件扫描、批量翻译。判据：单片的处理不需要看到其他片也基本正确。

## Agent 如何协作

无中心协商。Mapper 们互不知晓、完全并行、执行相同指令；Reducer 单独一层，只见 Mapper 的输出不见原始数据。可选：Splitter Agent 负责智能切片（按语义边界而非字数）。

## 信息如何传递

原始数据 → 切片 → 各 Mapper 独立处理 → 结构化片结果（必须 schema 统一，Reducer 靠它对齐）→ Reducer 聚合。**片结果要自带定位信息**（第几片、原文位置），否则聚合后无法溯源。

## 什么时候结束

所有 Mapper 完成（或超时的片被标记缺失）→ Reduce 完成 → 结束。天然有界，无失控风险。部分失败策略需预先定义：缺片继续（标注覆盖率）还是重跑。

## 优点

- 墙钟时间大幅缩短（并行度 = 片数）
- 每片上下文干净，单片质量高于"整书塞进去"
- 天然可扩展：数据翻十倍，架构不变
- Mapper 可用便宜小模型，成本可控

## 缺点

- **跨片信息丢失**：伏笔在第 3 章、揭晓在第 20 章的关联，任何单片都看不到
- Reduce 是瓶颈和信息损失点：几百个片结果本身就可能超窗口
- 全局统计类问题（"最常见的主题是什么"）依赖 Reduce 的质量，而 Reduce 只见摘要不见原文
- 同构假设不成立时（片间强依赖）质量崩塌

## Prompt 示例

（Mapper——注意"不知道全局"是设计而非缺陷）

```
你将看到一份长文档的第 {i}/{n} 片。独立完成分析，不要假设其他片的内容。
任务：提取本片中的 (a) 关键论点 (b) 出现的实体 (c) 未解决的悬念/前向引用。
输出 JSON：{"chunk_id": {i}, "claims": [...], "entities": [...], "open_refs": [...]}
规则：open_refs 用于跨片拼接，凡是"指向本片之外"的内容都记录在此，宁多勿漏。
```

## Workflow 示例

```
300 页报告
  → [Splitter] 按章节切 30 片
  → [Mapper × 30 并行] 各片抽取论点/实体/悬念 → 30 份 JSON
  → [Shuffle] 按实体分组对齐（代码完成，不用 LLM）
  → [Reducer] 合并同类项、解决 open_refs 配对、产出全局摘要 + 溯源表
覆盖率报告：30/30 片成功；跨片引用配对成功 17/21
```

## 未来还能如何改进

- **层级 Reduce**：片结果先按 10 个一组预聚合，再终聚合——解决 Reduce 超窗口
- **重叠切片**：相邻片重叠 10-15%，缓解边界信息切断
- **两遍 Map**：第一遍抽全局骨架（实体表、章节图），第二遍带着骨架重新 Map——用少量全局上下文修复跨片盲区
- **动态片粒度**：信息密度高的部分切细，样板内容切粗（由轻量模型预扫决定）
