# 模式 04 递归 Recursive

## 为什么存在

有一类任务是**自相似**的：把它变小一号，解法完全相同——总结 100 篇摘要的任务和总结 100 篇文章的任务是同一个任务；整理一个目录树和整理它的子目录是同一个任务。为这类任务设计多种 Agent 是浪费，**一个 Agent 反复调用自身（换更小的输入）** 是最简洁的表达。递归是树状分解的特例：分解者和求解者是同一个 Agent。

## 适合解决什么问题

自相似结构任务：目录树处理、嵌套数据清洗（JSON 套 JSON）、层层追问式研究（答案引出新问题，用同一研究流程处理）、代码依赖链分析（理解 A 需先理解 A 依赖的 B）。判据：**子问题与原问题同型，且规模严格递减**。

> 2026-Q4 重估补充：原先排在第一位的"摘要的摘要（递归总结超长文本）"，随着上下文窗口变大，适用面已大幅收窄——能整篇放进窗口时直接处理，或改用 [[02_MapReduce|MapReduce]]。递归总结只在材料远超窗口、且层层压缩的信息损失可以接受时才用。

## Agent 如何协作

单一 Agent 定义 + 运行时多实例。每个实例：检查基例（base case，输入足够小可直接解决）→ 是则直接解，否则把输入分割，对每块**以相同配置生成新实例**，收集子实例结果后合并返回。协作关系是调用栈，不是消息网络。

## 信息如何传递

参数向下（子输入 + 深度计数器 + 累积上下文的**摘要**而非全文），返回值向上。关键纪律：向下传的上下文必须有损压缩，否则深层实例的上下文比根还大，递归的意义归零。

## 什么时候结束

三个条件任一触发：到达基例（正常出口）、深度上限（安全出口，通常 3-5 层）、预算耗尽（经济出口）。**递归度量必须严格递减且可验证**（文本变短、目录变浅、待办变少），度量不减的递归就是死循环。

## 优点

- 架构最简：一份 Agent 定义处理任意规模
- 天然适配规模未知的输入（不用预先决定切几片）
- 与树状分解相比省掉了"设计分解者"的工作

## 缺点

- **失控风险最高的模式**：基例判断错误 = 无限递归 = 无限烧钱
- 上下文漂移：深层实例离原始意图越来越远（每层压缩都在丢信息）
- 调试困难：错误藏在第 4 层的某个实例里，栈式 trace 比平铺 trace 难读
- 合并逻辑在每层重复执行，合并损失逐层复利

## Prompt 示例

```
你是递归总结器。当前深度 {d}/最大 4。
输入：{n} 段文本（每段可能已是下层的总结）。
流程：
1. 若总量 < 3000 token：直接产出最终总结（基例）
2. 否则：把输入分成 3-5 组，你将被以相同指令对每组调用，
   然后你会收到各组总结，把它们合并为一份。
合并规则：保留分歧（两组结论矛盾时并列呈现，不要抹平）；
每个论点标注来源组编号，保持可回溯链。
```

## Workflow 示例

```
任务：总结 800 页年报合集
depth0: 输入 40 万 token > 基例阈值 → 切 5 组
  depth1 × 5: 每组 8 万 token 仍超阈 → 各切 4 组
    depth2 × 20: 每组 2 万 token < 阈值 → 直接总结（基例命中）
  depth1: 各自合并 4 份子总结
depth0: 合并 5 份 → 终稿（附来源链: 终稿→组→子组→原文页码）
保险丝：深度4、预算 200 次调用、每层输入必须 < 上层的 60%
```

## 未来还能如何改进

- **递减度量的运行时校验**：框架层自动检查"子输入 < 父输入 × 阈值"，不满足即熔断——把安全从 prompt 纪律变成代码保证
- **自适应基例阈值**：按任务类型和模型能力动态调整"多小算小"，避免过度递归
- **无损回溯链**：合并时保留指针而非复制内容，最终答案的每句话可以一路点回原文（解决逐层信息损失的审计问题）
- **尾递归展开**：识别"其实是线性迭代"的伪递归（如逐章处理），自动改写为循环，省掉栈开销
