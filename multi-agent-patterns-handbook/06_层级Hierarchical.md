# 模式 06 层级 Hierarchical

## 为什么存在

单个协调者的管理带宽有限：直接管理 20 个 worker 时，光是读状态报告就挤爆上下文。层级模式引入中层——**协调者的 worker 自己也是协调者**——用管理树扩展规模，代价是每层都要交"信息损耗税"。它是 Planner-Executor / Orchestrator-Workers 在规模压力下的自然延伸，也是人类组织结构的直接映射（连同它的官僚病一起继承）。

## 适合解决什么问题

规模大到单层协调装不下的任务：全代码库级重构（总协调→模块负责人→文件执行者）、多章节图书/标书撰写、跨领域尽调。判据只有一个：**先试单层，单层协调者的上下文确实爆了，再上层级**。层级永远是被逼出来的，不是设计出来的。

## Agent 如何协作

树状指挥链：根协调者拆大任务给中层，中层再拆给叶子执行者；结果逐层验收、逐层汇总上报。同层默认不横向通信（要通信走共同上级——这是可控性的来源，也是效率的损失点）。每个中层节点实际上是一个完整的 Planner-Executor 单元。

## 信息如何传递

向下：逐层细化的任务书（每层加约束、砍上下文）。向上：逐层压缩的状态与结果摘要。**每过一层，信息保真度按 60-80% 折损**——设计时必须假设根协调者看到的是"摘要的摘要"，所以关键数字和风险项要设计"直达通道"（结构化字段原样上传，禁止逐层改写）。

## 什么时候结束

根节点的验收标准满足。层级深意味着终止也慢：叶子完成 → 中层验收汇总 → 根验收。异常路径：中层无法完成其子树时上报，根决定重派/降级/中止。

## 优点

- 唯一能扩展到"百个 Agent 级"任务的可控结构
- 每层上下文都有界：根想战略、中层管战役、叶子干战术
- 故障隔离：一个子树崩了，其他子树不受影响
- 与人类组织同构，人容易理解和介入（想插手时知道找"哪一层"）

## 缺点

- **传话游戏**：信息逐层失真，根据摘要的摘要做的决策可能离现实很远
- 延迟高：一条指令到叶子、一个结果回根，都要走全链
- 官僚化开销：管理 token（拆解、汇报、验收）可能超过干活 token
- 横向协作弱：两个叶子明明该直接对话，却要绕两层
- 中层是新的单点故障且最难调试（既非源头也非终点）

## Prompt 示例

（中层协调者——夹在中间的角色最考验 prompt 设计）

```
你是"{模块名}"子任务的负责人。上级给你的任务书：{task}
你的职责：
1. 拆解为 2-5 个可执行子任务，派给执行者
2. 验收每个子任务（按 acceptance 字段，不合格打回，最多一次）
3. 向上汇报，格式：
   {"status": "done|partial|blocked",
    "summary": "≤200字",
    "verbatim_critical": ["关键数字/风险项原样上传，禁止改写"],
    "needs_escalation": "需要上级决策的事项或 null"}
规则：你无权修改任务目标；发现任务书与实际情况冲突时,不要自行变通，上报。
```

## Workflow 示例

```
任务：把 200 个文件的代码库从框架 A 迁移到 B
[根协调者] 按模块拆成 5 个子树，定全局约束（接口冻结、命名规范）
  [中层×5] 各自拆到文件级，派发给执行者
    [叶子×40] 逐文件迁移 + 跑测试 → 报中层
  [中层] 模块内集成测试 → 汇总上报（测试失败数原样上传）
[根] 跨模块集成 → 发现模块2和4的接口冲突 → 向两个中层下发协调指令 → 终验
管理开销核算：总 token 的 35% 用于协调而非迁移本身
```

## 未来还能如何改进

- **越级直达通道**：叶子发现全局性风险时直报根节点（绕过摘要链），解决传话失真的最恶性后果
- **动态扁平化**：框架监控各中层的"管理增值"，发现某中层只是转发消息时自动裁撤该层
- **同层协商协议**：受控的横向通信（共享黑板 + 上级可见），省掉两跳绕行
- **组织结构搜索**：把"几层、每层几个"当超参数，用评测集自动搜索最优结构，而不是拍脑袋定
