# 模式 03 树状分解 Tree

> **定义归属与辨析**：树状分解（本章，**任务分解**拓扑）与 [[llm-design-patterns/01_推理模式|Tree Search / ToT（**推理路径**搜索）]]是名字相近的两个不同模式——前者拆任务、后者搜推理，各自以所在书的定义为准。

## 为什么存在

MapReduce 处理的是**同构**分片（每片干同样的活），但许多大问题的正确拆法是**异构**的：一个研究问题拆成性质不同的子问题，子问题再拆。树状分解是分治法（divide and conquer）的 Agent 化：**父节点负责"怎么拆"和"怎么合"，叶子节点负责"真正干活"**。

## 适合解决什么问题

有天然层级结构、拆分方式依赖内容理解的复杂任务：综合研究报告（问题→子问题→子子问题）、大型代码库理解（系统→模块→文件）、复杂规划（战略→战役→战术）、法律/尽调分析（合同→条款族→条款）。判据：拆分本身需要智能（所以不能像 MapReduce 那样机械切）。

## Agent 如何协作

递归的两种角色：**分解者**（判断当前问题可否直接解决，不能则拆成 2-5 个子问题并定义每个子问题的验收标准）和**求解者**（叶子层实际执行）。子问题解决后结果回传父节点，父节点**合成**并向上回传。兄弟节点默认互不通信、可并行。

## 信息如何传递

向下：自包含的子任务描述（子节点看不到全树，任务书必须携带必要上下文——这是本模式质量的第一决定因素）。向上：结构化结论 + 证据 + 未解决项。父节点只见子节点的结论摘要，不见其过程。

## 什么时候结束

所有叶子完成且逐层合并到根。必须有三重保险：**最大深度**（通常 ≤3 层）、**最大节点数**（预算）、**分解者的"可直接解决"判断**（防止无限拆分）。超预算时按优先级剪枝，未展开的分支标注"未探索"。

## 优点

- 能处理"大到没人能一次看全"的问题，且每个节点的上下文都聚焦
- 异构拆分比机械切片更贴合问题结构
- 兄弟并行，深度换广度
- 树本身就是可读的推理结构：结论怎么来的，沿树可审计

## 缺点

- **高层拆错，整棵子树白跑**——分解者的错误成本随深度指数放大
- 成本失控风险：3 层 × 每层 4 分支 = 64 个叶子调用起步
- 合成层信息损失逐层累积（和 Hierarchical 同病）
- 子任务描述不自包含时，叶子跑偏而父节点无感知

## Prompt 示例

（分解者——注意"先判断能否直接解决"）

```
你是问题分解者。对以下问题：
1. 先判断：以你的可用工具能否直接高质量解决？能 → 输出 {"solve_directly": true}
2. 不能 → 拆成 2-4 个子问题，每个输出：
   {"sub_question": "自包含描述，执行者看不到本问题的上文",
    "why_needed": "对回答父问题的贡献",
    "acceptance": "什么样的答案算合格",
    "parallel_ok": true/false}
规则：宁可少拆不拆伪问题；两个子问题答案高度重叠说明拆错了；当前深度 {d}/最大 3。
```

## Workflow 示例

```
根：'我司应否进入东南亚市场？'
 ├─ 子1：目标市场规模与增长（→ 直接求解，搜索+估算）
 ├─ 子2：竞争格局
 │   ├─ 子2.1：现有玩家份额与打法（求解）
 │   └─ 子2.2：进入壁垒分析（求解）
 ├─ 子3：我司能力匹配度（求解，读内部资料）
 └─ [根合成] 汇总三路结论 → 发现子1与子2.1数据矛盾 → 发起补充核查节点 → 终报告
预算：最大深度3 / 最大15节点 / 实际用9
```

## 未来还能如何改进

- **最佳优先展开**：不平均展开所有分支，先展开"预期信息增益最高"的（Tree-of-Thoughts 的搜索思想引入任务分解）
- **分解自检**：拆完先让另一个 Agent 审"这个拆法遗漏了什么维度"，高层错误早拦截
- **跨枝通报机制**：某叶子发现颠覆性事实（如"该市场刚出新法规"）时广播全树，触发相关分支重跑
- **树结构缓存**：相似问题复用历史拆分骨架，冷启动成本大降
