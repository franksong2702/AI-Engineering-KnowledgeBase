# 模式 10 裁判 Judge

> **定义归属说明**：本章是 Judge（独立评审员作为质量闸门）的权威定义；其作为单体评价技术的用法见 [[llm-design-patterns/04_质量控制模式|Design Patterns 家族四·LLM-as-Judge]]，评价理论视角见 [[evaluation-of-ai-systems/06_评价设计模式|Evaluation Part 6]]。

## 为什么存在

规模化系统里人工审核跟不上产出速度，而纯规则校验只能查格式查不了质量。Judge 模式设立一个**独立的评审 Agent 作为质量闸门**：产出必须过审才能放行。与 Reflection 的区别：Critic 参与改进循环（教练），Judge 只做通过/拒绝的裁决（守门员）——裁决权和改进权分离，正如法官不帮被告改辩护词。

## 适合解决什么问题

三大场景：**运行时闸门**（客服回复出站前审合规、Agent 高危操作前审安全）、**离线评测**（两个 prompt 版本哪个好——LLM-as-judge 已是行业标准做法）、**竞争裁决**（多个候选答案选最优，配合 Voting/MoE 使用）。判据：有可陈述的评判标准，且错放的代价 > 一次额外调用的成本。

## Agent 如何协作

单向、无对话：被评对象（Agent 产出）提交给 Judge → Judge 按 rubric 独立评审 → 输出裁决（通过/拒绝/分数）+ 理由。**Judge 不与生成者交互**——交互会被说服（模型极易被"其实我是对的因为…"带偏）。拒绝件回炉（触发 Reflection）或转人工。

## 信息如何传递

候选产出 + 评审 rubric + 必要上下文（原始需求、事实依据）→ Judge。**Judge 不应看到生成者的身份与自辩**。输出：结构化裁决 {verdict, scores per dimension, reasons, evidence}。对比裁决时输入 A/B 两候选——必须做位置交换双跑（见缺点）。

## 什么时候结束

单次裁决即结束（无循环）。作为闸门时的下游路径要预定义：通过→放行；拒绝→重试 n 次→仍拒→降级或人工。**Judge 自己不重试**——同一裁决跑三次取多数是 Voting 的活，不要混在 Judge 里隐式发生。

## 优点

- 把质量标准集中在一处（rubric），可版本化、可审计、可持续改进
- 独立性带来的客观性：不受生成过程的沉没成本影响
- 廉价的规模化审核：万级产出全量过审成为可能
- 裁决日志是金矿：拒绝原因的分布直接指出系统最该修的地方

## 缺点

- **裁判自身带偏见**：位置偏差（A/B 对比偏爱先出现的）、长度偏差（更长≈更好）、自恋偏差（偏爱同基座模型的输出）、风格偏差（流畅但错 > 笨拙但对）
- **裁判没被评测过就是玄学**：它打的分和人类判断的一致率没验证前，整个闸门在测"裁判的口味"
- rubric 之外的问题永远查不出（能力上限 = rubric 完备性）
- 被评者会针对裁判优化（古德哈特定律）：迎合 rubric 措辞而非真质量

## Prompt 示例

```
你是独立质量裁判。按 rubric 评审以下客服回复，与撰写者无任何关系。
Rubric（逐项独立打分 1-5，先写理由再打分）：
1. 事实准确：回复中的政策条款与知识库一致吗？（附知识库原文比对）
2. 完整性：用户的每个问题都被回应了吗？
3. 合规性：是否有过度承诺/擅自例外/泄露内部信息？
4. 语气：专业且共情？
裁决规则：任何一项 ≤2 → REJECT；合规项 ≤3 → REJECT。
输出：{"verdict": "PASS|REJECT", "scores": {...}, "reject_reasons": [...],
"borderline_notes": "低分但未到拒绝线的隐患"}
注意：长回复不等于好回复；发现 rubric 未覆盖的严重问题也要报告。
```

## Workflow 示例

```
[客服 Agent] 生成回复
  → [Judge] 评审（p95 延迟 1.2s）
     ├─ PASS (88%) → 发送用户
     ├─ REJECT (12%) → 回炉重生成（带 reject_reasons）
     │    └─ 二次 REJECT → 转人工队列
     └─ 每周：抽 50 条 PASS 件人工复核 → 裁判-人类一致率 91%
          + 分析 reject_reasons 分布 → "过度承诺"占 60% → 修上游 prompt
校准闭环是这个 workflow 的一半价值。
```

## 未来还能如何改进

- **裁判的持续校准流水线**：人工标注抽样自动对比裁判裁决，一致率跌破阈值自动告警并触发 rubric 修订——把"裁判也要被评测"制度化
- **多裁判合议**：高风险裁决用 3 个不同基座模型的 Judge 投票，对冲单裁判偏见（成本换公正）
- **分诊式裁判**：轻量模型先筛明显 PASS/REJECT，边缘案例才给贵裁判——闸门成本降 70%
- **反古德哈特审计**：定期用"迎合 rubric 但实质差"的对抗样本测试裁判，检测被钻空子的程度
