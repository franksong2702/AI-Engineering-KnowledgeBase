# 模式 01 流水线 Pipeline

## 为什么存在

单次 LLM 调用同时做多件事（提取+分析+写作+排版）时，各子目标互相干扰，质量方差大且无法定位问题出在哪。流水线把固定流程拆成串行阶段，每段一个 Agent 只做一件事——这是制造业分工逻辑在 LLM 上的直接复用：**分工降低方差，分段使问题可定位**。

## 适合解决什么问题

步骤固定、顺序已知、每步产物可明确定义的任务：文档处理（解析→提取→摘要→翻译）、内容生产（大纲→初稿→润色→格式化）、数据 ETL、代码生成（规格→实现→测试→文档）。判据：你能在动手前画出流程图，且流程不随输入内容改变。

## Agent 如何协作

严格串行：Agent A 完成 → 产物交给 B → B 完成交给 C。每个 Agent 不知道全流程，只知道自己的输入契约和输出契约。无协商、无回头（基础版）。

## 信息如何传递

**结构化工件（artifact）**，不是对话历史。每段间定义 schema（JSON/固定格式 Markdown），上一段的输出必须通过格式校验才进下一段。工件应携带元数据（来源、置信度、处理记录）以便追溯。

## 什么时候结束

最后一段完成即结束。异常终止：某段输出校验失败且重试耗尽 → 整条中止或降级（跳过非关键段）。流水线没有"收敛"问题，终止天然明确——这是它最省心的地方。

## 优点

- 可预测、可测试：每段可单独评测、单独优化、单独换模型（贵模型只放在关键段）
- 可调试：出错时二分定位到段
- 可缓存：输入相同的段可直接复用结果
- 方差最小的多 Agent 模式，生产可靠性最高

## 缺点

- 刚性：流程变化就要改架构；处理不了"步骤依输入而变"的任务
- 错误级联：早段的错误被后段放大且后段无力纠正
- 延迟叠加：总延迟 = 各段之和，无并行红利
- 局部最优：每段各自尽力，无人对全局质量负责

## Prompt 示例

（中间段 Agent 的典型结构——注意它只见契约不见全局）

```
你是流水线中的"要点提取"环节。
输入：一篇清洗后的文章（上游已去除广告与乱码）。
任务：提取 5-8 个核心论点。
输出（严格 JSON）：{"points": [{"claim": "...", "evidence": "原文引用", "location": "段落号"}]}
规则：只提取不评论；原文没有的不要补；下游环节依赖 location 字段回溯原文，必须准确。
```

## Workflow 示例

```
输入文档
  → [清洗 Agent] 去噪、标准化 → artifact_1（校验：非空、编码正确）
  → [提取 Agent] 要点+证据    → artifact_2（校验：JSON schema）
  → [撰写 Agent] 成文         → artifact_3（校验：包含全部要点引用）
  → [审校 Agent] 事实与风格   → 终稿
失败策略：每段重试 2 次 → 仍失败则中止并报告断点
```

## 未来还能如何改进

- **自适应跳段**：入口加轻量分类器，简单输入跳过重段（短文不需要清洗段）
- **段级模型路由**：按段难度动态选模型，成本可再降一半
- **有限回溯**：审校段发现事实错误时允许打回提取段重跑（引入受控循环，向 Reflection 演化）
- **段间压缩学习**：分析历史 trace，自动发现"哪些字段下游从没用过"，瘦身工件 schema
