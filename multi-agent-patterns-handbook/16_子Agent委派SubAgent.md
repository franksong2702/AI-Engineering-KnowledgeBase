# 模式 16 子 Agent 委派 Sub-Agent

> **立项说明**：本章由 [[_governance/reevaluation/REEVALUATION_2026_Q4|2026-Q4 季度重估]] ESCALATE-2 裁决新增（2026-10-07）。教学版见 [[textbook-zero-to-agent/08_Agent设计模式与架构|教材第 8 章 8.5]]；本章是权威定义。

## 为什么存在

单 Agent 做长任务时，最先撑不住的往往不是能力，而是上下文：翻几十个网页、读一个大文件、试错跑十次测试，这些过程产生的大量中间内容会挤进主 Agent 的上下文，冲淡真正需要的信息，后面的决策随之变差。

子 Agent 委派把这类"过程很脏、结论很短"的子任务交给一个**新开上下文的 Agent**，让它在自己的上下文里完成，只把结论交回来。这是 [[multi-agent-patterns-handbook/00_INDEX#五条跨模式原则|Multi-Agent 原则 1（上下文隔离）]]最直接的实现，也是 2026 年生产环境里最常见的多 Agent 形态：大多数"多 Agent 系统"其实是一个主 Agent 加若干按需派生的子 Agent。

它和相近模式的区别：

| 模式 | 谁决定拆分 | 拆分时机 | 层级 |
|---|---|---|---|
| [[05_Planner-Executor\|Planner-Executor]] | Planner 先出完整计划 | 执行前一次性拆分（可重规划） | 两层 |
| [[06_层级Hierarchical\|Hierarchical]] | 各层协调者 | 预先设计好的管理树 | 多层 |
| **子 Agent 委派（本章）** | 主 Agent 在自己的循环里临场决定 | 边做边拆，需要时才派生 | 默认一层 |

子 Agent 在主 Agent 眼里只是**一个工具**（所以也叫 Agent-as-Tool）：调用它，传任务书，拿回结果。主 Agent 自始至终握有控制权和最终责任。

## 适合解决什么问题

满足以下任一条件的子任务：

- **过程噪声大、结论小**：代码库里找某个函数在哪被调用、调研某个库是否支持某功能、读完一份 200 页文档回答 3 个问题。
- **可以并行的独立探查**：同时从三个方向排查一个 bug，或同时调研五家竞品。
- **需要不同权限或工具**：主 Agent 能写文件，但"读外部网页"的子任务交给一个只读、不能对外发送的子 Agent，以拆开[[textbook-zero-to-agent/10_安全与生产部署|致命三重奏]]。
- **需要不同模型**：探查类子任务用便宜模型，主 Agent 用强模型做综合与决策。

判据：**你能用一段自包含的任务书说清子任务，并且能说清"交回来的结果长什么样"。**说不清，就别委派，主 Agent 自己做。

## Agent 如何协作

**主 Agent**：在自己的工作循环里判断"这一步该不该委派"→ 写任务书 → 调用子 Agent（可同时调用多个）→ 读结果 → 决定下一步。

**子 Agent**：拿到任务书和受限的工具集，在全新的上下文里独立工作（它看不到主 Agent 的历史），完成后返回结构化结果，然后销毁。

默认规则：**子 Agent 不再派生子 Agent。** 嵌套派生会把本模式变成没有设计过的 [[04_递归Recursive|递归]] 或 [[06_层级Hierarchical|层级]] 结构，失控风险陡增。确有需要时，应显式改用那两个模式并设计终止条件。

## 信息如何传递

**下行：任务书。** 必须自包含：目标、范围、已知信息、不要做什么、交付格式、预算。子 Agent 看不到主 Agent 的上下文，"如前所述""按刚才的思路"这类指代全部无效。

**上行：结论 + 证据指针，而不是原始材料。** 子 Agent 返回的应该是"结论、置信度、依据在哪里（文件路径与行号、URL、记录 ID）、还没查清的地方"。主 Agent 需要细节时，按指针自己去取，而不是让子 Agent 把几万 token 原文搬回来。

**大产物走文件。** 子 Agent 产出的长报告、数据、代码，写到共享文件里，只把路径和摘要交回主 Agent。

## 什么时候结束

- **子 Agent 层**：完成任务书的交付格式即返回；或达到自己的轮数 / token / 时间预算即返回"部分结果 + 卡在哪里"。预算耗尽时必须交回已有发现，不能空手返回。
- **主 Agent 层**：所有委派结果都已读取并据此做出决定。子 Agent 失败时，主 Agent 显式选择：换一种任务书重试、自己接手，或带着缺口继续并在最终产出里标明。

## 优点

- **主上下文保持干净**：探查过程的噪声留在子 Agent 里，主 Agent 只看到结论，长任务后段的决策质量明显更稳
- **天然并行**：独立探查同时派发，墙钟时间缩短
- **权限可以按任务收窄**：每个子 Agent 只拿到完成任务所需的最小工具集
- **成本可分层**：便宜模型做探查，强模型做综合
- **增量采用**：从单 Agent 出发，只在痛点处加委派，不需要一开始就设计整套拓扑

## 缺点

- **结论有损**：子 Agent 交回的摘要可能恰好丢掉了主 Agent 后面才发现需要的细节；证据指针能缓解，但主 Agent 回头取证也有成本
- **静默失败向上传染**：子 Agent 没真查清，却交回一个看起来合理的结论，主 Agent 信以为真（见 [[textbook-zero-to-agent/11_多Agent系统|教材 11.5]]）
- **重复劳动**：子 Agent 从零开始，可能要重新读主 Agent 已经读过的东西；多个子 Agent 之间也可能查重复的内容
- **成本倍增**：每次委派都有任务书和重建上下文的开销，并行委派的 token 消耗会成倍增加（经验量级，取决于委派粒度）
- **委派判断本身会出错**：该自己做的小事也派出去（延迟和成本白花），该派出去的大探查却自己做（上下文被淹没）

## Prompt 示例

（主 Agent 写给子 Agent 的任务书模板）

```
## 任务
找出 payment/ 目录下所有直接调用 charge_card() 的位置，并判断哪些调用点没有做幂等保护。

## 已知信息
- 幂等保护的标准写法是先调用 idempotency.check(request_id)
- 不需要看 tests/ 目录

## 不要做
- 不要修改任何文件
- 不要调研 charge_card() 的内部实现

## 交付格式（严格遵守）
{"call_sites": [{"file": "...", "line": n, "protected": true|false, "evidence": "相关代码一行"}],
 "confidence": "high|medium|low",
 "not_checked": ["没来得及看或无法判断的部分"]}

## 预算
最多 20 次工具调用。用完时交回已有结果，并在 not_checked 里写明剩余部分。
```

## Workflow 示例

```
目标：修复"重复扣款"的线上 bug（主 Agent：强模型，可读写代码）
[主 Agent] 读 issue 与报错日志 → 判断需要三条并行探查
  → 派生 子Agent-A（只读）：找所有 charge_card() 调用点及其幂等保护情况
  → 派生 子Agent-B（只读）：查最近 30 天对 payment/ 的提交，列出改动了重试逻辑的
  → 派生 子Agent-C（只读，便宜模型）：在日志样本里统计重复扣款请求的 request_id 模式
[子Agent ×3] 各自在独立上下文中工作，返回 JSON 结论 + 文件:行号
[主 Agent] 只读三份结论（约 2k token，而不是三条探查过程的数万 token）
  → A 指出 2 处无保护，B 指出其中一处正是上周新增的重试 → 交叉印证
  → 主 Agent 按指针打开这两处代码，亲自核实后修改 → 跑测试
终止：测试通过；A/B/C 的 not_checked 均为空或已被主 Agent 判定无关
```

## 未来还能如何改进

- **证据回传的标准化**：结论 + 证据指针 + 置信度成为子 Agent 返回的统一 schema，主 Agent 可以机械抽查
- **委派策略可学习**：从历史 trace 里学"什么样的子任务值得委派、委派给哪个模型"，减少委派判断失误
- **共享只读记忆**：子 Agent 能读主 Agent 维护的"已知事实"文件，减少重复探查，同时不污染主上下文
- **子 Agent 结果的自动核验**：对关键结论，主 Agent 自动派一个独立子 Agent 复核，或按证据指针做机械校验，把静默失败变成可见失败
