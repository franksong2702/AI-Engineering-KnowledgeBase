# Part 4 蒸馏与自部署：让定制的能力跑得起、跑得省

> 定制出一个好模型只是一半，另一半是让它以可持续的成本跑在生产里。这一部分讲蒸馏（用大模型教小模型降本）和自部署（自己托管模型的取舍）。核心是成本工程和"你接管了什么"的清醒认知。

## 4.1 蒸馏：大模型教小模型

**知识蒸馏**的思路：用一个强大的大模型（教师）生成高质量的输出，用这些输出训练一个小模型（学生），让小模型在特定任务上逼近大模型的表现，但成本低得多。

为什么有价值（[[laws-of-ai-engineering/06_经济与资源定律#Law 56 — 成本结构决定架构定律（Cost-Structure-Shapes-Architecture Law）|成本结构决定架构]]）：大模型质量高但贵、慢；小模型便宜、快但弱。蒸馏让你在**特定窄任务**上用小模型的成本获得接近大模型的质量。这是"大模型做难的 20%，小模型做简单的 80%"策略的训练版。

关键限制：蒸馏在**窄任务**上有效，学生模型继承的是教师在该任务上的能力，不是通用能力。它不会让小模型变得全面强大，只是在被蒸馏的任务上变强。且学生继承教师的偏见和错误（[[data-foundation-of-ai-systems/03_标注与合成|合成数据的继承偏见]]——蒸馏数据是教师生成的合成数据）。

### 蒸馏管线的工程细节

蒸馏数据就是合成数据，[[data-foundation-of-ai-systems/03_标注与合成|Data Foundation Part 3]] 的纪律全部适用，外加三条蒸馏特有的：

1. **教师输出先过滤再入库**。教师也会错——把教师的错误教给学生是最冤的失败。可验证任务（分类有标签、抽取可校验、代码可测试）用验证器过滤；不可验证任务至少抽样人审教师错误率，错误率高说明教师本身不胜任，先修教师侧（更好的 prompt/更强的模型）再蒸馏。**教师的天花板就是学生的天花板，信息守恒不豁免蒸馏。**
2. **蒸馏输入要覆盖真实分布**。用什么输入去"问"教师，决定学生见过什么世界。理想输入是生产真实流量的采样（脱敏后）；纯合成输入会引入[[data-foundation-of-ai-systems/03_标注与合成|分布偏差]]——学生在真实长尾上露怯。
3. **学生的成绩单对照教师打**。评测报告三列：学生 vs 教师 vs 成本比。"学生达到教师九成质量、5% 成本"才是蒸馏的正当叙事；只报学生的绝对分会掩盖差距在哪个子任务上——**按子任务切分看差距**，学生通常在难例/长尾上掉得最多，而那可能恰是业务在乎的。

## 4.2 自部署 vs API：一个"你接管了什么"的决定

用现成 API 还是自己部署开源模型，是一个重要的架构决定。

**用 API（托管模型）**：厂商负责 serving、扩缩容、更新、可靠性。你只管调用。省心，但数据要出域、成本按调用、依赖厂商、定制受限。

**自部署（开源模型）**：你完全控制，数据不出域，可深度定制，高频场景可能更便宜。**但你接管了全部复杂度**——serving、扩缩容、延迟优化、可靠性、监控、更新（[[laws-of-ai-engineering/04_系统与控制定律#Law 38 — 冗余-效率权衡定律（Redundancy-Efficiency Tradeoff Law）|冗余-效率权衡]]、[[laws-of-ai-engineering/04_系统与控制定律#Law 41 — 复杂度累积定律（Complexity-Accumulation Law）|复杂度累积]]）。

**判断（何时自部署）**：
- **数据不能出域**——隐私/合规硬约束（[[data-foundation-of-ai-systems/00_INDEX|数据主权]]），这是最强的自部署理由。
- **成本敏感的高频窄任务**——量大到自部署的固定成本被摊薄到低于 API 的边际成本。
- **需要深度定制**——微调自由、架构改动，API 给不了。

**否则默认用 API**——因为自部署让你接管了一大堆你可能不想要的复杂度（[[laws-of-ai-engineering/11_演化与元定律#Law 99 — 简单性存活定律（Simplicity-Survives Law）|简单性存活]]）。很多团队低估了"自己跑模型"的持续运维负担。

### 自部署的总成本清单（TCO，报价前先算完）

"自部署更便宜"的结论常常来自只算了 GPU 租金。完整清单：

- **容量按峰值配，账单按峰值付**：GPU 容量要覆盖峰值流量而非均值——峰谷比大的业务，为峰值配的卡在谷时闲着也在烧钱（API 的按调用计费天然吸收了这个波动）。
- **可用性有价格**：要几个 9？多副本、跨区冗余、故障转移——每个 9 都是成本的台阶。
- **人力是大头**：谁 on-call？推理服务的延迟优化、显存管理、版本升级、安全补丁——这通常是零点几到几个工程师的持续投入，按人力成本折算后很多"省钱"方案立刻翻转。
- **模型更新税**：开源基座也在换代，跟进换代 = 重新微调 + 重新评测 + 灰度迁移，每年数次（[[01_优化阶梯|换代税]]的自部署版）。
- **对照的正确基线**：API 侧也要算全——含缓存优化后的实际调用量，而非裸调用量。

算完这张表再对比。**经验上，只有"高频 + 窄任务 + 流量平稳"或"合规硬约束"两类场景，自部署的 TCO 能稳定占优**（经验判断，具体以你的数字为准）。

## 4.3 部署的成本工程

无论蒸馏还是自部署，成本工程是核心（[[laws-of-ai-engineering/06_经济与资源定律#Law 56 — 成本结构决定架构定律（Cost-Structure-Shapes-Architecture Law）|成本结构决定架构]]、[[laws-of-ai-engineering/06_经济与资源定律#Law 54 — 质量有成本定律（Quality-Costs Law）|质量有成本]]）：

- **模型大小 vs 质量**——更小的模型（蒸馏/量化）省成本但可能降质量，找质量-成本曲线的甜点（[[laws-of-ai-engineering/06_经济与资源定律#Law 52 — 边际定律（Marginal Law）|边际]]）。
- **量化（quantization）**——压缩模型权重（如 8bit/4bit），大幅降低显存和成本，通常质量损失可接受。
- **批处理与缓存**——[[laws-of-ai-engineering/06_经济与资源定律#Law 58 — 缓存定律（Caching Law）|缓存定律]]、批处理摊薄成本。
- **模型路由**——简单请求给小模型/蒸馏模型，难请求给大模型（[[llm-design-patterns/00_INDEX|Dynamic Routing]] 的成本版）。

**成本必须在部署设计阶段估算**（[[ai-engineering-anti-patterns/00_INDEX|Anti-Patterns]]："无成本核算"）——单次成本 × 规模，很多定制方案死在这道乘法上。

**量化的验收纪律**：量化的质量损失不均匀——平均指标（困惑度）可能只降一点，但特定能力（多步推理、长上下文、低资源语言）可能明显受损。所以量化的验收是**在自己的评测集上按任务切分做回归**，而不是看通用平均分；量化程度逐级试（先温和后激进），每级都过回归门。

## 4.4 蒸馏与部署的反模式

- **为降本牺牲太多质量**——过度蒸馏/量化，小模型在关键场景不够用。
- **不必要的自部署**——没有数据/成本/定制的硬需求却自部署，接管了一堆复杂度（[[ai-engineering-anti-patterns/00_INDEX|过度工程]]）。
- **蒸馏当通用能力提升**——以为蒸馏能让小模型全面变强（它只在被蒸馏的窄任务上强）。
- **无成本估算部署**——规模化后才发现成本不可持续。
- **递归蒸馏**——反复用模型数据训模型，[[data-foundation-of-ai-systems/03_标注与合成|模型坍缩]]。
- **只算 GPU 租金的"更便宜"**——TCO 没算人力、峰值容量、可用性、换代税（见 4.2）。
- **量化只看平均分**——平均没掉、关键子任务掉了（见 4.3）。

## 4.5 验收清单：怎么判断蒸馏/部署做对了

- ☐ 教师输出过滤了吗？教师错误率抽检数字是多少？
- ☐ 蒸馏输入采样自真实流量吗？长尾覆盖检查过吗？
- ☐ 学生成绩单是三列的吗（学生/教师/成本比），按子任务切分了吗？
- ☐ 自部署决策有完整 TCO 表吗（含人力、峰值、可用性、换代税）？
- ☐ 量化过回归门了吗——按任务切分，不是只看平均？
- ☐ 模型路由的难度判据是什么？路由错误（难题被发给小模型）率有监控吗？
- ☐ 单次成本 × 预期规模这道乘法，在设计文档里吗？

## Part 4 收束

蒸馏用大模型教小模型，在窄任务上以小模型的成本逼近大模型的质量——但只在窄任务，且继承教师的偏见，所以教师输出要过滤、输入要覆盖真实分布、成绩单对照教师按子任务打。自部署 vs API 是"你接管了什么"的决定：数据不出域、成本敏感高频、深度定制才自部署，且要算完整 TCO 而非 GPU 租金。成本工程（量化、路由、缓存、批处理）是部署的核心，必须在设计阶段估算；量化按子任务过回归门。

**最该记住的一句**：**自部署意味着你接管了 serving、扩缩容、维护的全部复杂度——除非有数据/成本/定制的硬需求，否则这个复杂度不值得。**
