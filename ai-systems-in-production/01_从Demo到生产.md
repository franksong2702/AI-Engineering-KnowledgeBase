# Part 1 从 Demo 到生产：换一个质量定义

> 这一部分是全书的守门人（如同[[model-adaptation/01_优化阶梯|优化阶梯]]之于定制）。它回答两个问题：demo 和生产之间到底差什么；以及"生产就绪"怎么分级判定——因为不是所有系统都需要同一档生产化投入。

## 1.1 鸿沟的解剖：demo 证明的和生产要求的

demo 到生产不是"加固"，是**质量定义的更换**。逐条对照：

| 维度 | Demo 证明的 | 生产要求的 |
|------|-----------|-----------|
| 成功 | 它能做到（一次、几次） | 成功率的**分布**可接受，含 P95/长尾（[[agent-decision-system/05_EVAL-CHECKLIST\|Q-02]]） |
| 输入 | 演示者选的友好输入 | 真实用户的五花八门 + 恶意者的对抗输入（[[laws-of-ai-engineering/10_对抗与安全定律#Law 87 — 一切输入皆指令定律（All-Input-Is-Instruction Law）\|一切输入皆指令]]） |
| 失败 | 重跑一次就好 | 失败被检测、被兜住、可恢复、可归因（[[06_故障与降级\|Part 6]]） |
| 时间 | 一个下午 | 数月——期间模型会更新、数据会漂移、依赖会故障（[[data-foundation-of-ai-systems/04_数据评价与漂移\|漂移]]） |
| 成本 | 无所谓 | 单位经济学成立：每任务成本 × 规模 < 每任务价值（[[05_成本工程\|Part 5]]） |
| 责任 | 没人问 | 出错有人负责、有留痕、可复盘（[[human-ai-collaboration-foundation/07_责任边界设计\|责任边界]]） |

**这张表也是"demo 惊艳但没人敢上线"的诊断表**：卡住的项就是生产化的工作清单。而 LLM 系统在"失败"一行有独特的加重——它的失败常常不是报错，是**返回一个流畅的错误答案**。传统软件的生产化默认"失败会暴露"（崩溃、超时、5xx），LLM 生产化必须默认"失败会伪装成成功"——这一条改变了监控（[[03_可观测性|Part 3]]）、降级（Part 6）、事故响应的全部设计。

## 1.2 生产化五问（立项时就问，不是上线前才问）

1. **它错了，我多快知道？**——[[laws-of-ai-engineering/02_计算与验证定律#Law 12 — 验证-生成不对称定律（Verification-Generation Asymmetry Law）|为可靠验证器创造条件]]的运维版：先设计独立失败信号，才能利用验证成本杠杆。答案决定监控投入（Part 3）。
2. **它错了，最坏伤到什么？**——爆炸半径决定权限与审批设计（[[human-ai-collaboration-foundation/06_权限系统设计|权限系统]]），也决定该不该全自动。
3. **它挂了，用户看到什么？**——决定降级链（Part 6）。"看到显式的不可用"合格，"看到编造的答案"不合格。
4. **它贵了，谁先发现？**——成本护栏与异常检测（Part 5）。
5. **它变了，谁批准的？**——变更管理（Part 4）。"模型供应商悄悄更新"也算"它变了"。

五问在设计期回答的成本，是上线后再回答的零头——生产化最贵的错误都是"当时没问"。

## 1.3 生产就绪分级：不是所有系统都要同一档投入

生产化自身要过[[foundation-of-ai-engineering/00_INDEX|简单优先]]检验。三档划分（按风险和规模，不按"感觉重要"）：

**L1 内部工具级**（低风险、小流量、用户是同事）：要求——基本日志（能事后查一条请求发生了什么）、成本上限（一个封顶数字）、显式失败（挂了就说挂了）。不要求：语义监控、灰度、降级链。**大多数内部辅助工具停在 L1 是正确的**，把 L3 的机器搬给它们是过度工程。

**L2 正式服务级**（对外、有 SLA 预期、错误有业务代价）：在 L1 上加——全量 trace（Part 3 的最小字段）、评测门禁（改动过 CI）、灰度发布、降级链第一级（备用路径）、成本按用户限额、值班响应。

**L3 关键业务级**（错误代价高/不可逆/合规敏感）：在 L2 上加——语义层在线监控与抽检、跨供应商冗余（含备用模型的独立评测，见 Part 6）、事故演练、审计留痕（[[human-ai-collaboration-foundation/07_责任边界设计|决策留痕]]）、回滚演练。

**分级的纪律**：级别写进系统的元数据，升级触发条件显式化（流量过阈值、接入外部用户、开始处理不可逆操作——任一发生即评估升级）。最常见的事故形态是"系统悄悄从 L1 场景长成了 L2 场景，生产化投入还停在 L1"。

## 1.4 反例与边界

- **"生产级"不是道德优越**。给一个日调用 50 次的内部脚本上全套监控/灰度/降级，浪费的工程时间本可以用来把 L2 系统的真实风险敞口关掉。生产化投入要跟着风险走，不跟着技术审美走。
- **有些 demo 就该死在 demo**。生产化五问的第 2 问答案是"伤到不可逆且无法有效兜住"、第 4 问答案是"单位经济学怎么算都不成立"时，正确决策是不上线——生产化不能修复一个不该生产化的产品判断（[[decision-frameworks-guide/00_INDEX|机会成本]]）。
- **"先上了再说"有一个合法版本**：小流量、真实用户、全量人工兜底（每个输出人工过目后才生效）——这是收集真实分布的 L1.5 灰度实验，不是逃避生产化。它的边界是人工兜底真的在兜（[[human-ai-collaboration-foundation/05_避免盖章者陷阱|盖章者检验]]）。

## 1.5 验收清单

- ☐ 生产化五问的答案写在设计文档里吗？
- ☐ 这个系统被显式分级了吗（L1/L2/L3）？级别和它的真实风险匹配吗？
- ☐ 升级触发条件定义了吗？最近一次核对是什么时候？
- ☐ "失败会伪装成成功"这个 LLM 特性，在监控和降级设计里被针对了吗？
- ☐ demo 表里的六个维度，哪几个还卡着？有工作项吗？

## Part 1 收束

demo 到生产是质量定义的更换：从"能做到"到"最差时刻也可靠、可查、可回滚、可负担"。LLM 系统的独特难点是失败会伪装成成功。生产化五问在设计期回答；生产化投入按 L1/L2/L3 分级，跟着风险走——过度生产化和不足生产化都是错配。

**最该记住的一句**：**生产系统的质量由它的最坏时刻定义——而 LLM 系统的最坏时刻，往往看起来一切正常。**

下一步：先让它跑得动、跑得快——[[02_Serving与延迟|Serving 与延迟]]。
