# Part 6 故障与降级：它一定会坏，坏得有尊严

> 一切会失败（墨菲）。生产工程的分水岭不是"会不会坏"，是坏的方式：显式的降级 vs 静默的错误。这一部分给出 LLM 系统的失败目录、降级链设计、和"错误输出"型事故的响应——最后落在把每次事故变成资产的复盘文化。

## 6.1 LLM 生产系统的失败目录

按来源分七类，各有不同的检测器和响应：

| # | 失败类 | 典型形态 | 最早的检测器 |
|---|--------|---------|------------|
| F1 | 上游故障 | API 超时/5xx/429 风暴/供应商区域故障 | TTFT 超时、错误率（[[02_Serving与延迟\|L1]]） |
| F2 | 供应商静默变更 | 模型行为漂移（没 pin 版本，或 pin 了但供应商动了底层） | L3 代理指标漂移 + 无发布记录（[[04_发布与变更管理\|Part 4]]） |
| F3 | 质量退化 | 输入分布漂移、语料过时 | [[data-foundation-of-ai-systems/04_数据评价与漂移\|输入侧监控]] + L3 |
| F4 | 对抗与滥用 | 注入、越狱、诱导烧钱 | 护栏触发率、成本毛刺（[[05_成本工程\|Part 5]]）、[[human-ai-collaboration-foundation/06_权限系统设计\|权限层]]兜底 |
| F5 | 成本失控 | 循环 bug、长输出攻击、流量异常 | 三级限额 + 毛刺告警 |
| F6 | 上下文/状态类 | 上下文溢出、记忆污染、会话状态错乱 | schema 合法率、轮数分布 |
| F7 | 工具链故障 | 工具超时/返回垃圾/权限变更 | 工具调用成功率（L2） |

**通用规律：F2/F3 型没有"事故时刻"**——它们是坡不是崖，靠漂移监控而非报警器发现。**最危险的组合是 F3 + 无 L3 监控**：系统好几周"一切正常"地越答越差。

## 6.2 降级链：每一级都比编造好

**设计原则：降级的每一级都必须比"静默返回一个错误答案"好**（[[laws-of-ai-engineering/08_可靠性与失败定律#Law 76 — 静默降级危险定律（Silent-Degradation-Danger Law）|静默降级危险定律]]）。标准链条，按服务质量递减：

```
主路径（主模型+全功能）
 → 备模型（能力略降，功能保全）
 → 功能降级（砍非核心环节：跳过反思/缩检索/禁用工具，标注"简化模式"）
 → 缓存/模板回答（仅高频稳定问题，标注时效）
 → 显式不可用（"暂时无法回答，已记录" + 替代路径如转人工）
```

四个工程细节：

- **备模型不是免费保险**。同一 prompt 在备模型上行为不同——**备用路径要有自己的评测基线**（哪怕门槛低一档），否则故障切换那一刻你上线了一个从没测过的系统。切换本身也要演练（每季度真切一次，比文档可靠）。
- **降级要显式标注**。给用户（"当前为简化服务"）和给下游系统（响应头/字段标注降级级别）——下游可能因此改变自己的处理（如提高人工抽检率）。**静默降级是把 F1 转化为 F3**。
- **触发与恢复都要自动 + 滞回**：错误率/超时率超阈值自动降级（人工确认来不及），恢复要有滞回区间（防在临界点反复横跳）；恢复到主路径后加密抽检一段时间。
- **每级的成本别忘了**：备模型可能更贵（应急容量），全局熔断（Part 5）在降级链之上——预算耗尽时直接跳到显式不可用。

## 6.3 "错误输出"型事故：LLM 特有的响应剧本

传统事故（宕机）有明确的开始、报警、结束。LLM 特有的事故是**F2/F3/F4 造成的一批错误输出**——没有报警、发现滞后（用户投诉/抽检/外部通报）、且"结束"不等于"处理完"。响应剧本：

1. **止血**：定位到变更就回滚（[[04_发布与变更管理|六类对象的回滚路径]]）；定位不到就降级到已知安全的配置。
2. **圈定影响面**：靠 trace 回答"从何时起、哪些请求、受什么影响"——**这就是 [[03_可观测性|Part 3]] 版本字段存在的意义**。没有 trace 的系统在这一步只能说"不知道"，而"不知道影响面"在合规场景等于最坏假设。
3. **主动处置**：受影响的输出能撤回的撤回（内部报告类），不能撤回的通知（已发给用户/客户的），进入人工复核队列的复核——按[[human-ai-collaboration-foundation/07_责任边界设计|责任矩阵]]走，事先就该知道这类事故谁拍板。
4. **回灌**：事故样本进回归集（门禁从此拦住同类）、进对抗集（若是 F4）、进[[ai-engineering-case-library/00_INDEX|案例库]]（组织记忆）。

## 6.4 复盘文化：每个事故都是买来的评测用例

- **无责复盘**（blameless postmortem）：追问系统为什么允许这个错误发生，而不是谁犯了错——追责文化的直接后果是瞒报，而 LLM 系统的 F3 型问题靠一线的"感觉不对劲"上报的比例极高，瞒报文化会杀死这个最灵敏的传感器。
- **复盘的固定产出**（不产出这三样的复盘是开会不是复盘）：①根因（用 [[decision-frameworks-guide/00_INDEX|5 Whys]] 挖到系统层——"prompt 写错了"不是根因，"prompt 变更没有门禁"才是）；②防再犯的机制变更（进 [[04_发布与变更管理|Part 4]] 的流水线，有 owner 有期限）；③新的评测/对抗用例（**事故是最贵的数据采集，不入库等于白付学费**——呼应[[textbook-zero-to-agent/09_评测与可靠性工程|"真实失败案例比合成数据值钱 10 倍"]]）。
- **演练**（成熟度的分水岭）：故障切换演练、回滚演练、注入红队（[[llm-design-patterns/00_INDEX|Red Team]]）、以及"错误输出事故"的桌面推演（走一遍 6.3 剧本，看哪步卡住——通常卡在"圈定影响面"，暴露 trace 的缺口）。

## 6.5 反例与边界

- **不是每个失败都值得一条降级链**。L1 系统"挂了就显式说挂了"完全合格；五级降级链是 L2/L3 的装备（[[01_从Demo到生产|分级]]）。降级链自身也是要测试维护的代码——它的复杂度要被可用性需求证明。
- **重试不是降级**。重试处理瞬时故障（网络抖动、限流），降级处理持续故障。对持续故障狂重试 = 加重上游 + 烧钱 + 拖延真正的降级决策——重试必须有预算（次数/总时长），预算尽则进入降级链。
- **"转人工"是有容量的降级**。把人工当无限兜底，故障时人工队列瞬间爆掉，等于没有兜底——人工兜底的容量要按故障场景（而非日常场景）预估，超容量时的下一级（显式不可用+排队号）也要设计。

## 6.6 验收清单

- ☐ 七类失败各自的"最早检测器"，你的系统都有吗？F3（静默质量退化）的检测器是什么？
- ☐ 降级链存在吗？每级都比"编一个答案"好吗？降级对用户和下游显式标注了吗？
- ☐ 备模型有自己的评测基线吗？上次故障切换演练是什么时候？
- ☐ 降级触发是自动的吗？恢复有滞回吗？
- ☐ 桌面推演过"错误输出事故"吗？"圈定影响面"那步能走通吗？
- ☐ 最近一次事故的三样产出（根因/机制变更/新用例）都有吗？
- ☐ 重试有预算吗？人工兜底按故障容量估过吗？

## Part 6 收束

LLM 生产失败分七类，F2/F3 是坡不是崖、靠漂移监控发现；降级链每级都要比编造好、显式标注、自动触发带滞回，备用路径要有自己的评测。"错误输出"型事故的剧本是止血→圈影响面（trace 的意义）→主动处置→回灌；复盘无责、产出三样（根因/机制/用例），事故是最贵的评测数据。

**最该记住的一句**：**系统的成熟度不看它多久坏一次，看它坏的时候多有尊严——显式、受控、可圈定、可回滚，以及坏完之后它是不是变得更难再坏一次。**

## 全书收束：生产化是"验证稀缺"的基础设施形态

《AI Systems in Production》补齐了知识库的 M4 缺失。六个 Part 的主线是一条：**生产系统的质量由分布和最坏时刻定义，而 LLM 系统会在 200 OK 里静默地错——所以语义可观测、全类变更管理、有尊严的降级、把事故变成评测用例，是这个时代生产工程的新增义务。**

它与知识库深度咬合：是 [[textbook-zero-to-agent/10_安全与生产部署|教材第 10 章]]的系统展开、[[model-adaptation/04_蒸馏与部署|Model Adaptation Part 4]] 的系统层配对、[[data-foundation-of-ai-systems/04_数据评价与漂移|Data Foundation Part 4]] 的输出侧镜像、[[evaluation-of-ai-systems/00_INDEX|Evaluation]] 的运行时化身；它在基础设施层杜绝的，正是 [[ai-engineering-anti-patterns/00_INDEX|Anti-Patterns]] 里静默失败、无评测上线、无失败恢复那一族。

**最该记住的一句**：**在生成廉价的时代，"跑一个 AI 系统"人人都会——"让它在最差的时刻也可靠、可查、可负担地跑着"，才是稀缺的工程判断力所在。**
