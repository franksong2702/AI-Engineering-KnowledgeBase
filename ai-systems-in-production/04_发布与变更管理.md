# Part 4 发布与变更管理：一切都是变更

> LLM 系统的变更面比传统软件宽得多：改一个字的 prompt、供应商静默更新模型、RAG 语料例行重建——每一件都可能改变系统行为。这一部分把"一切都是变更"落成六类变更对象的统一管理，和"评测门禁→灰度→回滚"的发布流水线。

## 4.1 六类变更对象：每类都要版本化

| 变更对象 | 为什么危险 | 版本化的形态 |
|---------|-----------|------------|
| 代码 | 常规 | git（已解决） |
| **Prompt** | 一个措辞变化可让某类输入崩溃，且 diff 看起来"无害" | prompt 文件入库、带版本号、走评审——**prompt 就是代码** |
| **模型版本** | 供应商更新=你的系统被别人改了 | **pin 具体版本号**，升级是显式变更不是自动发生 |
| **采样参数** | 温度/top_p/max_tokens 改变行为分布 | 与 prompt 同包版本化 |
| **工具集** | 加减工具=改权限面（[[human-ai-collaboration-foundation/06_权限系统设计\|权限]]）+改行为 | 工具清单与描述入库 |
| **RAG 语料/索引** | 语料更新=知识变更；重建索引=检索行为变更 | 语料版本（[[data-foundation-of-ai-systems/02_数据管线\|数据 manifest]]）+ 索引构建参数入库 |

**统一原则：这六类的任何一类变了，系统就变了——都要走同一条发布流水线（4.2）**。最常见的漏洞是后四类"不算发布"：运营改了 prompt、供应商升了模型、定时任务重建了索引——行为变了，没人知道为什么（[[03_可观测性|Part 3]] 的"L3 恶化 + 无发布记录"就是它的症状）。

**Pin 模型版本的细节**：用带日期/快照号的模型标识而非"最新"别名；供应商宣布弃用旧版本时，升级窗口内做的是一次正式发布（跑门禁、灰度），不是改个配置。**模型升级几乎总是"总体更好、局部退化"**——门禁里必须有你自己业务的回归集，通用能力的提升不保证你那个角落不塌（[[model-adaptation/05_定制的评价与风险|"失去了什么"]]的 API 版）。

## 4.2 发布流水线：门禁 → 灰度 → 观察 → 放量/回滚

```
变更提交（六类之一，带版本号与变更说明）
  → ① 评测门禁（离线）：回归集全量跑，判定门事先写死
  → ② 灰度（在线）：影子流量 或 小比例真实流量
  → ③ 观察窗：L3 代理指标 + 抽样裁判 对比对照组
  → ④ 放量 或 一键回滚
```

- **① 评测门禁**：回归集含冻结锚 + 滚动子集（[[data-foundation-of-ai-systems/04_数据评价与漂移|评测集双层结构]]）；非确定性输出每用例跑多次看通过率（[[textbook-zero-to-agent/09_评测与可靠性工程|pass@k]]）；判定门在变更前写死（防标准向结果妥协，[[model-adaptation/05_定制的评价与风险|同一纪律]]）。**门禁要快**——全量跑数小时的门禁会被绕过（"小改动就不跑了"），维护一个十几分钟的核心子集作为默认门禁、全量集夜间跑。
- **② 灰度的两种形态**：**影子流量**（新版本并行跑真实请求但不返回给用户，对比两版输出）——零用户风险，适合大变更，代价是双倍调用成本；**比例灰度**（少量用户先用新版）——能拿到真实用户信号，适合有影子验证后的放量。高风险变更两个都走。
- **③ 观察窗的长度由流量决定**：要够小流量类目也积累出样本，否则"观察 1 小时全绿"只是主流类目的全绿——长尾类目的回归要几天后才浮出来（[[laws-of-ai-engineering/03_统计与泛化定律#Law 31 — 长尾定律（Long-Tail Law）|长尾]]）。
- **④ 回滚**：六类对象各自的回滚路径都要存在且**演练过**——prompt 回滚是秒级的（换版本号），语料/索引回滚可能要重建（提前留旧索引快照），模型版本回滚受供应商弃用窗口限制（这是提前升级而非拖到最后一刻的理由）。

## 4.3 Prompt 变更的特殊纪律

Prompt 是变更频率最高、评审最松、后果最隐蔽的一类，值得单独立规矩：

- **Prompt diff 走代码评审**，但评审的问题不同：不是"逻辑对不对"，是"这个措辞变化可能影响哪类输入？回归集覆盖那类了吗？"——评审者答不出就先补用例再合入。
- **禁止生产环境直接改 prompt**（等价于生产改代码）。运营/产品的改 prompt 需求走同一条流水线——门禁快（见上）就不会被抱怨阻塞。
- **Prompt 与模型版本是配对测试的**：为旧模型调优的 prompt 在新模型上可能反效果，模型升级时全部 prompt 都要重新过门禁——这是模型升级真正的成本（[[model-adaptation/01_优化阶梯|换代税]]的 prompt 部分）。

## 4.4 反例与边界

- **变更冻结不是稳定**。"系统很稳，别动它"会积累：供应商弃用逼迫的被动升级、安全补丁、语料过时——冻结越久，解冻时的变更包越大、越不可控。**小步高频 + 门禁**比冻结安全（这与传统 SRE 的结论一致，LLM 不豁免）。
- **门禁不拦"正确但不同"**。LLM 变更常产生大量"和旧版不同但都对"的输出，门禁按对错判，不按 diff 判——把"输出变了"当失败会让一切变更都过不了门。需要 diff 审查的场景（如措辞风格约束）单独立 rubric。
- **小系统的流水线可以薄**（L1 级：版本号 + 一个小回归集 + 手动对比），但**"pin 模型版本"和"prompt 入库"两条没有豁免**——它们几乎零成本，而缺失它们的事故无法归因。

## 4.5 验收清单

- ☐ 六类变更对象各自的版本号，在 trace 里都能看到吗（[[03_可观测性|Part 3]] 字段）？
- ☐ 模型是 pin 到具体版本，还是跟着"最新"漂？
- ☐ prompt 在代码库里吗？上一次 prompt 变更有评审记录吗？
- ☐ 默认门禁跑多久？有没有人因为它慢而绕过它？
- ☐ 判定门是变更前写死的吗？
- ☐ 六类对象的回滚路径都演练过吗？语料/索引有旧快照吗？
- ☐ 观察窗覆盖到长尾类目了吗？
- ☐ 最近一次"行为变了但没人知道为什么"，最后归因到哪类变更？那类现在管住了吗？

## Part 4 收束

LLM 系统有六类变更对象（代码/prompt/模型版本/参数/工具/语料），每类都要版本化、走同一条"门禁→灰度→观察→放量/回滚"流水线。Pin 模型版本、prompt 入库是零成本无豁免的底线。门禁要快才不被绕过；判定门事先写死；回滚要演练。变更冻结不是稳定，小步高频才是。

**最该记住的一句**：**你没管理的变更类型，就是你无法归因的事故来源——"系统昨天还好好的"的下一句，永远是"那今天谁动了什么"。**
