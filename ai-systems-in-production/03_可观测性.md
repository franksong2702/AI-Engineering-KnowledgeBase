# Part 3 可观测性：让"200 OK 但内容错了"被看见

> 传统监控回答"跑没跑"，LLM 生产还必须回答"对不对"——这是本书第 2 定律（200 OK ≠ 正确）落地的地方。这一部分给出四层监控模型、trace 的最小字段、和语义层监控的具体做法。

## 3.1 四层监控模型

自下而上，每层回答一个问题，**上三层是 LLM 系统的新增义务**：

| 层 | 回答 | 指标示例 | 传统软件有吗 |
|----|------|---------|------------|
| L1 基础设施 | 跑没跑 | 错误率、四段延迟（[[02_Serving与延迟\|Part 2]]）、吞吐、队列深度 | 有 |
| L2 应用 | 每次调用发生了什么 | trace（见 3.2）、工具调用成功率、重试率、token 用量 | 部分 |
| L3 语义 | 对不对 | 拒答率、引用率、裁判抽检分、护栏触发率、输出长度分布 | **没有** |
| L4 业务 | 有没有用 | 任务完成率、用户改写率/放弃率、人工接管率、投诉率 | 有但常不接 |

**层间的错位是诊断信号**：L1 全绿 + L4 恶化 = 语义层在静默退化（去查 L3 和[[data-foundation-of-ai-systems/04_数据评价与漂移|输入漂移]]）；L3 恶化 + 无发布记录 = 供应商动了模型或数据漂了（[[04_发布与变更管理|Part 4]] 的 pin 版本问题）。

## 3.2 Trace：每次调用的最小字段

一条合格的 LLM trace 要能支撑三件事：**复现**（重放这次调用）、**归因**（表现变化归到哪个变更）、**审计**（出事后回答"影响了哪些输出"）。最小字段：

```
trace_id / 时间戳 / 用户或会话标识（可假名化）
prompt 版本号 · 模型标识与版本 · 采样参数 · RAG 语料版本（若有）
输入（或其哈希+摘要，按隐私分级）· 检索命中列表 · 工具调用链（名称/参数摘要/结果状态/耗时）
输出 · finish_reason · token 用量（输入/输出分开）· 分段延迟 · 成本
护栏/审批触发记录 · 用户反馈信号（若有）
```

三个纪律：**版本字段是归因的命根**——没有 prompt/模型/语料版本号的 trace，出问题时只能猜（[[laws-of-ai-engineering/04_系统与控制定律#Law 36 — 可观测性定律（Observability Law）|可观测性定律]]）；**trace 是 PII 重灾区**——输入输出里全是用户数据，脱敏、访问控制、保留期限直接适用 [[data-foundation-of-ai-systems/05_数据治理与伦理|Data Foundation Part 5]]（"最常见的泄漏点不是数据库，是日志"）；**采样存储平衡成本**——全量存元数据（便宜），输入输出正文按比例采样 + 失败/异常全量存（它们是评测集的原料，见 [[06_故障与降级|Part 6]]）。

## 3.3 语义层监控：三路信号

"对不对"无法像错误率一样直接测量，用三路信号交叉逼近：

**路一 · 廉价的全量代理指标**（每次调用都算，规则即可）：拒答率、引用率（RAG 场景答案带出处的比例）、输出长度分布、schema 合法率、护栏触发率、（Agent 场景）循环轮数分布。**看它们的分布漂移而非绝对值**——拒答率突然翻倍或归零，都说明有东西变了。这是 [[data-foundation-of-ai-systems/04_数据评价与漂移|Data Foundation]] 漂移监控方法论对输出侧的复用：固定基线 + 滑动窗口，双级告警（关注/行动），阈值用自然波动校准。
- 特别有用的一个：**置信度/不确定表达的频率**。模型"我不确定"的说法骤减，可能是变得更好，也可能是变得更自信地错——触发抽检。

**路二 · 抽样的裁判评分**（在线 LLM-as-Judge）：对生产输出按比例抽样送裁判打分（成本决定比例，高风险类提高）。全部纪律沿用 [[human-ai-collaboration-foundation/08_AI_Supervisor设计|AI Supervisor 设计]]：裁判要被人类校准、抽样要含"看起来正常"的自动通过区、防裁判被适应。
- **在线裁判与离线评测集的分工**：评测集回答"这个版本好不好"（发布前，[[04_发布与变更管理|Part 4]]），在线裁判回答"生产此刻正不正常"（发布后）。两者共享 rubric，不共享样本。

**路三 · 用户行为信号**（免费但滞后）：改写率（用户重新措辞再问=第一次没答好）、放弃率、人工接管率、点踩。它们是 L4 与 L3 的桥，**是最诚实的信号但有偏**——沉默的不满不产生信号（[[laws-of-ai-engineering/03_统计与泛化定律#Law 32 — 抽样偏差定律（Sampling-Bias Law）|抽样偏差]]），所以不能只靠它。

## 3.4 反例与边界

- **监控一切 = 什么都看不见**。指标数量与告警疲劳成正比（[[data-foundation-of-ai-systems/04_数据评价与漂移|告警疲劳]]）。每层选 3-5 个"值班的人半夜愿意为它起床"的指标进告警，其余进周报仪表盘。
- **语义监控不能替代发布门禁**。在线监控是事后发现（伤害已发生一部分），评测门禁是事前拦截——两者是串联防线，砍掉门禁只靠监控等于拿用户当测试集（[[ai-engineering-anti-patterns/00_INDEX|无评测上线]]的变体）。
- **代理指标会被古德哈特**。把"引用率"设成团队 KPI，就会得到"每句话都堆引用"的系统——代理指标用于**告警**（变化=去看看），不用于**考核**（[[laws-of-ai-engineering/03_统计与泛化定律#Law 24 — 古德哈特定律（Goodhart's Law）|古德哈特]]）。
- **L1 便宜不等于 L1 优先**。资源有限时，一个 L2 系统最先建的其实是"带版本字段的 trace + 两三个 L3 代理指标"——基础设施指标云厂商基本白送，别把预算全花在最不缺的地方。

## 3.5 验收清单

- ☐ 四层各有指标吗？L3 是空的吗（最常见的洞）？
- ☐ 随机抽一条 trace：能复现这次调用吗？能说出它用的 prompt/模型/语料版本吗？
- ☐ trace 的输入输出做过隐私分级和脱敏吗？保留期限定了吗？
- ☐ 代理指标有基线和双级告警吗？阈值是校准的还是拍的？
- ☐ 在线裁判的抽样覆盖自动通过区吗？裁判上次被人类校准是什么时候？
- ☐ 进告警的指标有几个？值班的人真的会为每一个起床吗？
- ☐ "L1 全绿 + L4 恶化"这种错位，有人会看吗？

## Part 3 收束

LLM 生产监控是四层：基础设施（跑没跑）、应用（发生了什么）、语义（对不对）、业务（有没有用）——语义层是新增义务，用全量代理指标 + 抽样裁判 + 用户行为三路信号交叉逼近。trace 的版本字段是归因命根，也是 PII 重灾区。指标进告警要克制，代理指标用于告警不用于考核。

**最该记住的一句**：**没有语义层监控的 LLM 系统，它的质量事故没有报警器——你的用户就是报警器，而他们报警的方式是离开。**
