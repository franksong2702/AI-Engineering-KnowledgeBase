# Part 2 Serving 与延迟：让它跑得动、跑得稳、跑得快

> 推理服务是 LLM 系统的引擎舱。这一部分讲延迟的解剖、容量与背压、以及 serving 层的三大杠杆（缓存/路由/流式）。模型本体的部署取舍（自部署 TCO、量化、蒸馏）在 [[model-adaptation/04_蒸馏与部署|Model Adaptation Part 4]]，本部分管系统层。

## 2.1 延迟的解剖：先拆开再优化

LLM 请求的延迟不是一个数，是四段之和，各段的优化手段完全不同：

```
总延迟 = 排队等待 + 预处理(检索/工具/上下文组装) + 首 token 时间(TTFT) + 生成时长(token数 ÷ 生成速率)
```

- **排队等待**——容量问题（见 2.2），加模型没用。
- **预处理**——RAG 检索、工具调用、上下文组装。**常被忽略但常是大头**：一次带检索+rerank+多工具的请求，预处理可能比生成还久。优化：并行化独立的检索/工具调用、缓存检索结果。
- **TTFT（首 token 时间）**——用户"感觉快不快"的主宰。输入越长 TTFT 越高——**上下文膨胀直接变成延迟**（与 [[05_成本工程|Part 5]] 的同一根源：token 既是钱也是时间）。
- **生成时长**——输出长度 × 生成速率。约束输出长度（schema、字数上限）是最便宜的生成提速。

**体感公式**：流式输出下，用户体感 ≈ TTFT + max(0, 生成速率是否跟得上阅读速度)。生成速率一旦超过阅读速度，继续优化它对体感无益——把预算挪去砍 TTFT。**先测四段各占多少，再决定优化哪段**（[[laws-of-ai-engineering/04_系统与控制定律#Law 33 — 瓶颈定律（Bottleneck Law）|瓶颈]]——优化非瓶颈是浪费）。

## 2.2 容量、并发与背压

- **LLM 的延迟方差天然大**：输出长度不定 + 上游负载波动，P99 常是 P50 的好几倍（经验量级）。**SLA 按分位数定（P95 X 秒），绝不按平均**。
- **背压设计**：上游限流（429）不能裸抛给用户。标准链条：请求进队列 → 队列深度有上限（超限快速拒绝，好过无限排队）→ 消费端按上游配额节流 → 429 指数退避重试（幂等前提，[[laws-of-ai-engineering/08_可靠性与失败定律#Law 77 — 恢复优于预防定律（Recovery-Over-Prevention Law）|恢复优于预防]]）。**队列深度是必监控指标**——它是容量事故的最早信号（先于延迟恶化）。
- **超时的分段设计**：只设一个"总超时"会误杀正常的长输出。分段设：预处理超时、TTFT 超时（最灵敏的上游健康信号——TTFT 超时基本等于上游出事了）、空闲超时（流式中断多久算死）。TTFT 超时触发的重试收益最高，因为它发生在花钱生成之前。
- **峰值容量**：自部署按峰值配卡的成本账见 [[model-adaptation/04_蒸馏与部署|TCO 清单]]；API 侧的对应物是**配额管理**——峰值流量逼近供应商配额时，提前谈配额或做多账户/多供应商分流，别等 429 风暴。

## 2.3 Serving 层三杠杆

**杠杆一 · 缓存（先拉，ROI 最高）**，三层各有边界：
- **精确缓存**：同 key 同答案。命中率取决于请求重复度；对含时间/个性化上下文的请求要把可变部分排除出 key，否则命中率归零。
- **前缀缓存**：system prompt / few-shot / 文档等公共前缀只算一次。**上下文组装顺序决定它的效果**——稳定内容放前、可变内容放后，一次重排序常常就是显著的成本与 TTFT 双降（这是"上下文工程"与"成本工程"的交点）。
- **语义缓存**（相似问题返回缓存答案）：命中率更高，但有**返回错误答案的真实风险**——"相似"不等于"同问"（[[llm-design-patterns/00_INDEX|语义相似≠相关]]的缓存版）。边界：只用于容错高的场景（FAQ 类），带相似度高阈值，且缓存答案要标注可溯源（出问题能定位到"这是缓存的锅"）。

**杠杆二 · 模型路由**：简单流量走小/快模型，难流量走大模型（[[llm-design-patterns/00_INDEX|Routing]] 的成本/延迟版）。两个纪律：路由器自己要便宜（用规则或小分类器，别用大模型来省大模型）；**路由错误率要监控**——难题被误发给小模型是质量事故，不是成本节约。
- **快慢分离**是路由的架构版：交互路径（用户在等）用快配置，后台路径（批量、离线）用慢而便宜的配置（批处理 API 半价一类）。同一个任务在两条路径上可以是两套模型/参数。

**杠杆三 · 流式**：改善体感（TTFT 主导）不改善成本。工程细节：流式中途失败的处理比整包难（已经给用户看了半个答案）——要么支持"续写"，要么显式标注"回答中断"，绝不静默截断装完整（[[laws-of-ai-engineering/08_可靠性与失败定律#Law 76 — 静默降级危险定律（Silent-Degradation-Danger Law）|静默降级]]的流式版）。下游是程序时（结构化输出）通常不流式——半个 JSON 没有意义。

## 2.4 反例与边界

- **过早优化延迟**。先问用户是否真的在乎：后台批处理任务的延迟优化是零价值；交互任务里，从 12s 到 6s 价值巨大、从 3s 到 2.5s 用户可能无感。**延迟优化预算应该由用户研究（或流失数据）分配，不由工程师的不适感分配。**
- **为延迟牺牲质量的暗账**。砍上下文、换小模型、限输出长度都会动质量——延迟优化必须带着评测门禁做（[[04_发布与变更管理|Part 4]]），否则是在做一次没有评审的质量变更。
- **语义缓存在个性化场景是错的**。两个用户问同一句话，正确答案可能不同（权限、上下文、历史）——个性化场景禁用语义缓存，或 key 里纳入用户维度（命中率会掉到不值得）。

## 2.5 验收清单

- ☐ 四段延迟各占多少，测过吗？优化的是瓶颈段吗？
- ☐ SLA 是按 P95/P99 定的吗？
- ☐ 队列深度在监控里吗？队列有上限和快速拒绝吗？
- ☐ 超时是分段的吗？TTFT 超时接了重试/告警吗？
- ☐ 上下文组装把稳定内容排在前面了吗（前缀缓存生效了吗）？
- ☐ 语义缓存只用在容错高、无个性化的场景吗？
- ☐ 路由错误率（难题进小模型）有监控吗？
- ☐ 流式中断是显式标注还是静默截断？

## Part 2 收束

延迟是四段之和（排队/预处理/TTFT/生成），先拆解再优化瓶颈段；体感由 TTFT 和"生成速率 vs 阅读速度"主宰。容量靠队列+背压+分段超时，SLA 按分位数。三杠杆按 ROI：缓存（注意语义缓存的错答风险）> 路由（监控路由错误）> 流式（体感不省钱）。一切延迟优化都是质量变更，要过门禁。

**最该记住的一句**：**token 既是钱也是时间——上下文膨胀同时推高账单和 TTFT，管住上下文是 serving 层性价比最高的一件事。**
