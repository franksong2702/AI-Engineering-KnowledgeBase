# Part 3 多智能体系统评价

> 多 Agent 系统不是"多个单 Agent 的加和"——它引入了协作、通信、协调、涌现这些单体不存在的维度。评价它，既要评每个 Agent（Part 2），更要评它们**之间**的东西。而最重要的评价问题往往是元层的：**这个系统真的需要多个 Agent 吗？**（[[multi-agent-patterns-handbook/00_INDEX|Multi-Agent 手册]]的核心焦虑）

---

## 3.1 协作质量 Collaboration Quality

**定义**：多个 Agent 共同产出的结果，相对于它们单独产出的加和，好了多少——协作的净增值。

**为什么重要**：多 Agent 存在的唯一正当理由就是协作产生了 1+1>2 的价值。如果协作没有净增值，多 Agent 就是纯开销（[[03_多Agent评价|见 3.9 的元问题]]）。

**如何测试**：**基线对照是唯一严肃的方法**——同一任务用单 Agent 和多 Agent 各跑，对比质量。没有单 Agent 基线的多 Agent 评价是无意义的（你无法证明"多"带来了什么）。

**常见失败**：协作产生负增值（互相干扰、噪声传染）却无人察觉（因为没测基线）；伪协作（Agent 各干各的，只是被拼在一起）；协作的收益其实来自其中一个 Agent，其他是拖累。

**评价指标**：协作增值 =（多 Agent 质量 − 最优单 Agent 质量）；各 Agent 的边际贡献；协作产出的一致性。

**改进方法**：先确认协作真有增值再上多 Agent；砍掉边际贡献为负的 Agent；真正的收益多来自[[multi-agent-patterns-handbook/00_INDEX|上下文隔离]]而非"分工"，据此设计。

---

## 3.2 通信效率 Communication Efficiency

**定义**：Agent 间传递信息的信噪比和成本——传递了多少有用信息，消耗了多少 token 和轮次。

**为什么重要**：通信是多 Agent 的主要开销来源，且通信质量差会导致噪声跨 Agent 传染（[[multi-agent-patterns-handbook/00_INDEX|Multi-Agent 定律 3：传结论不传对话]]）。

**如何测试**：测量 Agent 间传递的信息量 vs 有用信息量（信噪比）；测传递的是结构化结论还是原始对话（后者是 token 爆炸源）；测信息在传递中的损失率。

**常见失败**：传递完整对话历史导致 token 指数增长；噪声跨 Agent 传染；关键信息在传递中丢失（[[01_信息与压缩定律#Law 6 — 压缩必然丢失定律（Compression-Loses Law）|压缩必然丢失]]）；过度通信（每步都同步）。

**评价指标**：通信信噪比、每次交互的 token 成本、信息传递的无损率、通信轮次占总轮次的比例。

**改进方法**：传结构化结论 + 证据 + 置信度，不传原始过程；任务描述自包含（对方无你的上下文）；减少不必要的同步点。

---

## 3.3 协调成本 Coordination Cost

**定义**：为了让多个 Agent 协同工作而消耗的、不直接产生价值的开销——拆解、分派、汇报、验收、冲突解决的 token 和延迟。

**为什么重要**：协调成本是多 Agent 的"税"，随 Agent 数量[[06_经济与资源定律|超线性增长]]（[[06_层级Hierarchical|层级的官僚化]]）。协调成本超过分工收益时，多 Agent 就是净亏损。

**如何测试**：分离"协调 token"和"干活 token"——多少资源花在协调上 vs 真正的任务上。测协调成本随 Agent 数量的增长曲线。

**常见失败**：协调开销超过干活开销（管理成本压倒生产）；随 Agent 增多协调成本爆炸；层层汇报的[[06_层级Hierarchical|传话失真]]。

**评价指标**：协调成本占总成本比例、协调成本随 Agent 数的增长斜率、有效工作 token 占比。

**改进方法**：控制 Agent 数量（[[06_经济与资源定律|规模不经济]]拐点）；扁平化（裁撤只转发不增值的中层）；用确定性代码做协调而非 Agent 自主协调。

## 3.4 角色分配 Role Assignment

**定义**：任务是否被分配给了最合适的 Agent，以及角色划分是否合理（不重叠、不遗漏、边界清晰）。

**为什么重要**：角色划分不当导致重复劳动、遗漏、或[[04_系统与控制定律#Law 39 — 康威定律（Conway's Law）|康威定律]]式的错误结构。好的角色划分基于能力/上下文/工具边界，而非拟人的职位。

**如何测试**：检查角色是否[[01_问题定义型|MECE]]（不重叠不遗漏）；检查任务是否分给了相对最擅长的 Agent（[[06_经济与资源定律#Law 53 — 比较优势定律（Comparative-Advantage Law）|比较优势]]）；检查角色划分是按上下文边界还是按拟人职位。

**常见失败**：角色重叠（重复劳动）；角色遗漏（没人负责某部分）；按拟人职位分（CEO Agent/员工 Agent）而非上下文边界（[[multi-agent-patterns-handbook/00_INDEX#五条跨模式定律|Multi-Agent 定律 1：上下文隔离]]）；角色边界模糊。

**评价指标**：角色覆盖的完整性（无遗漏）、重叠度（无重复）、任务-Agent 匹配度、角色边界的清晰度。

**改进方法**：按上下文隔离和工具边界分角色，不按头衔；用 MECE 检验划分；砍掉职责重叠的 Agent。

---

## 3.5 涌现行为 Emergent Behavior

**定义**：系统整体表现出的、无法从单个 Agent 预测的行为——既包括意外的能力，也包括意外的失败。

**为什么重要**：多 Agent 是[[11_演化与元定律|复杂系统]]，会涌现出没设计的行为（[[14_群体Swarm|Swarm 的不可控性]]）。不监控涌现，就会被意外的集体行为（互相恭维的循环、失控的成本、集体幻觉）反噬。

**如何测试**：**不能只测设计的行为，必须监控没预期的**——运行系统观察是否出现无法从部件推出的整体行为。用分布式 trace 看整体动态。长时间运行观察涌现的稳定性。

**常见失败**：假设系统行为完全由各 Agent 设计决定（还原论错误）；不监控涌现被意外行为反噬；涌现的负面行为（成本失控、循环、集体盲区）无人察觉。

**评价指标**：涌现行为的可预测性、意外行为的发生率、涌现行为的影响（正/负）、系统整体行为的稳定性。

**改进方法**：把涌现监控纳入评价（不只测设计的行为）；分布式 trace 观察整体动态；为涌现的负面行为设[[04_系统与控制定律|护栏]]；从[[multi-agent-patterns-handbook/00_INDEX|中心化]]开始（涌现更可控）再谨慎放开。

## 3.6 冲突解决 Conflict Resolution

**定义**：当 Agent 之间产生分歧（不同结论、竞争资源、矛盾判断）时，系统解决冲突的机制和质量。

**为什么重要**：多视角必然产生冲突，冲突处理不当会导致僵局、和稀泥、或错误的一方压倒正确的一方。好的冲突解决保留有价值的分歧（[[11_委员会Committee|委员会]]）。

**如何测试**：制造 Agent 间的分歧，看系统如何解决——是有原则地裁决，还是随机/和稀泥/先发者胜；测它能否区分"事实分歧"（可查证）和"价值权衡"（需呈现）；测正确的少数派意见是否被保留。

**常见失败**：和稀泥（平均掉分歧，抹杀正确的少数派）；先发者/权威者胜（非基于论据）；僵局（无法解决而卡死）；[[04_质量控制模式|从众级联]]（一个 Agent 的意见污染其他）。

**评价指标**：冲突解决的正确率（是否选对了）、少数派正确意见的保留率、冲突解决的效率（不僵局）、裁决是否基于论据而非权威/顺序。

**改进方法**：独立意见先行（防从众）；区分事实分歧（查证）和价值权衡（呈现）；用[[11_委员会Committee|辩论/裁判]]机制而非简单投票；保留而非抹杀少数派。

---

## 3.7 共识质量 Consensus Quality

**定义**：当系统需要多个 Agent 达成一致时，这个"一致"是真正的高质量共识，还是虚假的趋同。

**为什么重要**：共识本身不是目的——**高质量的分歧胜过低质量的共识**。系统若为了"达成一致"而牺牲正确性（[[03_多Agent评价|共识成瘾]]，Part 7 的反模式），就本末倒置了。

**如何测试**：测共识是基于论据的真趋同，还是[[04_质量控制模式|从众]]导致的伪趋同；测达成共识时是否碾压了正确的少数意见；**测系统是否知道"何时不该达成共识"**（有些问题就该保留分歧）。

**常见失败**：共识成瘾（为一致而一致，牺牲正确性）；伪共识（同源 Agent 的从众，非独立趋同）；碾压正确的少数派；把"快速达成一致"当成质量信号。

**评价指标**：共识的正确率、共识形成中的独立性（防从众）、少数派正确意见的存活率、"恰当地不达成共识"的识别率。

**改进方法**：独立意见先行再审议（防从众级联）；用真差异化的 Agent（不同模型/知识，破[[multi-agent-patterns-handbook/00_INDEX|伪多样]]）；重视论据质量而非趋同速度；允许"保留分歧"作为合法结果。

## 3.8 失败传播 Failure Propagation

**定义**：一个 Agent 的失败如何影响整个系统——是被隔离在局部，还是级联放大、静默传染。

**为什么重要**：多 Agent 的最危险失败模式是[[08_可靠性与失败定律#Law 76 — 静默降级危险定律（Silent-Degradation-Danger Law）|静默失败向上传染]]——一个 Agent 编了个结果，其他 Agent 当真，错误沿协作链放大。失败隔离决定系统的鲁棒性。

**如何测试**：注入单个 Agent 的失败，观察[[08_可靠性与失败定律#Law 72 — 爆炸半径定律（Blast-Radius Law）|爆炸半径]]；测系统能否检测到某个 Agent 的失败（还是照单全收）；测部分失败时系统是[[04_系统与控制定律#Law 42 — 优雅降级定律（Graceful-Degradation Law）|优雅降级]]还是全线崩。

**常见失败**：静默失败向上传染（下游把上游的错误结论当真）；单点失败拖垮全局（[[04_系统与控制定律#Law 37 — 单点故障定律（Single-Point-of-Failure Law）|单点故障]]）；无失败检测（Agent 编的结果被全盘接受）；错误级联放大。

**评价指标**：单 Agent 失败的爆炸半径、失败检测率（能否发现某 Agent 出错）、部分失败下的系统存活率、错误传播的衰减/放大系数。

**改进方法**：Agent 回传结论附[[multi-agent-patterns-handbook/00_INDEX|置信度和依据]]，上游抽查；失败隔离（一个坏了不拖垮全部）；[[08_可靠性与失败定律#Law 71 — 显式失败定律（Fail-Loudly Law）|显式失败]]替代静默；协调者对子 Agent 结论做核查而非照单全收。

## 3.9 元问题：何时多 Agent 优于单 Agent，何时是过度设计

这是整个 Part 3 最重要的问题，也是评价一个多 Agent 系统时**首先该问**的——因为如果答案是"这本该用单 Agent"，那么再好的协作评价都是在评价一个不该存在的系统。

**多 Agent 真正优于单 Agent 的三种情况**（[[multi-agent-patterns-handbook/00_INDEX|Multi-Agent 手册的正当理由]]）：

其一，**上下文隔离**——任务需要多个各自干净聚焦的上下文，一个 Agent 的上下文会被不同子任务互相污染。这是最常见的真实收益。

其二，**真并行**——子任务真正独立可同时执行，多 Agent 换取墙钟时间。

其三，**权限/角色隔离**——不同部分需要不同的凭证、工具集、信任级别，安全上必须隔离。

**多 Agent 是过度设计的信号**：把单 Agent 调不好的问题拆成多个（现在你有多个调不好的 Agent 加通信问题）；为了"看起来高级"而多 Agent；按拟人职位而非上下文边界拆分；协调成本超过分工收益；砍掉任何一个 Agent 系统都不会变差（说明它没在贡献）。

**评价的判据**：对任何多 Agent 系统，问一个残酷的问题——**"如果把它压成一个设计良好的单 Agent，会更差吗？"** 如果答不出多 Agent 具体好在哪（且能用基线对照证明），那它就是过度设计。**多 Agent 的默认判决应该是"有罪推定"——它必须证明自己的存在合理，而非被假设合理。** 这与整套体系的[[04_最值得记忆的设计原则|简单优先]]原则一致：能用单 Agent 就不用多 Agent，正如能用工作流就不用 Agent。

## Part 3 收束

多 Agent 评价的八个维度（协作、通信、协调、角色、涌现、冲突、共识、失败传播）都服务于一个元判断：**这个系统的"多"是否被它的收益证明了。**

一个残酷但必要的事实：**大多数多 Agent 系统本该是更好的单 Agent。** 所以评价多 Agent 的第一动作不是打分，是质疑它存在的必要性——用单 Agent 基线对照。通过了这一关（证明"多"确有增值），再用八个维度评价它协作得好不好。跳过第一关直接评协作，是在精心评价一个不该存在的系统。

（本 Part 与 [[multi-agent-patterns-handbook/00_INDEX|《Multi-Agent 架构手册》]]互为表里：那本讲怎么设计多 Agent，这本讲怎么判断它设计得好不好、以及是否本该存在。）
