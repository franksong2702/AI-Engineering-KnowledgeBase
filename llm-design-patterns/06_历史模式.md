# 历史模式：被模型能力吸收的提示技巧

> 本页收录经 [[_governance/reevaluation/REEVALUATION_2026_Q4|2026-Q4 季度重估]] 裁决退役的模式。**原文完整保留，不删、不改**，只在每节前加退役说明。
>
> 退役不等于"错了"：这些模式在它们的年代是有效的工程手段，后来被推理模型内化成了默认能力。它们留在这里，是 [[foundation-of-ai-engineering/02_必将被淘汰的方法|Foundation 第 2 章]]"拐杖 vs 腿"的活样本——读它们的价值，是看清**哪类方法会被能力进步吸收，哪类不会**。
>
> 退役判据（季度协议四问）：如果模型推理能力强 100 倍，这个模式**作为独立的提示技巧**还有必要吗？三个模式的答案都是"没有"，但它们背后的思想以其他形式保留了下来，见各节的"去向"。

> [!note] 退役说明 · Tree Search / ToT（2026-10-07）
> **退役的是**：在提示层让 LLM 自己生成候选、自己打分、自己回溯的 ToT。推理模型已经在内部完成了这类探索，生产中很少再显式编排。
> **保留的是**：**带外部验证器的搜索**（程序搜索、以可执行测试为评估器）。评估器客观、廉价时，"多候选 + 验证 + 选优"依然有效，见 [[llm-design-patterns/01_推理模式|家族一 · Self-Consistency]] 的"未来方向"。
> **不要混淆**：Multi-Agent 手册的 [[multi-agent-patterns-handbook/03_树状分解Tree|树状分解]] 是任务分解拓扑，不受本次退役影响。

## H1. Tree Search / Tree-of-Thoughts（思维树与树搜索）

**为什么存在**：CoT 是单条线性推理，一步走错就到底。Tree-of-Thoughts 让模型在每步生成多个候选"想法"，形成树，通过评估和搜索（BFS/DFS/回溯）探索多条路径、剪掉差的、深入好的。它把"线性推理"升级为"带回溯的搜索"，为需要探索和试错的难题而生。

**什么时候使用**：解空间大、需要探索多条路径的难题（复杂规划、谜题、创意组合、需要回溯的推理）；一步错则满盘皆输、需要中途纠偏的任务；单条 CoT 和 Self-Consistency 都撑不住的高难度问题。

**什么时候不要使用**：绝大多数日常任务（成本高得离谱，5-30× 起步）；线性推理已够的问题；缺乏可靠的"中间状态评估"方法时（树搜索的灵魂是评估每个节点好坏，评不准则搜索失效）；实时场景。

**架构图**：
```
              问题
             /  |  \
        想法A  想法B  想法C      ← 每步生成多个候选
        /\      |评估:剪枝       ← 评估器打分,剪掉差的
     A1  A2    B1
     |评估      |
    (死路)   最优路径 → 解        ← DFS/BFS + 回溯搜索
```

**Prompt**（两个角色：生成器 + 评估器）：
```
[生成器] 针对当前状态 {state}，生成 3 个不同的下一步想法，各自独立可行。
[评估器] 评估以下想法通向最终解的希望：{想法}
输出 {"score": 0-1, "reason": "...", "verdict": "sure|maybe|impossible"}
（impossible 的分支被剪枝，sure/maybe 继续展开）
```

**Workflow**：
```
初始化根节点 → while 未达解 and 预算未尽:
  选择待展开节点(按评估分) → 生成 k 个子想法 → 评估每个
  → 剪掉 impossible → 把 promising 加入前沿 → 可回溯
终止：找到满足解 / 预算耗尽 / 前沿为空
```

**Agent**：可作为 Agent 处理高难度子问题的"深思模块"（大部分步骤用 ReAct，遇到硬骨头切换 ToT 深搜）。与 [[03_树状分解Tree|Multi-Agent 树状分解]] 的区别：那个是把不同任务分给不同 Agent，这个是单一问题的解路径搜索。

**优点**：能解 CoT 解不了的难题，提供推理的"探索+回溯"能力；中途可纠偏，不会一条路走到黑；评估器让搜索有方向，比盲目采样高效。

**缺点**：成本极高（生成×评估×多节点×多层）；严重依赖评估器质量，评估不准则南辕北辙；实现复杂；绝大多数任务用不上，容易过度工程。

**案例**：解一个需要多步且易走死路的规划谜题（如 24 点、复杂日程排布）。CoT 单路径经常卡死；ToT 在每步生成几个候选走法、评估器剪掉明显死路、DFS 深入有希望的分支并在碰壁时回溯，最终找到解。代价是几十倍于 CoT 的调用量——只在这类高难度、高价值问题上才划算。

**未来方向**：更便宜的评估（用小模型或学习到的价值函数替代 LLM 评估每个节点）；与推理模型结合（推理模型内部可能已隐式做类似搜索）；蒙特卡洛树搜索（MCTS）等经典搜索算法与 LLM 的深度融合；自适应决定"这题值不值得上树搜索"。

## H2. Least-to-Most（由易到难分解）

**为什么存在**：有些问题直接解太难，但拆成"由简到繁的子问题序列"后，每个子问题都不难，且后面的可以用前面的答案。Least-to-Most 先让模型把问题分解为递进的子问题，再依次求解，前面的解喂给后面。它介于 CoT 和 [[03_树状分解Tree|树状分解]] 之间，专治"需要先解决简单情形才能解决复杂情形"的任务。

**什么时候使用**：问题有清晰的"由易到难"递进结构（数学归纳式、组合问题、需要先建立子结论的推理）；直接 CoT 会因跨度太大而出错，但分步可解时；泛化要求高（用小例子的解法推广到大例子）。

**什么时候不要使用**：问题无自然递进结构（强行分解反而混乱）；子问题相互独立无依赖（用 [[02_MapReduce|MapReduce]] 并行更好）；简单问题（分解是过度设计）。

**架构图**：
```
复杂问题 → [分解] → 子问题1(最简) → 子问题2 → … → 子问题N(=原问题)
                        ↓解         ↓解(用上一步)      ↓解
                       解1 ────────→ 解2 ──────────→ 最终解
                    (解逐步累积,后者依赖前者)
```

**Prompt**：
```
阶段1(分解)：把问题分解为一系列由简到难、后者依赖前者的子问题。
问题：{问题}
输出子问题列表(从最基础到最终)。
阶段2(依次求解)：已知前面子问题的解 {已解},现在解决下一个子问题:{子问题}。
```

**Workflow**：
```
问题 → [分解调用] 得到有序子问题序列
     → for 每个子问题(按序): 带着已有解求解 → 累积
     → 最后一个子问题的解 = 原问题的解
```

**Agent**：适合 Agent 处理"需要建立中间结论才能推进"的任务，作为 Planner 的一种分解策略（当子任务有强顺序依赖时优于并行拆解）。

**优点**：把大跨度推理拆成小步，降低单步难度、提升准确率；显式利用子问题间的依赖（后者复用前者）；泛化能力强（小例子解法推广到大例子）。

**缺点**：依赖分解质量，分解错则全错；串行执行、无并行红利；对无递进结构的问题不适用；比单次 CoT 成本高。

**案例**：解"某表达式在嵌套括号下的求值"或"最后一个字母拼接"类任务，直接算易错。Least-to-Most 先分解为"先处理最内层→再外一层→…"，每步只处理一层、复用上一层结果，逐步逼近答案。这种"先易后难、逐步累积"显著优于让模型一口气算完。

**未来方向**：自动判断问题是否适合 Least-to-Most（vs 并行分解 vs 直接 CoT）的元推理；与 ReAct 结合（每个子问题可调工具）；分解质量的自我验证（解完回头检查分解是否合理）。

## H3. Step-back（退一步）

**为什么存在**：模型直接冲向具体问题时容易钻进细节、忽略适用的一般原理。Step-back 先让模型"退一步"抽象出背后的一般性问题或原理，再用它指导具体求解；Rephrase 则让模型先用自己的话重述问题，澄清歧义。二者都是"先对齐问题理解，再求解"的元提示技巧。

**什么时候使用**：具体问题背后有可复用的一般原理（物理题先想定律、具体决策先想通用框架）时；问题表述含糊、易被误解时；模型容易钻进细节而忽略大局时；需要提升推理稳健性时。

**什么时候不要使用**：简单直接的问题（退一步是绕远）；抽象化对该任务无帮助（纯事实查询）；成本/延迟敏感（多一次抽象调用）；问题已足够清晰无需重述时。

**架构图**：
```
具体问题 →[Step-back: 这背后的一般性问题/原理是什么?]→ 一般原理
                                                        ↓
              [用一般原理指导] ←──────────────────────┘
                     ↓
              具体问题的解
```

**Prompt**：
```
[Step-back] 在解决这个具体问题前，先退一步：
这个问题背后涉及的一般性原理/概念是什么？
问题：{具体问题}
先陈述相关的一般原理，再用它来解决具体问题。

[Rephrase 变体] 先用你自己的话重述这个问题，澄清任何歧义，
确认你的理解后再作答。
```

**Workflow**：
```
问题 →[抽象/重述调用]→ 一般原理 or 澄清后的问题
     →[求解调用: 带着原理/澄清求解]→ 答案
可合并为单次(先抽象再求解)或两次调用
```

**Agent**：Agent 接到模糊任务时，先 Rephrase 确认理解（甚至向用户回问）能大幅减少"跑偏做错"；Step-back 帮 Agent 在复杂任务前先建立正确的框架再行动。

**优点**：提升推理稳健性（先建立正确框架再求解）；减少因误解问题导致的错误；抽象出的原理可复用于同类问题；实现简单。

**缺点**：增加一次调用的成本延迟；对简单问题是绕远；抽象本身可能抽错方向；收益不如 CoT 稳定普适。

**案例**：问"某物体从 80 米高度自由下落几秒着地"。直接算易错或漏条件；Step-back 先抽象"这是自由落体问题，适用 h=½gt²"，再代入求解，稳健性明显提升。又如模糊需求"帮我优化这个"，Rephrase 先重述"你是想优化性能、可读性还是成本？我理解你主要关心 X"，避免优化错方向。

**未来方向**：自适应触发（模型自己判断"这题需不需要先退一步"）；与 [[01_推理模式|第一性原理]]式抽象结合；作为推理模型内部机制的一部分被内化；多层 step-back（层层抽象直到找到最有用的原理层）。
