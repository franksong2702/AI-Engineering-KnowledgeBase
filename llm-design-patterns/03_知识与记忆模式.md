# 家族三 知识与记忆模式：如何给模型它没有的东西

> 模型的知识冻结在训练时刻、局限于公开数据、且对话结束即遗忘。这一族解决三个缺口：不知道的（RAG 喂知识）、做不到的（工具扩展能力）、记不住的（记忆机制）。共同本质：**在推理时把外部世界按需接入上下文**。

> 关联 Laws：[[laws-of-ai-engineering/01_信息与压缩定律#Law 4 — 信息守恒定律（No-Information-From-Nothing Law）|Law 4：信息守恒定律]]说明模型不会凭空获得事实，[[laws-of-ai-engineering/01_信息与压缩定律#Law 5 — 检索优于记忆定律（Retrieval-Over-Memorization Law）|Law 5：检索优于记忆定律]]说明为什么知识应外置，[[laws-of-ai-engineering/01_信息与压缩定律#Law 6 — 压缩必然丢失定律（Compression-Loses Law）|Law 6：压缩必然丢失定律]]提醒记忆摘要和上下文压缩必须验收。

## 1. RAG（检索增强生成）

**为什么存在**：模型知识过时、不含私有数据、且会对不知道的东西编造。RAG 在生成前先从外部知识库检索相关材料，拼进上下文再回答——用"检索到的事实"锚定生成，把幻觉从"凭空编造"降级为"基于材料综合"。详见 [[06_RAG与个人知识库|教材第 6 章]]。

**什么时候使用**：需要基于私有/专有/实时知识回答（企业文档、个人笔记、最新信息）；知识量远超上下文窗口、需按需取用时；要求答案可溯源、带引用时；降低幻觉、提升事实准确性。

**什么时候不要使用**：知识量小于上下文窗口一半时（直接全塞更简单，长上下文吃掉了一批 RAG 场景）；需要全局统计/汇总的问题（RAG 只见检索到的片段，见树不见林）；纯推理/创意任务（无外部知识需求）；检索质量无法保证时（检索错则全错）。

**架构图**：
```
文档库 →[切分→embedding→向量库]  (离线建库)
                                  
查询 →[检索 top-k 相关块]→ 相关材料 ┐
查询 ──────────────────────────────┴→[LLM: 基于材料作答]→ 带引用的回答
```

**Prompt**：
```
基于且仅基于以下资料回答，每个论断标注来源编号：
资料：{检索到的块}
问题：{查询}
规则：资料不足以回答时，明确说"资料中无相关信息"，不要编造。
```

**Workflow**：
```
离线：文档 → 切分(300-800token,语义边界) → embedding → 存向量库
在线：查询 → (混合检索:向量+关键词) → rerank → top-k → 拼prompt → 生成 → 带引用输出
评测：检索命中率 + 忠实度 + 拒答率
```

**Agent**：RAG 是 Agent 的知识后端，常作为一个"检索工具"供 ReAct 调用；Agent 可多轮检索（据初步结果决定再查什么），比一次性检索更强。

**优点**：注入私有/实时知识，突破训练边界；降低幻觉、答案可溯源；知识更新只需更新库、无需重训模型；成本远低于微调。

**缺点**：质量上限在检索（检索不到=答不对；经验上多数 RAG 问题出在检索环节，先看检索日志）；切分/embedding/rerank 每环都是坑；全局性问题不擅长；增加延迟和系统复杂度。

**案例**：企业内部问答，问"我们的报销政策上限是多少"。模型本身不知道，RAG 检索到报销制度文档的相关条款，基于它回答并附上出处。政策更新时只需更新文档库，无需任何模型改动。关键工程点是检索要能命中正确条款（混合检索 + rerank）。

**未来方向**：长上下文与 RAG 的边界持续移动（部分场景被"全塞"取代，但海量/实时知识仍需 RAG）；Agentic RAG（模型自主决定查什么、查几次、够不够）；GraphRAG（引入知识图谱解决全局关联问题）；contextual retrieval（给块附上下文降低孤儿块问题）成为标配。

> [!note] 长时程 / 编码 Agent 边界（2026-Q4 重估补充）
> 当 Agent 能自己调用搜索、文件浏览、grep 等工具时，"检索"可以不再是一次性的向量查询，而是 Agent 多轮自主探查（agentic search）。在代码库、结构化文档这类**有精确标识符、可以按路径和名字定位**的场景，编码 Agent 普遍直接用 grep / 文件浏览，不建向量索引：结果精确、不用维护索引、天然随文件更新。向量检索仍然更适合**措辞多变、只能靠语义找**的自然语言语料，以及**低延迟、单次调用**的问答。选择时问两个问题：材料能不能按名字或路径精确定位？能接受多轮探查带来的延迟和成本吗？两个都是"能"，先试 agentic search。

## 2. Memory Retrieval（记忆机制）

**为什么存在**：对话/Agent 任务是无状态的——模型不记得上一次交互。记忆机制用外部存储 + 检索模拟"记忆"：把过往交互、用户偏好、任务状态存起来，需要时检索回上下文。它让 AI 从"每次重新认识你"变成"记得你是谁、上次聊过什么"。

**什么时候使用**：需要跨会话记住用户/上下文的应用（个人助理、长期陪伴、客服）；长任务需要保持状态、超出单次上下文时；Agent 需要积累和复用经验（[[01_推理模式|Reflexion]] 的教训存储）时。

**什么时候不要使用**：一次性、无状态的任务（无需记忆）；记忆隐私敏感、合规不允许长期存储时；简单短对话（上下文窗口本身够用）；记忆检索的复杂度不值当时。

**架构图**：
```
短期记忆 = 当前上下文窗口
                        ┌──写入──[记忆存储: 向量库/DB/文件]
交互 →[判断值得记的]────┘                    │
新查询 →[检索相关记忆]←──────────────────────┘
       → 拼入上下文 → 生成(带记忆的回应)
分层: 短期(上下文) / 中期(会话摘要) / 长期(持久存储+检索)
```

**Prompt**：
```
[写入判断] 这段交互中有什么值得长期记住的用户信息/偏好/事实？
输出简洁的记忆条目(或"无")。
[检索使用] 相关的历史记忆：{检索到的记忆}
当前对话：{查询}
自然地利用记忆作答，不要生硬复述。
```

**Workflow**：
```
每次交互 →[提取值得记的] → 写入长期存储(去重/更新冲突项)
新查询 →[按相关性检索记忆] → 注入上下文 → 生成
长任务：定期把历史压缩为"状态摘要"存中期记忆(见下方 Context Compression)
```

**Agent**：记忆是高级 Agent 的核心能力——短期（上下文）、中期（任务状态摘要，写进文件/DB）、长期（跨任务经验库 + 检索）。文件系统是被低估的 Agent 记忆方案（可读、可查、可人工修正）。见 [[08_Agent设计模式与架构|设计模式第 8 章]]。

**优点**：实现个性化和连续性，体验质变；让 Agent 积累经验、越用越懂你；突破单次上下文限制处理长任务；记忆可审计、可编辑。

**缺点**：检索错误记忆会误导（记忆也需要相关性排序）；记忆膨胀与陈旧（旧偏好过时、需要更新/遗忘机制）；隐私与合规风险（存了什么、存多久）；冲突记忆的处理复杂（用户偏好变了怎么办）。

**案例**：个人助理记住"用户是素食者、常出差、偏好简洁回复"。下次用户问"推荐几家餐厅"，助理无需重新询问就默认排除肉食、考虑其常去的城市、给简短列表。记忆把每次的"冷启动"变成"接着上次"，但需要遗忘机制——若用户不再素食，旧记忆要能更新。

**未来方向**：更智能的记忆管理（自动判断记什么、何时遗忘、如何解决冲突）；记忆的结构化（从平铺条目到用户模型/知识图谱）；跨应用的统一记忆层（你的 AI 在不同产品间共享对你的理解，伴随隐私挑战）；记忆与个性化微调的结合。

## 3. Tool Use / Function Calling（工具使用）

**为什么存在**：模型只会生成文本，不会算精确数学、查实时信息、执行操作、访问系统。工具使用让模型声明"我要调用工具 X、参数 Y"，由外部代码执行并返回结果——把 LLM 的"语言能力"接上"行动能力"。它是 Agent 的定义性特征，也是 [[01_推理模式|ReAct]] 的"Act"部分。

**什么时候使用**：任务需要精确计算、实时/私有数据、或执行外部操作（发消息、改文件、调 API）时；模型的固有能力有明确短板（算术、时效）需外接时；构建任何与外部世界交互的 Agent。

**什么时候不要使用**：任务纯语言、无需外部能力（加工具是过度设计）；工具的可靠性/安全性无法保证时（尤其不可逆操作）；简单场景下工具往返的延迟不值当时。

**架构图**：
```
[工具声明: name/description/参数schema] 提供给模型
问题 →[LLM 决定: 调用tool(args)]  ← 模型只生成"调用意图"
         ↓ 意图
      [你的代码执行工具] ← 执行永远在代码侧,不在模型内
         ↓ 结果
      [结果返回模型] → 模型继续推理 → 最终回答
```

**Prompt**：核心在工具的 **description**（模型只凭它决定用不用、怎么用）：
```
工具定义：
  name: search_database
  description: 查询产品库存。当用户询问某商品是否有货/数量时使用。
               不要用于价格查询(用get_price)。
  parameters: {product_id: string, warehouse: string|null}
  returns: {stock: int} 或 {error: "..."}
```

**Workflow**：
```
声明工具集 → 模型输出调用意图 → 解析 → 执行(带错误处理)
→ 结果(成功值 or 有用的错误信息)返回模型 → 循环直到模型给最终答案
安全：不可逆操作前人工确认;工具返回值视为不可信内容
```

**Agent**：工具使用**就是** Agent 的核心机制，详见 [[07_工具调用与第一个Agent|教材第 7 章]]。工具描述质量、错误反馈设计、权限分层是三大关键。MCP（Model Context Protocol）是工具接入的标准化方向。

**优点**：突破模型固有能力边界（计算、实时、操作）；把 LLM 变成能行动的 Agent；工具可组合、可复用、可标准化（MCP）；能力扩展无需改模型。

**缺点**：工具描述不清导致乱调用；工具错误处理不当会静默失败（Agent 最阴险的 bug）；安全风险大（尤其可执行操作、prompt injection 经工具返回值注入）；增加延迟和系统复杂度。

**案例**：问"帮我算一下这笔投资 8% 年化 15 年的复利终值"。模型自己算易错，通过 calculator 工具精确计算返回结果。再如客服 Agent 调 `check_order` 工具查真实订单状态而非编造。工具让模型的回答从"大概"变成"精确且真实"。

**未来方向**：已经落地的——MCP 等标准让工具生态可复用（AI 的"USB 接口"，见 [[textbook-zero-to-agent/08_Agent设计模式与架构|教材 8.6]]）；computer use 类通用工具让 Agent 能操作图形界面软件；原生工具调用的准确率与错误恢复持续提升。仍在演进的——工具的自动发现与组合；面向工具的权限、沙箱与注入防御机制的标准化。

## 4. Context Compression（上下文压缩 / 摘要记忆）

**为什么存在**：长对话/长任务会撑爆上下文窗口，且塞太多会稀释注意力（context rot：垃圾累积→决策变差）。Context Compression 定期把历史压缩为摘要/状态笔记，只保留精华——用"有损压缩"换"上下文清爽"。它是长任务 Agent 和长对话的续命机制。

**什么时候使用**：对话/任务长到接近或超出上下文窗口时；上下文中大量内容对当前决策已无关（历史工具输出、旧轮次）时；长任务需要保持"当前状态"但不需要全部细节时；成本优化（短上下文更便宜）。

**什么时候不要使用**：任务短、上下文充裕时（压缩是多余且有损）；每个历史细节都可能被后续需要时（压缩会丢关键信息）；压缩的计算成本高于其节省时；对信息完整性要求极高的场景（法律、审计）。

**架构图**：
```
长历史[轮1,轮2,…,轮N] 逼近窗口上限
        ↓[压缩调用: 提炼为状态摘要]
[状态摘要(精华)] + [最近几轮(保留细节)] → 继续任务
       每隔M轮触发一次压缩;旧细节丢弃,状态保留
```

**Prompt**：
```
把以下对话/任务历史压缩为简洁的"当前状态摘要"，保留：
- 已确定的关键事实、决策、用户偏好
- 当前进度和待办
- 未解决的问题
丢弃：寒暄、已完成且无后续影响的细节、冗余重复
历史：{历史}
输出结构化状态摘要。
```

**Workflow**：
```
监控上下文长度 → 达阈值 → 压缩较旧部分为状态摘要
→ 用"摘要 + 最近N轮原文"替换全历史 → 继续
分层: 保留最近细节 + 压缩中期 + 长期存外部记忆(见 Memory)
```

**Agent**：长任务 Agent 必备——把"做到哪了"写成状态笔记（常存入文件），既防上下文腐烂又实现断点续跑。子 Agent 模式的本质也是压缩：把脏活派给独立上下文，只回传结论。见 [[08_Agent设计模式与架构|第 8 章]]上下文工程。

**优点**：突破上下文窗口限制，支持任意长任务；对抗 context rot，保持决策质量；降低成本（短上下文更便宜快速）；状态摘要本身可读、可审计。

**缺点**：有损——压缩必然丢信息，可能丢掉后来才需要的细节；压缩本身消耗调用；压缩质量决定后续质量（压错=状态错）；何时压、压多狠是需要调的超参。

**案例**：一个跑了 50 轮的研究 Agent，前 30 轮的搜索原文早已不需要，只需结论。每 10 轮压缩一次，把"已确认的发现 + 当前假设 + 待查项"写成状态摘要，丢弃原始搜索垃圾。上下文从爆炸边缘回到清爽，决策质量和成本都改善，且中断后能从状态摘要恢复。

**未来方向**：更长的原生上下文缓解部分压缩需求（但海量场景仍需）；智能压缩（模型自主判断什么该保留、什么该丢，甚至预测未来会用到什么）；分层记忆架构标准化（短/中/长期自动流转）；压缩与检索结合（压缩掉的细节存外部，需要时检索回来，实现"无损压缩"体感）。

> [!note] 长时程 / 编码 Agent 边界（2026-Q4 重估补充）
> 长时程 Agent（跑几小时、几百轮工具调用）不能只靠"压缩历史"续命，压缩本身有损且会累积误差。生产中更稳的做法是**把状态外置**：把目标、已完成事项、关键决定和待办写进进度文件（或 todo 列表），定期设**检查点**（代码 Agent 通常就是一次 git 提交），上下文压缩或会话中断后，从进度文件和检查点恢复，而不是从被压缩过的对话摘要恢复。判据：如果上下文被清空，Agent 能否只靠外部状态在几分钟内接着干？不能，就说明关键状态还只存在于上下文里。
