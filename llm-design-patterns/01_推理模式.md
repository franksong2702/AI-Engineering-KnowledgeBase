# 家族一 推理模式：如何让模型"想清楚"

> 这一族是最贴近 LLM 本质的模式。核心洞察：**模型的"思考"就是生成 token**——不给它生成推理过程的空间，就等于不让它思考。这些模式全部围绕"如何用输出空间换推理质量"展开。

> 关联 Laws：[[laws-of-ai-engineering/02_计算与验证定律#Law 12 — 验证-生成不对称定律（Verification-Generation Asymmetry Law）|Law 12：验证-生成不对称定律]]解释为什么推理输出必须可检查，[[laws-of-ai-engineering/02_计算与验证定律#Law 14 — 误差累积定律（Error Compounding Law）|Law 14：误差累积定律]]提醒长链推理会放大早期错误，[[laws-of-ai-engineering/02_计算与验证定律#Law 21 — 停机与预算定律（Termination-Budget Law）|Law 21：停机与预算定律]]约束反思、搜索和多轮推理不能无限延伸。

## 1. Chain-of-Thought（CoT 思维链）

**为什么存在**：LLM 逐 token 生成，若被要求直接给答案，它没有"演算"的空间，复杂推理只能靠一步蒙对。CoT 让模型先输出中间推理步骤再给结论，等于给了它"草稿纸"——把隐式的多步推理外化为显式的 token 序列。

**什么时候使用**：需要多步推理的任务（数学、逻辑、规划、因果分析）；答案对错依赖中间步骤时；需要推理过程可审查、可调试时；任何"直接问答错、拆开想就对"的任务。

**什么时候不要使用**：简单的事实检索或分类（多余的推理增加成本和延迟，甚至引入错误）；已用推理模型（reasoning model，内部已做思维链）时显式 CoT 收益递减；延迟极度敏感的场景；创意生成（过度分析伤害发散）。

**架构图**：
```
问题 → [LLM: "让我一步步想…" step1 → step2 → step3] → 结论
        └──────── 推理链在输出中显式展开 ────────┘
```

**Prompt**：
```
问题：{问题}
请一步步推理，先展示你的思考过程，最后给出结论。
格式：
思考：<逐步推理，每步一句>
结论：<最终答案>
```
（零样本触发词"让我们一步步思考"是最著名的 CoT 激活方式；复杂任务配 few-shot 推理示例更稳。）

**Workflow**：
```
输入 → CoT 提示 → 模型输出(推理链 + 结论)
     → 可选：解析出结论字段供下游使用
     → 可选：推理链留档,用于调试和评测轨迹
```

**Agent**：CoT 是 Agent 每一步决策的基础——要求 Agent 在选工具/下结论前先输出简短推理（这也是 [[07_工具调用与第一个Agent|ReAct]] 的"Reason"部分），既提升决策质量又让 trace 可调试。

**优点**：显著提升推理任务准确率；推理过程可见、可审计、可定位错误；实现成本极低（改 prompt 即可）；是几乎所有高级推理模式的基础构件。

**缺点**：增加 token 和延迟；推理链可能看似合理实则错误（流畅的错误推理有误导性）；对简单任务是纯开销；模型可能"事后编造"推理来为已定的答案辩护（后合理化）。

**案例**：算"一家店周一卖 23 个、每天比前一天多卖 5 个，周五卖几个"。直接问模型容易错；加 CoT 后它输出："周一 23，周二 28，周三 33，周四 38，周五 43。结论：43。"推理链既提升了正确率，也让人一眼能验证哪步错。

**未来方向**：推理模型将 CoT 从"提示技巧"内化为"训练能力"，显式 CoT 提示的作用在变化（从"教它想"转向"控制它想多久/展示多少"）；自适应 CoT（简单问题不想、难问题深想）以省成本；推理链的忠实性研究（让展示的推理真实反映内部计算，而非事后编造）。

> [!note] CoT 的三重口径，一次说清（消除跨书表面矛盾）
> 本知识库在三处对 CoT 有看似不一致的态度，这里统一——它们其实是一条时间线上的三个位置：
> - **教它**（本书/教材）：需要多步推理的任务，CoT 显著提升准确率，是基础构件。
> - **别滥用它**（[[ai-engineering-anti-patterns/00_INDEX|Anti-Patterns]] 的"CoT 成瘾"）：简单任务上强制 CoT 是纯开销甚至有害，按需使用。
> - **它在过时中**（[[foundation-of-ai-engineering/00_INDEX|Foundation]] 的"模式重洗"）：随推理模型普及，显式 CoT 正被内化，其作用从"教它想"转为"控制它想多久"。
>
> **统一表述**：需要多步推理时用，简单任务别滥用，且知道它的角色正在从"技巧"退化为"被内化的能力"——这正是"[[foundation-of-ai-engineering/00_INDEX|拐杖 vs 腿]]"的活例子。

## 2. Self-Consistency（自洽性）

**为什么存在**：CoT 单次采样可能走错一条推理路径。Self-Consistency 利用"多条不同推理路径若都指向同一答案，则该答案更可信"——对同一问题采样多条 CoT，取多数答案。本质是 [[12_投票Voting|投票]] 在推理链上的应用。

**什么时候使用**：有唯一正确答案且可比对的推理任务（数学、多选、事实判断）；单次 CoT 不够可靠、值得花数倍成本换准确率时；需要附带置信度信号（票数分布）时。

**什么时候不要使用**：开放生成任务（答案无法机械比对，无法投票）；成本/延迟敏感（n 倍开销）；简单任务（单次已够）；错误高度相关时（同模型可能稳定地错向同一答案，投票只是放大错误——见 [[12_投票Voting]]）。

**架构图**：
```
          ┌→ CoT 路径1 → 答案 A
问题 ──────┼→ CoT 路径2 → 答案 A
(高温采样) ├→ CoT 路径3 → 答案 B
          └→ CoT 路径4 → 答案 A
                          ↓
                   [多数投票] → A
```

**Prompt**：单条路径的 prompt 就是普通 CoT，关键在**高温采样多次** + 代码层投票。可加多样化前缀（"用不同方法解一遍"）增加路径去相关。

**Workflow**：
```
问题 → 同一 CoT 提示跑 N 次(temperature 高) → 抽取每次的最终答案
     → 规范化答案 → 计票 → 输出多数答案 + 一致度(置信信号)
     → 可选：一致度低时升级(加采样/转人工)
```

**Agent**：Agent 在关键决策点（选哪条路径、判断是否完成）可用自洽性提升可靠性；但因成本高，通常只在高风险节点启用，而非每步。

**优点**：显著提升推理准确率（比单次 CoT 更稳）；附赠置信度（5:0 vs 3:2 可信度不同）；实现简单（多跑几次 + 投票）。

**缺点**：成本线性 ×N；只适用于答案可比对的任务；对相关错误无能为力；收益随 N 递减（3→5 明显，5→10 边际很小）。

**案例**：一道有陷阱的应用题，单次 CoT 有 40% 概率掉进陷阱。跑 5 次高温采样：3 次正确、2 次掉陷阱（且掉的方式不同），多数投票选出正确答案，把 60% 单次正确率提到约 80%+。一致度 3:2 也提示这题较难、值得人工复核。

**未来方向**：自适应采样（先跑 3 次，一致就停，分歧才加采样，省成本）；加权投票（按推理链质量而非等权）；与验证器结合（用一个 verifier 模型评估每条链的可信度再加权），逼近"生成-验证"范式。

## 3. ReAct（Reason + Act 推理与行动交替）

**为什么存在**：纯 CoT 只能在模型脑内推理，碰不到外部世界，无法获取新信息或执行操作。ReAct 让模型交替进行"推理"和"行动"（调用工具）——想一步、做一步、看结果、再想。它是把推理接入现实的桥，也是几乎所有工具型 Agent 的底层范式。

**什么时候使用**：任务需要外部信息或操作（搜索、查库、算数、调 API）；答案依赖实时/私有数据，纯靠模型记忆不可靠；需要模型根据中间结果动态调整下一步时。

**什么时候不要使用**：任务纯靠推理即可完成（无需外部工具，用 CoT 更省）；步骤完全固定可预知（写死的 [[01_流水线Pipeline|工作流]] 比动态 ReAct 更可靠便宜）；延迟敏感（多轮往返累加延迟）。

**架构图**：
```
问题 →┌─────────────────────────────────────┐
      │ Thought: 我需要查X                    │
      │ Action: search("X")                  │
      │ Observation: <工具返回>  ←── 外部工具 │
      │ Thought: 根据结果,我还需要…           │  ← 循环直到
      │ Action: …                            │     Thought 判定可答
      └─────────────────────────────────────┘
                     ↓
                Final Answer
```

**Prompt**：
```
你可以使用工具解决问题。按以下循环输出：
Thought: <你的推理>
Action: <工具名>(<参数>)
（系统会返回 Observation，然后你继续）
当你能回答时，输出：
Thought: 我现在可以回答了
Final Answer: <答案>
可用工具：{工具清单及描述}
```

**Workflow**：
```
while 未完成 and 轮次<上限:
  模型输出 Thought+Action → 解析 Action → 执行工具
  → 把 Observation 追加进上下文 → 继续
终止：模型输出 Final Answer / 达到最大轮数 / 人工中断
```

**Agent**：ReAct **就是**基础 Agent 循环本身，详见 [[07_工具调用与第一个Agent|教材第 7 章]]。所有工具调用型 Agent 都是 ReAct 的工程化。关键设计：工具错误要返回有用信息让模型自愈、最大轮数防死循环、trace 全程可见。

**优点**：把推理接入现实，突破模型知识边界；动态适应中间结果，比预设流程灵活；trace（Thought+Action+Observation）天然可调试；通用性极强。

**缺点**：多轮往返，延迟和成本高；可能陷入循环或反复无效调用；工具描述不清会导致乱调用；错误会沿轨迹传播（早期错误观察污染后续推理）。

**案例**：问"某公司最新季度营收比上季度增长多少"。ReAct 循环：Thought 需查最新财报 → Action search → Observation 得两季数据 → Thought 需计算 → Action calculator → Observation 得增长率 → Final Answer。纯 CoT 无法完成（模型没有最新数据），ReAct 通过工具接力解决。

**未来方向**：更强的错误恢复（识别死循环并主动换策略）；推理与行动的并行化（同时发起多个独立工具调用）；ReAct 与规划结合（先 [[05_Planner-Executor|Planner]] 定框架再 ReAct 执行每步）；把成功轨迹沉淀为可复用技能，减少重复推理。

## 4. Tree Search / Tree-of-Thoughts（思维树与树搜索）

**为什么存在**：CoT 是单条线性推理，一步走错就到底。Tree-of-Thoughts 让模型在每步生成多个候选"想法"，形成树，通过评估和搜索（BFS/DFS/回溯）探索多条路径、剪掉差的、深入好的。它把"线性推理"升级为"带回溯的搜索"，为需要探索和试错的难题而生。

**什么时候使用**：解空间大、需要探索多条路径的难题（复杂规划、谜题、创意组合、需要回溯的推理）；一步错则满盘皆输、需要中途纠偏的任务；单条 CoT 和 Self-Consistency 都撑不住的高难度问题。

**什么时候不要使用**：绝大多数日常任务（成本高得离谱，5-30× 起步）；线性推理已够的问题；缺乏可靠的"中间状态评估"方法时（树搜索的灵魂是评估每个节点好坏，评不准则搜索失效）；实时场景。

**架构图**：
```
              问题
             /  |  \
        想法A  想法B  想法C      ← 每步生成多个候选
        /\      |评估:剪枝       ← 评估器打分,剪掉差的
     A1  A2    B1
     |评估      |
    (死路)   最优路径 → 解        ← DFS/BFS + 回溯搜索
```

**Prompt**（两个角色：生成器 + 评估器）：
```
[生成器] 针对当前状态 {state}，生成 3 个不同的下一步想法，各自独立可行。
[评估器] 评估以下想法通向最终解的希望：{想法}
输出 {"score": 0-1, "reason": "...", "verdict": "sure|maybe|impossible"}
（impossible 的分支被剪枝，sure/maybe 继续展开）
```

**Workflow**：
```
初始化根节点 → while 未达解 and 预算未尽:
  选择待展开节点(按评估分) → 生成 k 个子想法 → 评估每个
  → 剪掉 impossible → 把 promising 加入前沿 → 可回溯
终止：找到满足解 / 预算耗尽 / 前沿为空
```

**Agent**：可作为 Agent 处理高难度子问题的"深思模块"（大部分步骤用 ReAct，遇到硬骨头切换 ToT 深搜）。与 [[03_树状分解Tree|Multi-Agent 树状分解]] 的区别：那个是把不同任务分给不同 Agent，这个是单一问题的解路径搜索。

**优点**：能解 CoT 解不了的难题，提供推理的"探索+回溯"能力；中途可纠偏，不会一条路走到黑；评估器让搜索有方向，比盲目采样高效。

**缺点**：成本极高（生成×评估×多节点×多层）；严重依赖评估器质量，评估不准则南辕北辙；实现复杂；绝大多数任务用不上，容易过度工程。

**案例**：解一个需要多步且易走死路的规划谜题（如 24 点、复杂日程排布）。CoT 单路径经常卡死；ToT 在每步生成几个候选走法、评估器剪掉明显死路、DFS 深入有希望的分支并在碰壁时回溯，最终找到解。代价是几十倍于 CoT 的调用量——只在这类高难度、高价值问题上才划算。

**未来方向**：更便宜的评估（用小模型或学习到的价值函数替代 LLM 评估每个节点）；与推理模型结合（推理模型内部可能已隐式做类似搜索）；蒙特卡洛树搜索（MCTS）等经典搜索算法与 LLM 的深度融合；自适应决定"这题值不值得上树搜索"。

## 5. Least-to-Most（由易到难分解）

**为什么存在**：有些问题直接解太难，但拆成"由简到繁的子问题序列"后，每个子问题都不难，且后面的可以用前面的答案。Least-to-Most 先让模型把问题分解为递进的子问题，再依次求解，前面的解喂给后面。它介于 CoT 和 [[03_树状分解Tree|树状分解]] 之间，专治"需要先解决简单情形才能解决复杂情形"的任务。

**什么时候使用**：问题有清晰的"由易到难"递进结构（数学归纳式、组合问题、需要先建立子结论的推理）；直接 CoT 会因跨度太大而出错，但分步可解时；泛化要求高（用小例子的解法推广到大例子）。

**什么时候不要使用**：问题无自然递进结构（强行分解反而混乱）；子问题相互独立无依赖（用 [[02_MapReduce|MapReduce]] 并行更好）；简单问题（分解是过度设计）。

**架构图**：
```
复杂问题 → [分解] → 子问题1(最简) → 子问题2 → … → 子问题N(=原问题)
                        ↓解         ↓解(用上一步)      ↓解
                       解1 ────────→ 解2 ──────────→ 最终解
                    (解逐步累积,后者依赖前者)
```

**Prompt**：
```
阶段1(分解)：把问题分解为一系列由简到难、后者依赖前者的子问题。
问题：{问题}
输出子问题列表(从最基础到最终)。
阶段2(依次求解)：已知前面子问题的解 {已解},现在解决下一个子问题:{子问题}。
```

**Workflow**：
```
问题 → [分解调用] 得到有序子问题序列
     → for 每个子问题(按序): 带着已有解求解 → 累积
     → 最后一个子问题的解 = 原问题的解
```

**Agent**：适合 Agent 处理"需要建立中间结论才能推进"的任务，作为 Planner 的一种分解策略（当子任务有强顺序依赖时优于并行拆解）。

**优点**：把大跨度推理拆成小步，降低单步难度、提升准确率；显式利用子问题间的依赖（后者复用前者）；泛化能力强（小例子解法推广到大例子）。

**缺点**：依赖分解质量，分解错则全错；串行执行、无并行红利；对无递进结构的问题不适用；比单次 CoT 成本高。

**案例**：解"某表达式在嵌套括号下的求值"或"最后一个字母拼接"类任务，直接算易错。Least-to-Most 先分解为"先处理最内层→再外一层→…"，每步只处理一层、复用上一层结果，逐步逼近答案。这种"先易后难、逐步累积"显著优于让模型一口气算完。

**未来方向**：自动判断问题是否适合 Least-to-Most（vs 并行分解 vs 直接 CoT）的元推理；与 ReAct 结合（每个子问题可调工具）；分解质量的自我验证（解完回头检查分解是否合理）。

## 6. Self-Critique / Reflexion（自我批评与反思）

**为什么存在**：模型初次输出是"初稿质量"，但**评价比生成容易**——让模型回看自己的输出、找出问题、再改，能显著提质。Reflexion 进一步把"失败的教训"写成语言反思存入记忆，指导下次尝试。这是单体版的 [[04_质量控制模式|反思]]，也是 Agent 从失败中学习的关键机制。

**什么时候使用**：输出质量重要且值得多次迭代（代码、重要文书、复杂推理）；有客观反馈信号（测试结果、执行报错、规则校验）时效果最好；Agent 任务失败后需要调整策略重试时。

**什么时候不要使用**：无客观反馈、纯靠模型自评时要警惕（同模型自评偏宽容，易自我表扬）；简单任务（一次就够）；成本敏感（每轮反思翻倍成本）；已知反思会震荡（改来改去不收敛）时。

**架构图**：
```
任务 → [生成] → 输出v1 → [执行/测试] → 反馈(报错/评分)
                              ↓
                        [自我反思] "哪里错了?为什么?下次怎么改?"
                              ↓ (反思写入记忆)
                        [重新生成] → 输出v2 → … 循环直到达标/上限
```

**Prompt**（反思环节）：
```
你之前的尝试：{输出}
执行反馈：{测试结果/报错/评分}
请反思：
1. 哪里出了问题？具体是什么导致的？
2. 根本原因是什么（不只是表面症状）？
3. 下一次尝试应该如何改进？给出具体调整。
把这条反思作为经验，用于改进下一次尝试。
```

**Workflow**：
```
for 尝试 in 1..上限:
  生成输出 → 执行获得客观反馈
  → 达标? 是→返回 / 否→自我反思生成"教训" → 教训入记忆 → 下一轮带教训重试
终止：达标 / 达上限 / 连续两轮反思重复(震荡)
```

**Agent**：Reflexion 是 Agent 自我改进的核心——失败时不盲目重试，而是先反思根因、调整策略再试。语言化的反思可存入长期 [[03_知识与记忆模式|记忆]]，跨任务复用（"上次这类任务栽在 X 上"）。

**优点**：利用"评价易于生成"的不对称性提质；有客观反馈时提升显著（代码 pass 率明显上升）；反思可积累为经验，越用越强；实现相对简单。

**缺点**：无客观反馈时自评不可靠（自我表扬）；成本随轮数翻倍；可能过度修改把对的改错；收敛不保证（第 3 轮后常是布朗运动）。

**案例**：让 Agent 写一个函数，v1 跑测试挂了 3 个用例。Agent 反思："失败源于没处理空输入和边界值，根因是我没先想清楚边界情形。" 带着这条教训重写 v2，测试全过。反思把"盲目重试"变成"针对性修复"，且这条教训可存入记忆供同类任务复用。

**未来方向**：更可靠的自我批评（接入外部验证器、跨模型批评破除自我表扬）；反思记忆的结构化与检索（把零散教训组织成可查的经验库）；判断"何时该反思、何时该放弃换路"的元认知；与强化学习结合，让反思真正改变模型行为而非仅停留在上下文。
