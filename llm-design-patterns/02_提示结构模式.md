# 家族二 提示结构模式：如何组织给模型的指令

> 这一族关注"输入怎么写"。它们是最基础、最高频、性价比最高的模式——不改架构、不加调用，仅靠提示的组织方式就能大幅改变输出。本质都是"降低任务的不确定性，让模型的概率分布向你要的方向收窄"。

---

## 1. Few-shot / In-context Learning（示例驱动）

**为什么存在**：抽象的任务描述会有歧义，模型可能理解偏。给几个"输入→输出"示例，模型能从中归纳出你要的模式——这是 LLM 的涌现能力"上下文学习"：不改权重，仅凭示例就临时学会一个任务。示例常比描述更精确地传递意图。

**什么时候使用**：任务的输出格式/风格/标准难以用语言描述清楚，但容易举例时；零样本效果不稳定、需要锚定时；分类/抽取/转换类任务；需要输出高度一致时。

**什么时候不要使用**：任务极简单、零样本已够（示例是浪费）；找不到高质量代表性示例时（坏示例会教坏模型）；示例会占用大量上下文、挤压真正的输入时；需要模型发挥创造性而非模仿时。

**架构图**：
```
[示例1: 输入→输出]
[示例2: 输入→输出]   ← 模型从中归纳"任务模式"
[示例3: 输入→输出]
[真实输入] ────────→ 模型按归纳的模式输出
```

**Prompt**：
```
按示例完成任务：
输入：很棒的产品，物流也快
输出：{"sentiment": "正面", "aspects": ["产品", "物流"]}
输入：东西还行，但客服态度差
输出：{"sentiment": "混合", "aspects": ["产品", "客服"]}
输入：{真实输入}
输出：
```

**Workflow**：
```
准备示例池 → 选取 2-5 个代表性示例(覆盖典型+边界)
→ 拼入 prompt → 模型输出 → 校验格式
可选：动态 few-shot(按输入从示例库检索最相似的几个,见 RAG 思想)
```

**Agent**：Agent 的工具使用、输出格式常靠 few-shot 稳定；动态 few-shot（按当前情境检索最相关示例）是提升 Agent 一致性的有效手段。

**优点**：不训练即可"教会"新任务；示例传意精确，输出一致性高；实现零成本（改 prompt）；对格式控制尤其有效。

**缺点**：占用上下文（示例越多越挤）；示例质量和代表性决定成败，坏示例误导；示例的顺序和分布会引入偏差；对需要真推理的任务，示例帮助有限。

**案例**：做情感+方面抽取，零样本时模型输出格式五花八门（有时中文有时英文、字段不一）。加 3 个覆盖正面/负面/混合的示例后，输出格式立刻统一为规范 JSON，可直接程序处理。示例在这里比任何格式描述都管用。

**未来方向**：动态检索式 few-shot（按输入实时选最相关示例）成为标配；示例的自动优选（用评测挑出最有效的示例组合）；长上下文让"多示例"成本下降，many-shot learning 兴起；与结构化输出结合，进一步减少格式不确定性。

## 2. Role / Persona Prompting（角色扮演）

**为什么存在**：给模型指定一个角色（"你是资深安全工程师"），能激活相关的知识分布、语气和评判标准，让输出更贴合专业语境。本质是用角色作为"上下文锚"，把模型的通用分布收窄到某个专业子空间。

**什么时候使用**：需要特定专业视角、语气或评判标准时；希望输出符合某种身份的风格（法律严谨、儿童友好、营销热情）；[[04_质量控制模式|多视角评审]]中给不同评审员分配角色时；需要模型代入特定受众思考时。

**什么时候不要使用**：把角色当"能力开关"误用时（"你是世界最强数学家"不会真的让它数学变强，只影响风格不影响能力上限）；简单事实任务（角色无关）；角色约束与任务实际需求冲突时；过度堆砌角色描述挤占有效指令时。

**架构图**：
```
[角色设定: 你是X,具备Y视角/标准/语气]
        ↓ (收窄模型的输出分布到该专业子空间)
[任务] ────────→ 带该角色特征的输出
```

**Prompt**：
```
你是一位资深网络安全审计师，习惯用攻击者视角审视系统，对风险高度敏感，
表达精确、不夸大。请审查以下设计的安全隐患：{设计}
按严重度分级输出，每项附具体攻击场景。
```

**Workflow**：
```
定义角色(专业/视角/语气/标准) → 融入 system prompt
→ 任务在该角色框架下执行
多角色场景：为不同子任务/评审员配不同角色(见 Debate/Committee)
```

**Agent**：Agent 的 system prompt 本质就是角色定义（"你是文件助手，规则是…"）；多 Agent 系统给每个 Agent 分配角色以区分职责——但注意 [[multi-agent-patterns-handbook/00_INDEX|Multi-Agent 手册]]原则 2：同模型换角色≠真变专家,多样性主要来自上下文与工具而非头衔。

**优点**：低成本地调整输出的视角、语气、标准；对专业语境和风格控制有效；便于构造多视角评审；直观易用。

**缺点**：常被高估——角色改变风格但不改变能力上限（"你是专家"不会凭空提升准确率）；过度角色描述浪费 token；角色刻板印象可能引入偏见；同模型的不同角色相关性高（伪多样性）。

**案例**：同一份产品设计，分别以"挑剔的安全审计师""急躁的终端用户""成本敏感的 CFO"三个角色让模型评审，得到三份视角迥异的反馈——安全角色揪出注入风险、用户角色抱怨流程繁琐、CFO 角色质疑投入产出。角色让单模型模拟出多视角评审的骨架（但真正的多样性仍需配合不同知识/工具）。

**未来方向**：角色与真实差异化结合（不同角色配不同知识库/工具，把伪多样变真多样）；持久化角色（Agent 的稳定人格与记忆）；对"角色影响风格但不影响能力"这一边界的更清晰认知，避免滥用。

## 3. Structured Output（结构化输出 / Schema 约束）

**为什么存在**：LLM 默认输出自由文本，程序无法可靠解析。结构化输出用 schema（JSON Schema / Pydantic / 语法约束）强制模型产出固定结构，让程序可以直接解析。它是"把 LLM 从聊天对象变成软件组件"的关键——也是 [[07_工具调用与第一个Agent|工具调用]]的底层机制。

**什么时候使用**：输出要被程序消费（存数据库、传下游、触发动作）时；需要稳定字段结构、不容格式漂移时；抽取/分类任务；[[05_编排模式|流水线]]中段间传递结构化工件时。

**什么时候不要使用**：输出是给人读的自由文本（散文、创意、对话）时；过度结构化会束缚需要灵活表达的任务；schema 过于复杂导致模型难以填满时（拆成多次更好）。

**架构图**：
```
任务 + Schema定义 → [LLM(受schema约束解码)] → 保证合法的结构化对象
                                                    ↓
                                          程序直接消费(无需解析散文)
```

**Prompt**：
```
从文本抽取信息，严格按 schema 输出 JSON，不要任何额外文字：
Schema: {"name": string, "age": int|null, "skills": string[], "confidence": "high|low"}
规则：文本中没有的字段填 null，禁止编造；不确定填 confidence=low。
文本：{输入}
```
（优先用 API 的 JSON mode / structured outputs / 工具调用能力强制，而非仅靠 prompt 恳求。）

**Workflow**：
```
定义 schema(Pydantic/JSON Schema) → 传给支持约束解码的 API
→ 模型输出保证合法的结构 → 直接反序列化为对象 → 下游使用
兜底：校验失败则重试或修复
```

**Agent**：结构化输出是工具调用的基础（工具参数就是 schema 约束的输出）；Agent 间传递工件、Planner 输出任务列表都依赖它保证可解析性。

**优点**：输出可靠可解析，是 LLM 工程化的基石；减少下游解析的脆弱代码；schema 本身就是接口契约，清晰可测；降低格式漂移。

**缺点**：过度约束可能损害内容质量（模型忙于满足格式而非思考——复杂任务可先自由推理再抽成结构）；复杂/深嵌套 schema 模型易出错；schema 设计不当会限制表达。

**案例**：一个流水线要把简历文本转成数据库记录。仅靠 prompt 求 JSON 时,偶尔会夹带解释文字或字段缺失,导致解析崩溃。改用 structured outputs 强制 schema 后,每条输出都是合法对象,可直接入库,下游解析代码从几十行正则降到一行反序列化。

**未来方向**：约束解码已在主流 API 中普及（structured outputs / 原生工具调用参数），"保证合法"基本成为默认能力，剩下的问题是复杂 schema 下的内容质量；"先推理后结构化"的两阶段范式（自由推理想清楚，再抽成 schema，兼得质量与可解析）；schema 的自动生成与演化；类型系统与 LLM 输出的深度整合。

## 4. Prompt Chaining（提示链）

**为什么存在**：把复杂任务拆成多个串联的 prompt，每个只做一件事，前一个的输出是后一个的输入。首要理由是**工程上的可控**：每一环可以单独测试、单独优化、单独换模型、单独缓存，出错时能定位到环。其次才是质量：模型较弱时，一个 prompt 塞进太多子任务（提取+分析+写作+翻译）会互相干扰；模型越强，这个理由越弱，但可控性的理由不变。它是单体版的 [[01_流水线Pipeline|流水线]]，也是最朴素的编排。

**什么时候使用**：任务可分解为清晰的顺序步骤；单 prompt 做全部导致质量下降或不可控时；需要在中间步骤插入校验/加工时；想让每步可单独测试、优化、换模型时。

**什么时候不要使用**：任务简单、一个 prompt 足够（拆分是过度设计，徒增延迟）；步骤间无清晰边界、强行拆反而丢失整体上下文时；延迟敏感（每链一环加一次往返）。

**架构图**：
```
输入 →[Prompt1:提取]→ 中间结果1 →[Prompt2:分析]→ 中间结果2 →[Prompt3:成文]→ 输出
       每环单一职责,可独立校验/优化/换模型;上一环输出=下一环输入
```

**Prompt**：每环是一个聚焦的单任务 prompt。关键是**环间契约**：
```
环1输出 → (校验/格式化) → 作为环2的输入变量注入
环2 prompt："基于以下已提取的要点{环1输出}，进行…"
```

**Workflow**：
```
输入 → Prompt1 → 校验 → Prompt2 → 校验 → … → 输出
每环可用不同模型(贵模型只放关键环)、可缓存、可单独评测
失败：某环校验不过 → 重试该环 / 中止
```

**Agent**：Prompt Chaining 是确定性工作流的基本形态；当步骤固定时，它比让 Agent 自主决策更可靠便宜（见 [[multi-agent-patterns-handbook/00_INDEX|Multi-Agent 手册]]的"Agent vs 工作流"判据）。

**优点**：每环单一职责，质量和可控性高；可独立调试、优化、换模型、缓存；把大问题分解为可管理的小块；确定性强、方差低。

**缺点**：串行延迟叠加；早环错误会传导放大；环间上下文传递可能丢信息；比单 prompt 复杂、需要工程管理。

**案例**：把"将一篇英文技术文章改写成面向初学者的中文教程"拆成链：环1 提取核心概念与结构 → 环2 逐概念生成初学者友好的解释 → 环3 组织成教程并翻译润色 → 环4 校对术语一致性。相比一个巨型 prompt 一步到位，每环质量都更可控，且环2 发现概念提取有误时可只重跑相关环。

**未来方向**：动态链（根据中间结果决定下一环是什么，向 [[05_Planner-Executor|Planner]] 演化）；链的自动优化（评测驱动地调整每环 prompt）；链与 Agent 的混合（固定部分用链、不确定部分用 Agent）；可视化编排工具让非工程师也能搭链。

## 5. 意图澄清（Rephrase / Clarify）

> 2026-Q4 重估：原"Step-back / Rephrase"条目拆分。Step-back 已移入 [[llm-design-patterns/06_历史模式|历史模式]]；本节保留并改写 Rephrase 部分。

**为什么存在**：很多"答错"不是能力不够，而是没搞清用户要什么。意图澄清让模型在动手前先用自己的话重述任务、指出歧义，必要时向用户回问。它处理的是**信息缺失**，模型再强也无法凭空补上，所以这个模式不会被能力进步吸收。

**什么时候使用**：需求模糊或有多种合理解读（"帮我优化这个"）；做错的代价高、返工成本大；长任务或 Agent 任务开工前；用户与模型对术语的理解可能不一致时。

**什么时候不要使用**：需求清晰明确；回问成本高于猜错成本的低风险任务；用户明确要求"不要问，直接做"时（此时应在输出里写明自己采用的解读）。

**架构图**：
```
模糊请求 →[重述 + 列出歧义]→ 歧义影响大? ─是→ 向用户回问 → 确认后执行
                                    └否→ 采用最合理解读并写明 → 执行
```

**Prompt**：
```
在开始之前，先用一两句话重述你理解的任务。
如果存在会显著改变结果的歧义，列出来并向我提问（最多 3 个问题）；
如果歧义不影响结果，直接采用最合理的解读，并在回答开头写明你的假设。
```

**Workflow**：
```
请求 → 重述与歧义识别 → 判断歧义是否影响结果
     → 影响：回问用户，拿到答复后执行
     → 不影响：写明假设，直接执行
```

**Agent**：Agent 接到模糊任务时先重述并确认，是减少"跑偏做错"最便宜的手段；长任务开工前的一次澄清，往往比中途纠偏省得多。回问要克制：一次问清关键问题，不要每一步都停下来问。

**优点**：从源头减少误解导致的返工；把模型的假设显式化，便于用户纠正；成本低。

**缺点**：多一轮交互，增加延迟；回问过多会打扰用户；模型可能把明确的需求也当成有歧义。

**案例**：用户说"帮我优化这个函数"。模型先重述："你是想提升性能、可读性，还是减少依赖？从代码看，主要瓶颈在循环里的重复查询，我先按性能优化理解，可以吗？"一次回问避免了按错方向重写整个函数。

**未来方向**：更好地判断"哪些歧义值得问"（按猜错的代价排序）；从历史交互中学习用户的默认偏好，减少重复回问；与界面结合，把常见歧义做成可选项，而不是开放式提问（见 [[human-ai-interaction-design/00_INDEX|Human-AI Interaction Design]]）。
