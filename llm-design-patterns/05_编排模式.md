# 家族五 编排模式：如何组织多次调用

> 当一次调用做不完时，就需要编排多次调用。这一族与 [[multi-agent-patterns-handbook/00_INDEX|Multi-Agent 架构手册]]高度重叠——那本从"多智能体协调"讲，本书从"LLM 调用的组织方式"讲。此处给每个模式精要版 + 交叉引用，深入细节请看那本对应章节。
> **正典声明**：Planner-Executor 与 Map-Reduce 的权威完整版在 Multi-Agent 手册（05 / 02），本族条目为精要版。共同心法（[[llm-design-patterns/00_INDEX#六条跨模式定律|本书跨模式定律 5]]）：能用一次调用/一个工作流解决的，别上编排；每叠一层，可观测性要跟上。

---

## 1. Planner-Executor（规划-执行）

**为什么存在**：单次调用边想边做易鼠目寸光——忘全局、陷细节、重复劳动。把"规划"（全局、深思、一次）与"执行"（局部、可并行、可用便宜模型）分离，各自都变强。是"先想清楚再动手"的调用级架构。深入见 [[05_Planner-Executor|Multi-Agent 手册对应章]]。

**什么时候使用**：多步骤、有依赖、但拆解后每步明确的任务（复杂研究、功能开发、迁移）；需要在执行前人工审查计划（拦截方向性错误）时；想用贵模型规划、便宜模型执行以控成本时。

**什么时候不要使用**：任务简单/步骤固定（写死 [[#2. Map-Reduce（分片并行-聚合）|工作流]]更省）；探索型任务（做了才知道下一步，用 [[01_推理模式|ReAct]] 边走边想）；计划极易失效的高动态环境（重规划成本盖过收益）。

**架构图**：
```
目标 →[Planner: 深思,产出计划]→ [任务1,任务2(依赖1),任务3] + 验收标准
                                        ↓ 派发(无依赖的并行)
                              [Executor(s): 便宜模型,专注执行]→ 结果
                                        ↓
                              [验收/或计划失效→重规划(≤2-3次)]→ 交付
```

**Prompt**（Planner）：
```
为目标制定计划,输出JSON任务列表:
{"id":n,"task":"自包含描述","depends_on":[ids],"acceptance":"可验证完成标准","tools":[...]}
规则:每任务应≤10次工具调用能完成;标注"探路型"任务(其结果可能改变后续计划)排前面;
最后给出你对计划最大的不确定点。
```

**Workflow**：
```
目标 → Planner出计划 →(可选:人工审查) → Executor按依赖并行执行 → 验收每步
→ 计划失效则带进度重规划 → 全部通过则交付
```

**Agent**：经典多 Agent 骨架，常与每步内嵌 [[04_质量控制模式|Reflection]]、出口加 [[04_质量控制模式|Judge]] 组合。详见 [[05_Planner-Executor]]。

**优点**：全局一致（有人对整体负责）；成本优（贵模型只规划一次）；天然并行；计划可人工预审，安全性高于全自主。

**缺点**：计划赶不上变化（僵化执行错误计划更糟）；规划-执行鸿沟（Planner 不懂执行端约束）；重规划的状态同步复杂；对探索型任务不适用。

**案例**：写竞品分析报告。Planner 出计划（①定竞品清单[探路] ②并行调研各家 ③定价对比 ④综合撰写[依赖②③]）。执行中①发现竞品翻倍 → 重规划分档处理 → 各 Executor 并行完成 → 综合交付。规划与执行分离让全局连贯，探路任务前置让计划及时纠偏。

**未来方向**：交错规划（每完成一步轻量更新计划，计划从静态变活）；执行反馈进规划先验（越用越准）；计划可行性预演；双 Planner 制衡。详见 [[05_Planner-Executor]]。

## 2. Map-Reduce（分片并行-聚合）

**为什么存在**：数据量超上下文窗口，且长上下文注意力稀释。把数据切片、同一操作并行作用于每片（Map）、再聚合（Reduce）——用多个干净小上下文替代一个臃肿大上下文。深入见 [[02_MapReduce|Multi-Agent 手册对应章]]。

**什么时候使用**：大量、分片间弱耦合的同构任务（千条评论分析、长文逐章摘要、代码库逐文件扫描、批量处理）；单片处理不需看到其他片也基本正确时；需要并行以缩短墙钟时间时。

**什么时候不要使用**：分片间强依赖（伏笔在此章、揭晓在彼章，单片看不到）；需要全局统计且 Reduce 撑不住时；数据量小（直接全塞）；同构假设不成立时。

**架构图**：
```
大数据 →[Split: 切片]→ 片1,片2,…,片N
              ↓ Map(相同操作,并行)
         结果1,结果2,…,结果N (schema统一,带定位信息)
              ↓ Reduce(聚合)
         全局结果 (Reduce是瓶颈与信息损失点)
```

**Prompt**：Map 端是聚焦的单片处理 prompt（强调"不假设其他片内容"）；Reduce 端是聚合 prompt（合并同类、解决跨片引用、保留分歧）。

**Workflow**：
```
数据 → Split(按语义边界,可重叠) → Map×N并行 → 统一schema的片结果
→ (可选Shuffle按key分组) → Reduce聚合 → 全局输出 + 覆盖率报告
```

**Agent**：Mapper 可用便宜小模型批量处理；Reduce 阶段可用 [[04_质量控制模式|Committee]] 防单点综合偏差。详见 [[02_MapReduce]]。

**优点**：墙钟时间大幅缩短；每片上下文干净、单片质量高；天然可扩展；Mapper 可用便宜模型。

**缺点**：跨片信息丢失；Reduce 是瓶颈和信息损失点；全局统计问题依赖 Reduce 质量；同构假设破则质量崩。

**案例**：总结 300 页报告。切 30 片 → 30 个 Mapper 并行各抽论点/实体/悬念 → Reduce 合并同类项、配对跨片引用、产出全局摘要 + 溯源表。用便宜模型跑 Map、只在 Reduce 用强模型，成本和速度双优。改进可用两遍 Map 修复跨片盲区（详见 [[02_MapReduce]]）。

**未来方向**：层级 Reduce（防聚合超窗口）；重叠切片缓解边界切断；两遍 Map（先抽全局骨架再带骨架重跑）；动态片粒度。

## 3. Routing（路由分发）

**为什么存在**：一个 prompt 通吃所有输入类型会"样样通样样松"。先用轻量分类器分诊输入类型，再分发给专属处理器——关注点分离 + 按需付费（简单请求走便宜通道）。深入见 [[07_动态路由DynamicRouting|Multi-Agent 手册对应章]]。

**什么时候使用**：输入异构的服务型系统（客服分咨询/投诉/退款/技术、内容按类型审核）；模型成本分层（简单问题给小模型、难题给大模型）；输入可划分为 3-10 个处理逻辑不同的类别时。

**什么时候不要使用**：输入同质（无需分流）；类别边界极模糊（强行单标签丢意图）；单一处理器已够好时；路由本身的延迟/成本不值当。

**架构图**：
```
输入 →[Router: 轻量分类,只贴标签不加工]→ 标签+置信度
         ├─ confidence高 → 对应专属Handler(短而专的prompt/合适的模型)
         └─ confidence低 → 默认通道/人工
      (Handler输出直接返回,不再过Router)
```

**Prompt**（Router）：
```
把输入分类到唯一类别：{类别定义}
输出：{"category":"...","confidence":0-1,"secondary":"次要意图或null"}
规则：confidence<0.7宁可标other;不要试图回答问题,只分类。
```

**Workflow**：
```
输入 → Router分类 → 按类别+置信度分发到Handler
→ Handler深度处理 → 返回
监控: other占比、Handler拒收率 → 触发类别体系检修
```

**Agent**：多 Handler 各是独立 Agent；model routing 用于 Agent 内部按子任务难度选模型。详见 [[07_动态路由DynamicRouting]]。

**优点**：每个 Handler 短而专，质量与可维护性高；成本精准（简单流量走便宜通道）；增量演化友好（加类别不动存量）；Router 日志是业务数据金矿。

**缺点**：Router 是单点（分错全错，Handler 难自查收错活）；边界模糊输入丢意图；类别体系会腐烂（other 悄悄涨）；长尾类别维护成本高。

**案例**：客服系统。Router（小模型）先分类：高置信直接进对应 Handler（退款查订单+政策RAG、技术走排查树+知识库…），低置信转通用 Handler 或人工。80% 简单流量走便宜小模型，复杂问题才用强模型。级联路由（规则先接确定性流量、拿不准才进 LLM Router）是生产常态。

**未来方向**：级联路由（规则+LLM 分层）；Handler 反馈闭环改进 Router；多标签路由（复合意图并行处理）；在线学习的专用小模型 Router。

## 4. Orchestrator-Workers（协调者-执行者）

**为什么存在**：任务能拆但子任务的数量和内容**事前不可知**（依赖对输入的理解才知道要拆几个、拆成什么）。协调者动态拆解、分发给执行者、再合成——比 Map-Reduce 灵活（子任务异构且数量动态）、比固定工作流适应性强。是 [[03_树状分解Tree|树状分解]]的一层实现，规模再大则演化为 [[06_层级Hierarchical|层级]]。

**什么时候使用**：子任务数量/内容依输入动态变化（复杂研究、多文件动态处理）；拆解需要智能（不能像 Map-Reduce 机械切）；单层协调够用（未爆上下文，无需上层级）时。

**什么时候不要使用**：拆解方式固定可预知（用 Map-Reduce/工作流更省）；子任务同构（Map-Reduce）；规模大到单协调者上下文装不下（升级 [[06_层级Hierarchical|Hierarchical]]）；简单任务。

**架构图**：
```
任务 →[Orchestrator: 动态拆解(数量不定)]→ 子任务1,子任务2,…(异构)
              ↓ 分发(自包含任务书)
       [Worker(独立上下文)] 各自执行 → 结构化结论
              ↓ 回传
       [Orchestrator: 合成]→ 结果 (可迭代:据结果再拆新子任务)
```

**Prompt**（Orchestrator 分派）：
```
把任务动态拆解为若干子任务(数量由任务复杂度定,不预设)。每个输出:
{"task":"自包含描述(worker看不到全局)","output_format":"...","depends_on":ids或null}
宁可少拆不拆伪任务;无依赖的将并行执行。
```

**Workflow**：
```
Orchestrator分析任务 → 动态生成子任务集 → 分发给独立上下文的Workers
→ 收集结构化结论 → 合成 →(可选:据结果发起新一轮子任务) → 交付
```

**Agent**：这是最常见的生产级多 Agent 拓扑（Anthropic 多 Agent 研究系统即此形态）；子 Agent 独立上下文是核心收益。详见 [[08_Agent设计模式与架构|第 8 章]]与 [[03_树状分解Tree]]。

**优点**：适应子任务动态的复杂任务；子 Agent 上下文隔离、各自聚焦；可并行；比固定工作流灵活。

**缺点**：协调者拆错则整体白跑；合成层信息损失；成本高（协调 token + 多 worker）；任务书不自包含则 worker 跑偏而协调者无感知。

**案例**：研究"某技术的现状"。Orchestrator 动态判断需要拆成"发展历史、当前主流方案、争议点、未来趋势"四个子任务（另一个问题可能拆成完全不同的几个），分发给独立 Worker 并行调研，各回传带引用的结论，Orchestrator 合成为报告；若发现"争议点"结论与"主流方案"矛盾，再发起一个核查子任务。动态拆解是它区别于 Map-Reduce 的关键。

**未来方向**：更智能的动态拆解与合成；协调者的拆解自检（拆完先审遗漏了什么维度）；子 Agent 结论的置信度传递与抽查（防静默失败向上传染）；与 MCP 生态结合让 Worker 能力标准化扩展。详见 [[08_Agent设计模式与架构]]、[[multi-agent-patterns-handbook/00_INDEX|Multi-Agent 手册]]。
