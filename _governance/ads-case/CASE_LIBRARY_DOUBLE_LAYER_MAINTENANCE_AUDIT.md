# 案例库双层结构维护候选审计

> 本文只做候选审计，不改 100 个 case 正文。当前判断：案例库不应该全量深度化；它应该保留“100 个精简案例的覆盖层”，只挑少数案例升级为“深度样板层”。

## 1. 双层结构到底是什么

案例库现在有两个价值，不应该互相替代：

1. **广覆盖精简层**：100 个案例让读者快速扫到 AI Engineering 的常见失败模式。这个层的价值是“广、快、可检索”，不要求每个案例都展开成文章。
2. **深度样板层**：少数案例承担“怎么做工程归因、怎么复盘错误修复、怎么设计评价和护栏”的教学职责。这个层的价值是“慢、深、可模仿”。

因此，维护原则是：**每类保留 10 个精简案例；每类只在必要时升级 1–2 个深度样板。**

## 3. 候选选择标准

一个 case 值得升级为深度版，至少应满足多数条件：

1. **代表本类的核心失败模式**：不是边角技巧，而是这一类最常见、最危险或最能教学的事故类型。
2. **能写出失败轨迹**：有清楚的 before / after、错误链条、trace 片段或可模拟的工程日志。
3. **能体现“第一次修复为什么错”**：深度版不只是加长版，而要展示工程归因的反转。
4. **能连接决策系统**：可以自然引用 ADS 的 Law / Pattern / Anti-pattern / Eval，而不是硬塞链接。
5. **不和已有深度样板重复**：如果只是在另一个类别重复同一个教训，就不优先升级。

### 01 RAG 与知识系统

**已有样板**：[[ai-engineering-case-library/01_RAG与知识系统#Case 1 · 企业政策问答答非所问（深度版）|Case 1]] 已经承担“RAG 先查检索、再查切分、最后才改生成”的旗舰教学职责。

**建议候选**：

1. [[ai-engineering-case-library/01_RAG与知识系统#Case 5 · 检索库被污染（深度版）|Case 5 · 检索库被污染]]
   - **为什么值得深度化**：它把 RAG、长期记忆、安全、输入即指令连在一起，是“知识库也是攻击面”的典型案例。
   - **升级边界**：重点写上传写入校验、检索内容降权为数据、输出侧护栏和红队测试；不要写成泛泛的“prompt injection 科普”。
2. [[ai-engineering-case-library/01_RAG与知识系统#Case 9 · RAG 上线后质量悄悄下滑|Case 9 · RAG 上线后质量悄悄下滑]]
   - **为什么值得深度化**：它补上 RAG 的生产生命周期问题：代码没变，查询分布和语料覆盖变了。
   - **升级边界**：重点写持续评价、查询分布漂移、拒答率/重问率监控；不要写成“多加监控就好”的口号。

**暂不优先**：Case 10 的“先测瓶颈再上图谱”很重要，但更像原则性提醒；在 Case 1 已经覆盖“先归因再优化”的情况下，不急着深度化。

### 02 Agent 架构

**已有样板**：[[ai-engineering-case-library/02_Agent架构#Case 11 · 把分类任务做成了自主 Agent（深度版）|Case 11]] 已经承担“不要把简单确定性任务过度 Agent 化”的旗舰职责。

**建议候选**：

1. [[ai-engineering-case-library/02_Agent架构#Case 14 · Agent 静默失败编造结果（深度版）|Case 14 · Agent 静默失败编造结果]]
   - **为什么值得深度化**：这是 Agent 系统里最危险的失败形态之一：错误没有中断，而是伪装成成功继续传播。
   - **升级边界**：重点写工具错误如何被吞、状态如何污染下游、如何设计显式失败和 trace；不要只写“加日志”。
2. [[ai-engineering-case-library/02_Agent架构#Case 16 · Agent 照字面执行酿成损失|Case 16 · Agent 照字面执行酿成损失]]
   - **为什么值得深度化**：它能很好展示“指令是意图的有损压缩”和“不可逆操作必须确认”。
   - **升级边界**：重点写澄清机制、权限分级、可逆/不可逆操作边界；不要把问题简化为“用户表达不清”。

**暂不优先**：Case 15 的无 trace 很重要，但它可以作为 Case 14 深度版中的一段机制展开，不必单独抢一个深度名额。

### 03 多 Agent 系统

**已有样板**：[[ai-engineering-case-library/03_多Agent系统#Case 21 · 8 个 Agent 做单 Agent 能做的事（深度版）|Case 21]] 已经承担“多 Agent 有罪推定”的旗舰职责。

**建议候选**：

1. [[ai-engineering-case-library/03_多Agent系统#Case 27 · 一个 Agent 的幻觉污染了全系统（深度版）|Case 27 · 一个 Agent 的幻觉污染了全系统]]
   - **为什么值得深度化**：它展示多 Agent 的独有风险：局部错误跨角色传播，并被后续 Agent 放大。
   - **升级边界**：重点写置信度传递、证据链、下游抽查、跨 Agent 错误传播图；不要写成普通幻觉问题。
2. [[ai-engineering-case-library/03_多Agent系统#Case 22 · Agent 间传完整对话历史导致爆炸|Case 22 · Agent 间传完整对话历史导致爆炸]]

   - **升级边界**：重点写“传结论不传过程”、消息 schema、状态压缩、信息边界；不要把它等同于普通上下文管理。

**暂不优先**：Case 30 是总结性案例，容易变成“多 Agent 掩盖根因”的总论；已有 Case 21 覆盖相近教学目标。

### 04 可靠性与生产

**当前缺口**：本类没有深度样板，优先级高。

**建议候选**：

1. [[ai-engineering-case-library/04_可靠性与生产#Case 31 · Demo 惊艳，生产翻车（深度版）|Case 31 · Demo 惊艳，生产翻车]]
   - **为什么值得深度化**：它是生产系统的第一原则案例：能力峰值不是产品价值，可靠性分布才是产品价值。
   - **升级边界**：重点写 demo 样本选择偏差、线上分布、P50/P95/失败类型分层、上线前验收集；不要写成“demo 不可信”的泛泛批评。
2. [[ai-engineering-case-library/04_可靠性与生产#Case 40 · 非幂等操作重试导致重复扣款（深度版）|Case 40 · 非幂等操作重试导致重复扣款]]
   - **为什么值得深度化**：它是生产工程里非常硬的“副作用 + 重试 + 不可逆”案例，能把抽象可靠性落到机制。
   - **升级边界**：重点写幂等键、重试语义、副作用隔离、金融类不可逆操作验收；不要写成普通异常处理。

**暂不优先**：Case 37 与 07 成本类高度重叠；Case 39 更像通用性能瓶颈原则，生产类第一篇不应从它开始。

### 05 评价与质量

**已有样板**：[[ai-engineering-case-library/05_评价与质量#Case 41 · 刷高 benchmark 真实表现没提升（深度版）|Case 41]] 已经承担“benchmark 不等于真实目标”的旗舰职责。

**建议候选**：

1. [[ai-engineering-case-library/05_评价与质量#Case 43 · 裁判模型从没和人对齐（深度版）|Case 43 · 裁判模型从没和人对齐]]
   - **为什么值得深度化**：LLM-as-judge 是当前评价体系的高频工具，未校准裁判会把系统带向裁判偏好。
   - **升级边界**：重点写人类金标、裁判一致率、偏好偏差、定期重校准；不要把“模型裁判”简单否定掉。
2. [[ai-engineering-case-library/05_评价与质量#Case 44 · 平均分掩盖了致命的尾部失败|Case 44 · 平均分掩盖了致命的尾部失败]]
   - **为什么值得深度化**：它补上 Case 41 没完全展开的尾部可靠性问题，适合连接生产和安全。
   - **升级边界**：重点写分层指标、高风险 slice、尾部失败的人工兜底；不要只把平均分换成更多分数。

**暂不优先**：Case 48 的排行榜误导与 Case 41 接近；如果先深度化它，容易重复“指标代理真实目标”的主题。

### 06 安全与对抗

**已有样板**：[[ai-engineering-case-library/06_安全与对抗#Case 51 · 邮件正文里的注入指令被执行（深度版）|Case 51]] 已经承担“外部输入诱导工具调用”的旗舰职责。

**建议候选**：

1. [[ai-engineering-case-library/06_安全与对抗#Case 54 · 记忆被投毒长期潜伏（深度版）|Case 54 · 记忆被投毒长期潜伏]]
   - **为什么值得深度化**：它把安全问题从一次性 prompt injection 推到长期状态污染，风险更隐蔽。
   - **升级边界**：重点写记忆写入审批、记忆来源分级、过期/撤销、检索时不可信处理；不要和 RAG 污染案例写成同一篇。
2. [[ai-engineering-case-library/06_安全与对抗#Case 55 · 工具组合涌现出危险能力|Case 55 · 工具组合涌现出危险能力]]
   - **为什么值得深度化**：它能展示“单个工具安全不等于组合安全”，是 agentic security 的核心风险。
   - **升级边界**：重点写工具组合审查、权限裁剪、数据外流路径、砍掉致命三重奏的一角；不要只列安全清单。

**暂不优先**：Case 52 与 Case 51 重叠度高；它适合作为 Case 51 的反面材料，不急着独立深度化。

### 07 成本与性能

**当前缺口**：本类没有深度样板，优先级高。

**建议候选**：

1. [[ai-engineering-case-library/07_成本与性能#Case 61 · 简单任务也用最贵的模型（深度版）|Case 61 · 简单任务也用最贵的模型]]
   - **为什么值得深度化**：它是成本工程的第一原则：模型能力要和任务难度匹配，不是所有请求都值得最强模型。
   - **升级边界**：重点写任务分层、路由阈值、fallback、质量不下降的验收；不要写成“用小模型省钱”的单点技巧。

   - **升级边界**：重点写历史分层、摘要策略、缓存、外置记忆、成本曲线；不要和 08 类的上下文腐烂完全重复。

### 08 记忆与上下文

**当前缺口**：本类没有深度样板，优先级高。

**建议候选**：

1. [[ai-engineering-case-library/08_记忆与上下文#Case 73 · 长任务上下文腐烂决策变差（深度版）|Case 73 · 长任务上下文腐烂决策变差]]
   - **为什么值得深度化**：它是长任务 Agent 的核心问题：上下文不是越多越好，状态会被失败尝试和噪声污染。
   - **升级边界**：重点写上下文清理、阶段性摘要、状态重建、失败尝试归档；不要写成“定期总结一下”。
2. [[ai-engineering-case-library/08_记忆与上下文#Case 75 · 压缩丢掉了后续需要的细节（深度版）|Case 75 · 压缩丢掉了后续需要的细节]]
   - **为什么值得深度化**：它能展示压缩的根本取舍：压缩一定有损，关键是知道什么不能丢。
   - **升级边界**：重点写任务感知摘要、关键字段保留、细节外置可检索；不要把它写成“摘要 prompt 改好一点”。

**暂不优先**：Case 71 的“全量历史塞满上下文”是基础问题，但 Case 73 更能体现长任务中的状态腐烂和工程治理。

### 09 数据与模型定制

**当前缺口**：本类没有深度样板，优先级高。

**建议候选**：

1. [[ai-engineering-case-library/09_数据与模型定制#Case 81 · 想微调注入公司知识（深度版）|Case 81 · 想微调注入公司知识]]
   - **为什么值得深度化**：它是模型定制最常见误区：把“知识更新”误判成“权重修改”。
   - **升级边界**：重点写 prompt / RAG / 微调的选择树、知识时效、可溯源、维护成本；不要把微调一概打成错误。
2. [[ai-engineering-case-library/09_数据与模型定制#Case 88 · 数据泄漏导致评测虚高（深度版）|Case 88 · 数据泄漏导致评测虚高]]
   - **为什么值得深度化**：它把训练、评测和数据治理串起来，是“模型看起来变好”的典型假象。
   - **升级边界**：重点写训练/评测隔离、泄漏检测、异常高分排查、上线回落解释；不要写成一般数据清洗。

**暂不优先**：Case 83 的脏数据微调很重要，但它可以作为 Case 81 或 Case 88 深度版中的风险分支，不必第一批单独展开。

### 10 人机与产品决策

**当前缺口**：本类没有深度样板，优先级高。

   - **为什么值得深度化**：它是人机协作和产品责任的核心案例：AI 可以生成，但不可逆发布必须有人守门。

## 6. 深度版模板建议

未来把一个 case 升级为深度版时，不要只是把文字写长。建议每个深度版至少包含这些块：

1. **失败前提**：系统、用户、权限、数据和上线环境。
2. **失败轨迹**：一条具体 trace、日志、对话或调用链。
3. **根因归因**：先判断瓶颈在哪，不直接给方案。
4. **第一次错误修复**：写出一个看似合理但失败的修复，以及为什么失败。
5. **架构决策**：最终为什么选这个方案，放弃了哪些方案。
6. **评价方法**：如何证明修复有效，最好分层而不是单一平均分。
7. **护栏/运营机制**：上线后如何持续发现退化或滥用。
8. **Lessons Learned**：保留 3–5 条可迁移教训，避免写成案例摘要。

## 7. 不做什么

- 不把 100 个案例全部深度化；那会破坏案例库的扫描价值。
- 不改现有 case 编号；编号是案例库导航资产。
- 不为了“每类平均”而硬凑深度版；候选必须有真实教学密度。
- 不在深度版里新增未经核验的外部事实或 citation；需要事实性来源时另开核验任务。
- 不让深度版替代 ADS 链接系统；深度版应该使用现有 `LAW / PAT / ANTI / Q / SIT` 路由，而不是另造一套分类。

## 8. 总编辑判断

最合理的下一步不是“继续审计”，而是让一个强写作模型或主编按 Batch A 写 5 个深度样板。写完后再复查三件事：

1. 是否每个新增深度版都真的有失败轨迹和错误修复反转；
2. 是否保留了精简层，不把同类其他 9 个案例拖成长文；
3. 是否继续通过 ADS ↔ Case Library 的 cross-reference 验证。

Batch A/B/C 完成后，案例库双层结构已从“5 个孤立深度样板”变成“10 类各有 2 个深度样板”的稳定结构。此后默认停止深度化，除非另有明确教学缺口。
