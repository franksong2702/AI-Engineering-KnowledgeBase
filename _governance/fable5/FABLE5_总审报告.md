## 3. 必须保留的 10 个优点（不能被重写洗掉的核心资产）

1. **根命题及其演绎树**（00_总图）。"不可靠部件造可靠系统｜生成廉价、验证稀缺"确实能推出全库主要结论，这是知识库的脊椎，也是它区别于"模型堆百科"的根本。
2. **五层抽象 = 保值期刻度**（Foundation 元命题一 + 总图倒金字塔）。"投入与保值期成正比"是全库最可操作的元指导。
3. **《The Constitution》的四问格式**（为什么重要/违反会怎样/如何应用/如何判断做对）。60 条全部自包含、判断硬、无一条是空话，是全库压缩质量的天花板。
4. **Laws 的"硬度分级"**（数学级→工程强规律级）。诚实标注每条定律的根扎在哪，这是对"定律"一词的负责任用法，极少有资料这么做。
5. **"何时不用"的全库纪律**。每个模式、每个框架都带 When-not-to-use；多 Agent 有罪推定、反思无锚不做、微调是最后手段——负空间知识是这套库最值钱的部分。
6. **编辑审计的自我诚实**（01_编辑审计）。🔴🟡🟢 分级、显式列出重复/矛盾/缺失，包括"C1 多 Agent 张力"的调和已真实落进 Multi-Agent INDEX 的 warning callout——自知是真的，不是姿态。
7. **Agent Decision System 的架构设计**。决策循环 7 步（STEP 3 约束与 STEP 7 验证不可跳过）、6 字段输出、7 字段卡片、17 情境路由——这个"操作层投影"的设计本身是原创且正确的，值得保护。
8. **教材的项目硬关卡制**。"项目没跑通不进下一章"、七日 AI 日记作为后续需求来源——教学设计有真实的学习科学依据（检索练习、做中学）。
9. **有意保留的多视角重复**（R3 反思四处、R4 决策原则三处）。各处讲不同层面且共享同一核心洞察，这是知识网络该有的形态，不是冗余。
10. **Foundation 第 7 章**（稀缺性转移、负空间、隐性知识悖论）。全库判断密度最高的一章，几乎没有模型腔，是"有总编辑"的最好证明。

## 4. 最危险的 10 个问题（按严重程度排序）

### 问题 1 · 自描述层与实际内容脱节一个版本 🔴

- **描述**：README 标题"十一本书（核心九本 + 补充两本）+ 102 个文件"，但正文列出 ⑩⑪⑫ **三本**补充书（12 本）；00_总图的"知识库全景"表只有 11 本，**完全没有《Human-AI Collaboration Foundation》**；Constitution 说"11 本书、102 文件"。实际 md 文件 **131 个**（102 = 加入 Constitution、Case Library(11)、Human-AI(11)、Decision System(6) 这 29 个文件**之前**的历史值：102+29=131，严丝合缝）。
- **为什么危险**：README 是全库第一屏。新读者第一分钟就能发现"它说 102 实际 131、说 11 本列了 12 本"，对一套反复强调"自描述要准确""诚实校准"的知识库，这是自反性的信任伤害；对未来 Agent，错误的全景表意味着永远路由不到 Human-AI 那本书。
- **证据**：`README.md` L10 vs L65–72；`00_Knowledge-Graph-总图.md` L10、L15–27（表中无 human-ai-collaboration-foundation）；`The-Constitution-of-AI-Engineering.md` L11；实测文件数 131。
- **修复**：统一为"12 本书 + 案例库 + 决策系统 + 图谱层，131 文件"；总图全景表补第 12 行；Constitution 序言同步。可写一个"自描述校验脚本"防再犯。

### 问题 2 · 生成环境泄漏链接混入正文 🔴

- **描述**：正文中存在指向**生成模型自身工作环境**（而非知识库）的 wikilink：`[[product-management:write-spec]]`、`[[product-management:roadmap-update]]`（agent-bible/02 L119, L121）、`[[skill-creator|评测]]`（agent-bible/03 L120）、`[[docx]]`×2（agent-bible/03 L151, L157）、`[[user_wellbeing]]`×3（agent-bible/05 L83；anti-patterns/07 L281, L289）、`[[wikilink]]`（agent-bible/01 L132，从 vault 宪法漏进来的）。
- **为什么危险**：这是"模型堆出来的百科"最实锤的物证——Claude 把自己 system prompt 里的 skill 名当成了知识库页面。它们全部是断链，且暴露了生成过程，严重损害"有总编辑"的可信度。
- **证据**：路径与行号如上，全 vault 检索确认这些目标页不存在。
- **修复**：逐一改写为普通文本或指向库内正确页面（如 `[[user_wellbeing|谄媚]]` → 直接写"谄媚"或链到 Evaluation Part 5）。共约 10 处，半小时可清完。

### 问题 3 · Agent Decision System 的 ID 引用错乱 🔴

- **描述**：`04_LAW-INVARIANTS` 的正典定义 LAW-04=古德哈特、ANTI-08=记忆倾倒、ANTI-11=谄媚。但 `01_SITUATION-ROUTER` 里 SIT-02/SIT-12 写"LAW-04(信息守恒)"、SIT-02 写"ANTI-11(推理不接地)"、SIT-02/SIT-08 写"ANTI-08(检索盲信)"；`02_PATTERN-CARDS` PAT-03 也写"LAW-04(信息守恒)"。而"信息守恒""检索盲信""推理不接地"**在 12 条 invariants / 12 个 detectors 里根本没有 ID**。污染已扩散到 Case Library（Case 1 的"ANTI-08(不再盲信纯向量检索)"）。
- **为什么危险**：这套系统的全部卖点是"机器可按 ID 精确取用"。一个 Agent 按 SIT-02 的指引去查 LAW-04，取回的是古德哈特而非信息守恒——**在最强调机械可判定的模块里，引用本身不可判定**。
- **证据**：`agent-decision-system/01_SITUATION-ROUTER.md` L29, L31, L83–86, L119；`02_PATTERN-CARDS.md` L37；`ai-engineering-case-library/01_RAG与知识系统.md` Case 1。
- **修复**：两种修法需你选择——(a) 扩充 invariants/detectors 把"信息守恒""检索盲信"收编为新 ID；(b) 保持 12+12 不变，把所有错误引用改到正确 ID 或改为无 ID 的文字引用。然后全库 grep 校验每个 `LAW-xx/ANTI-xx/PAT-xx/Q-xx` 与正典一致。

### 问题 4 · 344 处 `[[00_INDEX]]` 歧义链接 🔴

- **描述**：13 个模块共用文件名 `00_INDEX.md`（vault 全域 14 个），全库有 **344 处** `[[00_INDEX|…]]` 形式的链接，Obsidian 无法确定指向哪本书。审计 H1 已识别，README 用完整路径做了入口级缓解，但正文的 344 处（占全库 1699 个链接的 20%）仍然是"显示正常、点开随机"。
- **为什么危险**：这不是装饰问题——跨书链接是这套库"网络价值"的载体，20% 的链接失灵意味着知识图谱在 Obsidian 里实际上是断裂的；graph view 也全部坍缩到错误节点。
- **证据**：程序化解析 1699 个 wikilink，`[[00_INDEX]]` 344 次命中、13 个候选文件。
- **修复**：两种修法——(a) 全部改为路径式 `[[laws-of-ai-engineering/00_INDEX|…]]`（脚本可自动化，按上下文推断目标书，需人工抽检）；(b) INDEX 物理重命名为唯一名（更彻底但要同步改 344+ 处引用）。建议 (a) 先行，风险低。

### 问题 5 · 指向不存在章节的"幽灵链接" 🟠

- **描述**：正文引用了从未写出的文件：`[[07_沟通与协作]]`×2（Agent 圣经只有 5 个家族，疑似原计划 7 章）、`[[16_质量控制模式]]`（llm-design-patterns 只有 01–05）、`[[07_分布内可靠定律|分布内可靠]]`（laws 是 11 个家族文件，无此名）、`[[Cynefin]]`×5（全 vault 无此页，指向的应是 decision-frameworks/01 内的小节）。
- **为什么危险**：幽灵链接暴露"目录曾经变更但正文没同步"，与问题 1 同源；`[[07_沟通与协作]]` 还说明 Agent 圣经可能有一个被砍掉的家族，INDEX 却没有任何说明。
- **证据**：agent-bible/03 L157、agent-bible/04；llm-design-patterns/01；laws/11_演化与元定律；foundation/03、laws/02、anti-patterns/04、anti-patterns/06×2。
- **修复**：Cynefin 改为 `[[01_问题定义型|Cynefin]]`；其余改指真实存在的文件/小节；确认 Agent 圣经"沟通与协作家族"是补写还是删引用（需你决定）。

### 问题 6 · 审计承诺的结构化字段基本未落地 🟠

- **描述**：aliases **0/131**；`abstraction_layer` 仅 **24/131**（只有 INDEX 和少数顶层文件有，全部正文章节没有）。审计 H3 说这是"最有价值的结构化改进"、02_学习路径把它列为"持续维护"第一项——说了，没做。
- **为什么危险**："投入与保值期成正比"这条全库最重要的使用指南，因为字段缺失而**不可操作**（无法按层过滤）；aliases 缺失加剧 INDEX 歧义。
- **证据**：frontmatter 全量扫描结果。
- **修复**：批量补 `abstraction_layer`（每本书内的章节可继承书级默认值，脚本可做 80%）；为 13 个 INDEX 补唯一 aliases。

### 问题 7 · 三本"补充书"名实不副 🟠

- **描述**：data-foundation 全书 12k 字符、model-adaptation 12k、human-ai-collaboration 21k——分别只有 Laws（80k）、Anti-Patterns（65k）的 1/7 到 1/3。它们在 README 里与核心书平级并列为"第⑩⑪⑫本书"。
- **为什么危险**：读者按"书"的预期进入，拿到的是提纲式小册子；更实质的是，per-Part 平均 2k 字符的内容撑不起"数据质量决定系统上限"这种地基级主张的展开——它们目前是**正确的目录 + 正确的判断 + 不足的血肉**。
- **证据**：各目录字符数统计；data-foundation/01 全文仅 68 行。
- **修复**：二选一——(a) 诚实降格：在 README/总图里标注为"纲要版（v0.5，待扩写）"；(b) 分批扩写到与主张匹配的深度（每 Part 补反例、验收标准、工程细节）。不建议假装它们已是完整的书。

### 问题 8 · 数字断言与"真实案例"缺乏事实支撑标注 🟠

- **描述**：全库**零外部引用**。多处具体数字无来源也无"典型化"标注：如"多 Agent 的 token 消耗是单 Agent 的 3-15 倍"（multi-agent INDEX）、"80% 的 RAG 问题在检索环节"（Case 1）、"混合检索命中率从 60% 提到 90%"（Case 1）、"每步 97% 可靠整体仅约 40%，加反思提到 85%"（Law 14"真实案例"）。Case Library 有诚实声明（"典型化、综合化"），但 Laws 的"真实案例"字段和各 INDEX 的数字没有同等声明。
- **为什么危险**：这些数字会被读者当实证转述、被 Agent 当参数使用。数学推导类（0.95²⁰≈0.36）是硬的，没问题；但"3-15 倍""80%"是经验估计冒充测量值——这正是本库自己定义的"流畅≠正确"。
- **证据**：路径如上；全库 grep 无 URL/文献引用（教材阅读资料除外）。
- **修复**：给此类数字统一加标注（"经验量级，非测量值"），或在各书开篇加一条与 Case Library 相同的诚实声明；Laws 的"真实案例"字段改名"典型案例"。不建议未经核验补外部 citation（符合你的工作纪律）。

### 问题 9 · 审计承诺的两处调和（C2/C4）未落地 🟡

- **描述**：审计说"建议在 Design Patterns 的 CoT 条目加演化说明"（C2：教 CoT vs 警告成瘾 vs 终将内化）、"建议教材第 6 章补 RAG 边界说明"（C4）。抽查显示 llm-design-patterns 的跨模式定律 6 有一句"推理模型内化了 CoT"，但 CoT 条目本身无三书串联的演化说明；教材第 6 章未见边界句。
- **为什么危险**：审计的公信力依赖"说了就做"。C2 是零基础读者最容易困惑的点（教材刚学完 CoT 就在 Anti-Patterns 撞见"CoT 成瘾"）。
- **证据**：`01_编辑审计.md` C2/C4 的"建议"措辞 vs 对应文件现状。
- **修复**：按审计原方案执行，各加一段"演化说明"，属低风险小改。

### 问题 10 · 决策系统缺机器可读格式，"可调用"停留在人读层 🟡

- **描述**：Agent Decision System 全部是 markdown 散文字段。一个真实 Agent 要用它，得先做非平凡的解析（字段名是中英混排的加粗文本，条目间格式有微小漂移）。
- **为什么危险**：不致命（LLM-Agent 可以直接读 markdown），但"SELF-CONTAINED、可查询"的承诺与"需要自己写 parser"之间有落差；且格式漂移（如 SIT 条目的 Checklist 有的用 ☐ 有的用问句）让机械校验困难。
- **证据**：`agent-decision-system/` 全部 6 文件的格式比对。
- **修复**：P2——为 5 个模块各生成一份对照的 YAML/JSON 影子文件（由 md 编译而来，md 仍是正典），并统一字段格式。

## 8. 不应做的事（看似优化，实际破坏）

1. **不要统一全库文风**。Laws 的字段体、Foundation 的散文体、教材的教程体是三种正确的体裁——洗成一个腔调会毁掉"多本书"的真实感和各自的功能。
2. **不要删除 R3/R4 类多视角重复**。反思出现四处是网络的价值不是冗余；"消重"到只剩一处会把知识网络退化成树。
3. **不要给每条断言补外部 citation**。未经核验的引用比没有引用更糟（本库自己的定律）；标注"经验量级"比伪造学术感诚实。
4. **不要把三本薄书硬灌成厚书**。用生成填充物把 12k 撑到 80k 是最典型的模型行为——扩写必须每段带新的反例/验收标准/工程细节，否则宁可保持"纲要版"标注。
5. **不要在修 ID 时顺手"改进"卡片内容**。P0-3 是纯机械修复，混入内容修改会让 diff 不可审计。
6. **不要物理重命名 00_INDEX 一步到位**。344+ 处引用的大爆炸式重命名风险高；先走路径式链接方案，重命名留作独立的、可回滚的任务。
7. **不要把 Constitution 扩长**。它的价值就在 20 页的纪律；每次想加内容，应该问的是"该删哪条给它腾位"。
8. **不要一轮全量重写任何一本书**。这套库的骨架是对的，错的是校对层——用重写解决校对问题，会把已经沉淀的正确判断置于回归风险中。
9. **不要为凑"每书同构"强行给案例库/决策系统加书式 INDEX 结构**。它们是应用层和机器层，形态本该不同。

## 9. 最终判断：这套 KB 应该被定位为什么

**多层混合体，且应该显式承认并标注这个混合结构**——它事实上已经是四层：

1. **公理层教材**（Constitution + Laws + Foundation）：最接近"教材"定位，是可以对外单独成立的部分，保值期最长。
2. **工程手册**（Design Patterns + Multi-Agent + Anti-Patterns + Evaluation + Decision Frameworks + Agent Bible + 三本补充书）：查阅型资产，按需进入。
3. **Agent 操作系统**（Agent Decision System + Case Library）：这是全库最有野心的定位，架构已成立、实现差一次校对——修完 P0-3 它就是你未来 Agent 的真实运行时依赖，这也是全库长期价值最高的一层。
4. **个人知识库 / 课程资产**（Textbook + 图谱层 + 学习路径）：服务你自己和潜在学习者的封装层。

主编判断：**不要在四个定位里选一个，要把"哪层服务谁"写进 README**。当前 README 已经隐约这么做了（"只有 20 页时间？""你是 AI Agent？"），方向对，执行到一半。这套库的独特价值不在任何单层——市面上有更全的教材、更深的手册——而在**四层从同一个根命题派生、且相互引用可验证**这个结构本身。所以一切维护动作的优先级都应该服从一个标准：**保卫派生链的可验证性**（数字对、链接通、ID 准、正典明）。这正是本轮 P0 全部指向的东西。
