# 《Agent 圣经》P1-C 生产级样板立项审计

> 本文只回答：P1-C 是否值得做、应该做成什么、五个样板如何避免与 ADS 和反模式冲突。本轮**不改 Agent Bible 正文，不新建 Agent 编号，不实现机器编译链**。后续若实施，唯一活任务状态仍回到 [编辑审计](../../01_编辑审计.md)。

> [!success] 实施状态（2026-07-12）
> 用户随后授权按推荐顺序完成四个 Batch。Batch A–D 已全部落地：INDEX 承诺收窄、共享 Schema、五个能力契约、50 个契约测试用例定义、5 条终态 trace 样例、Markdown → machine JSON 编译器、语义检查器、角色/ADS/Maintenance 接入均已完成。当前验证契约与 fixture，不声称真实模型行为测试已通过。本文保留为立项依据；最终运行入口见 [能力契约索引](../../agent-bible/contracts/00_INDEX.md)。

## 一、裁决先行

### 1.1 立项，但要改写项目名称

**建议立项。**但不应把它理解成“把五个角色卡写得更长”，而应命名为：

> **五个能力契约样板（Capability Contract Samples）**

保留 [Agent Bible INDEX](../../agent-bible/00_INDEX.md) 的 21 个角色名称作为人类容易理解的目录；生产样板改用能力名称：

| 现有角色入口 | 生产样板的能力名称 | 核心可验证差异 |
|---|---|---|
| [研究员](../../agent-bible/01_研究与知识.md) | 研究取证 `research_evidence` | 多源读取、来源账本、事实/推断分离 |
| [事实核查员](../../agent-bible/01_研究与知识.md) | 独立事实核查 `fact_verification` | 独立上下文、逐论断裁决、假阴性优先 |
| [架构师](../../agent-bible/03_工程与构建.md) | 架构取舍设计 `architecture_tradeoff` | 需求/约束、方案比较、ADR、失败路径 |
| [调试专家](../../agent-bible/04_质量与审查.md) | 根因诊断 `root_cause_diagnosis` | 假设队列、复现证据、诊断与修复分离 |
| [通用评审](../../agent-bible/04_质量与审查.md) | 标准化评审 `rubric_review` | 外部 rubric、逐项证据、校准记录 |

这五个可以由同一个底层模型执行；它们不需要被部署成五个长期在线的“虚拟员工”。只有上下文、工具、权限或评价标准确实需要隔离时，才值得拆成独立调用。

### 1.2 一个必须先修的名实问题

INDEX 当前写道：“拿走 System Prompt 就能用，配上 Memory 和工具设计就能进生产。”这个承诺过强。

现状只能支持：

> 21 个条目是高质量角色卡和 System Prompt 起点；进入生产还需要输入输出 schema、工具权限、状态协议、停止与升级条件、测试集、trace 和运行时门禁。

因此若实施 P1-C，第一项不是写新内容，而是先收窄 INDEX 的产品承诺。否则新增五个样板后，读者仍可能误以为另外十六个也已达到生产级。

### 1.3 为什么不是二十一个全量扩写

逐条结构审计结果：

- 21/21 都已有职责、适用问题、输入、输出、System Prompt、Memory、工具、评价、失败模式、最佳实践和未来扩展；
- 每条正文约 1,027–1,252 字，平均约 1,107 字；
- 作为“角色目录 + prompt 起点”，现有完成度足够；
- 全量扩写会制造重复 schema、维护负担和“每个职位都应部署一个 Agent”的错误暗示。

所以 P1-C 的价值来自**做出五个可比较的样板和一套共享契约**，不是增加 21 倍篇幅。

## 二、与全库架构的边界

### 2.1 与拟人化分工反模式

[Agent 架构反模式](../../ai-engineering-anti-patterns/01_Agent架构反模式.md) 的 AP-6 明确反对按 CEO、经理、员工等职位拆 Agent。其检测标准不是“名字像不像人”，而是：这个角色能否由真实的上下文、工具或权限差异解释。

本项目必须执行以下防线：

1. 角色名称只作人类入口，不作多 Agent 拓扑；
2. 每个契约必须写出与邻近角色的可判定边界；
3. 如果两个契约只有 System Prompt 不同，工具、权限、输入和评价都相同，默认合并为同一能力的不同模式；
4. 不新增 CEO/CTO/PM 等职位型生产样板；
5. 示例编排优先展示“一个执行器按契约切换”，而不是五个 Agent 互相传话。

### 2.2 与 ADS 的主从关系

[Agent Decision System](../../agent-decision-system/00_PROTOCOL.md) 决定跨任务的运行纪律：怎么分类处境、约束风险、选择模式和定义验收。Agent Bible 决定某项能力的输入、工具、输出和失败协议。

两者关系应固定为：

```text
ADS：这次任务是否值得用 Agent、必须守什么约束、如何验收
  ↓
能力契约：选定能力后，执行器接受什么、能做什么、何时停、交付什么
```

能力契约只引用现有 `SIT / LAW / PAT / ANTI / Q`，不复制定义，不新开 `AGENT-01` 之类编号空间。

### 2.3 与 Evaluation 和教材实验包

- [Evaluation 端到端样板](../../evaluation-of-ai-systems/08_端到端评价工程样板.md)负责评价体系和发布证据链；
- [教材第 7 章实验包](../../textbook-zero-to-agent/labs/07_裸写文件Agent实验包.md)负责最小 Agent 循环；
- Agent Bible 的五个样板负责**能力级契约**，不重复 Agent 循环代码，也不另造评价理论。

## 三、统一契约应该包含什么

现有 11 个角色卡字段继续保留给人阅读。生产样板新增一套统一的 14 段契约：

| 段 | 说人话的含义 | 机械要求 |
|---|---|---|
| `capability` | 这是什么能力，不是什么职位 | 稳定英文 slug，不设数字 ID |
| `contract_version` | 这份契约是哪一版 | 语义版本，例如 `1.0.0` |
| `when_to_use` | 什么任务该调用 | 至少一个可判定条件 |
| `when_not_to_use` | 什么任务不该调用 | 包含更简单方案或邻近能力 |
| `input_schema` | 调用前必须给什么 | 严格 JSON Schema，缺字段拒绝 |
| `output_schema` | 成功、部分完成、失败分别返回什么 | 三种状态都可机器解析 |
| `tools_and_permissions` | 能读什么、能写什么、能不能联网 | 默认拒绝；每项工具写作用域和副作用 |
| `state_schema` | 本次任务进行到哪里 | 状态与长期记忆分开 |
| `memory_policy` | 什么能记、何时更新、冲突怎么办 | 来源、更新时间、删除/过期规则 |
| `budget` | 最多走多少步、花多少时间/调用 | 达到上限显式停止 |
| `stop_block_escalate` | 何时成功停止、何时受阻、何时交人 | 三类条件不能混写 |
| `failure_protocol` | 工具坏了、证据不足、输出校验失败怎么办 | 不得伪装成功；定义降级和部分结果 |
| `trace_schema` | 事后如何知道它做了什么 | 事件、工具、证据、决策、停止原因 |
| `evaluation_suite` | 如何证明契约真的约束行为 | 5 正常 + 5 反例/对抗 + 关键硬门禁 |

### 人工维护内容与自动生成文件

建议采用与 ADS 相似、但更轻的单一来源方案：

1. Markdown 运行规则页是唯一需要人工维护的来源；
2. 每页包含一个带标记的严格 JSON contract block；
3. 编译器从 Markdown 抽取并生成 `agent-bible/contracts/_machine/contracts.json`；
4. 编译器校验必填字段、schema 可解析、能力 slug 唯一、引用的 ADS ID 存在；
5. `_machine` 文件不手改。

不建议 Markdown 和独立 JSON 各维护一份，否则五个样板很快漂移。

## 四、五个样板的具体边界

## 4.1 研究取证

**存在理由**：需要主动发现外部证据、维护来源账本并综合结论，而不是只改写用户给定材料。

- 输入：研究问题、目标分布、时间/地域边界、允许/禁止信源、预算、输出受众；
- 工具：搜索与网页/文档读取默认只读；写入只能落到任务 workspace；不拥有发布和外发权；
- 状态：子问题、已访来源、来源 hash/时间、claim-evidence 对照、待查项；
- 停止：关键问题达到证据门槛；或预算耗尽后交付明确的 partial report；
- 升级：一手资料不可得、权威来源冲突、任务涉及高风险专业判断；
- 邻近边界：Research Planner 只拆计划；Fact Verification 独立验证已有论断；Knowledge Curator 负责入库，不负责新事实发现；
- ADS：`SIT-02/03/08/09/15`；`LAW-01/02/03/05/06/07/13`；`PAT-03/04/07/09/15`；重点防 `ANTI-01/08/10/12`；验收 `Q-01/02/06/08`。

硬门禁：编造来源、来源不能支撑对应论断、把推断标为事实，任一出现即失败。

## 4.2 独立事实核查

**存在理由**：它必须与原作者/研究过程隔离上下文，优化目标是假阴性和证据可追溯，而不是报告完整度。

- 输入：待核查文本或 claim 列表、权威信源规则、判定标签定义、风险等级；
- 工具：权威数据库、搜索、文档读取，只读；默认不能改原稿或直接发布；
- 状态：claim ledger、检索查询、支持/反驳证据、终态判定；
- 停止：每条 claim 都进入“属实/存疑/证伪/无法核实”之一；
- 升级：医学、法律、财务等高风险领域；来源冲突无法按规则裁决；
- 邻近边界：Reviewer 判断是否符合 rubric，不替代事实核查；Researcher 产出综合结论，不可自称独立核查；
- ADS：`SIT-02/15`；`LAW-01/02/03/13`；`PAT-03/04/07/15`；重点防 `ANTI-02/10`；验收 `Q-02/06/07/10`。

硬门禁：没有证据却判“属实”、虚构核查来源、高风险论断只由同源模型放行。

## 4.3 架构取舍设计

**存在理由**：把需求和约束转成组件、接口、数据流、失败路径和 ADR；它不负责替业务方确定价值目标。

- 输入：功能需求、质量属性、规模、预算、团队、现有系统、不可违反约束；
- 工具：代码库/架构文档/运行指标只读；默认不能改代码或部署；
- 状态：需求假设、备选方案、决策矩阵、被拒方案、ADR；
- 停止：最简可行方案、取舍、失败路径、验证计划和开放问题齐全；
- 升级：价值目标冲突、缺少安全/合规责任人、不可逆迁移、关键约束未知；
- 邻近边界：CTO 偏战略与团队长期能力；Workflow Designer 偏步骤编排与恢复；PM 负责问题和价值；
- ADS：`SIT-01/04/06/07/14/17/18`；`LAW-05/06/09/10/11/12`；`PAT-07/08/15/18`；重点防 `ANTI-04/06/07`；验收 `Q-01/03/04/05`。

硬门禁：未说明更简单替代方案、只画 happy path、把未知约束假装成确定结论。

## 4.4 根因诊断

**存在理由**：围绕一个已经发生的故障维护假设—证据—实验链；它和主动代码评审、修复执行是三个阶段。

- 输入：预期/实际、复现步骤、日志、版本与环境、最近变更、允许执行的诊断命令；
- 工具：日志/代码读取、测试与沙箱命令；生产默认只读；修复写入需进入另一个明确授权阶段；
- 状态：候选假设、支持/反驳证据、实验结果、当前最小复现；
- 停止：根因有可重复证据；或信息不足，列出下一条最有信息价值的检查；
- 升级：需要生产写操作、涉及秘密/个人数据、可能扩大事故、两轮关键实验仍无法区分假设；
- 邻近边界：Code Reviewer 主动审 diff；Security Auditor 从攻击路径找漏洞；Debugger 解释已发生故障；
- ADS：`SIT-13/17/20`；`LAW-01/06/07/09/12`；`PAT-04/07/15`；重点防 `ANTI-01/10/12`；验收 `Q-02/03/08`。

硬门禁：没有复现或证据就宣称根因、诊断阶段擅自改生产、把症状缓解写成根因修复。

## 4.5 标准化评审

**存在理由**：依据外部 rubric 对产物作逐维度、有证据、可校准的裁决；它不是泛化的“再看一遍”。

- 输入：产物、真实目标、rubric、受众、严重度定义、发布权限、领域边界；
- 工具：产物/规范读取，可选测试和事实核查；默认只读，不替作者静默改稿；
- 状态：逐维证据、问题清单、严重度、校准样本；
- 停止：每个 rubric 维度都有证据和裁决，整体结果与硬门禁一致；
- 升级：rubric 缺失或自相矛盾、需要专业事实裁决、评审者与作者同源且高风险；
- 邻近边界：Critic 在无固定 rubric 时挖盲点；Fact Verification 判断事实；Code Reviewer 面向代码专用风险；
- ADS：`SIT-05/10/15/17`；`LAW-01/03/04/12`；`PAT-05/06/07/15`；重点防 `ANTI-03/05/09/11`；验收 `Q-01/05/06/10`。

硬门禁：无 rubric 却给精确总分、关键问题被平均分抵消、未校准 Judge 独自放行高风险产物。

## 五、测试与 trace 最小标准

### 5.1 每个契约的十个用例

五个正常用例不能都是 happy path，应覆盖：标准输入、工具暂时失败、证据不足、部分完成和预算边界。

五个反例/对抗用例至少覆盖：

1. 要求越权或绕过审批；
2. 不可信工具返回值夹带指令；
3. 缺必需输入却诱导 Agent 猜测；
4. 重复调用/循环无出口；
5. 让该能力承担邻近能力的职责。

测试结果必须验证**状态、工具调用、权限和停止原因**，不能只看最终文本像不像。

### 5.2 trace 统一事件

五个样板统一使用：

```text
task_received → input_validated → state_updated → tool_requested
→ tool_allowed/tool_denied → tool_result → evidence_recorded
→ blocked/escalated/completed
```

trace 不要求隐藏思维链；只记录任务状态、可审计行动依据、工具参数摘要、结果、证据引用和停止原因。敏感输入先脱敏再落盘。

## 七、实施批次与冲击控制

### Batch A：承诺收窄 + schema

- 收窄 INDEX 的“直接进生产”承诺；
- 新建 contracts INDEX 和统一 schema；
- 只做一个最小 contract fixture，先验证编译方式；
- 不动五个角色正文主体。

**停手检查**：人能说清角色卡与生产契约差别；机器能拒绝缺字段和未知 ADS ID。

### Batch B：研究取证 + 独立事实核查

- 两者一起做，强制验证上下文独立和职责边界；
- 各 10 个用例、1 条完整 trace；
- 用同一份输入演示“产出研究”和“核查研究”为什么不是两个头衔。

**停手检查**：Fact Verification 不复用 Research 的未验证结论作证据；两者工具/状态/评价存在真实差异。

### Batch C：架构取舍 + 根因诊断 + 标准化评审

- 三者共享只读 repo 工具，但权限、状态和停止条件不同；
- 明确诊断不等于修复、评审不等于改稿、架构不替业务拍板；
- 各 10 个用例、1 条完整 trace。

**停手检查**：同一底层模型切换契约时，执行边界能被测试识别，不只是输出语气不同。

### Batch D：编译、交叉校验与全库接入

- 生成 `_machine/contracts.json`；
- 校验 5 个 slug、必填字段、ADS ID、用例数、trace 终态；
- Agent Bible INDEX、五个原角色 heading、ADS source map、Maintenance 接入；
- 不把五个能力做成新的 ADS 编号空间。

**停手检查**：Markdown 与 machine 文件同步；所有入口可一键直达；全库体检通过。

### 全局影响面

| 区域 | 应改 | 不应改 |
|---|---|---|
| Agent Bible | INDEX 承诺、五个 heading 的入口、新 contracts 子目录 | 其余十六个角色正文批量加厚 |
| ADS | Source Map 增加能力契约入口；校验引用 ID | LAW/PAT/ANTI/Q 定义和编号 |

## 八、停手判据与最终建议

P1-C 完成必须同时满足：

1. 五个能力使用同一套 14 段结构；
2. 作为定义来源的 Markdown 能生成单一 JSON 文件且严格同步；
3. 每个能力 5 正常 + 5 反例/对抗用例可重复执行；
4. 每个能力至少一条完整 trace 到达明确终态；
5. 每个能力能用上下文、工具、权限或评价差异证明存在理由；
6. INDEX 不再暗示全部 21 个角色已可直接进入生产；
7. ADS 编号空间不变，体检与交叉校验通过。

满足后停止。不要把“生产级”继续升级成完整运行平台，也不要顺手为剩余十六个角色复制模板。

### 最终裁决

**P1-C 值得实施，推荐按 Batch A → B → C → D 执行。**它修复的是 Agent Bible 最重要的名实问题：把五张优秀角色卡编译成真正可约束执行器的能力契约；同时保留二十一个角色目录的阅读价值，不把职位比喻误做成多 Agent 组织架构。
