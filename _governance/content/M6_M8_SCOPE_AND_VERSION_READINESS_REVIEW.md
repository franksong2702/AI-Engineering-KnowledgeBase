# M6–M8 立项与 v1.0 收束审计

> 本文只做架构裁决，不启动新书写作。它回答四个问题：M6、M7、M8 是否是当前缺口；应该以什么形态进入；是否阻塞本知识库进入 v1.0；什么条件下才重新立项。

## 一、结论先行

| 候选 | 当前裁决 | 是否阻塞 v1.0 | 未来形态 |
|---|---|---|---|
| M6 合规、法律、治理与伦理 | **不单独写“法律大全”；与 M7 合并为未来的组织级运行层** | 否 | 《AI Governance & Organizational Adoption》薄书；稳定运行机制为正文，法域/行业规则为带日期的 profile |
| M7 组织与团队采纳 | **有真实剩余缺口，但目前缺少具体组织场景，暂不写泛化新书** | 否 | 与 M6 共用同一运行层，覆盖组合治理、决策权、试点到规模化、能力建设和变革反馈 |
| M8 benchmark 与具体工具 | **继续排除在正典之外** | 否 | 只有明确课程或项目需要时才做 dated snapshot；不让快变量反向定义慢变量正文 |
| 知识库 v1.0 | **内容架构就绪** | — | 可以进入发布候选；本审计不创建 `v1.0` Git tag 或 GitHub Release |

这不是“以后永远不写”。准确含义是：**当前十五本书已经构成完整的 AI Engineering 系统层知识架构；M6–M8 属于组织落地与时效资料层，不应为了凑书目数量抢进正典。**

## 二、现有覆盖与真正缺口

### M6：不是“没有治理”，而是没有组织级治理操作系统

现有覆盖已经包括：

- [[data-foundation-of-ai-systems/05_数据治理与伦理|Data Foundation · 数据治理与伦理]]：隐私、偏见、版权来源、数据主权与持续治理；
- [[human-ai-collaboration-foundation/06_权限系统设计|权限]]、[[human-ai-collaboration-foundation/07_责任边界设计|责任边界]]、[[human-ai-collaboration-foundation/02_Human-in-the-loop设计|有效人工控制]]：谁能做、谁负责、哪里保留控制；
- [[ai-systems-in-production/04_发布与变更管理|生产变更管理]]与 [[evaluation-of-ai-systems/00_INDEX|Evaluation]]：发布门禁、持续评价和事故证据；
- [[laws-of-ai-engineering/09_人机与信任定律#Law 86 — 责任不可委托定律（Accountability-Cannot-Be-Delegated Law）|Law 86]]：问责不能止于 AI，具体义务服从角色、场景和司法辖区。

真正缺少的是组织级闭环：AI 系统台账、风险分类、决策权、采购与第三方、影响评估、证据包、事件上报、申诉补救、跨团队复盘，以及这些机制如何持续改进。

这个缺口值得未来补，但不能写成脱离法域和行业的“通用法律答案”。截至本审计日期，[NIST AI RMF](https://www.nist.gov/itl/ai-risk-management-framework) 明确处于修订中；[欧盟 AI Act 官方实施页](https://digital-strategy.ec.europa.eu/en/policies/regulatory-framework-ai)也显示适用时间表会随立法调整；[ISO/IEC 42001](https://www.iso.org/standard/42001)则说明更稳定的组织层对象是持续改进的 AI 管理体系，而不是一份静态法规清单。

### M7：微观协作已覆盖，组织采纳仍缺一层

[[human-ai-collaboration-foundation/00_INDEX|Human-AI Collaboration Foundation]] 已覆盖人机分工、信任、权限、责任、监督者和长期能力退化；[[human-ai-interaction-design/00_INDEX|Interaction Design]] 负责把这些政策实现为界面。这已经解决“一个流程里人与 AI 怎么合作”。

仍缺的是“一个组织如何把许多 AI 用例放进同一套经营与治理系统”：

1. 用例组合如何发现、排序和退出；
2. 试点如何用证据进入规模化，而不是被 demo 或高层口号推动；
3. 产品、工程、法务、数据、安全、业务和一线人员的决策权如何分配；
4. 指标和激励如何避免把人推成盖章者或让团队隐瞒失败；
5. 岗位与能力如何重组，如何保留接管、质疑和责任能力；
6. 事故、用户反馈和监管变化如何回流到组织决策。

这些问题与 M6 的治理机制共享同一个对象——组织的 AI operating model。把 M6 和 M7 写成两本，会在角色、责任、流程、证据和变更管理上产生大面积重复，因此未来应合并立项。

### M8：缺失是有意的，而且应该继续有意

现有 [[evaluation-of-ai-systems/06_评价设计模式|评价设计模式]] 已解释 benchmark 怎么设计和组合，Production / Model Adaptation 已解释工具选择背后的慢变量。当前缺少的是产品名、版本、价格、命令和榜单；它们更新快，进入正典后会制造大量失效内容。

因此 M8 只能是任务型附件，而不是“第十六本书”。每份快照至少要声明：

- `as_of`：资料截至日期；
- `scope`：课程、实验或项目场景；
- `versions`：工具、模型、依赖和运行环境；
- `evidence`：可复现实验或官方来源；
- `review_by`：最迟复核日期；
- `status`：active / stale / archived。

## 三、未来若立项，只允许这一种架构

未来候选书名：**《AI Governance & Organizational Adoption》**，定位为“组织级运行层”，不新增 Law 编号、不重复数据治理或 Human-AI 的微观协作内容。

建议六章：

1. **系统台账与使用边界**：组织里有哪些 AI、谁提供、影响谁；
2. **风险分级与决策权**：谁能批准、暂停、扩大和退出；
3. **生命周期证据**：影响评估、评价、变更、监控、事件与补救；
4. **采购、供应商与数据责任**：第三方依赖和责任链；
5. **从试点到规模化**：价值证据、组合管理、团队能力和激励；
6. **持续改进与 dated profiles**：法域/行业 profile 单独维护，不混进稳定正文。

边界纪律：

- 法律内容必须标明法域、适用对象、截至日期和复核日期；
- 不把 NIST、ISO 或某部法律写成本库自己的“新定律”；
- 不重复 [[human-ai-collaboration-foundation/00_INDEX|Human-AI Collaboration]] 的流程内分工，也不重复 [[data-foundation-of-ai-systems/05_数据治理与伦理|数据治理]]；
- 每章都必须落到组织产物，如台账、RACI/责任矩阵、影响评估、证据包、退出条件和复盘机制。

## 四、重新立项的机械触发条件

M6/M7 只有同时满足以下条件才进入写作：

1. 有明确读者或真实组织场景，不再以“所有公司”作为假想用户；
2. 能提供至少三个真实用例或事故（**编排阈值**，用于防止空泛立项），验证章节不是管理口号；
3. 已确定法域/行业边界，或明确只写非法律的管理系统层；
4. 有维护责任人和复核节奏，能处理标准与法规更新；
5. 先完成与现有五本相关书的重叠矩阵，证明新增内容不是换标题复述。

M8 只有在存在具体课程、实验或项目交付时立项；交付结束后按 `review_by` 复核，过期即标 stale 或 archived，不进入正典学习路径。

## 五、v1.0 就绪度

### 已满足

- 十五本书、Case Library、ADS、知识图谱和使用路由已经形成闭环；
- M1–M5 均已落地，M6–M8 已完成架构裁决，不再作为模糊的“以后再说”；
- Law System 的 Core 与高影响主张已优先核验，当前集中 citation 覆盖 41/102，未核验条目不伪装成已有外部证明；
- Core Laws P0/P1/P2、Law 96 与高影响非 Core 收窄完成；
- ADS 21 个情境均可直达 Case Library，108 个案例中有 20 个深度样板；
- repo 有维护手册、唯一任务队列、自动体检和 private GitHub CI。

### 不阻塞发布但必须继续诚实标注

- 剩余 61 条 Law 尚未做逐条外部核验；它们是季度候选池，不是被证明正确的空白支票；
- 法规、产品、模型与 benchmark 属于高时效内容，需要 dated profile / snapshot；
- 具身智能仍有意暂缓，直到出现可复用的系统工程边界与真实案例；
- GitHub 网页阅读镜像仍暂缓，Obsidian 原生可用性优先。

### 版本裁决

**内容架构可以进入 v1.0 发布候选。** 这里的 v1.0 表示“结构完整、边界清楚、可维护、关键链路可验证”，不表示 102 条 Law 都获得外部证明，也不表示未来不再新增内容。

本审计没有创建 `v1.0` tag 或 GitHub Release。那是一次独立的远端发布动作，应在最终 CI 通过后由维护者明确决定。

## 六、初见审查

> 反驳：还有 61 条 Law 未核验、M6/M7 也没写，凭什么叫 v1.0 就绪？

回应：如果 v1.0 被定义成“所有可能内容都完成”，它永远不会发生。当前更机械的标准是：核心架构闭环、已知高风险主张优先处理、未知被明确标注、维护机制可运行、所有主动链接与机器层可验证。61 条进入透明候选池，M6/M7 被明确裁决为条件性组织层而不是正典缺洞；它们是已知边界，不是隐藏缺陷。

> 反驳：把 M6 和 M7 合并，会不会把法律合规和组织变革混成一锅？

回应：合并的是共同的组织运行骨架，不是把具体法律写进通用正文。稳定正文负责台账、角色、证据、生命周期和持续改进；具体法域规则由 dated profile 独立维护。这样既保留边界，也避免两本书重复写同一套责任与流程。
