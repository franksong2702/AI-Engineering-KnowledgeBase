## Case 31 · Demo 惊艳，生产翻车（深度版）

- **Problem**: 一个 Agent 在演示中完美完成复杂任务，团队据此上线，实际生产成功率只有 40%。
- **Context**: 演示任务是团队预先挑过的 12 条“最能体现能力”的路径；生产任务来自真实用户，输入格式、权限状态、工具错误、业务边界都更混乱。上线前只做过 3 次人工演示，没有跑分布评测。
- **Constraints**: 生产需要稳定成功率；失败必须可发现、可恢复；不能把一次惊艳 demo 当成上线承诺。
- **Analysis**: 这是典型的峰值驱动设计。demo 证明的是“系统在有利条件下可以做到”，不是“系统在真实分布下可靠做到”。复盘 100 条生产任务后发现：简单任务成功率约 70%，需要跨工具状态同步的任务约 35%，遇到权限/文件缺失/接口超时的任务低于 15%。总体 40% 不是模型突然变笨，而是上线后分布变宽、长尾变多、错误恢复机制缺失。
- **Relevant Laws**: [[agent-decision-system/04_LAW-INVARIANTS#LAW-03 · 分布证据有边界 + 校准（Distribution-Bounded Evidence + Calibration）|LAW-03]]（分布变化后重评） · [[agent-decision-system/04_LAW-INVARIANTS#LAW-08 · 信任应随可靠性而非能力增长（Trust-Reliability Scissors）|LAW-08]]（信任不能超过可靠性） · [[agent-decision-system/04_LAW-INVARIANTS#LAW-06 · 误差多步累积 + 恢复优于预防（Error Compounding + Recovery）|LAW-06]]（多步误差会累积）
- **Relevant Patterns**: [[agent-decision-system/02_PATTERN-CARDS#PAT-15 · Guardrails / Validation（护栏）|PAT-15]]（上线护栏/结果验证） + 分层评测 + canary 发布

**Trace 片段（demo 与生产的差异）**：

```text
Demo task: “帮我整理这 3 个指定文件并生成摘要”
- 文件都存在
- 权限已开
- 文件格式一致
- 人在旁边修正歧义
- 成功：1/1

Production task: “把上周客户反馈整理成给销售看的材料”
- 文件位置不固定
- 有一份权限不足
- 反馈来自邮件、表格、聊天记录三处
- 中间一次工具超时
- Agent 继续编了一个“看似完整”的反馈总结
- 实际成功：0/1，且失败没有被及时暴露
```

- **Architecture Decision**: 不按 demo 承诺上线能力，而是先建真实任务分布评测集：50 条简单任务、50 条跨工具任务、30 条权限/缺文件任务、20 条长尾异常任务。上线门槛从“能不能做一次”改为“各 slice 成功率、失败可见性、恢复率是否达标”。高风险路径先降级为半自动：Agent 起草，人在关键提交点确认。
- **第一次修复与反转**: 第一版修复是“把 system prompt 写得更严格，并给工具失败加一次重试”，总体成功率从 40% 到约 46%，但权限不足和歧义任务仍大量失败。反转点是看 trace 后发现瓶颈不在“模型不够努力”，而在“任务不在 demo 分布内 + 失败不可恢复”。于是把工作从调 prompt 转为分层评测、失败显式化、canary 和人工兜底。
- **Anti-Patterns Avoided**: [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-05 · 无评测上线（Vibe-Check Deployment）— 🔴|ANTI-05]]（用演示代替评测） · [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-02 · 过度信任（Over-Trust）— 🔴|ANTI-02]]（把能力峰值当可靠性） · [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-01 · 静默失败（Silent Failure）— 🔴最危险|ANTI-01]]（失败后继续产出）
- **Evaluation Method**: [[agent-decision-system/05_EVAL-CHECKLIST#Q-02 · 它可靠吗——看分布不是峰值？🔴|Q-02]] + [[agent-decision-system/05_EVAL-CHECKLIST#Q-06 · 它在分布外/长尾/对抗下如何？🔴|Q-06]]。指标不只看平均成功率，而是按任务类型报成功率、失败显式率、人工接管率和恢复率。
- **Final Solution**: 用真实分布重设上线承诺：简单任务自动化，跨工具任务 canary，小概率高损失败进入人工确认；所有工具错误必须显式返回，不允许生成端“补一个看似合理的结果”。总体自动成功率未被包装成 90%，而是诚实标为“低风险任务约 70%，复杂任务需人机协作”。
- **Lessons Learned**: ① demo 证明的是能力存在，不证明可靠性足够。② 生产价值由分布和最坏时刻决定，不由最好一次决定。③ prompt 只能改善一部分失败；分布外、权限错误、工具超时需要架构和运营机制。④ 数字为教学编排值，用于展示评测分层，不代表实测数据。
## Case 32 · 依赖单一模型 API 全线瘫痪

- **Problem**: 整个系统依赖一个模型 API，该 API 宕机时全线瘫痪。
- **Context**: 无 fallback。
- **Constraints**: 需要高可用。
- **Analysis**: 单点故障。
- **Relevant Laws**: 单点故障 · 冗余-效率权衡
- **Relevant Patterns**: fallback 链 + 优雅降级
- **Architecture Decision**: 主模型失败 → 备用模型 → 缓存回答 → 优雅报错的 fallback 链。
- **Anti-Patterns Avoided**: 无工具/模型回退。
- **Evaluation Method**: 模拟 API 宕机，测系统是否优雅降级。
- **Final Solution**: fallback 链，主 API 宕机时降级而非全崩。
- **Lessons Learned**: 关键依赖是单点故障。给它 fallback 和优雅降级。

## Case 33 · 上线后静默退化半年无人知

- **Problem**: 系统上线后停止监控，因数据分布漂移半年已严重退化，直到大量投诉才发现。
- **Context**: 一次性评估即部署。
- **Constraints**: 需及早发现退化。
- **Analysis**: 静默退化——缓慢无声，一次性评价发现不了。
- **Relevant Laws**: 分布漂移 · 静默降级危险
- **Relevant Patterns**: 持续评价 + 漂移监控
- **Architecture Decision**: 持续监控生产表现 + 数据分布漂移告警 + 定期用新数据重评。
- **Anti-Patterns Avoided**: 一次性评估即部署。
- **Evaluation Method**: 持续评价（生产监控）。
- **Final Solution**: 加监控及时发现漂移，及早干预。
- **Lessons Learned**: 上线不是终点。持续评价是静默退化的唯一解药。

## Case 34 · 一步失败丢失全部进度

- **Problem**: 一个 30 步任务在第 28 步失败，因无检查点只能从头重跑，浪费前 27 步。
- **Context**: 无状态持久化。
- **Constraints**: 长任务要能恢复。
- **Analysis**: 无失败恢复。长任务一定会中断。
- **Relevant Laws**: [[agent-decision-system/04_LAW-INVARIANTS#LAW-06 · 误差多步累积 + 恢复优于预防（Error Compounding + Recovery）|LAW-06]]（恢复优于预防）· 墨菲定律
- **Relevant Patterns**: 状态检查点 + 断点续跑
- **Architecture Decision**: 每步保存状态到文件，中断后从最近检查点恢复。
- **Anti-Patterns Avoided**: [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-12 · 无失败恢复/循环无出口（No Recovery / Loop Without Exit）— 🟠|ANTI-12]]（无失败恢复）。
- **Evaluation Method**: 中途注入故障，测能否从检查点恢复。
- **Final Solution**: 检查点 + 续跑，故障后不丢进度。
- **Lessons Learned**: 长任务一定会中断。检查点比祈祷不出错可靠。

## Case 35 · 变更全量上线引发大面积事故

- **Problem**: 一个 prompt 变更直接全量上线，引入的问题立刻影响所有用户，紧急回滚。
- **Context**: 无灰度、无版本管理。
- **Constraints**: 变更风险要可控。
- **Analysis**: 无灰度 + 无回滚，爆炸半径最大化。
- **Relevant Laws**: 爆炸半径 · 恢复优于预防
- **Relevant Patterns**: 灰度发布 + 可回滚
- **Architecture Decision**: 变更先灰度 5% 流量，观察无问题再扩大；版本 pin + 一键回滚。
- **Anti-Patterns Avoided**: 无灰度发布 + 版本不可回滚。
- **Evaluation Method**: 灰度期间对比新旧版本指标。
- **Final Solution**: 灰度 + 回滚，把变更风险限制在小流量。
- **Lessons Learned**: 变更灰度发布 + 可回滚。别把爆炸半径开到最大。

## Case 36 · 单步可靠但长链条整体不可靠

- **Problem**: 一个 20 步流程每步 97% 可靠，整体成功率却只有约 54%，团队想不通。
- **Context**: 只优化了单步，没算连乘。
- **Constraints**: 需要提升整体成功率。
- **Analysis**: 误差累积——0.97²⁰≈0.54，长链条指数衰减。
- **Relevant Laws**: [[agent-decision-system/04_LAW-INVARIANTS#LAW-06 · 误差多步累积 + 恢复优于预防（Error Compounding + Recovery）|LAW-06]]（误差累积）
- **Relevant Patterns**: 分解 + 每步验证纠错
- **Architecture Decision**: 关键步加验证/自纠打破纯连乘；能合并的步骤合并（减少步数）。
- **Anti-Patterns Avoided**: 忽视误差累积。
- **Evaluation Method**: 测单步成功率 + 整体成功率，加纠错后对比。
- **Final Solution**: 加纠错点 + 减步数，整体成功率提到 85%。
- **Lessons Learned**: 单步 97% 感觉高，连乘 20 次只剩 54%。长任务必须有纠错。

## Case 37 · 无成本核算规模化后不可行

- **Problem**: 一个工作流每次成本 2 元，设计时没算，规模化到日百万次后成本不可持续，被迫重构。
- **Context**: 把成本当上线后的事。
- **Constraints**: 成本要可持续。
- **Analysis**: 无成本核算——成本结构决定架构，设计阶段没算。
- **Relevant Laws**: 成本结构决定架构 · 机会成本
- **Relevant Patterns**: 成本估算 + 模型路由 + 缓存
- **Architecture Decision**: 设计阶段估算单次成本 × 规模；简单请求路由到便宜模型；缓存重复。
- **Anti-Patterns Avoided**: 无成本核算。
- **Evaluation Method**: [[agent-decision-system/05_EVAL-CHECKLIST#Q-04 · 代价可接受吗？🟠|Q-04]]（质量÷成本，规模化可持续性）。
- **Final Solution**: 分层 + 缓存，成本降到可持续。
- **Lessons Learned**: 成本估算是设计阶段的事，不是上线后。

## Case 38 · 某环节失败静默跳过污染下游

- **Problem**: 一个流水线的校验环节失败后被静默跳过，大量未校验的错误数据流入下游，几天后才发现。
- **Context**: 怕打断流程，失败静默跳过。
- **Constraints**: 数据质量。
- **Analysis**: 静默降级——流程看起来成功实则部分环节没做。
- **Relevant Laws**: [[agent-decision-system/04_LAW-INVARIANTS#LAW-06 · 误差多步累积 + 恢复优于预防（Error Compounding + Recovery）|LAW-06]]（显式失败）· 静默降级危险
- **Relevant Patterns**: 显式失败 + 质量关卡拦截
- **Architecture Decision**: 校验失败显式拦截并告警，不静默跳过。
- **Anti-Patterns Avoided**: [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-01 · 静默失败（Silent Failure）— 🔴最危险|ANTI-01]]（静默降级）。
- **Evaluation Method**: 注入校验失败，看是拦截还是静默通过。
- **Final Solution**: 显式拦截，脏数据不再静默流入。
- **Lessons Learned**: 数据管线最危险的失败是静默通过脏数据。质量关卡要显式拦截。

## Case 39 · 优化了非瓶颈环节整体没变快

- **Problem**: 团队花几周优化一个占总延迟 5% 的环节，整体几乎没变快。
- **Context**: 优化了熟悉/容易改的环节。
- **Constraints**: 要真正提速。
- **Analysis**: 瓶颈误优化——真正的瓶颈（检索）没动。
- **Relevant Laws**: 瓶颈定律
- **Relevant Patterns**: 先测量找瓶颈
- **Architecture Decision**: 先测各环节耗时找到瓶颈（检索占 70%），只优化它。
- **Anti-Patterns Avoided**: 瓶颈误优化。
- **Evaluation Method**: 测量各环节耗时，定位瓶颈。
- **Final Solution**: 优化检索环节，整体延迟大降。
- **Lessons Learned**: 优化前先找瓶颈。优化非瓶颈是纯浪费。

## Case 40 · 非幂等操作重试导致重复扣款（深度版）

- **Problem**: 一个下单工具非幂等，网络超时触发统一重试，用户被下了两次单、扣了两次款。
- **Context**: Agent 调用 `create_order()` 后没有收到响应。系统把所有工具超时都当成“可能没执行”，于是自动重试。支付网关实际上第一次已经成功，只是响应包丢了。
- **Constraints**: 有副作用操作必须重试安全；用户不能承担重复副作用；失败要可查、可补偿。
- **Analysis**: 这不是“要不要重试”的问题，而是“哪些操作允许重试”。读操作、纯计算、可覆盖写入通常可以安全重试；下单、扣款、发邮件、删除文件这类有外部副作用的操作，如果没有幂等键，重试就是复制副作用。
- **Relevant Laws**: [[agent-decision-system/04_LAW-INVARIANTS#LAW-06 · 误差多步累积 + 恢复优于预防（Error Compounding + Recovery）|LAW-06]]（恢复机制必须显式） · [[agent-decision-system/04_LAW-INVARIANTS#LAW-09 · 不可逆慢做可逆快做（Reversibility Governs Caution）|LAW-09]]（不可逆操作慢做） · [[agent-decision-system/04_LAW-INVARIANTS#LAW-11 · 确定性优先（Determinism First）|LAW-11]]（副作用边界要确定）
- **Relevant Patterns**: [[agent-decision-system/02_PATTERN-CARDS#PAT-04 · Tool Use / Function Calling|PAT-04]]（工具语义清晰） + [[agent-decision-system/02_PATTERN-CARDS#PAT-15 · Guardrails / Validation（护栏）|PAT-15]]（副作用护栏）

**Trace 片段（事故链条）**：

```text
T+00s  Agent → create_order(user=U1, item=A, amount=199)
T+02s  Payment gateway: charge succeeded, order_id=O1001
T+03s  Network timeout: caller did not receive response
T+04s  Retry policy: timeout -> retry same tool call
T+06s  Agent → create_order(user=U1, item=A, amount=199)
T+08s  Payment gateway: charge succeeded again, order_id=O1002
T+30m  用户发现两笔扣款
```

- **Architecture Decision**: 把工具按副作用等级分类：只读工具可自动重试；可覆盖写工具需版本号；不可逆工具必须带 idempotency key，并在执行前后写入操作账本。`create_order()` 的入参改为 `idempotency_key=hash(user, cart, checkout_session)`，重试时先查同 key 是否已有成功结果。
- **第一次修复与反转**: 第一版修复是“关掉下单工具的自动重试”。这避免了重复扣款，却把网络抖动变成大量未知状态：用户不知道到底下单没下单，客服也查不清。反转点是：正确目标不是“不重试”，而是“重试不产生新副作用”。所以最终方案是幂等键 + 操作账本 + 明确补偿流程。
- **Anti-Patterns Avoided**: [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-12 · 无失败恢复/循环无出口（No Recovery / Loop Without Exit）— 🟠|ANTI-12]]（恢复策略无副作用意识） · [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-01 · 静默失败（Silent Failure）— 🔴最危险|ANTI-01]]（超时后状态不明却继续推进）
- **Evaluation Method**: [[agent-decision-system/05_EVAL-CHECKLIST#Q-03 · 它错得起吗——失败廉价可查？🔴|Q-03]] + [[agent-decision-system/05_EVAL-CHECKLIST#Q-02 · 它可靠吗——看分布不是峰值？🔴|Q-02]]。用故障注入模拟响应丢失、重复请求、部分成功、账本写失败，检查是否只产生一次外部副作用。
- **Final Solution**: 所有不可逆工具必须声明副作用等级和幂等策略；重试层读取该声明，不再“一刀切重试”。下单接口通过幂等键保证同一 checkout session 最多生成一笔订单；异常状态进入人工/补偿队列。
- **Lessons Learned**: ① 重试不是免费恢复，非幂等重试会复制灾难。② 不可逆操作要先设计账本和幂等键，再谈自动化。③ 关掉重试只是止血，不是可靠性设计。④ 数字和链路为教学编排，用于展示副作用语义。
