## Case 61 · 简单任务也用最贵的模型（深度版）

- **Problem**: 系统对所有请求都用最强最贵的模型，简单请求占 80%，成本巨大但质量没有相应提升。
- **Context**: 一个内部知识助手同时处理“改写一句话”“提取表格字段”“分析复杂合同”“跨文档推理”等任务。为了省工程时间，团队把所有请求统一打到最强模型。
- **Constraints**: 成本要可持续；路由不能明显伤害质量；复杂任务仍要保留强模型能力；失败时要能 fallback。
- **Analysis**: 这是成本结构没有进入架构设计。模型能力不是越强越好，而是要和任务难度匹配。抽样 1000 条请求后发现，约 55% 是格式转换/短文本改写，约 25% 是结构化抽取，真正需要强推理或长上下文的不到 20%。统一用最贵模型，相当于用吊车搬纸箱。
- **Relevant Laws**: [[agent-decision-system/04_LAW-INVARIANTS#LAW-10 · 简单优先（Simplicity First）|LAW-10]]（简单优先） · [[agent-decision-system/04_LAW-INVARIANTS#LAW-03 · 分布内才可靠 + 校准（In-Distribution + Calibration）|LAW-03]]（简单任务可由便宜通道稳定覆盖） · [[agent-decision-system/04_LAW-INVARIANTS#LAW-11 · 确定性优先（Determinism First）|LAW-11]]（能规则化就别模型化）
- **Relevant Patterns**: [[agent-decision-system/02_PATTERN-CARDS#PAT-16 · Routing（路由分发）|PAT-16]]（model routing） + [[agent-decision-system/02_PATTERN-CARDS#PAT-07 · Structured Output（结构化输出）|PAT-07]]（低难任务结构化约束）

**Trace 片段（修复前的成本画像）**：

```text
一天 10,000 次请求：
- 3,200 次：一句话润色/改写                  → 强模型
- 2,300 次：JSON 字段抽取                    → 强模型
- 2,500 次：FAQ/固定模板回答                 → 强模型
- 1,400 次：跨文档总结                       → 强模型
-   600 次：复杂推理/模糊业务判断             → 强模型

结果：80% 流量没有吃到强模型的边际收益，却承担了强模型的价格和延迟。
```

- **Architecture Decision**: 建一个轻量路由层：规则先拦截确定性任务；小模型处理短文本、字段抽取、固定模板；中等模型处理普通摘要；强模型只处理高不确定、高价值、长上下文、复杂推理任务。路由器本身不做复杂 Agent，只做可解释分类，并保留“低置信度升档”和“用户显式要求升档”的 fallback。
- **第一次修复与反转**: 第一版修复是“压缩 prompt、减少输出 token”，成本只降了约 12%，因为根本问题不是单次调用太胖，而是大量请求根本不该进强模型。反转点是按任务类型重算成本后发现：把 80% 简单流量路由出去，比继续抠 prompt 省得多，而且风险更低。
- **Anti-Patterns Avoided**: 没有把路由器做成新的自主 Agent，避免 [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-06 · 过度 Agent 化（Over-Agentization）— 🟠|ANTI-06]]；没有只用“平均质量分”掩盖成本结构，避免 [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-05 · 无评测上线（Vibe-Check Deployment）— 🔴|ANTI-05]] 的成本版本。
- **Evaluation Method**: [[agent-decision-system/05_EVAL-CHECKLIST#Q-04 · 代价可接受吗？🟠|Q-04]] + [[agent-decision-system/05_EVAL-CHECKLIST#Q-02 · 它可靠吗——看分布不是峰值？🔴|Q-02]]。每个路由桶分别报告质量、延迟、成本、fallback 率，而不是只报全局均值。
- **Final Solution**: 分层路由后，约 80% 流量走便宜通道；复杂任务仍进强模型；低置信度自动升档。总体成本大幅下降，P95 延迟下降，人工抽检质量无明显下降。关键收益来自“能力匹配任务”，不是“把强模型用得更省”。
- **Lessons Learned**: ① 成本不是上线后的财务问题，而是架构输入。② 大模型做难的 20%，小模型/规则做简单的 80%。③ 路由必须可解释、可回退、可抽检。④ 数字为教学编排值，用于展示成本结构，不代表实测数据。
## Case 62 · 无脑上多次采样成本暴涨

- **Problem**: 对所有任务无脑上最贵的多次采样投票，简单任务成本暴涨而质量没提升。
- **Context**: 把质量模式当默认。
- **Constraints**: 质量提升要划算。
- **Analysis**: 质量有成本——对不需要的任务用重型质量模式是浪费，边际收益为零。
- **Relevant Laws**: 质量有成本 · 边际
- **Relevant Patterns**: 按需用 [[agent-decision-system/02_PATTERN-CARDS#PAT-10 · Ensembling / Voting / Self-Consistency（集成投票）|PAT-10]]（只在难/高风险任务）
- **Architecture Decision**: 只在答案分散/高风险的任务上用投票，简单任务单次。
- **Anti-Patterns Avoided**: 质量模式滥用。
- **Evaluation Method**: 测"质量提升÷成本倍数"，找划算的点。
- **Final Solution**: 按需投票，成本回落，质量该高的高。
- **Lessons Learned**: 没有免费的质量。每个质量模式先算"提升÷成本"。

## Case 63 · 重复计算不缓存

- **Problem**: 一个系统对同一个常见查询反复调 API，不缓存，成本和延迟高。
- **Context**: 无缓存。
- **Constraints**: 降本提速。
- **Analysis**: 重复计算是浪费——可复用结果应缓存。
- **Relevant Laws**: 缓存定律
- **Relevant Patterns**: 缓存 + prompt caching
- **Architecture Decision**: 缓存常见查询的检索/生成结果；稳定 prompt 前缀用 prompt caching。
- **Anti-Patterns Avoided**: 不缓存重算。
- **Evaluation Method**: 测重复率和缓存命中率。
- **Final Solution**: 缓存，命中时省去重算，成本和延迟双降。
- **Lessons Learned**: 重复计算是浪费。缓存用存储换计算（注意新鲜度）。

## Case 64 · 上下文无限增长越来越贵（深度版）

- **Problem**: 一个长期对话助手不做历史管理，几百轮后每次调用都极贵极慢，最终超过上下文窗口并开始丢关键约束。
- **Context**: 团队为了“让模型记住一切”，把完整对话历史、工具输出、检索片段和用户文件摘要全部追加到下一轮 prompt。早期效果好，使用几周后成本和延迟失控。
- **Constraints**: 长对话要可持续；关键事实不能丢；成本和延迟不能随轮次无限线性增长。
- **Analysis**: 无限历史把“状态管理”伪装成“上下文堆叠”。它同时制造三个问题：token 成本线性增长，模型注意力被旧噪声稀释，窗口接近上限时不得不粗暴截断，反而丢掉关键事实。
- **Relevant Laws**: [[agent-decision-system/04_LAW-INVARIANTS#LAW-07 · 上下文即状态（Context Is State）|LAW-07]]（上下文即状态） · [[agent-decision-system/04_LAW-INVARIANTS#LAW-02 · 压缩必然有损→会幻觉（Lossy Compression）|LAW-02]]（压缩有损） · [[agent-decision-system/04_LAW-INVARIANTS#LAW-10 · 简单优先（Simplicity First）|LAW-10]]（先做简单可控的状态层）
- **Relevant Patterns**: [[agent-decision-system/02_PATTERN-CARDS#PAT-11 · Context Compression（上下文压缩）|PAT-11]]（滚动摘要） + [[agent-decision-system/02_PATTERN-CARDS#PAT-12 · Memory Retrieval（记忆机制）|PAT-12]]（外置记忆检索）

**Trace 片段（成本曲线）**：

```text
第 10 轮：  8k input tokens，P95 2.1s，单次成本低
第 80 轮： 42k input tokens，P95 8.7s，开始召回旧噪声
第 180 轮：96k input tokens，P95 24s，接近窗口上限
第 220 轮：系统自动截断最早 40k tokens
结果：最早的“不要联系客户本人”约束被截掉，助手后续给出错误动作建议
```

- **Architecture Decision**: 把长期对话拆成三层：短期工作窗口只放最近交互和当前任务；中期状态摘要保存目标、偏好、约束、待办；长期记忆外置，按需检索。长工具输出不进工作窗口，只保存 artifact 指针和结构化摘要。
- **第一次修复与反转**: 第一版修复是“超过 80k token 就截掉最早历史”。成本立刻下降，但关键约束也被截掉，质量更差。反转点是：问题不是历史太长，而是没有区分“当前需要的状态”和“仅供审计的历史”。最终改为状态账本 + 外置历史，而不是粗暴截断。
- **Anti-Patterns Avoided**: [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-08 · 记忆倾倒/上下文污染（Memory Dumping）— 🟠|ANTI-08]]（把全部历史当工作记忆） · [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-05 · 无评测上线（Vibe-Check Deployment）— 🔴|ANTI-05]]（只看早期体验不看长程成本曲线）
- **Evaluation Method**: [[agent-decision-system/05_EVAL-CHECKLIST#Q-04 · 代价可接受吗？🟠|Q-04]] + [[agent-decision-system/05_EVAL-CHECKLIST#Q-08 · 对自主系统：轨迹合理吗，不只结果？🔴（仅自主系统）|Q-08]]。用固定长对话脚本测 input tokens、P95 延迟、关键约束保持率、旧噪声引用率。
- **Final Solution**: 采用滚动窗口 + 任务感知摘要 + 外置记忆检索。对话 200 轮后，工作上下文保持在稳定区间；关键约束显式保留；历史仍可查但不再每轮都喂给模型。
- **Operational Guardrail**: 给每个会话记录 token 预算、摘要更新时间、关键约束数量和外置记忆命中率。若 input token 连续三轮上升但有效状态字段没有增加，就触发“上下文瘦身”任务；若摘要后关键约束数量下降，则阻止进入下一轮。
- **Lessons Learned**: ① 长上下文不是状态管理的替代品。② 成本曲线是架构健康指标，不是财务后验。③ 粗暴截断会把成本问题变成可靠性问题。④ 数字为教学编排，用于展示量级变化。
## Case 65 · 为微小质量提升消耗巨大资源

- **Problem**: 团队为把质量从 90 分提到 92 分，投入了三倍的计算和复杂度。
- **Context**: 追求极致质量。
- **Constraints**: 资源有限。
- **Analysis**: 边际收益递减——从 90 到 99 的成本可能是从 0 到 90 的十倍。
- **Relevant Laws**: 边际 · 质量有成本
- **Relevant Patterns**: 找边际最优点
- **Architecture Decision**: 明确"多少分够用"（产品决策），停在边际收益≈边际成本处。
- **Anti-Patterns Avoided**: 追求 100 分。
- **Evaluation Method**: 画质量-成本曲线，找递减点。
- **Final Solution**: 停在 90 分（够用），把资源投到更高价值的地方。
- **Lessons Learned**: "多少分够用"是产品决策。别为最后几分投入十倍。

## Case 66 · 自部署接管了不想要的复杂度

- **Problem**: 团队为省 API 费自部署开源模型，结果接管了 serving、扩缩容、维护的全部复杂度，总成本更高。
- **Context**: 没有数据/定制的硬需求，只为省钱自部署。
- **Constraints**: 权衡自部署 vs API。
- **Analysis**: 不必要的自部署——接管了一大堆运维复杂度，隐性成本被低估。
- **Relevant Laws**: 冗余-效率权衡 · 复杂度累积
- **Relevant Patterns**: 自部署 vs API 判断
- **Architecture Decision**: 无数据主权/成本/定制硬需求 → 用 API；自部署留给真有硬需求的场景。
- **Anti-Patterns Avoided**: 不必要的自部署。
- **Evaluation Method**: 算含运维的总成本对比。
- **Final Solution**: 回退用 API，总成本（含人力）更低。
- **Lessons Learned**: 自部署接管全部运维复杂度。除非有硬需求，否则不值得。

## Case 67 · 延迟敏感场景用了慢的重型方案

- **Problem**: 一个需要即时响应的场景用了多步 Agent + 树搜索，延迟到用户无法接受。
- **Context**: 追求质量忽略延迟。
- **Constraints**: 延迟是硬约束。
- **Analysis**: 方案与延迟约束不匹配——重型方案在延迟敏感场景不可用。
- **Relevant Laws**: 质量有成本（延迟版）· 成本结构决定架构
- **Relevant Patterns**: 流式输出 + 轻量方案
- **Architecture Decision**: 用单次调用 + 流式输出降低体感延迟；重型推理留给可异步的场景。
- **Anti-Patterns Avoided**: 方案-约束错配。
- **Evaluation Method**: 测首 token 延迟和总延迟。
- **Final Solution**: 轻量 + 流式，延迟可接受。
- **Lessons Learned**: 延迟是"好"的内在组成。方案要匹配延迟约束。

## Case 68 · 过度分解增加了无谓开销

- **Problem**: 一个简单文本改写被分解成 5 步流水线，每步一次调用，成本和延迟 5 倍，而本可一步完成。
- **Context**: 把分解当万能。
- **Constraints**: 简单任务要高效。
- **Analysis**: 过度分解——简单任务被拆得支离破碎，开销超过收益。
- **Relevant Laws**: [[agent-decision-system/04_LAW-INVARIANTS#LAW-10 · 简单优先（Simplicity First）|LAW-10]] · 边际
- **Relevant Patterns**: 适度分解（够验证即止）
- **Architecture Decision**: 简单改写用一次调用；只对复杂任务分解。
- **Anti-Patterns Avoided**: 过度分解。
- **Evaluation Method**: 对比分解 vs 一步的成本和质量。
- **Final Solution**: 一步完成，成本降 80%，质量不变。
- **Lessons Learned**: 分解到"可验证且不再受益于继续拆"即止。别过度。

## Case 69 · 长工具输出灌爆上下文

- **Problem**: 一个 Agent 把整个 API 响应（几千行）灌进上下文，成本高且信噪比崩溃。
- **Context**: 工具返回值不加工直接入上下文。
- **Constraints**: 上下文成本和质量。
- **Analysis**: 工具返回值未截断——无关字段稀释信号、增加成本。
- **Relevant Laws**: 信噪比 · 有效注意力有限
- **Relevant Patterns**: 工具输出截断/摘要
- **Architecture Decision**: 工具返回值只保留下游需要的字段，长输出摘要后入上下文。
- **Anti-Patterns Avoided**: [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-08 · 记忆倾倒/上下文污染（Memory Dumping）— 🟠|ANTI-08]]（上下文污染）。
- **Evaluation Method**: 测上下文中有效信息占比。
- **Final Solution**: 截断工具输出，成本降、质量升。
- **Lessons Learned**: 别把整个 API 响应灌进上下文。截断到下游需要的。

## Case 70 · 规模不经济的多 Agent

- **Problem**: 多 Agent 从 3 个加到 20 个，协调开销（规模不经济）超过分工收益，整体变差变贵。
- **Context**: 以为 Agent 越多越强。
- **Constraints**: 找最优规模。
- **Analysis**: 规模不经济——协调成本超线性增长，超过拐点后"多"是净亏损。
- **Relevant Laws**: 规模效应 · 复杂度累积
- **Relevant Patterns**: 控制 Agent 数量
- **Architecture Decision**: 找到规模经济转不经济的拐点，砍回最优数量。
- **Anti-Patterns Avoided**: [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-07 · 多 Agent 过度设计（Multi-Agent Overkill）— 🟠|ANTI-07]]（多 Agent 过度设计）。
- **Evaluation Method**: 逐步增减 Agent 数，测单位产出成本找拐点。
- **Final Solution**: 砍回合理数量，成本和质量都改善。
- **Lessons Learned**: 规模有拐点。加 Agent 到某点后是净亏损。
