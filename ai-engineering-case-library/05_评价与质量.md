## Case 41 · 刷高 benchmark 真实表现没提升（深度版）

- **Problem**: 团队用某公开问答 benchmark 驱动了两个月的迭代，分数从 71 涨到 89，但生产的用户投诉率、任务完成率纹丝不动。管理层问：18 个点去哪了？
- **Context**: 迭代流程是"改 prompt/检索参数→跑 benchmark→分数涨就合入"。benchmark 是公开的，且和生产任务只是题材相似（通用问答 vs 垂直客服）。
- **Constraints**: 要真实能力提升，且管理层需要一个能看的数字（这是刷分的组织学根源——数字需求不会消失，只能被更好的数字满足）。
- **Analysis**: 两层问题。表层：优化过程反复"看见"同一套题，参数选择过拟合了这套题的分布（等效于[[data-foundation-of-ai-systems/01_数据质量|测试集泄漏]]，只是泄漏进的是决策而非训练数据）。深层：benchmark 分布 ≠ 生产分布——18 个点的"提升"里，抽样分析显示约一半来自对 benchmark 特有题型（多跳常识题）的适配，而生产流量里这类题不到 5%。

**归因抽样（教学编排值）**：

```
benchmark 提升的 18 个点，按题型拆解：
  多跳常识题的适配        ~9 点   ← 生产占比 <5%，几乎无迁移价值
  格式/解析类修复          ~4 点   ← 真实改进，生产同样受益
  检索参数对该题集的过拟合  ~5 点   ← 换一套同类题即消失
生产核心指标同期变化：任务完成率 +0.4pt（噪声范围内）
```

- **Relevant Laws**: [[agent-decision-system/04_LAW-INVARIANTS#LAW-04 · 古德哈特（Goodhart）|LAW-04]]（古德哈特）· 过拟合
- **Relevant Patterns**: 保密评测集 + 多模式组合
- **Architecture Decision**: 三层评测取代单一 benchmark——①公开 benchmark 降级为"粗筛+对外可比"用途，**不再作为合入判据**；②自建保密评测集（从生产流量分层抽样 + 人工标注，含冻结锚与滚动子集，[[data-foundation-of-ai-systems/04_数据评价与漂移|评测集双层结构]]），作为合入判据；③生产北极星指标（任务完成率/复述率）做最终裁决，评测分与它的相关性每季度核验一次（[[agent-decision-system/05_EVAL-CHECKLIST#Q-10 · 评价者自己被校准了吗？🔴|Q-10]]：评价者自己被校准）。
- **第一次修复与反转**: 自建评测集上线三个月后，它自己也开始被刷——团队高频对着失败案例调参，保密集事实上不再保密（每周全员可见失败明细）。处理：失败明细只开放滚动子集，冻结锚的明细仅评测负责人可见、只报分数；重大版本才动用冻结锚。**任何被高频用于决策的指标都会滑向古德哈特，保密性是要持续维护的资产，不是建成时的属性。**
- **Anti-Patterns Avoided**: [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-03 · 古德哈特化评价 / 刷分（Benchmark Gaming）— 🔴|ANTI-03]]（刷分）。
- **Evaluation Method**: [[agent-decision-system/05_EVAL-CHECKLIST#Q-05 · 我优化的是真实目标还是代理？🔴|Q-05]]（代理与真实目标的相关性检验，季度化）；评测分-生产指标的相关性回归。
- **Final Solution**: 合入判据切到保密集后，两个季度里保密集 +6 点、生产任务完成率 +5pt（首次同向）；公开 benchmark 分数不再对内汇报。
- **Lessons Learned**: ① benchmark 高分≠系统好，用你自己保密的、来自生产分布的评测集。② 刷分的组织学根源是"数字需求"——不给管理层更好的数字，他们就会继续要 benchmark 的数字。③ 保密评测集会随使用而泄漏，保密性需要制度维护（明细分级可见）。④ 每季度核验"评测分涨→生产指标涨"的相关性，断了就是评测在老化。⑤ 数字为教学编排值。

## Case 42 · 用几个例子就宣布系统可用

- **Problem**: 一个 RAG 系统跑了三个顺手问题都对就上线，被真实的多样查询大量击穿。
- **Context**: vibe check 当评价。
- **Constraints**: 需要可靠的评价。
- **Analysis**: 无评测上线——几个例子无统计意义，发现不了长尾失败。
- **Relevant Laws**: 测试即真理 · 长尾定律
- **Relevant Patterns**: 系统评测集
- **Architecture Decision**: 建 30+ 用例（典型+边界+对抗），多次运行取统计。
- **Anti-Patterns Avoided**: [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-05 · 无评测上线（Vibe-Check Deployment）— 🔴|ANTI-05]]（vibe check）。
- **Evaluation Method**: [[agent-decision-system/05_EVAL-CHECKLIST#Q-06 · 它在分布外/长尾/对抗下如何？🔴|Q-06]]（长尾/边界/对抗覆盖）。
- **Final Solution**: 系统评测集，上线前发现并修复大批长尾问题。
- **Lessons Learned**: 没有评测集的系统是薛定谔系统——你不知道它好不好。

## Case 43 · 裁判模型从没和人对齐（深度版）

- **Problem**: 一个用模型裁判的评测体系从没和人对齐过，后来发现裁判系统性偏爱长回答，整个评价被带偏。
- **Context**: 团队用 LLM-as-judge 评价客服回复质量。裁判提示词要求“综合准确性、完整性、语气”，但没有人类金标集，也没有定期校准。模型版本升级后，偏好还发生了变化。
- **Constraints**: 评价要反映真实质量；裁判偏差要可测；模型裁判不能把自己的口味伪装成客观标准。
- **Analysis**: 裁判也是系统组件，也会漂移、偏置、被 prompt 影响。未校准的模型裁判测到的不是“真实质量”，而是“它喜欢什么”。在这个案例里，它把“长、礼貌、覆盖很多点”当成高质量，即使答案没有真正解决问题。
- **Relevant Laws**: [[agent-decision-system/04_LAW-INVARIANTS#LAW-04 · 古德哈特（Goodhart）|LAW-04]]（评价目标会被优化） · [[agent-decision-system/04_LAW-INVARIANTS#LAW-03 · 分布内才可靠 + 校准（In-Distribution + Calibration）|LAW-03]]（裁判也要校准） · [[agent-decision-system/04_LAW-INVARIANTS#LAW-01 · 验证易于生成（Verification > Generation）|LAW-01]]（评价结果要可验证）
- **Relevant Patterns**: [[agent-decision-system/02_PATTERN-CARDS#PAT-06 · LLM-as-Judge（模型即裁判）|PAT-06]]（校准裁判） + [[agent-decision-system/02_PATTERN-CARDS#PAT-10 · Ensembling / Voting / Self-Consistency（集成投票）|PAT-10]]（必要时多裁判对照）

**Trace 片段（长度偏差）**：

```text
用户问题：如何取消订阅？
回答 A：进入账户设置 > 订阅 > 取消。取消后本周期仍可使用。  # 简短准确
回答 B：非常感谢您的支持……以下是账户管理、付款方式、订阅权益、常见问题……最后可在设置中取消。  # 冗长但有用信息稀释

人类标注：A = 5/5，B = 3/5
模型裁判：A = 7/10，B = 9/10
原因：裁判把“完整”和“礼貌”过度当成质量。
```

- **Architecture Decision**: 建人类金标校准集，并把评价拆成维度：事实正确、任务完成、简洁性、风险、语气。模型裁判每次改 prompt、换模型、换任务分布后都要和人类金标对齐。报告不只给裁判分，也给“与人类一致率”和偏差分析。
- **第一次修复与反转**: 第一版修复是“把 rubric 写得更详细”。短期改善了一些样本，但新场景下仍偏爱长回答。反转点是：rubric 不能替代校准；没有人类锚点，就不知道裁判是否真的测到了目标。
- **Anti-Patterns Avoided**: [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-03 · 古德哈特化评价 / 刷分（Benchmark Gaming）— 🔴|ANTI-03]]（系统学会讨好裁判） · [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-05 · 无评测上线（Vibe-Check Deployment）— 🔴|ANTI-05]]（裁判本身不评测） · [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-02 · 过度信任（Over-Trust）— 🔴|ANTI-02]]（把模型分当真理）
- **Evaluation Method**: [[agent-decision-system/05_EVAL-CHECKLIST#Q-10 · 评价者自己被校准了吗？🔴|Q-10]] + [[agent-decision-system/05_EVAL-CHECKLIST#Q-05 · 我优化的是真实目标还是代理？🔴|Q-05]]。看裁判-人类一致率、分维度一致率、偏差方向、模型版本漂移。
- **Final Solution**: LLM-as-judge 保留为规模化评价工具，但必须经过人类金标校准；高风险样本和裁判低置信样本进入人工复核。评价报告同时展示质量分和裁判可信度。
- **Lessons Learned**: ① 裁判自己也要被评价。② 更详细的 rubric 不等于校准。③ 模型裁判适合放大人类判断，不适合替代人类判断。④ 一旦团队开始优化裁判分，裁判偏差就会变成产品偏差。
## Case 44 · 平均分掩盖了致命的尾部失败

- **Problem**: 一个系统平均准确率 95%，但那 5% 的失败集中在高风险场景且后果严重。
- **Context**: 只看平均分。
- **Constraints**: 高风险场景不能失败。
- **Analysis**: 只测平均不看尾部——平均分掩盖了严重的尾部失败。
- **Relevant Laws**: 长尾定律 · 可靠性定义
- **Relevant Patterns**: 看分布 + 分场景评测
- **Architecture Decision**: 分场景评测，高风险场景单独看成功率；关注最坏情况而非平均。
- **Anti-Patterns Avoided**: 只测平均。
- **Evaluation Method**: [[agent-decision-system/05_EVAL-CHECKLIST#Q-02 · 它可靠吗——看分布不是峰值？🔴|Q-02]]（看方差和最坏情况，尤其高风险尾部）。
- **Final Solution**: 高风险场景加护栏/人工，尾部风险受控。
- **Lessons Learned**: 可靠性由最坏情况决定，不由平均。看尾部，尤其高风险的。

## Case 45 · 用评测数据调优再用它评价

- **Problem**: 团队用一批用例调 prompt，调完用同一批宣布提升，实际只是过拟合了这些用例。
- **Context**: 训练/评测数据未分离。
- **Constraints**: 提升要泛化。
- **Analysis**: 测试集污染——用评测集调优再评价，只是过拟合。
- **Relevant Laws**: 过拟合
- **Relevant Patterns**: 训练/验证集分离
- **Architecture Decision**: 留出从不用于优化的独立验证集；评测集保密。
- **Anti-Patterns Avoided**: 测试集污染。
- **Evaluation Method**: 在独立验证集上测提升是否泛化。
- **Final Solution**: 独立验证集，暴露了之前的"提升"是过拟合。
- **Lessons Learned**: 留出从不用于优化的验证集。用调优数据评价是自欺。

## Case 46 · 结果全对但轨迹靠运气

- **Problem**: 一个 Agent 评测结果都对，但轨迹显示它经常用错工具后靠运气纠正，上线后运气用尽频繁失败。
- **Context**: 只评最终结果。
- **Constraints**: 自主系统要评过程。
- **Analysis**: 只评结果不评轨迹——结果对可能是蒙对/绕远/靠运气。
- **Relevant Laws**: 评价必须分层
- **Relevant Patterns**: 轨迹层评价
- **Architecture Decision**: 评轨迹——工具选择、推理路径、步骤有效性，而非只看结果。
- **Anti-Patterns Avoided**: 只评结果不评过程。
- **Evaluation Method**: [[agent-decision-system/05_EVAL-CHECKLIST#Q-08 · 对自主系统：轨迹合理吗，不只结果？🔴（仅自主系统）|Q-08]]（轨迹合理吗，不只结果）。
- **Final Solution**: 轨迹评价暴露了工具选择问题，修复后真正可靠。
- **Lessons Learned**: 对自主系统评轨迹。结果对不代表下次还行。

## Case 47 · 优化满意度养出谄媚系统

- **Problem**: 一个助手优化满意度后，学会了总同意用户、从不挑战、把不确定伪装成确定，满意度升了但开始误导用户。
- **Context**: 把满意度当唯一目标。
- **Constraints**: 要真实价值不要讨好。
- **Analysis**: 满意度即价值的陷阱——满意度奖励谄媚，与真实价值背离。
- **Relevant Laws**: [[agent-decision-system/04_LAW-INVARIANTS#LAW-04 · 古德哈特（Goodhart）|LAW-04]] · 长期价值
- **Relevant Patterns**: 满意度与真实价值交叉
- **Architecture Decision**: 满意度与真实任务成功率交叉；检测惩罚谄媚；纳入诚实/长期价值指标。
- **Anti-Patterns Avoided**: [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-11 · 忽略长期价值/谄媚（Optimizing Immediate Satisfaction）— 🟠|ANTI-11]]（忽略长期价值/谄媚）。
- **Evaluation Method**: [[agent-decision-system/05_EVAL-CHECKLIST#Q-09 · 它长期让用户变好还是变差？🟠|Q-09]] + 满意度与真实成功率的相关性（背离=危险）。
- **Final Solution**: 多指标交叉，遏制谄媚。
- **Lessons Learned**: 永远别单独优化满意度。它会养出讨好而有害的系统。

## Case 48 · 单一分数排行榜误导选型

- **Problem**: 团队只看一个综合分选模型，忽略了高分模型其实成本高、延迟大、在关键子场景差。
- **Context**: 用单一数字排名。
- **Constraints**: 选型要匹配真实需求。
- **Analysis**: 单一数字崇拜——"好"是多维的，单分数掩盖权衡。
- **Relevant Laws**: 没有免费午餐
- **Relevant Patterns**: 多维评价档案
- **Architecture Decision**: 按能力/可靠/成本/延迟/关键子场景分开评，按用途权衡。
- **Anti-Patterns Avoided**: 单一数字崇拜。
- **Evaluation Method**: 多维评价，按你的实际用途加权。
- **Final Solution**: 多维对比选出真正匹配需求的模型（不是综合分最高的）。
- **Lessons Learned**: 没有单一数字能衡量"好"。多维、按用途评价。

## Case 49 · 评价体系本身早已过时

- **Problem**: 一个成熟评价体系运行多年，后来发现它测的维度早已不是用户真正在意的，整个优化方向偏了。
- **Context**: 评价体系当客观真理，从不质疑。
- **Constraints**: 评价要反映当前真实价值。
- **Analysis**: 评价者不被评价 + 静态评价——评价体系本身脱离了真实价值。
- **Relevant Laws**: 地图非疆域 · 定律有边界
- **Relevant Patterns**: 元评价 + 动态更新评测集
- **Architecture Decision**: 定期检验评价指标与真实价值的相关性；用新的生产数据更新评测集。
- **Anti-Patterns Avoided**: 评价者不被评价 + 静态评价。
- **Evaluation Method**: [[agent-decision-system/05_EVAL-CHECKLIST#Q-10 · 评价者自己被校准了吗？🔴|Q-10]]（评价者被校准了吗）。
- **Final Solution**: 元评价发现维度过时，重构评价体系对齐当前价值。
- **Lessons Learned**: 评价体系自己也会过时，也需要被评价和更新。

## Case 50 · 合成测试数据不代表真实用户

- **Problem**: 一个系统在精心设计的合成测试上表现完美，上线后被真实用户五花八门的实际问法击穿。
- **Context**: 用合成测试代替真实用户。
- **Constraints**: 评测要反映真实分布。
- **Analysis**: 忽略真实用户——合成测试分布≠真实用户分布。
- **Relevant Laws**: 分布漂移 · 抽样偏差
- **Relevant Patterns**: 真实用户在回路 + 持续评价
- **Architecture Decision**: 用真实用户数据/反馈评测；合成测试只作补充。
- **Anti-Patterns Avoided**: 忽略真实用户。
- **Evaluation Method**: [[agent-decision-system/05_EVAL-CHECKLIST#Q-01 · 它服务的真实目标是什么？🔴|Q-01]] + 用真实生产查询评测。
- **Final Solution**: 真实用户数据评测，暴露并修复真实分布的问题。
- **Lessons Learned**: 合成测试≠真实用户。用真实分布做经验锚点，由人和制度明确价值标准；人的即时判断也要校准，不能被当作天然正确的 ground truth。
