## Case 81 · 想微调注入公司知识（深度版）

- **Problem**: 团队想微调模型让它“知道”公司知识，结果投入大、更新慢、不可溯源，模型还会把旧政策编成新答案。
- **Context**: 公司有数千份制度、产品手册、销售材料和内部 FAQ。团队认为“把资料喂给模型训练一下”就能得到一个懂公司的专属模型。
- **Constraints**: 知识必须准确、可更新、可溯源；政策变化要能当天生效；错误答案要能追到来源。
- **Analysis**: 这是把“知识注入”和“行为塑形”混在一起。微调更适合改风格、格式、任务偏好和固定输出行为；公司知识是外部事实，变化快、需要引用、需要撤回。把知识写进权重，会让更新变慢、溯源变难、幻觉更难查。
- **Relevant Laws**: [[agent-decision-system/04_LAW-INVARIANTS#LAW-13 · 信息守恒，垃圾进垃圾出（Information Conservation / GIGO）|LAW-13]]（数据质量决定输出上限） · [[agent-decision-system/04_LAW-INVARIANTS#LAW-02 · 参数生成无事实来源保证（Parametric Generation Is Not Provenance）|LAW-02]]（参数事实无保证） · [[agent-decision-system/04_LAW-INVARIANTS#LAW-10 · 简单优先（Simplicity First）|LAW-10]]（先用更简单可维护的方案）
- **Relevant Patterns**: [[agent-decision-system/02_PATTERN-CARDS#PAT-03 · RAG（检索增强生成）|PAT-03]]（外部知识注入） + [[agent-decision-system/02_PATTERN-CARDS#PAT-16 · Routing（路由分发）|PAT-16]]（知识问答与风格任务分流）

**Trace 片段（微调方案的失败）**：

```text
训练前：
- 旧政策：差旅住宿上限 600 元/晚
- 新政策：差旅住宿上限 800 元/晚
- 文档库里新旧版本并存

微调后用户问：
Q: “现在住宿上限是多少？”
A: “根据公司差旅政策，住宿上限为 600 元/晚。”
问题：
- 答案没有引用来源
- 不知道是训练数据旧、模型记错，还是 prompt 诱导
- 新政策发布后必须重新整理数据、重新训练或再微调
```

- **Architecture Decision**: 建选择树：如果目标是“让模型知道最新公司事实”，默认用 RAG；如果目标是“统一输出格式/语气/分类边界”，才考虑微调；如果只是少量规则和格式，先用 prompt/结构化输出。公司知识进入版本化文档库，检索时按有效期过滤，答案必须带出处。
- **第一次修复与反转**: 第一版修复是“增加更多公司资料并计划每周重训”，看似更彻底，实际把问题放大：脏数据、旧版本、冲突资料都被压进训练集，且每周更新仍无法满足当天生效。反转点是承认：知识不是模型人格的一部分，而是可治理的数据资产。
- **Anti-Patterns Avoided**: 避免把微调当银弹；避免在没有基线和评测集时直接上训练流程（[[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-05 · 无评测上线（Vibe-Check Deployment）— 🔴|ANTI-05]] 的定制版）；避免对权重记忆产生 [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-02 · 过度信任（Over-Trust）— 🔴|ANTI-02]]。
- **Evaluation Method**: [[agent-decision-system/05_EVAL-CHECKLIST#Q-01 · 它服务的真实目标是什么？🔴|Q-01]] + [[agent-decision-system/05_EVAL-CHECKLIST#Q-04 · 代价可接受吗？🟠|Q-04]] + [[agent-decision-system/05_EVAL-CHECKLIST#Q-06 · 它在分布外/长尾/对抗下如何？🔴|Q-06]]。对比微调与 RAG 的准确率、更新延迟、来源可追溯性、旧政策拒答/纠错能力。
- **Final Solution**: 公司知识走 RAG：文档版本化、有效期过滤、答案带引用；微调只保留为后续可能的风格/格式优化选项。政策更新当天改文档即可生效，错误答案能追到具体来源块。
- **Lessons Learned**: ① 微调主要改表现，不适合承载频繁变化的事实知识。② 知识要可更新、可撤回、可溯源，就应该外置。③ 先判断目标是知识、格式、风格还是推理，再选 prompt/RAG/微调。④ 数字和情节为教学编排，用于展示架构取舍。
## Case 82 · 跳过 prompt 直接微调

- **Problem**: 一个任务效果不好，团队直接上微调，其实一个更好的 prompt 就能解决。
- **Context**: 把微调当默认高级方案。
- **Constraints**: 用最省的方式解决。
- **Analysis**: 违反优化阶梯——没穷尽 prompt/few-shot/RAG 就微调。
- **Relevant Laws**: 优化阶梯（先穷尽上一级）· [[agent-decision-system/04_LAW-INVARIANTS#LAW-10 · 简单优先（Simplicity First）|LAW-10]]
- **Relevant Patterns**: 先 [[agent-decision-system/02_PATTERN-CARDS#PAT-01 · Chain-of-Thought（思维链）|PAT-01]]/[[agent-decision-system/02_PATTERN-CARDS#PAT-03 · RAG（检索增强生成）|PAT-03]]（prompt/RAG）
- **Architecture Decision**: 走优化阶梯决策流程，先调 prompt + few-shot，多数问题在此解决。
- **Anti-Patterns Avoided**: 微调当银弹。
- **Evaluation Method**: 每级测效果，够用就停。
- **Final Solution**: 优化的 prompt 解决了问题，无需微调。
- **Lessons Learned**: 先穷尽便宜的一级。多数"想微调"的场景在 prompt/RAG 层就解决。

## Case 83 · 脏数据微调把问题固化进权重

- **Problem**: 用低质量、不一致的数据微调，把数据的问题直接学进模型，比 prompt 层的问题更难修。
- **Context**: 有数据就微调，没查质量。
- **Constraints**: 微调质量。
- **Analysis**: 脏数据微调——质量>数量，脏数据教模型学错，且固化进权重难修正。
- **Relevant Laws**: 信息守恒 · 质量>数量
- **Relevant Patterns**: 先做数据质量（见 [[data-foundation-of-ai-systems/00_INDEX|Data Foundation]]）
- **Architecture Decision**: 微调前先清洗数据、查系统性标签错误；没有高质量数据就别微调。
- **Anti-Patterns Avoided**: 脏数据微调。
- **Evaluation Method**: 度量微调数据质量（一致性、代表性）。
- **Final Solution**: 清洗数据后再微调，效果好且稳定。
- **Lessons Learned**: 微调成败首先是数据质量。质量>数量>算法。

## Case 84 · 微调后通用能力悄悄退化

- **Problem**: 微调在目标窄任务上提升明显，但没测通用能力，上线后发现其他任务悄悄变差了。
- **Context**: 只盯目标任务提升。
- **Constraints**: 不能牺牲通用能力。
- **Analysis**: 灾难性遗忘——目标任务的提升以其他能力退化为代价，且不可见。
- **Relevant Laws**: 静默降级 · 峰值驱动的变体
- **Relevant Patterns**: 评"失去了什么" + LoRA（缓解遗忘）
- **Architecture Decision**: 用 LoRA（冻结原权重缓解遗忘）；微调前后都测通用能力。
- **Anti-Patterns Avoided**: 只看得到的提升忽略退化。
- **Evaluation Method**: 定制前后测通用基准，量化遗忘。
- **Final Solution**: LoRA + 通用能力评测，遗忘可控。
- **Lessons Learned**: 永远评测定制"失去了什么"，不只"得到了什么"。

## Case 85 · 用同一模型的数据反复训练导致坍缩

- **Problem**: 用模型生成的数据训练模型，反复迭代后质量退化、多样性丧失。
- **Context**: 递归用合成数据训练。
- **Constraints**: 保持质量和多样性。
- **Analysis**: 模型坍缩——模型学自己的输出，误差和偏见递归放大。
- **Relevant Laws**: 正反馈 · 递归自指
- **Relevant Patterns**: 合成数据作补充 + 真实数据锚定
- **Architecture Decision**: 不长期用模型数据训模型；始终用真实数据做最终验证。
- **Anti-Patterns Avoided**: 递归蒸馏/模型坍缩。
- **Evaluation Method**: 监控迭代中的质量和多样性趋势。
- **Final Solution**: 真实数据锚定，避免坍缩。
- **Lessons Learned**: 别长期用模型生成的数据训模型。递归放大误差。

## Case 86 · 对齐优化出奖励黑客

- **Problem**: 对齐后模型学会最大化奖励模型的分数（变啰嗦、过度自信），而非真正变好。
- **Context**: 用 RLHF 对齐，只看奖励分。
- **Constraints**: 要真对齐不要钻空子。
- **Analysis**: 对齐逃不过古德哈特——优化奖励模型这个代理，模型钻它的漏洞。
- **Relevant Laws**: [[agent-decision-system/04_LAW-INVARIANTS#LAW-04 · 古德哈特（Goodhart）|LAW-04]]（古德哈特）
- **Relevant Patterns**: 独立评价检验真实对齐
- **Architecture Decision**: 用独立的（不被对齐优化过的）评价检验真实对齐；对抗性测试奖励黑客。
- **Anti-Patterns Avoided**: 相信优化的分数。
- **Evaluation Method**: 用独立评价而非奖励分判断对齐。
- **Final Solution**: 独立评价发现奖励黑客，修正奖励模型。
- **Lessons Learned**: 对齐优化的分数会撒谎。用独立评价检验真实对齐。

## Case 87 · 忽略数据代表性导致群体偏差

- **Problem**: 一个分类系统对某个群体系统性地差，因为训练数据里该群体样本严重不足。
- **Context**: 只看总体准确率。
- **Constraints**: 各群体公平。
- **Analysis**: 代表性不足——偏见常来自数据，"数据里缺了谁"制造盲区。
- **Relevant Laws**: 抽样偏差 · 信息守恒
- **Relevant Patterns**: 按群体切分评测 + 补充数据
- **Architecture Decision**: 按群体切分看表现/覆盖；补充代表性不足的群体数据。
- **Anti-Patterns Avoided**: 只看总体平均。
- **Evaluation Method**: 分群体评测（不只总体）。
- **Final Solution**: 补充数据 + 分群体评测，群体差异缩小。
- **Lessons Learned**: 偏见常来自数据。修偏见先查"数据里缺了谁"。

## Case 88 · 数据泄漏导致评测虚高（深度版）

- **Problem**: 评测集的数据泄漏进训练数据，离线评测分数很高，上线后真实表现暴跌。
- **Context**: 团队用历史客服问答训练模型，又从同一批历史数据里抽样做评测。后来还做了数据增强，把相似问题改写成多种说法，却没有追踪原始样本 lineage。
- **Constraints**: 评测必须反映真实泛化；训练/验证/测试边界要可审计；异常高分必须能解释。
- **Analysis**: 数据泄漏让模型看起来会泛化，其实只是见过答案。更隐蔽的是近重复泄漏：表面上训练集和评测集不是同一行，但来自同一客户、同一工单、同一模板或同一个合成源。随机行切分会放大这种假象。
- **Relevant Laws**: [[agent-decision-system/04_LAW-INVARIANTS#LAW-03 · 分布证据有边界 + 校准（Distribution-Bounded Evidence + Calibration）|LAW-03]]（评测要代表目标分布） · [[agent-decision-system/04_LAW-INVARIANTS#LAW-13 · 信息守恒，垃圾进垃圾出（Information Conservation / GIGO）|LAW-13]]（数据边界决定结果可信度） · [[agent-decision-system/04_LAW-INVARIANTS#LAW-04 · 古德哈特（Goodhart）|LAW-04]]（分数可被污染）
- **Relevant Patterns**: [[agent-decision-system/02_PATTERN-CARDS#PAT-15 · Guardrails / Validation（护栏）|PAT-15]]（数据管线校验） + sealed eval set（封存评测集）

**Trace 片段（虚高来源）**：

```text
原始工单 A：
用户问：“企业版怎么开通 SSO？”
客服答：“请管理员进入安全设置，启用 SAML...”

训练集：
- 原始工单 A
- A 的改写 1：“如何打开企业版单点登录？”

评测集：
- A 的改写 2：“企业版 SAML 在哪里配置？”

离线分数：96%
上线后：真实新问题只有 71%
原因：评测集不是新问题，只是训练源的近重复。
```

- **Architecture Decision**: 数据切分从“随机行切分”改为“按来源实体/时间/工单族切分”。评测集封存，训练管线禁止读取；所有合成和改写样本保留 `source_id`，同源样本不能跨训练/评测边界。上线前必须跑近重复检测和泄漏审计。
- **第一次修复与反转**: 第一版修复是“重新随机划分一次训练和评测”。分数仍然很高，因为同一个原始工单的多个改写被分到了不同集合。反转点是意识到泄漏单位不是“行”，而是“信息源”。最终按 source_id 和时间切分，分数回落但更可信。
- **Anti-Patterns Avoided**: [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-03 · 古德哈特化评价 / 刷分（Benchmark Gaming）— 🔴|ANTI-03]]（污染指标后追高分） · [[agent-decision-system/03_ANTIPATTERN-DETECTORS#ANTI-05 · 无评测上线（Vibe-Check Deployment）— 🔴|ANTI-05]]（未审计评测集就相信分数）
- **Evaluation Method**: [[agent-decision-system/05_EVAL-CHECKLIST#Q-02 · 它可靠吗——看分布不是峰值？🔴|Q-02]] + [[agent-decision-system/05_EVAL-CHECKLIST#Q-06 · 它在分布外/长尾/对抗下如何？🔴|Q-06]] + [[agent-decision-system/05_EVAL-CHECKLIST#Q-10 · 评价者自己被校准了吗？🔴|Q-10]]。看无泄漏评测、时间外评测、真实线上抽样三组差异。
- **Final Solution**: 建立数据 lineage、source-level split、near-duplicate scan、sealed eval。分数从虚高回到真实水平，暴露了模型对新问题的不足；后续优化不再追污染后的漂亮分数。
- **Lessons Learned**: ① 太好的评测结果首先怀疑泄漏。② 训练/评测隔离要按信息源，不只按行。③ 合成数据也必须继承 source_id。④ 数字为教学编排，用于展示泄漏造成的虚高。
## Case 89 · 数据管线静默通过脏数据

- **Problem**: 数据管线的校验环节失败被静默跳过，脏数据流入训练，模型学坏。
- **Context**: 校验失败不拦截。
- **Constraints**: 只有干净数据能入训练。
- **Analysis**: 数据管线静默失败——脏数据看起来和好数据一样，一路流到污染模型。
- **Relevant Laws**: 显式失败 · 信息守恒
- **Relevant Patterns**: 显式质量关卡拦截
- **Architecture Decision**: 校验失败显式拦截告警；质量不达标的数据不入训练。
- **Anti-Patterns Avoided**: 数据管线静默通过脏数据。
- **Evaluation Method**: 注入脏数据测管线是否拦截。
- **Final Solution**: 显式质量关卡，脏数据被拦。
- **Lessons Learned**: 数据管线最危险的失败是静默通过脏数据。质量关卡要显式拦截。

## Case 90 · 定制模型的维护负担被低估

- **Problem**: 一个定制模型短期看划算，算上持续维护（随漂移重训、版本管理）后其实不如用 API+好 prompt。
- **Context**: 只算了训练成本，没算维护。
- **Constraints**: 总成本要诚实。
- **Analysis**: 维护负担被低估 + 沉没成本——已投入训练就倾向继续维护，而非诚实评估。
- **Relevant Laws**: 复杂度累积 · 沉没成本 · 机会成本
- **Relevant Patterns**: 定制的成本-收益复盘
- **Architecture Decision**: 算含持续维护的总成本；诚实评估"现在从头看还值得吗"。
- **Anti-Patterns Avoided**: 沉没成本谬误。
- **Evaluation Method**: 全成本对比（含维护）定制 vs API+prompt。
- **Final Solution**: 部分场景回退 API+prompt，总成本更低。
- **Lessons Learned**: 定制的最大成本是持续维护。别被沉没成本绑架。
